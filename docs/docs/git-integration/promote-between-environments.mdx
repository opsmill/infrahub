You run one Infrahub instance per environment, and promote a change from development to the next environments, ending in production. Each instance imports its own long-lived Git branch of one repository. [Multiple environments from a single repository](./multi-environment.mdx) explains the workflow, the reasons for each setting and the rules for the team.

The steps depend on the type of the repository:

- With [read-write repositories](#with-read-write-repositories), the recommended type from Infrahub 1.12, a reviewer merges the change through a Proposed Change on each instance, and Infrahub pushes each merge to Git.
- With [read-only repositories](#with-read-only-repositories), no instance writes to Git. A promotion is a merge request on your Git host, which you test and import on an Infrahub branch of the target instance.

## With read-write repositories

The example uses three instances: development imports the Git branch `develop`, integration imports `integration`, and production imports `production`. The promotion steps are steps 3 to 5 of the [read-write diagram](./multi-environment.mdx#how-you-promote-a-change-between-environments).

### Prerequisites

- Infrahub 1.12 or later on every instance.
- One Git repository with one long-lived branch per environment: `develop`, `integration` and `production`.
- A Git credential for each instance that can push to the branches of the repository.
- Branch protection on your Git host that blocks deletion and force-push of the long-lived branches.

### Set up each instance

Run these two steps once on each instance, in this order. The instance imports branches as soon as you connect the repository, so set the import filter first.

#### Step 1: Set the configuration

Set these environment variables on the Infrahub server and on the task workers of each instance, then restart them. Only the import filter differs between instances:

| Instance | `INFRAHUB_GIT_IMPORT_SYNC_BRANCH_NAMES` |
| --- | --- |
| Development | `["feature/.*"]` |
| Integration | `["promote/integration/.*"]` |
| Production | `["promote/production/.*"]` |

For the development instance:

```shell
INFRAHUB_GIT_IMPORT_SYNC_BRANCH_NAMES='["feature/.*"]'
INFRAHUB_DELETE_BRANCH_AFTER_MERGE=true
INFRAHUB_GIT_DELETE_GIT_BRANCH_AFTER_MERGE=true
INFRAHUB_GIT_USE_EXPLICIT_MERGE_COMMIT=true
```

- `INFRAHUB_GIT_IMPORT_SYNC_BRANCH_NAMES` limits which new Git branches the instance imports. In `infrahub.toml`, the key is `import_sync_branch_names` in the `[git]` section.
- With `INFRAHUB_DELETE_BRANCH_AFTER_MERGE` and `INFRAHUB_GIT_DELETE_GIT_BRANCH_AFTER_MERGE` set, Infrahub deletes the merged branch in Infrahub and in Git. Infrahub does not start when the second one is `true` and the first one is not.
- With `INFRAHUB_GIT_USE_EXPLICIT_MERGE_COMMIT` set, Infrahub creates a merge commit in Git for every merge. You can then [undo a promoted change](./multi-environment.mdx#undo-a-promoted-change) with one revert.

[How to configure Infrahub](../deploy-manage/install-configure/configure-infrahub) describes how to set environment variables for your deployment.

Connect the repository as a read-write repository, and set its default branch to the Git branch of the environment: `develop`, `integration` or `production`.

### Convert an existing read-only repository

An instance that imports its Git branch through a read-only repository can switch to the read-write workflow without connecting a second repository. Convert the read-only repository to a read-write repository. Infrahub keeps the queries, Transformations, checks, Generator definitions and artifact definitions that it imported, with the same IDs, and keeps the artifacts, Generator actions and webhooks that use them. If you delete the read-only repository instead, Infrahub deletes the queries, Transformations, checks and Generator definitions with it.

The conversion changes these things:

- The repository keeps its name, location and credential. Its `ref` is removed, and the repository imports the Git branch named in `default_branch` instead. If you do not set `default_branch`, it is `main`.
- The repository gets a new ID. Update any script or pipeline that uses the old ID.
- Every other Infrahub branch changes to the `NEED_REBASE` status, as described in [object conversion](../objects/convert-object-kind.mdx#version-control-integration).
- Right after the conversion, Infrahub synchronizes the repository. It imports the Git branch in `default_branch` into `main`, and creates an Infrahub branch for each Git branch that matches the import filter.

Infrahub runs the conversion only on the `main` branch. Follow these steps on each instance:

1. Back up the database, as described in [database backup](../deploy-manage/maintain-upgrade/database-backup/backup-and-restore.mdx).
2. Merge or delete the Infrahub branches that you no longer need. Each branch that stays open changes to `NEED_REBASE`, and you rebase it in step 5.
3. Set the configuration on the server and the task workers, as described in [Step 1](#step-1-set-the-configuration), and restart them. The conversion starts a synchronization, so the import filter has to be active first. Without it, the instance imports every Git branch.
4. Convert the repository, and set `default_branch` to the Git branch of the environment, for example `develop`:

   <Tabs groupId="method" queryString>
   <TabItem value="Via the Web Interface" default>
     1. Go to **Integrations > Git Repositories**, and select the read-only repository.
     2. Select **Actions**, then **Convert object type**.
     3. In **Select target object type**, select **Repository**. The form lists the fields of a read-write repository. Every field that also exists on the read-only repository is set to **From source**.
     4. In **Default Branch**, replace `main` with the Git branch of the environment.
     5. Select **Convert**. Infrahub opens the details page of the converted repository.
   </TabItem>
   <TabItem value="Via the GraphQL Interface">
     Query the ID of the read-only repository:

     ```graphql
     query {
       CoreReadOnlyRepository {
         edges { node { id name { value } ref { value } } }
       }
     }
     ```

     Convert it on `main`. Only `default_branch` needs a value. Infrahub copies every field that has the same name on both kinds.

     ```graphql
     mutation {
       ConvertObjectType(

         node
       }
     }
     ```

     The `node` in the response contains the new ID of the repository.
   </TabItem>
   <TabItem value="Via the Infrahub SDK">

     ```python
         target_kind="CoreRepository",
         fields_mapping={
             "default_branch": ConversionFieldInput(data=ConversionFieldValue(attribute_value="develop")),
         },
     )
     ```

   </TabItem>
   </Tabs>

5. [Rebase](../branches/rebase.mdx) each Infrahub branch that is still open.

When the synchronization completes, the **Sync Status** of the repository is **In Sync**, and its **Commit** is the latest commit of the Git branch in `default_branch`.

### Develop a change on the development instance

Develop the change on a `feature/` branch, and merge its Proposed Change on the development instance, as described in [develop changes from a Git repository](./develop-changes.mdx#with-a-read-write-repository). Infrahub then merges the change into `develop` and pushes `develop`.

### Promote the change to the next environment

1. Create a promotion branch in Git from the current `develop` and push it. Give it a name that you have not used before:

   ```bash
   git fetch origin
   git branch promote/integration/7 origin/develop
   git push origin promote/integration/7
   ```

   The development instance ignores the branch, because the name does not match its import filter. The part after `promote/integration/` can be any unique name, such as `add-tag-color`. If you use another prefix, change the import filter of the integration instance to match it.

2. Wait for the integration instance to import the branch.
3. On the integration instance, open a Proposed Change from `promote/integration/7` to `main` and review it.
4. Merge the Proposed Change. Infrahub merges the Git branch into `integration`, pushes `integration`, and deletes the promotion branch.

To promote to production, repeat these steps with a branch such as `promote/production/3`, created from `origin/integration`.

Keep one open promotion branch per target instance. Merge or delete it before you create the next one.

### Recover from a mistake

| What happened | What you view | What to do |
| --- | --- | --- |
| You created a second promotion branch before the first one merged | One Proposed Change fails its checks after the other one merges | Delete the failing branch on the target instance. Promote again under a new name |
| You mistyped the name of the promotion branch | The target instance does not import the branch | Delete the Git branch. Create it again with the correct name |
| Someone pushed a conflicting commit directly to an environment branch, such as `integration` | The Proposed Change fails the repository check, and Infrahub pushes nothing | Merge that environment branch into a new feature branch, resolve the conflict, and merge it on the development instance. Delete the failed promotion branch, then promote again under a new name |
| Someone pushed a commit directly to an environment branch, and you merge right after | Infrahub refuses the merge: `Unable to merge branch ..., because Infrahub has not recorded the latest commit of branch ...` | Merge again after about one minute, when Infrahub has imported the commit |
| Infrahub cannot push a merge to Git | The repository shows a failed push | See [when a push to the remote fails](./branch-synchronization.mdx#when-a-push-to-the-remote-fails) |

## With read-only repositories

The example uses three environments: development imports the Git branch `develop`, staging imports `staging`, and production imports `main`. Each instance has a read-only repository whose `ref` on `main` is the Git branch of its environment.

The promotion steps are steps 6 to 10 of the [read-only diagram](./multi-environment.mdx#alternative-read-only-repositories). Develop the change first, as described in [develop changes from a Git repository](./develop-changes.mdx#with-a-read-only-repository). Infrahub never writes to Git in this workflow.

Git and Infrahub both have branches, a `main` and a merge step. In this section, a **Git branch** and a **merge request** are on your Git host. An **Infrahub branch** and a **Proposed Change** are inside one instance. The Git branch `main` of production is not related to the Infrahub branch `main` of any instance.

### Connect the repository on each instance

Connect the repository on each instance as a read-only repository, with `ref` set to the Git branch of that environment.

```graphql
mutation {
  CoreReadOnlyRepositoryCreate(data: {
    name: { value: "infra" }
    location: { value: "https://github.com/<org>/<repo>.git" }
    ref: { value: "develop" }          # "main" on the production instance
    credential: { id: "<credential-id>" }
  }) { ok }
}
```

On the Infrahub branch `main`, the `ref` of the repository always names the Git branch of the environment. A promotion changes the commit that the instance imported, not the `ref`.

### Promote a change

A promotion is a Git merge into the branch of the next environment. You test the source branch on an Infrahub branch of the target instance before you merge it in Git. Do not import onto `main` directly: an import can fail, and you cannot undo a failed import on `main`. Import onto an Infrahub branch instead: if the import fails, you delete that branch.

1. On your Git host, open a merge request from the source branch to the target branch, for example from `develop` to `staging`. Do not merge it yet.
2. On the target instance, create an Infrahub branch. On that branch, set the `ref` of the repository to the source branch, `develop`. Changing the `ref` starts the import.
3. Check the import and the result on the Infrahub branch. If the import fails, delete the Infrahub branch and fix the change on the development instance.
4. When the import succeeds, merge the merge request on your Git host.
5. On the Infrahub branch, set the `ref` back to the target branch, `staging`. The instance imports the merged commit.
6. Open a Proposed Change from the Infrahub branch to `main`, review it, and merge it.

Repeat the promotion for each environment in the chain, for example from `develop` to `staging`, then from `staging` to `main`.

:::caution Point the `ref` back before you merge

The `ref` of the repository and the imported commit are recorded per Infrahub branch. When you merge an Infrahub branch on which you changed them, Infrahub also changes them on `main`. That is why step 5 sets the `ref` back to the Git branch of the environment before the merge. Otherwise `main` of the instance tracks the source branch from then on.

:::

### Automate the promotion (optional)

:::note Experimental

Only the manual steps above are supported. Adapt the example below to your CI system. Keep production promotions manual until you have tested your automation from start to finish.

:::

A CI system can run the same steps in two jobs:

1. When a merge request into an environment branch opens, the first job creates an Infrahub branch on the target instance and sets its `ref` to the source branch. The job then opens a Proposed Change. As a required status check, the job blocks the merge request until the checks of the Proposed Change pass.
2. After the merge request merges, the second job sets the `ref` on the Infrahub branch to the target branch. A reviewer then merges the Proposed Change.

The first job reads the checks from the `validations` of the Proposed Change. Each validation has a `state` (`queued`, `in_progress`, `completed`) and a `conclusion` (`unknown`, `failure`, `success`):

```graphql
query {
  CoreProposedChange(ids: ["<proposed-change-id>"]) {
    edges { node {
      validations { edges { node {
        display_label
        state { value }
        conclusion { value }
      } } }
    } }
  }
}
```

Query until the `state` of every validation is `completed`, then fail the CI job unless every `conclusion` is `success`. Store the address of each instance and an [API token](../deploy-manage/user-management/managing-api-tokens.mdx) as CI secrets, and authenticate with the `X-INFRAHUB-KEY` header.
