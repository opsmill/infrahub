In this guide, you set up one Infrahub instance per environment with a read-write repository. You then develop a change and promote it from development to integration and production. A reviewer merges the change through a Proposed Change on each instance, and Infrahub pushes each merge to Git. [Multiple environments from a single repository](./multi-environment.mdx) explains the workflow and the reasons for each setting.

The example uses three instances: development imports the Git branch `develop`, integration imports `integration`, and production imports `production`.

## Prerequisites

- Infrahub 1.12 or later on every instance.
- One Git repository with one long-lived branch per environment: `develop`, `integration` and `production`.
- A Git credential for each instance that can push to the branches of the repository.
- Branch protection on your Git host that blocks deletion and force-push of the long-lived branches.

## Set up each instance

Run these two steps once on each instance, in this order. The instance imports branches as soon as you connect the repository, so set the import filter first.

### Step 1: Set the configuration

Set these environment variables on the Infrahub server and on the task workers of each instance, then restart them. Only the import filter differs between instances:

| Instance | `INFRAHUB_GIT_IMPORT_SYNC_BRANCH_NAMES` |
| --- | --- |
| Development | `["feature/.*"]` |
| Integration | `["promote/integration/.*"]` |
| Production | `["promote/production/.*"]` |

For the development instance:

```shell
INFRAHUB_GIT_IMPORT_SYNC_BRANCH_NAMES='["feature/.*"]'
INFRAHUB_DELETE_BRANCH_AFTER_MERGE=true
INFRAHUB_GIT_DELETE_GIT_BRANCH_AFTER_MERGE=true
INFRAHUB_GIT_USE_EXPLICIT_MERGE_COMMIT=true
```

- `INFRAHUB_GIT_IMPORT_SYNC_BRANCH_NAMES` limits which new Git branches the instance imports. In `infrahub.toml`, the key is `import_sync_branch_names` in the `[git]` section.
- With `INFRAHUB_DELETE_BRANCH_AFTER_MERGE` and `INFRAHUB_GIT_DELETE_GIT_BRANCH_AFTER_MERGE` set, Infrahub deletes the merged branch in Infrahub and in Git. Infrahub does not start when the second one is `true` and the first one is not.
- With `INFRAHUB_GIT_USE_EXPLICIT_MERGE_COMMIT` set, Infrahub creates a merge commit in Git for every merge. You can then [undo a promoted change](./multi-environment.mdx#undo-a-promoted-change) with one revert.

[How to configure Infrahub](../deploy-manage/install-configure/configure-infrahub) describes how to set environment variables for your deployment.

### Step 2: Connect the repository

Connect the repository as a read-write repository, and set its default branch to the Git branch of the environment: `develop`, `integration` or `production`.

The instance imports the Git branch of its environment into its `main` branch. [Connect a repository](./connect-repository.mdx) describes credentials and the other options.

## Develop a change on the development instance

1. Create a feature branch from the current `develop` and push it:

   ```bash
   git fetch origin
   git switch -c feature/add-tag-color origin/develop
   ```

   Add a schema file that adds a `color` attribute to the built-in Tag, then commit and push it:

   ```bash
   mkdir -p schemas
   cat > schemas/tags.yml <<'EOF'
   ---
   version: '1.0'
   extensions:
     nodes:
       - kind: BuiltinTag
         attributes:
           - name: color
             kind: Text
             optional: true
   EOF
   git add schemas/tags.yml
   git commit -m "Add color attribute to Tag"
   git push -u origin feature/add-tag-color
   ```

   The `schemas` list in `.infrahub.yml` must include `schemas/tags.yml`, so that Infrahub imports the file.

   You can also create the branch on the development instance, with **Sync with Git** turned on. Infrahub then creates the Git branch, and you push your commits to it.

2. Wait for the development instance to import the branch. Infrahub checks Git for new branches and commits once a minute.
3. Open a [Proposed Change](../proposed-changes/overview.mdx) from `feature/add-tag-color` to `main` and review it.
4. Merge the Proposed Change. Infrahub merges the Git branch into `develop`, pushes `develop`, and deletes the feature branch.

## Promote the change to the next environment

1. Create a promotion branch in Git from the current `develop` and push it. Give it a name that you have not used before:

   ```bash
   git fetch origin
   git branch promote/integration/7 origin/develop
   git push origin promote/integration/7
   ```

   The development instance ignores the branch, because the name does not match its import filter. The part after `promote/integration/` can be any unique name, such as `add-tag-color`. If you use another prefix, change the import filter of the integration instance to match it.

2. Wait for the integration instance to import the branch.
3. On the integration instance, open a Proposed Change from `promote/integration/7` to `main` and review it.
4. Merge the Proposed Change. Infrahub merges the Git branch into `integration`, pushes `integration`, and deletes the promotion branch.

To promote to production, repeat these steps with a branch such as `promote/production/3`, created from `origin/integration`.

Keep one open promotion branch per target instance. Merge or delete it before you create the next one.

:::note Rehearse a production promotion first

Before you merge on production, test the promotion on a separate instance restored from a current [database backup](../deploy-manage/maintain-upgrade/database-backup/backup-and-restore.mdx) of production. See [test a promotion against a copy of production](./multi-environment.mdx#test-a-promotion-against-a-copy-of-production).

:::

## Recover from a mistake

| What happened | What you view | What to do |
| --- | --- | --- |
| You created a second promotion branch before the first one merged | One Proposed Change fails its checks after the other one merges | Delete the failing branch on the target instance. Promote again under a new name |
| You mistyped the name of the promotion branch | The target instance does not import the branch | Delete the Git branch. Create it again with the correct name |
| Someone pushed a conflicting commit directly to an environment branch, such as `integration` | The Proposed Change fails the repository check, and Infrahub pushes nothing | Merge that environment branch into a new feature branch, resolve the conflict, and merge it on the development instance. Delete the failed promotion branch, then promote again under a new name |
| Someone pushed a commit directly to an environment branch, and you merge right after | Infrahub refuses the merge: `Unable to merge branch ..., because Infrahub has not recorded the latest commit of branch ...` | Merge again after about one minute, when Infrahub has imported the commit |
| Infrahub cannot push a merge to Git | The repository shows a failed push | See [when a push to the remote fails](./branch-synchronization.mdx#when-a-push-to-the-remote-fails) |
