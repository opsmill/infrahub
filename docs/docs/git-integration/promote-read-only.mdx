You can promote changes between environments with [read-only repositories](./overview.mdx#read-only-vs-core), so that no Infrahub instance writes to Git. Each instance imports one long-lived Git branch. A promotion is a merge request on your Git host, which you test and then import on an Infrahub branch of the target instance. From Infrahub 1.12, the recommended workflow uses read-write repositories instead: see [promote changes between environments](./promote-between-environments.mdx). Choose read-only repositories when your policy does not allow a tool to push to Git. Also choose them when you want your Git host to enforce the order of the environments.

The example uses three environments: **development** imports the Git branch `develop`, **staging** imports `staging`, and **production** imports `main`. Repeat the steps for any number of environments.

## How each instance imports its branch

One repository holds one long-lived Git branch per environment. Each instance has a read-only repository whose `ref` is the branch of its environment:

| Git branch | Infrahub instance | `ref` of the read-only repository |
| --- | --- | --- |
| `develop` | Development | `develop` |
| `staging` | Staging | `staging` |
| `main` | Production | `main` |

<PromotionReadOnly role="img" style={{width: '100%', height: 'auto'}} />

Follow the numbers in the diagram. Hover over a step to show only that step. Steps 1 to 5 develop a change on the development instance:

1. A developer creates the Git branch `feature/x` from `develop`.
2. On the development instance, the developer creates an Infrahub branch for testing and sets its `ref` to `feature/x`. After each push to `feature/x`, the developer runs **Import latest commit** on that Infrahub branch.
3. A reviewer merges the merge request from `feature/x` into `develop` on the Git host.
4. The developer sets the `ref` on the Infrahub branch back to `develop`.
5. A reviewer merges the Proposed Change of the Infrahub branch into `main`.

Steps 6 to 10 promote the change to staging, then to production:

6. A user opens a merge request from `develop` into `staging` on the Git host, and does not merge it yet.
7. On the staging instance, the user creates an Infrahub branch and sets its `ref` to `develop`, the source branch of the merge request.
8. When the import succeeds, a reviewer merges the merge request.
9. The user sets the `ref` on the Infrahub branch to `staging`, the target branch of the merge request.
10. A reviewer merges the Proposed Change of the Infrahub branch into `main`.

The promotion to production repeats steps 6 to 10, from `staging` into `main`. Infrahub never writes to Git in this workflow. Each instance only reads the Git branch named in a `ref`.

A read-only repository does not check the remote for new commits on its own. It imports only when you run **Import latest commit**, or when you change its `ref`, which starts an import by itself.

Git and Infrahub both have branches, a `main` and a merge step. On this page, a **Git branch** and a **merge request** are on your Git host. An **Infrahub branch** and a **Proposed Change** are inside one instance. The Git branch `main` of production is not related to the Infrahub branch `main` of any instance.

## Prerequisites

- One Infrahub instance per environment.
- A change already developed and merged on the development instance. [Develop changes from a Git repository](./develop-changes.mdx) describes how.

## Connect the repository on each instance

Connect the repository on each instance as a read-only repository, with `ref` set to the Git branch of that environment.

```graphql
mutation {
  CoreReadOnlyRepositoryCreate(data: {
    name: { value: "infra" }
    location: { value: "https://github.com/<org>/<repo>.git" }
    ref: { value: "develop" }          # "main" on the production instance
    credential: { id: "<credential-id>" }
  }) { ok }
}
```

On the Infrahub branch `main`, the `ref` of the repository always names the Git branch of the environment. A promotion changes the commit that the instance imported, not the `ref`.

## Promote a change

A promotion is a Git merge into the branch of the next environment. You test the merge on an Infrahub branch of the target instance before you merge it in Git. Do not import onto `main` directly: an import can fail, and you cannot undo a failed import on `main`. Import onto an Infrahub branch instead: if the import fails, you delete that branch.

1. On your Git host, open a merge request from the source branch to the target branch, for example from `develop` to `staging`. Do not merge it yet.
2. On the target instance, create an Infrahub branch. On that branch, set the `ref` of the repository to the source branch, `develop`. Changing the `ref` starts the import.
3. Check the import and the result on the Infrahub branch. If the import fails, delete the Infrahub branch and fix the change on the development instance.
4. When the import succeeds, merge the merge request on your Git host.
5. On the Infrahub branch, set the `ref` back to the target branch, `staging`. The instance imports the merged commit.
6. Open a Proposed Change from the Infrahub branch to `main`, review it, and merge it.

Repeat the promotion for each environment in the chain, for example from `develop` to `staging`, then from `staging` to `main`.

:::caution Point the `ref` back before you merge

The repository's `ref` and imported commit are recorded per Infrahub branch. When you merge an Infrahub branch on which you changed them, Infrahub also changes them on `main`. That is why step 5 sets the `ref` back to the Git branch of the environment before the merge. Otherwise `main` of the instance tracks the source branch from then on.

:::

:::note Rehearse a production promotion first

Before you promote to production, rehearse the promotion on a separate instance restored from a current [database backup](../deploy-manage/maintain-upgrade/database-backup/backup-and-restore.mdx) of production. See [test a promotion against a copy of production](./multi-environment.mdx#test-a-promotion-against-a-copy-of-production).

:::

## Automate the promotion (optional)

:::note Experimental

Only the manual steps above are supported. Adapt the example below to your CI system. Keep production promotions manual until you have tested your automation from start to finish.

:::

A CI job can run the same steps. On a merge request into an environment branch, the job creates an Infrahub branch and imports the change onto it. The job then opens a Proposed Change. The job then blocks the merge request, as a required status check, until the checks of the Proposed Change pass. The CI job reads those checks from the `validations` of the Proposed Change. Each validation has a `state` (`queued`, `in_progress`, `completed`) and a `conclusion` (`unknown`, `failure`, `success`):

```graphql
query {
  CoreProposedChange(ids: ["<proposed-change-id>"]) {
    edges { node {
      validations { edges { node {
        display_label
        state { value }
        conclusion { value }
      } } }
    } }
  }
}
```

Query until the `state` of every validation is `completed`, then fail the CI job unless every `conclusion` is `success`. Store the address of each instance and an [API token](../deploy-manage/user-management/managing-api-tokens.mdx) as CI secrets, and authenticate with the `X-INFRAHUB-KEY` header.
