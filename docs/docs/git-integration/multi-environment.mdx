You can run one Infrahub instance per environment, such as development, integration and production, from one Git repository. You then promote each change that you make in the repository through each environment, ending in production. The repository holds one long-lived Git branch per environment, and each instance imports its own branch.

From Infrahub 1.12, the recommended way to promote a change is with a [read-write repository](./overview.mdx#read-only-vs-core) on every instance. A reviewer merges the change through a [Proposed Change](../proposed-changes/overview.mdx) on each instance. Infrahub then merges the Git branch of that environment and pushes it. Each instance imports its promotion branches by itself, and the Proposed Change is the only review step. If you cannot give Infrahub push access to Git, use [read-only repositories](#alternative-read-only-repositories) instead.

## What you promote between environments

You promote the content that a repository declares in [`.infrahub.yml`](./infrahub-yml.mdx):

- Schemas
- Objects defined in object files
- GraphQL queries
- Jinja2 and Python Transformations
- Artifact definitions
- Generators
- Checks
- Menus

Objects that you create through the web interface or the API stay in that instance. They are not stored in Git, so a promotion does not copy them to the next environment.

## How you promote a change between environments

<PromotionReadWrite role="img" style={{width: '100%', height: 'auto'}} />

Follow the numbers in the diagram. Hover over a step to show only that step.

1. A developer creates a `feature/` branch, either in Git or in Infrahub with **Sync with Git** turned on. The development instance syncs the branch with Git in both directions.
2. A reviewer merges the Proposed Change of the branch on the development instance. Infrahub merges the Git branch into `develop` and pushes `develop`.
3. A user creates a promotion branch, such as `promote/integration/7`, in Git from `develop`.
4. The integration instance imports the promotion branch as a new Infrahub branch. Infrahub checks for new Git branches once a minute.
5. A reviewer merges the Proposed Change of the promotion branch on the integration instance. Infrahub merges the Git branch into `integration` and pushes `integration`.

Repeat steps 3 to 5 from `integration` to `production`. This example uses three environments. Two environments, or more than three, use the same workflow. Add or remove a long-lived Git branch and the instance that imports it.

Each promotion needs its own branch, because an Infrahub branch merges only once. After the merge, Infrahub marks the branch as merged and makes it read-only. A long-lived branch such as `develop` therefore cannot be promoted a second time.

Create the promotion branch in Git. You can also create it on the development instance with **Sync with Git** turned on, so that Infrahub pushes it to Git. The integration instance then imports it in the same way. But the branch stays open on the development instance after a reviewer merges it on the integration instance, and you have to delete it there yourself.

## How each instance is set up

Each instance has a read-write repository for the same Git repository, with two settings that differ per instance:

| Instance | `default_branch` of the repository | Import filter, `INFRAHUB_GIT_IMPORT_SYNC_BRANCH_NAMES` |
| --- | --- | --- |
| Development | `develop` | `["feature/.*"]` |
| Integration | `integration` | `["promote/integration/.*"]` |
| Production | `production` | `["promote/production/.*"]` |

- **`default_branch`** names the Git branch that Infrahub imports into its default branch, `main`. Infrahub pushes every merge into `main` to this Git branch.
- **The import filter** is a list of regular expressions. Infrahub creates an Infrahub branch for a new Git branch only when the whole name matches one of them. Infrahub always imports the Git branch named in `default_branch`, even when its name does not match the filter.

The names `feature/`, `promote/integration/` and `promote/production/` are examples. You can name the branches in any way, as long as the import filter of each instance matches the names of its branches. If you change the naming, change the filters too. A promotion branch needs a unique name, but the part after the prefix does not have to be a number. For example, `promote/integration/add-tag-color` works too.

Without an import filter, an instance imports every Git branch. That includes the long-lived branches and the promotion branches of the other environments. Set a filter on every instance, including development. For the full filter syntax, read [branch synchronization](./branch-synchronization.mdx).

Name the production branch something other than `main`, for example `production`. An instance whose `default_branch` is not `main` does not import a Git branch named `main`. It logs a warning about the skipped branch instead. The workflow still works when the production Git branch is named `main`, but every other instance then logs that warning.

For every setting on each instance, follow the [promotion guide](./promote-between-environments.mdx).

## Rules for the team

Infrahub does not enforce the rules below. Each rule names the failure that it prevents.

- **Protect the long-lived Git branches on your Git host.** Block deletion and force-push of `develop`, `integration` and `production`. With branch deletion turned on, Infrahub deletes the Git branch with the same name when you merge an Infrahub branch that syncs with Git. Infrahub does not check that name against the long-lived branches. When an Infrahub branch named `integration` merges, Infrahub deletes the Git branch `integration`.
- **Turn on branch deletion after a merge.** Set `INFRAHUB_DELETE_BRANCH_AFTER_MERGE` and `INFRAHUB_GIT_DELETE_GIT_BRANCH_AFTER_MERGE` to `true` on every instance. Infrahub then deletes the feature or promotion branch in Infrahub and in Git after the merge. The instances and the Git host do not keep merged branches. Infrahub does not start when the Git setting is on and the Infrahub setting is off.
- **Turn on explicit merge commits.** Set `INFRAHUB_GIT_USE_EXPLICIT_MERGE_COMMIT` to `true` on every instance. Infrahub then creates one merge commit in Git for each merge. You need that commit to [undo a change](#undo-a-promoted-change) with one revert. Without it, Git fast-forwards the branch when it can and records no merge commit.
- **Set an import filter on every instance.** Without a filter, an instance imports the branches of the other environments.
- **Use a new name for every promotion branch.** Do not reuse a name. If you delete an Infrahub branch and create it again under the same name, Infrahub keeps its old Git commit. Merging its Proposed Change can then promote the old content.
- **Keep one open promotion branch per target instance.** Merge or delete it before you start the next promotion. When two open promotions change the same objects, one Proposed Change fails its checks after the other merges.
- **Never give an Infrahub branch the name of a long-lived Git branch.** When that Infrahub branch merges, Infrahub deletes the long-lived Git branch with the same name.

## Undo a promoted change

A promotion merges the change into the next Git branch and into the next instance. To undo it, revert the change in Git and promote the revert like any other change:

1. Create a `feature/` branch from `develop`.
2. Revert the change on that branch. With explicit merge commits turned on, the change has one merge commit on `develop`. Run `git revert -m 1 <merge-commit>` to revert it. Without them, revert each commit of the change.
3. Merge the branch on the development instance, then promote it to the next environments.

Infrahub imports a schema change by adding to the schema. When a revert removes an attribute or a node from a schema file, Infrahub keeps it in the instance. To remove it from the instance, set `state: absent` on that attribute or node in the revert. `infrahubctl schema load` uses the same setting.

## Known limitations

- **Removing a schema element needs `state: absent`.** Deleting an attribute or a node from a schema file does not remove it from an instance. Set `state: absent` instead, as in [undo a promoted change](#undo-a-promoted-change).
- **Data stays in each instance.** Only the content of the repository is promoted. Objects created through the web interface or the API stay in the instance where you created them.

## Test a promotion against a copy of production

You find many problems on the lower environments, but those environments are not a copy of production. Over time an integration instance has different data, and a different history of applied changes, from production. A change that merged without errors on integration can still fail on production.

To test a promotion against the real state of production, restore a current [database backup](../deploy-manage/maintain-upgrade/database-backup/backup-and-restore.mdx) of production into a separate instance. Merge the promotion there first, then on production. Give that instance a read-only Git credential, so that its merge does not push to Git.

## Alternative: read-only repositories

A [read-only repository](./overview.mdx#read-only-vs-core) imports one Git branch and never writes to Git. With read-only repositories, a promotion is a merge request on your Git host. You test it on an Infrahub branch of the target instance by changing the `ref` of that branch, then merge it in Git and through a Proposed Change. Choose this setup when your policy does not allow a tool to push to Git. Also choose it when you want your Git host to enforce the order of the environments.

| Criterion | Read-write repositories (recommended) | Read-only repositories |
| --- | --- | --- |
| Review steps per promotion | One: the Proposed Change | Two: the merge request on the Git host and the Proposed Change |
| Work on each target instance | Merge the Proposed Change | Create a branch, set its `ref` to the source branch, merge the merge request, set the `ref` to the target branch, then merge the Proposed Change, manually or with a pipeline that you maintain |
| Git access that Infrahub needs | Push to the long-lived branch of each environment | Read |
| What enforces the order of the environments | Nothing: you create each promotion branch from the correct source branch | The Git host |

To set up this workflow, follow [promote changes with read-only repositories](./promote-read-only.mdx).
