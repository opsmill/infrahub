# Observability stack

Infrahub ships an observability stack that runs alongside Infrahub:

- **Grafana Alloy** — collects logs and metrics
- **Loki** — log storage
- **Prometheus** — metric storage
- **Tempo** — distributed tracing
- **Grafana** — dashboards and visualization
- **Prefect exporter** — task-manager metrics, see [Metrics](../../run-observe/metrics.mdx)

You can deploy it with **Docker Compose** or on **Kubernetes** with the `infrahub-observability` Helm chart. Grafana comes provisioned with pre-built dashboards and data sources for Infrahub, Neo4j, RabbitMQ, and Prefect.


Once running, Grafana is available at [http://localhost:3500](http://localhost:3500) with the default credentials `admin` / `admin`. To set other credentials, add `INFRAHUB_GRAFANA_ADMIN_USER` and `INFRAHUB_GRAFANA_ADMIN_PASSWORD` to a `.env` file next to the compose file before the first start.

### Request tracing

Infrahub exports OpenTelemetry traces, so you can follow one request or background task across the API server, the task workers and the database. The Compose file of the stack, `docker-compose-observability-standalone.yml`, turns tracing on for the `infrahub-server` and `task-worker` services and sends the traces to the bundled Tempo instance, which Grafana shows under the Tempo data source. Infrahub then records one new trace in ten; see [Trace sampling](#trace-sampling) to change that. Without the stack, tracing stays off in a Compose deployment. To turn it off with the stack, set `INFRAHUB_TRACE_ENABLE=false` in a `.env` file alongside the compose file.

To turn tracing on in a Compose deployment that does not include these settings, add the following to a `.env` file alongside the compose file:

```bash
INFRAHUB_TRACE_ENABLE=true
INFRAHUB_TRACE_EXPORTER_TYPE=otlp
INFRAHUB_TRACE_EXPORTER_PROTOCOL=grpc
INFRAHUB_TRACE_EXPORTER_ENDPOINT=http://infrahub-tempo:4317
INFRAHUB_TRACE_INSECURE=true
INFRAHUB_TRACE_SAMPLE_RATIO=0.1
```

`INFRAHUB_TRACE_INSECURE=true` sends spans over a plaintext connection, which is what the bundled Tempo instance expects. Set it to `false` when your collector terminates TLS.

### Exporting to a collector that uses TLS

When the collector presents a certificate issued by a private or internal certificate authority, the default trust store cannot verify it and every export fails with `StatusCode.UNAVAILABLE` (gRPC) or a certificate verification error (HTTP). Point Infrahub at the issuing CA instead:

```bash
INFRAHUB_TRACE_EXPORTER_ENDPOINT=otel-collector.example.com:4317
INFRAHUB_TRACE_TLS_CA_BUNDLE=/etc/ssl/certs/internal-ca.pem
```

The bundle is a PEM file that must be readable by the Infrahub server and task workers, so mount it into both containers. With the `grpc` protocol, setting it also switches the connection to TLS, so `INFRAHUB_TRACE_INSECURE` can be left at its default. With `http/protobuf` the endpoint URL scheme is what selects TLS, so the endpoint must start with `https://`. Infrahub checks the bundle when configuration loads and refuses to start if it cannot be loaded, rather than starting and silently dropping every span.

To skip certificate verification entirely in a test environment, set `INFRAHUB_TRACE_TLS_INSECURE=true`. This requires `INFRAHUB_TRACE_EXPORTER_PROTOCOL=http/protobuf` and an `https://` endpoint, because the gRPC client cannot skip verification; use a CA bundle for gRPC collectors. Never enable it in production.

For the full Compose install, see the [Community](./community) or [Enterprise](./enterprise) install guide.

## Kubernetes with Helm

On Kubernetes the stack is the `infrahub-observability` Helm chart, which wraps the upstream Grafana and Prometheus community charts. Deploy it bundled with your Infrahub release or as a standalone release.

### Prerequisites

- A Kubernetes cluster (version 1.24 or later)
- [Helm](https://helm.sh/docs/intro/install/) (version 3 or later) installed on your system
- A persistent volume provisioner in the cluster. Loki, Prometheus, Tempo, and Grafana enable persistence by default

The stack installs and runs on its own. To collect Infrahub's own metrics and Prefect task data, install it in the same namespace as an Infrahub or Infrahub Enterprise release (or set `global.infrahubReleaseName` when the release name differs). Without a reachable Infrahub, the stack still starts, but the Prefect exporter stays unhealthy and the Infrahub scrape targets report no data.

### Deploy

Deploy the stack either bundled with your Infrahub release or as its own release.

#### Bundled with Infrahub

The `infrahub` and `infrahub-enterprise` charts package the observability stack as a subchart, gated by `infrahub-observability.enabled` (default `false`). Enable it in your Infrahub values to deploy the stack as part of the same release and namespace — no separate install.

For the `infrahub` (Community) chart:

```yaml
# infrahub values
infrahub-observability:
  enabled: true
```

For the `infrahub-enterprise` chart, nest the key under `infrahub`:

```yaml
# infrahub-enterprise values
infrahub:
  infrahub-observability:
    enabled: true
```

Apply the change with `helm upgrade` on your Infrahub release. Enabling the bundled stack also turns tracing on automatically: Infrahub emits traces to the bundled Tempo at `<release>-tempo:4317` (where `<release>` is your Infrahub release name) with no further configuration. The chart does not set the sampling ratio, so Infrahub records one new trace in ten, its default; see [Trace sampling](#trace-sampling).

#### Standalone release

To manage the stack on its own release lifecycle — for example, to add it next to an existing Infrahub release without changing that release — install the chart directly. The `--create-namespace` flag creates the target namespace if it does not already exist; drop it when installing into the namespace where Infrahub already runs:

```bash
helm install obs oci://registry.opsmill.io/opsmill/chart/infrahub-observability --version 0.1.0 -n infrahub --create-namespace
```

The release name (`obs` above) prefixes the service names referenced throughout this guide.

A standalone release does not wire Infrahub's tracing for you. To send traces to its Tempo, set `global.tracing` on the Infrahub release:

```yaml
# infrahub values
global:
  tracing:
    enabled: true
    endpoint: "obs-tempo:4317"
    protocol: grpc
    insecure: true
```

### Services and access

Every component is exposed through a `ClusterIP` service, reachable only from inside the cluster:

| Service | Purpose |
|---------|---------|
| `<release>-grafana` | Grafana UI |
| `<release>-loki` | Log storage (Alloy pushes logs here) |
| `<release>-prometheus-server` | Metric storage (Alloy remote-writes here) |
| `<release>-tempo` | Trace storage (OTLP receiver on port 4317) |
| `<release>-prometheus-node-exporter` | Host metrics |
| `<release>-infrahub-observability-prefect-exporter` | Prefect metrics (scraped by Alloy on port 8000) |

`<release>` is your Infrahub release name when bundled, or the observability release name (`obs` above) when standalone. Run `kubectl get svc -n infrahub` to list the exact service names for your release.

The log, metric, and trace services only need to be reachable from inside the cluster, so keep them as `ClusterIP`. Grafana is the only component intended for people to browse.

To open Grafana, forward its service to your machine (replace `obs` with your Infrahub release name if you bundled the stack):

```bash
kubectl port-forward svc/obs-grafana 3000:80 -n infrahub
```

Then browse to [http://localhost:3000](http://localhost:3000) and sign in with the default credentials `admin` / `admin`.

To reach Grafana without port-forwarding, set `grafana.service.type` to `LoadBalancer` or `NodePort`, or enable an ingress with `grafana.ingress.enabled`.

:::warning

Change the default Grafana credentials before exposing it outside the cluster. Set `grafana.admin.existingSecret` to a secret you manage rather than relying on the default `admin` / `admin`.

:::

### Configure the stack

The component values below set the size, retention, and exposure of each part of the stack:

```yaml
# Turn off components you don't need
tempo:
  enabled: false        # disable tracing

# Persistence and retention
loki:
  singleBinary:
    persistence:
      size: 20Gi
prometheus:
  server:
    retention: 7d
    persistentVolume:
      size: 50Gi

# Expose Grafana through an ingress and use a managed admin secret
grafana:
  ingress:
    enabled: true
  admin:
    existingSecret: grafana-admin
```

Where you place these values depends on how you deploy:

- **Standalone** — set them at the top level of the observability `values.yml`.
- **Bundled** — nest the same blocks under `infrahub-observability:` (or `infrahub.infrahub-observability:` for Enterprise) in your Infrahub values:

```yaml
# infrahub values (bundled)
infrahub-observability:
  tempo:
    enabled: false
  grafana:
    ingress:
      enabled: true
```

:::warning global values are shared, not nested

`global.*` values are Helm global values, shared across Infrahub and the bundled subchart, so they always stay at the **top level** of your values — never nest them under `infrahub-observability:`. The same applies to the Infrahub chart's `global.tracing`. When bundled, the stack resolves the Infrahub release name and namespace from the release itself, so `global.infrahubReleaseName` and `global.infrahubNamespace` are only needed for a standalone release that points at a separately named or located Infrahub.

:::

| Option | Default | Description |
|--------|---------|-------------|
| `<component>.enabled` | `true` | Toggle any of `alloy`, `loki`, `tempo`, `grafana`, `prometheus`, `prometheus-node-exporter`, `prefectExporter` |
| component persistence `size` | Loki `10Gi`, Tempo `10Gi`, Prometheus `20Gi`, Grafana `5Gi` | Persistent volume size per component |
| `loki.loki.limits_config.retention_period` | `24h` | Log retention |
| `tempo.tempo.retention`, `prometheus.server.retention` | `96h` | Trace and metric retention |
| `grafana.service.type`, `grafana.ingress.enabled` | `ClusterIP`, `false` | How Grafana is exposed |
| `grafana.adminPassword`, `grafana.admin.existingSecret` | `admin` | Grafana credentials |
| `alloy.cadvisor.enabled` | `true` | Scrape per-container metrics from the kubelet cAdvisor endpoint. Disable where cluster policy forbids `nodes/proxy` access |
| `tempo.tempo.metricsGenerator.enabled` | `false` | Generate request metrics from spans. Requires `tempo.tempo.metricsGenerator.remoteWriteUrl` |
| `prefectExporter.enabled` | `true` | Deploy the Prefect metrics exporter |
| `grafanaMcp.enabled` | `false` | Deploy the Grafana MCP server, see [Connect an AI assistant](#connect-an-ai-assistant) |
| `global.infrahubReleaseName`, `global.infrahubNamespace` | `infrahub`, release namespace | Standalone only (top-level, never nested): point the release at a separately named or located Infrahub. Auto-resolved when bundled |

For the complete list of values, see the chart's `values.yaml`.

The Docker Compose stack keeps traces and logs for the same time as the chart: 96 hours of traces, set by `block_retention` in the Tempo configuration, and 24 hours of logs, set by `retention_period` in the Loki configuration. Both files are embedded in the Compose file of the stack.

### Verify the deployment

Check that the stack's pods are running:

```bash
kubectl get pods -n infrahub
```

You should see an Alloy pod on each node (deployed as a DaemonSet), single-instance Loki, Tempo, Prometheus, and Grafana pods, a node exporter on each node, and the Prefect exporter. The Prefect exporter only becomes healthy once it can reach the Infrahub task manager, so deploy it alongside an Infrahub release. Once Grafana is reachable, open it and confirm that the Infrahub dashboards render and that the Prometheus and Loki data sources connect successfully.

To upgrade the stack later, see [Upgrade the observability stack](../../maintain-upgrade/upgrade/observability-stack).

## Connect an AI assistant

The stack can run a Grafana MCP server, which gives an AI assistant such as Claude Code read access to the stack's Grafana: the metrics in Prometheus, the traces in Tempo, the logs in Loki and the dashboards. When Infrahub is slow, the assistant can then query the same data you would open in Grafana and point to the component that takes the time. With the Infrahub skill `infrahub-diagnosing-performance` installed, the assistant follows Infrahub's own order of checks and names the metric query, trace or log line behind each finding.

The server is off by default. Each person connects with one URL and one token that you share with them.

### Turn on the Grafana MCP server

Choose a token, a long random value, and keep it secret: anyone with the token can read all the telemetry of the stack.

<Tabs groupId="deployment" queryString>
<TabItem value="compose" label="Docker Compose" default>

Add the profile and the token to the `.env` file next to the compose file, then start the stack again:

```bash
COMPOSE_PROFILES=grafana-mcp
INFRAHUB_GRAFANA_MCP_TOKEN=<token>
```

```bash
docker compose -p infrahub up -d
```

The profile adds two services. `infrahub-grafana-mcp-init` runs at each start and stops: it logs in to Grafana as the admin user, creates the service account `infrahub-grafana-mcp` with the Viewer role if it does not exist, and stores a token for it. `infrahub-grafana-mcp` starts after it and serves the assistants on port 8100 of `127.0.0.1`.

</TabItem>
<TabItem value="helm" label="Kubernetes with Helm">

Store the token in a Secret, then turn the server on in the values of the observability stack (nested under `infrahub-observability:` when the stack is bundled with Infrahub):

```bash
kubectl create secret generic grafana-mcp-token --from-literal=token=<token> -n infrahub
```

```yaml
grafanaMcp:
  enabled: true
  serverToken:
    existingSecret: grafana-mcp-token
```

Apply the change with `helm upgrade`. After each install and upgrade, a Job logs in to Grafana as the admin user, creates the service account `infrahub-grafana-mcp` with the Viewer role if it does not exist, and stores its token in a Secret. The server runs as the Deployment `<release>-infrahub-observability-grafana-mcp`, with a `ClusterIP` Service on port 8000.

</TabItem>
</Tabs>

#### Change the Grafana admin password

The service account step logs in with the Grafana admin user each time it runs, so the server depends on that account. Change the default `admin` / `admin` before you turn the server on:

- **Docker Compose:** set `INFRAHUB_GRAFANA_ADMIN_USER` and `INFRAHUB_GRAFANA_ADMIN_PASSWORD` in the `.env` file. Grafana and the service account step both read these two settings. Grafana applies them when it creates its database, at the first start. If you change the password later in Grafana, change the setting too, or the step stops with `Grafana refused the admin login`.
- **Helm:** set `grafana.admin.existingSecret` to a Secret you manage, as described in [Services and access](#services-and-access). The Job reads the same Secret. To give the Job another Secret, set `grafanaMcp.grafana.adminSecret`.

### Connect your assistant

The server listens on `http://localhost:8100/mcp`. In Kubernetes, forward its Service to that port first:

```bash
kubectl port-forward svc/<release>-infrahub-observability-grafana-mcp 8100:8000 -n infrahub
```

Then add the server to your assistant with the token in an `Authorization` header. For Claude Code:

```bash
claude mcp add --transport http grafana http://localhost:8100/mcp --header "Authorization: Bearer <token>"
```

The server uses the Streamable HTTP transport of MCP. For another assistant, use the same URL and header, and see its MCP documentation for where the entry goes.

### Reach the server from another computer

By default the server answers only on the computer or cluster where the stack runs. To use it from a laptop, choose one of these:

- **An SSH tunnel** to the Docker host, for example `ssh -L 8100:127.0.0.1:8100 <docker-host>`. Nothing changes in the stack.
- **`kubectl port-forward`** in Kubernetes, as shown above. Nothing changes in the stack.
- **A reverse proxy with TLS** in front of the server, for example the ingress controller of the cluster. Add the host name and port that the proxy sends to the allowed hosts.
- **Open the server to a network with TLS.** The server then serves HTTPS with your certificate.

The server checks the `Host` header of each request against a list of allowed hosts, and refuses a request from any other host name. The default list is `localhost:8100,127.0.0.1:8100`.

<Tabs groupId="deployment" queryString>
<TabItem value="compose" label="Docker Compose" default>

To open the server to a network, set these four settings together in the `.env` file:

```bash
INFRAHUB_GRAFANA_MCP_LISTEN_ADDRESS=0.0.0.0
INFRAHUB_GRAFANA_MCP_TLS_CERT_FILE=/etc/infrahub/grafana-mcp/tls.crt
INFRAHUB_GRAFANA_MCP_TLS_KEY_FILE=/etc/infrahub/grafana-mcp/tls.key
INFRAHUB_GRAFANA_MCP_ALLOWED_HOSTS=grafana-mcp.example.com:8100
```

The two file settings are paths on the Docker host. The server runs as user `1000`, so that user must be able to read the key file. Without both files, the server refuses to start on an address outside `127.0.0.0/8` and `::1`. Each person then connects to `https://grafana-mcp.example.com:8100/mcp`.

</TabItem>
<TabItem value="helm" label="Kubernetes with Helm">

To open the server to a network, give it a `kubernetes.io/tls` Secret, for example one that cert-manager manages, and add the host name to the allowed hosts:

```yaml
grafanaMcp:
  service:
    type: LoadBalancer
  tls:
    existingSecret: grafana-mcp-tls
  allowedHosts: "grafana-mcp.example.com:8000"
```

Without `tls.existingSecret`, the install fails when `service.type` is `LoadBalancer` or `NodePort`.

</TabItem>
</Tabs>

When your own certificate authority signed the certificate, each person's computer must trust that authority, or the assistant cannot connect.

### Change the token or the certificate

The server reads the token and the certificate when it starts. After you change either one, restart the server:

<TabItem value="compose" label="Docker Compose" default>

```bash
docker compose -p infrahub up -d --force-recreate infrahub-grafana-mcp
```

</TabItem>


Then send the new token to each person who connects. The token of the Grafana service account is separate: the service account step replaces it on its own when Grafana refuses it.

### When the server does not start

In Docker Compose, the server stops at once, with one of these messages in its log, when its settings are not valid together:

| Message | Fix |
|---|---|
| `INFRAHUB_GRAFANA_MCP_TOKEN is not set` | Set the token in the `.env` file |
| `Set both INFRAHUB_GRAFANA_MCP_TLS_CERT_FILE and INFRAHUB_GRAFANA_MCP_TLS_KEY_FILE, or neither` | Set the missing file, or remove the one you set |
| `INFRAHUB_GRAFANA_MCP_LISTEN_ADDRESS is <address>, which is open to a network` | Set the two TLS files, or set the address back to `127.0.0.1` |
| `Grafana refused the admin login` (in `infrahub-grafana-mcp-init`) | Set the admin user and password that Grafana uses, as described in [Change the Grafana admin password](#change-the-grafana-admin-password) |

In Kubernetes, `helm install` and `helm upgrade` fail before anything is created when `grafanaMcp.serverToken` has no value and no `existingSecret`, or when the Service is open to a network without TLS. The service account Job writes the same `Grafana refused the admin login` message.

### What the assistant can read, and where it goes

The server only reads. In this stack it has no tool that creates or changes dashboards, folders, annotations, incidents, alert rules or data sources, and it has no tool that calls a host outside your network. The service account it uses has the Viewer role.

Everything that the server returns to the assistant goes to the provider of the AI model that the assistant uses. Before you share the token, check what the telemetry of your instance contains:

- **Traces:** Infrahub masks tokens, passwords, user names, email addresses, client IP addresses and URL query strings, and keeps database queries, query names and URL paths readable. See [Values that spans never contain](#values-that-spans-never-contain).
- **Logs:** Infrahub does not mask log lines. Two lines that Infrahub writes on purpose contain data from your instance:
  - Each webhook delivery writes, at the `INFO` level, the first 2048 characters of the event payload: the values of the object that changed, for example the name of an account. In every URL inside that payload, Infrahub removes the user and password and replaces the query string and the fragment with `[MASKED]`.
  - The same lines name the webhook URL with its path. Slack, Discord and Microsoft Teams put the secret of an incoming webhook in the path, so that secret is in the log.
- **Other pods in Kubernetes:** the Alloy of the chart collects the logs of every pod in the Infrahub namespace. Keep workloads whose logs you do not want to share out of that namespace.

## Trace sampling

When tracing is on, Infrahub records a share of the new traces, set by `INFRAHUB_TRACE_SAMPLE_RATIO` on the API server and on every task worker:

| Value | Effect |
|---|---|
| `0.1` (default) | Records one new trace in ten |
| `1` | Records every new trace |
| `0` | Records no new trace |

Infrahub recorded every trace before this setting existed. Each recorded trace adds work to the API server and the task workers and uses storage in Tempo, so a higher ratio costs more. Infrahub reads the value when a process starts. To record more traces for a limited time without a restart, see [Record more traces during an incident](#record-more-traces-during-an-incident).

For a request or a flow run that arrives with a trace context, Infrahub keeps the decision of its caller: it records the request when the caller recorded its own span, and does not record it otherwise. A flow run started by an API request therefore belongs to the same trace as that request, and a trace is either complete or absent.

### Record more traces during an incident

A slow component is easier to find when every request is traced, and a restart can remove the slow behavior you want to observe. An account with the `super_admin` permission can therefore replace the ratio on every API server process and task worker for 1 second to 24 hours, without a restart. Send a `PUT` request to `/api/troubleshooting/trace-sample-ratio` with the ratio and the number of seconds it applies:

```bash
curl -X PUT "https://infrahub.example.com/api/troubleshooting/trace-sample-ratio" \
  -H "X-INFRAHUB-KEY: <api-token>" \
  -H "Content-Type: application/json" \
  -d '{"ratio": 1, "duration_seconds": 1800}'
```

The response shows the sampling state of the API server process that handled the request:

```json
{
  "enabled": true,
  "default_ratio": 0.1,
  "temporary_ratio": 1.0,
  "expires_at": "2026-10-21T14:30:00Z",
  "ratio_in_force": 1.0
}
```

- A `GET` request to the same path returns this state without changing it.
- A `DELETE` request to the same path clears the temporary ratio before the end time, so every process uses `INFRAHUB_TRACE_SAMPLE_RATIO` again.
- A new `PUT` request replaces the ratio and the end time of the previous one.
- At the end time, every process uses `INFRAHUB_TRACE_SAMPLE_RATIO` again, with no request needed.
- A process that starts or restarts while the temporary ratio applies uses `INFRAHUB_TRACE_SAMPLE_RATIO`. Send the `PUT` request again to apply the temporary ratio to it.
- When tracing is off, the `PUT` and `DELETE` requests fail with `Tracing is not enabled on this instance; set INFRAHUB_TRACE_ENABLE`, and the `GET` request returns `"enabled": false`.

For each change, Infrahub records an `infrahub.trace.sample_ratio_updated` event with the account that made the change, the ratio before and after it, and the end time. See the [trace events reference](../../../reference/infrahub-events/trace.mdx).

### Check that every process applied the change

Each API server process and task worker writes one log line when it applies the change: `Set the temporary trace sampling ratio`, with the `ratio` and `expires_at` fields, or `Cleared the temporary trace sampling ratio`. In Grafana, search Loki for that text and check that you find one line per API server process and per task worker. A process without the line did not receive the change; send the request again.

### Reduce the cost of tracing

To stop recording new traces at once, send a `PUT` request with `"ratio": 0` and a duration of up to 86400 seconds. At the next restart, lower `INFRAHUB_TRACE_SAMPLE_RATIO`, or set `INFRAHUB_TRACE_ENABLE=false` to turn tracing off.

### Find the log lines of a trace

Each log line that the API server or a task worker writes while a trace is recorded has a `trace_id` field: the trace ID as 32 lowercase hexadecimal characters, the form Tempo uses. The API server wrote it before as a `0x` hexadecimal number without leading zeros; update the log queries and alert rules that read `trace_id`.

In Grafana, open a span in Tempo and select **Logs for this span** to view the log lines of its trace, from one hour before to one hour after the span. From a log line in Loki, open the line and select **View trace in Tempo** next to its `trace_id` field. The task logs that the Infrahub web interface shows for each task don't have a `trace_id`.

To set up the same links in your own Grafana, see [Send Infrahub telemetry to your own monitoring](../../run-observe/own-monitoring.mdx).

### Values that spans never contain

Before a span leaves the API server or a task worker, Infrahub replaces these attribute values with `[MASKED]` and keeps the attribute name:

- Client IP addresses
- URL query strings, for example the `code` and `state` parameters of a single sign-on login. The scheme, the host name and the path of the URL stay readable.
- Attributes whose name contains `token`, `password`, `secret`, `email`, `user_name` or `username`
- The `account_name` attribute

Database queries and query names stay readable. Log lines are not masked; for the log lines that contain data from your instance, see [What the assistant can read, and where it goes](#what-the-assistant-can-read-and-where-it-goes).
