# Migrate from Community to Enterprise <EnterpriseBadge />

This guide describes how to convert an existing Infrahub Community deployment into an Infrahub Enterprise deployment **in place**, preserving the existing graph database, Git repositories, and Prefect flow run history.

The procedure covers the two container-based deployment methods — Docker Compose and Helm on Kubernetes. Both follow the same shape: swap the Community images for the Enterprise images while keeping every data volume attached, then run `infrahub upgrade` against the existing databases.

:::note Bare metal deployments

Infrahub Enterprise also supports [bare metal installations](../../install-configure/install/enterprise.mdx), but migrating a bare metal Community deployment is not covered here. Reach out to the OpsMill team on [Discord](https://discord.gg/opsmill) or at [contact@opsmill.com](mailto:contact@opsmill.com).

:::

## What changes during the migration

The data layers — Neo4j, Redis, RabbitMQ or NATS, the Prefect PostgreSQL database, and the API server's Git working directory — are reused. What changes is the container images and the process each one runs:

| Component | Before | After |
|---|---|---|
| API server image | `registry.opsmill.io/opsmill/infrahub` | `registry.opsmill.io/opsmill/infrahub-enterprise` |
| Task worker image | `registry.opsmill.io/opsmill/infrahub` | `registry.opsmill.io/opsmill/infrahub-enterprise` |
| Task manager (Prefect) image | `registry.opsmill.io/opsmill/infrahub` | `registry.opsmill.io/opsmill/infrahub-enterprise` |
| Server Gunicorn app | `infrahub.server:app` | `infrahub_enterprise.server:app` |
| Task worker type | `infrahubasync` | `infrahubentasync` |
| Work pool name | `infrahub-worker` | `infrahub-worker` (unchanged) |
| Neo4j edition (bundled deployment only) | community | enterprise |
| Neo4j store format | `aligned` | `block`, after the [store format migration](#migrate-the-neo4j-store-to-the-block-format) |
| `/api/config` `installation_type` | `community` | `enterprise` |

### How the work pool is switched

The task worker changes type, but the Prefect work pool keeps the name `infrahub-worker`, so any externally registered flows continue to route to it.

The pool itself has to be recreated, because a Prefect work pool is typed and an `infrahubentasync` worker cannot poll an `infrahubasync` pool. Infrahub Enterprise sets `INFRAHUB_WORKFLOW_DEFAULT_WORKER_TYPE` to `infrahubentasync`, and both `infrahub upgrade` and the primary server's startup recreate the pool with that type. Running `infrahub upgrade` after the swap — a required step in both procedures below — is what guarantees the pool is retyped before the new workers start polling.

`infrahub upgrade` runs its full six-step pipeline, not only the task manager step. Because the prerequisites keep the version unchanged, Step 1/6 reports no pending database migrations; Step 5/6 is the step that retypes the work pool. See [what the upgrade does](./overview.mdx#what-the-upgrade-does) for the whole pipeline and the output to expect.

:::info Licensing

No license file, license key, or image pull secret is required. Images can be pulled from the Enterprise registry (`registry.opsmill.io/opsmill/infrahub-enterprise`) without authentication.

:::

## Neo4j deployment and licensing

OpsMill recommends running Neo4j using the Neo4j deployment bundled with Infrahub Enterprise — the `database` service in the Enterprise Docker Compose file, or the Neo4j sub-chart in the Enterprise Helm chart — rather than a managed Neo4j offering from a cloud provider:

- OpsMill validates the performance of Infrahub Enterprise against the bundled Neo4j deployment. OpsMill does not validate the performance of managed Neo4j instances.
- The Neo4j Enterprise license is already included in your Infrahub Enterprise agreement. With a managed offering, you would pay for the Neo4j license twice.

No separate Neo4j license key is required when using the bundled deployment. Infrahub Enterprise accepts the Neo4j license agreement on your behalf, under the terms of your Infrahub Enterprise agreement.

## Prerequisites

Before starting, confirm the following:

1. **Your target Enterprise version matches your current Community version.** Check the running version via `curl https://<your-infrahub-host>/api/config | jq .` or by inspecting the running image tag. Do not combine an edition swap with a version upgrade in a single step.
2. **A database backup exists and you have verified that it can be restored.** Take a recent `neo4j-admin database dump` or an equivalent volume snapshot with the database stopped or paused. The Enterprise edition rewrites license metadata in the store on first boot, and a rollback past that point requires the dump. See [Backup and restore](../database-backup/backup-and-restore.mdx).
3. **The name that binds your deployment to its data is recorded and does not change.** For Helm this is the release name; for Docker Compose it is the project name. Reusing it is what guarantees the existing volumes, service DNS entries, and credentials are picked up by the Enterprise deployment. The tabs below cover each case.
4. **The existing configuration is in source control.** You will be replacing the Compose file or restructuring the values file; keep the original so you can revert to it.
5. **If your Neo4j runs outside the deployment**, plan the Neo4j edition switch as a separate operation. See [External Neo4j edition switch](#external-neo4j-edition-switch).

## Prepare the new configuration

<Tabs groupId="deployment" queryString>
<TabItem value="docker" label="Docker Compose" default>

Keep the Community Compose file, then fetch the Enterprise Compose file for the version you are currently running:

```bash
# Keep the current file so you can revert to it
cp docker-compose.yml docker-compose.community.yml

# Retrieve the Enterprise Compose file, pinned to your current version
curl https://infrahub.opsmill.io/enterprise/1.10.6 > docker-compose.yml
```

Replace `1.10.6` with the version reported by `/api/config`. Fetching `https://infrahub.opsmill.io/enterprise` without a version returns the latest release, which would combine the edition swap with a version upgrade.

You can append a sizing preset — `?size=small`, `?size=medium`, `?size=large` — to configure replica counts and Neo4j memory settings for your hardware. See [Install Infrahub Enterprise](../../install-configure/install/enterprise.mdx) for the sizing table.

### Configuration that carries over

Environment variable names are identical between editions, so an existing `.env` file or Compose override file applies unchanged. The Enterprise Compose file adds two variables specific to Enterprise features, both empty by default:

- `INFRAHUB_POLICY_REQUIRED_PROPOSED_CHANGE_APPROVALS`
- `INFRAHUB_POLICY_REVOKE_PROPOSED_CHANGE_APPROVALS`

It also adds a `task-manager-background-svc` service, which starts fresh and holds no persistent state of its own.

:::warning The project name must not change

Docker Compose prefixes volume names with the project name, so `-p infrahub` gives volumes named `infrahub_database_data`, `infrahub_storage_data`, and so on. Starting the Enterprise stack under a different project name creates a new, empty set of volumes and the migrated instance will come up with no data.

Use the same `-p <project-name>` value you used for the Community deployment on every command below. Confirm it with `docker compose ls`.

:::

</TabItem>
<TabItem value="helm" label="Helm">

The Enterprise Helm chart (`infrahub-enterprise`) is a wrapper chart that declares the Community chart (`infrahub`) as a dependency, and exposes the entire Community values tree under a top-level `infrahub:` key. Every override you currently set at the root of your values file must move under `infrahub:`.

**Before** (`values-community.yaml`):

```yaml
infrahubServer:
  replicas: 2
  ingress:
    enabled: true
    hostname: infrahub.example.com
  infrahubServer:
    env:
      INFRAHUB_DB_ADDRESS: neo4j.example.internal
      INFRAHUB_DB_PASSWORD: <password>

infrahubTaskWorker:
  replicas: 3
  infrahubTaskWorker:
    env:
      INFRAHUB_DB_ADDRESS: neo4j.example.internal
      INFRAHUB_DB_PASSWORD: <password>
```

**After** (`values-enterprise.yaml`):

```yaml
infrahub:
  global:
    infrahubTag: "1.9.3"  # set to your current Infrahub version

  infrahubServer:
    replicas: 2
    ingress:
      enabled: true
      hostname: infrahub.example.com
    infrahubServer:
      env:
        INFRAHUB_DB_ADDRESS: neo4j.example.internal
        INFRAHUB_DB_PASSWORD: <password>

  infrahubTaskWorker:
    replicas: 3
    infrahubTaskWorker:
      env:
        INFRAHUB_DB_ADDRESS: neo4j.example.internal
        INFRAHUB_DB_PASSWORD: <password>

  prefect-server:
    global:
      prefect:
        image:
          prefectTag: "1.9.3"  # set to your current Infrahub version
```

### Pin the Infrahub version

`global.infrahubTag` is an override, not a required value. Left unset, the image tag defaults to the chart's `appVersion` — chart `4.18.0` declares `appVersion: "1.10.6"`, so it deploys Infrahub 1.10.6.

The chart version and the `appVersion` move independently, so choosing a chart version also chooses an Infrahub version, whether or not you meant to. Prerequisite 1 requires the version to stay unchanged across the edition swap, so set both tags explicitly — that pins the outcome to your current version and keeps it pinned when the chart version moves:

```yaml
infrahub:
  global:
    infrahubTag: "1.9.3"          # pins infrahub-server and infrahub-task-worker
  prefect-server:
    global:
      prefect:
        image:
          prefectTag: "1.9.3"     # pins the Prefect server container
```

### Choose a chart version

The chart version is separate from the image tags above, and is set with `--version` on the `helm upgrade` command rather than in the values file. Pin it explicitly — without `--version`, Helm resolves the latest published chart, which changes more than the edition.

For production, use a flavored chart. Available from chart version 4.0.0, these come pre-configured with replica counts and resource allocations for a sizing plan, so the values you would otherwise hand-write are already set. Appending the flavor to any chart version selects it:

| Flavor      | Chart version example | Required memory |
|-------------|-----------------------|-----------------|
| small       | 4.18.0-small          | 16 GB           |
| medium      | 4.18.0-medium         | 32 GB           |
| medium-data | 4.18.0-medium-data    | 32 GB           |
| large       | 4.18.0-large          | 64 GB           |
| large-data  | 4.18.0-large-data     | 64 GB           |

Pick the flavor matching the sizing your Community deployment already runs at. The base chart (for example, `4.18.0`) is the alternative when you provide your own sizing configuration. See [Install Infrahub Enterprise](../../install-configure/install/enterprise.mdx) for the values behind each preset.

:::info Redis host configuration for flavored charts

When using a flavored chart, you must also configure the Redis host for the Prefect background services. Add the following to your values file:

```yaml
infrahub:
  prefect-server:
    backgroundServices:
      messaging:
        redis:
          host: "infrahub-cache-master"
```

The `host` value should match your Redis service name. If you deployed Redis using the bundled dependency, this defaults to `infrahub-cache-master`. This configuration is only required when using sizing presets — the base chart does not require it.

:::

:::warning The release name must not change

The release name is what guarantees the PVC names, service DNS entries, and credential secrets are reused. Find it with `helm list -n <namespace>` and use that same name for every command below.

:::

## Pre-flight checks

<Tabs groupId="deployment" queryString>
<TabItem value="docker" label="Docker Compose" default>

```bash
# Confirm the project name
docker compose ls

# Confirm the running services and their images
docker compose -p infrahub ps

# Confirm the volumes that must survive the swap
docker volume ls --filter name=infrahub

# Render the merged Enterprise configuration without starting anything
docker compose -p infrahub config
```

Review the rendered configuration for:

- Identical volume names — `database_data`, `database_logs`, `storage_data`, `workflow_db`, `workflow_data`.
- Image references showing `infrahub-enterprise:<version>` at the version you pinned.
- A `database` service on `neo4j:<version>-enterprise`.

</TabItem>
<TabItem value="helm" label="Helm">

Run the following from a workstation with `kubectl` and `helm` configured against the production cluster:

```bash
# Confirm the release exists and note its name
helm list -n <namespace>

# Confirm current PVCs — these must survive the swap
kubectl -n <namespace> get pvc

# Confirm current images
kubectl -n <namespace> get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{range .spec.containers[*]}{.image}{"\n"}{end}{end}'

# Confirm Helm history is clean (no pending revisions)
helm history <release-name> -n <namespace>

# Dry-run the upgrade to inspect the rendered manifests
helm upgrade <release-name> oci://registry.opsmill.io/opsmill/chart/infrahub-enterprise \
  -n <namespace> -f values-enterprise.yaml --version 4.18.0-small --dry-run
```

Use the same `--version` you intend to run for real — a dry-run against a different chart version renders manifests you are not going to apply.

Review the dry-run output for:

- Identical PVC names (the StatefulSet `volumeClaimTemplates` and any standalone PVCs should match what `kubectl get pvc` showed).
- Identical service names.
- Image references showing `infrahub-enterprise:<version>`.

</TabItem>
</Tabs>

## Perform the migration

### Announce a maintenance window

Expect 5–10 minutes of API unavailability while the Infrahub server containers are recreated. If you run the bundled Neo4j, it also restarts to switch editions during this window.

Add time for the [Neo4j store format migration](#migrate-the-neo4j-store-to-the-block-format) if you convert the store in the same window. That conversion is offline and its duration scales with the size of the graph, so measure it against a copy of your data before committing to a window length.

### Run the swap

<Tabs groupId="deployment" queryString>
<TabItem value="docker" label="Docker Compose" default>

```bash
# Stop the Community stack, keeping the volumes
docker compose -p infrahub down

# Run the upgrade pipeline against the existing databases
docker compose -p infrahub run --rm infrahub-server infrahub upgrade

# Start the Enterprise stack on the same volumes
docker compose -p infrahub up -d
```

:::danger Never pass `-v` to `docker compose down`

`docker compose down -v` deletes the named volumes, which destroys the graph database, the Git working directory, and the Prefect flow run history. The migration requires `docker compose down` with no flags.

:::

Expected behavior:

- The `database` service restarts on the Neo4j Enterprise image, attached to the same `database_data` volume. Neo4j rewrites license metadata in the store on this first boot.
- `infrahub upgrade` runs its six-step pipeline. Step 5/6 recreates the `infrahub-worker` pool with the `infrahubentasync` type. See [what the upgrade does](./overview.mdx#what-the-upgrade-does) for the output to expect.
- The `task-manager-background-svc` service starts for the first time.
- Task workers register against the `infrahub-worker` pool as `InfrahubEntWorkerAsync`.

Old Community images stay on the host and consume disk space. Remove them with `docker image prune -a` once the migration is verified.

</TabItem>
<TabItem value="helm" label="Helm">

```bash
# Swap the chart on the existing release
helm upgrade <release-name> oci://registry.opsmill.io/opsmill/chart/infrahub-enterprise \
  -n <namespace> \
  -f values-enterprise.yaml \
  --version 4.18.0-small \
  --timeout 15m

# Run the upgrade pipeline from inside the new server pod
kubectl -n <namespace> exec deploy/<release-name>-infrahub-server -- infrahub upgrade
```

Helm replaces the chart on the existing release. Expected behavior during the rollout:

- The `infrahub-server` Deployment rolls. Old Community pods drain as new Enterprise pods become Ready. On a single-replica setup expect roughly 30–60 seconds of HTTP 502 errors through the ingress.
- The `infrahub-task-worker` Deployment rolls. The worker registers against the same `infrahub-worker` pool with the new `InfrahubEntWorkerAsync` type — any flows running at the moment of the swap may need to be triggered again.
- The `prefect-server` Deployment rolls. Flow run history in PostgreSQL is preserved.
- The first Enterprise server pod may crash once or twice with `ServiceUnavailable` against Neo4j if Neo4j is restarting. The `wait-for-prefect` init container plus the Kubernetes restart policy resolve any transient connection failure within about 60 seconds.

Run `infrahub upgrade` once the server Deployment reports Ready. Step 5/6 recreates the `infrahub-worker` pool with the `infrahubentasync` type. See [what the upgrade does](./overview.mdx#what-the-upgrade-does) for the output to expect.

### Watch the rollout

```bash
watch -n 2 kubectl -n <namespace> get pods
```

Wait until all `infrahub-server-*`, `infrahub-task-worker-*`, and `prefect-server-*` pods are `1/1 Running` on the new image.

</TabItem>
</Tabs>

## Migrate the Neo4j store to the block format

Neo4j Community stores data in the `aligned` format. The `block` format is available only on Neo4j Enterprise, where it is the format new databases are created with.

An existing store keeps the format it was created with when an Enterprise binary opens it, so the edition swap on its own leaves the graph on `aligned`. Converting the store is a separate, explicit step.

Run the conversion after the edition swap — it needs the Enterprise binary — and treat it as part of the migration rather than as an optional follow-up: an Enterprise deployment left on an `aligned` store does not get the storage and read performance characteristics the Enterprise edition is tuned for.

:::danger This step is one-way

A `block` store cannot be opened by a Neo4j Community binary, and cannot be converted back to `aligned`. Once you convert, the dump taken during the [prerequisites](#prerequisites) is the only route back to Community. Verify that the dump restores before you start.

:::

### Check the current store format

<Tabs groupId="deployment" queryString>
<TabItem value="docker" label="Docker Compose" default>

```bash
docker compose -p infrahub exec database \
  cypher-shell -u neo4j -d system "SHOW DATABASES YIELD name, store"
```

</TabItem>
<TabItem value="helm" label="Helm">

```bash
kubectl -n <namespace> exec -it <neo4j-pod> -- \
  cypher-shell -u neo4j -d system "SHOW DATABASES YIELD name, store"
```

</TabItem>
</Tabs>

A `store` value starting with `record-aligned` means the `neo4j` database is still on the Community format. A value starting with `block` means the conversion is done.

### Convert the store

The [`infrahub-backup` CLI](https://docs.infrahub.app/backup/) is the supported path. Restoring a backup recreates the databases, and the tool exposes an option on `restore` that migrates the Neo4j store format as part of that restore, so the conversion rides along with a backup you should be taking anyway:

```bash
# Take a fresh backup of the migrated Enterprise deployment
./infrahub-backup create

# Restore it, converting the Neo4j store to the block format
./infrahub-backup restore infrahub_backup_<timestamp>.tar.gz
```

Pass the store format migration option to `restore`, and on Kubernetes add `--k8s-namespace <namespace>`. See the [infrahub-backup CLI reference](https://docs.infrahub.app/backup/) for the exact flags. The tool stops the application containers, restores PostgreSQL and Neo4j, and restarts the services in order — see [Backup and restore](../database-backup/backup-and-restore.mdx) for what a restore covers, including object storage, which the tool does not yet handle.

Converting the store in place with `neo4j-admin database migrate --to-format=block` against a stopped database is the alternative when you cannot run a restore. It works on the same store rather than on a copy, which leaves no intact fallback if it fails partway, so take the dump first either way. Consult the [Neo4j store formats documentation](https://neo4j.com/docs/operations-manual/current/database-internals/store-formats/) for the constraints that apply to your Neo4j version.

Re-run the `SHOW DATABASES YIELD name, store` query above once the deployment is back up, and confirm the `neo4j` database reports a `block` store.

## External Neo4j edition switch

:::note

The steps below apply only when your Neo4j runs outside the Infrahub deployment. If you use the bundled Neo4j — the setup recommended by OpsMill — Infrahub Enterprise switches Neo4j to Enterprise edition for you during the swap, and the only remaining database work is the [store format migration](#migrate-the-neo4j-store-to-the-block-format).

:::

Swapping the Infrahub images only affects the containers Infrahub manages. If your Neo4j runs elsewhere, switching Neo4j from Community to Enterprise edition is a separate operation:

- The Neo4j Community storage format is forward-compatible with Neo4j Enterprise of the same minor version. The same data volume can be mounted by an Enterprise binary.
- Switching edition requires a new Neo4j installation, because Community and Enterprise are different distributions and Docker images.

The procedure is:

1. Stop the existing Community Neo4j instance.
2. Take a `neo4j-admin database dump` of the `neo4j` database and the `system` database.
3. Provision the Enterprise instance with a valid Neo4j Enterprise license.
4. Restore the dumps into the Enterprise instance with `neo4j-admin database load`.
5. Point Infrahub at the new endpoint via `INFRAHUB_DB_ADDRESS`.
6. Convert the store to the `block` format, as described in [Migrate the Neo4j store to the block format](#migrate-the-neo4j-store-to-the-block-format). A restored store keeps the `aligned` format it had on Community.

This can happen before, simultaneously with, or after the edition swap — Infrahub Enterprise runs against Neo4j Community. The performance and high-availability benefits of Infrahub Enterprise that depend on Neo4j Enterprise features (online backups, causal clustering, and advanced indexing) only apply once Neo4j is also on the Enterprise edition.

If you want to defer the Neo4j edition switch, you can temporarily run the Infrahub Enterprise containers against Neo4j Community. The application will function; you will not get the scale-out database properties. Consider using this opportunity to move your external Neo4j to the bundled deployment, as described in [Neo4j deployment and licensing](#neo4j-deployment-and-licensing).

## Verify the migration

Once every service is running, confirm the migration. These two checks are the same for both deployment methods:

```bash
# 1. installation_type changed
curl -s https://<your-host>/api/config | jq .installation_type
# expect: "enterprise"

# 2. Application-level data sanity check
curl -s -X POST https://<your-host>/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"query { Branch { name description } }"}' | jq .
# expect: main branch plus any other branches that existed pre-upgrade
```

The remaining checks depend on how you deployed:

<TabItem value="docker" label="Docker Compose" default>

```bash
# 3. Worker registered as the Enterprise worker
docker compose -p infrahub logs task-worker --tail=200 | grep "Worker '"
# expect a line like: Worker 'InfrahubEntWorkerAsync <uuid>' started!

# 4. Images on the Enterprise repository
docker compose -p infrahub ps

# 6. Every migration applied
docker compose -p infrahub exec infrahub-server infrahub db showmigrations
```

## Roll back

Reverting the images and configuration returns the application layer to Community. Whether that is enough depends on the database:

- **Neo4j still on the Community edition** (external Neo4j you have not switched yet): reverting the configuration is sufficient. The `installation_type` field changes back to `community`.
- **Neo4j switched to the Enterprise edition** (the bundled deployment always does this): reverting the configuration is not sufficient, because the Neo4j Enterprise store cannot be read by a Neo4j Community binary. Restore the dump taken during the [prerequisites](#prerequisites). This is definitive once the store has been [converted to the block format](#migrate-the-neo4j-store-to-the-block-format), a format Neo4j Community cannot open at all.

<Tabs groupId="deployment" queryString>
<TabItem value="docker" label="Docker Compose" default>

```bash
docker compose -p infrahub down
cp docker-compose.community.yml docker-compose.yml
docker compose -p infrahub up -d
```

</TabItem>
<TabItem value="helm" label="Helm">

```bash
helm history <release-name> -n <namespace>
helm rollback <release-name> <previous-revision> -n <namespace> --timeout 15m
```

Helm reapplies the Community chart manifests; the pods roll back to the Community images; the PVCs remain bound.

</TabItem>
</Tabs>

:::warning

Do not rely on a configuration rollback for recovery after an extended period of Enterprise-only feature use. Restore the Neo4j dump taken during the [prerequisites](#prerequisites) instead.

:::
