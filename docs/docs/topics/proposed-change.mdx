# Understanding Proposed Changes

A Proposed Change represents Infrahub's systematic approach to reviewing, validating, and merging changes between branches. It combines the familiar concepts of pull requests from software development with infrastructure-specific validation and safety mechanisms, creating a comprehensive change management system for infrastructure data.

## Core concepts

### Mental model: Infrastructure pull requests

For those familiar with software development, a Proposed Change serves a similar purpose to a pull request or merge request in Git platforms like GitHub or GitLab. However, while traditional pull requests focus on code changes, Proposed Changes operate on structured infrastructure data, configuration artifacts, and their relationships.

Key parallels with pull requests:

- **Branch comparison**: Visualize differences between source and destination branches
- **Review process**: Collaborative evaluation of proposed modifications
- **Automated validation**: CI/CD-style checks and tests
- **Conflict detection**: Identify and resolve competing changes
- **Controlled merging**: Gated integration into the main branch

### Beyond text diffs: Data-aware comparisons

Traditional version control systems compare files as text, line by line. Proposed Changes transcend this limitation by understanding the semantic meaning of infrastructure data:

#### Structured data diffs

Instead of seeing:

```diff
- hostname: "router01.nyc"
+ hostname: "router01.ny1"
```

Proposed Changes present:

- **Object-level changes**: "Device router01 hostname changed"
- **Relationship modifications**: "Interface eth0 moved from VLAN 100 to VLAN 200"
- **Schema evolution**: "New required attribute 'location' added to Device model"

#### Artifact impact analysis

Proposed Changes automatically trace how data modifications cascade through your infrastructure:

- **Configuration generation**: Preview how device configs will change
- **Template rendering**: See the effect on Jinja2/Python templates
- **Dependency tracking**: Understand which systems are affected
- **Change scope**: Visualize the blast radius of modifications

## Architecture and components

### The validation pipeline

When you create a Proposed Change, Infrahub orchestrates a comprehensive validation pipeline that ensures changes are safe, compliant, and ready for production.

#### Pipeline stages

1. **Initialization**
   - Calculate diff between branches
   - Identify affected objects and relationships
   - Determine which checks to execute

2. **Parallel validation**
   - Data integrity checks
   - Schema compatibility validation
   - Custom business logic checks
   - Repository synchronization
   - Artifact generation and comparison

3. **Result aggregation**
   - Collect check outcomes
   - Identify conflicts and issues
   - Generate comprehensive report

4. **Continuous monitoring**
   - Re-run checks on branch updates
   - Track conflict resolution progress
   - Update status in real-time

### Check types and their purposes

Infrahub runs multiple categories of checks, each serving a specific validation purpose:

#### Data integrity checks

These ensure your infrastructure data remains consistent:

- **Uniqueness validation**: No duplicate IP addresses, hostnames, or identifiers
- **Referential integrity**: All relationships point to valid objects
- **Required fields**: Mandatory attributes have values
- **Data type validation**: Values conform to expected formats

#### Schema integrity checks

Validate that changes maintain schema compatibility:

- **Backward compatibility**: Existing data works with schema changes
- **Migration feasibility**: Changes can be safely applied
- **Constraint satisfaction**: New constraints don't break existing data
- **Inheritance consistency**: Class hierarchies remain valid

#### Repository checks

Ensure external Git repositories stay synchronized:

- **Branch synchronization**: Database and Git branches align
- **Merge compatibility**: No Git conflicts prevent merging
- **File validation**: Generated files are syntactically correct
- **Commit consistency**: Changes are properly tracked

#### Custom checks

User-defined validations that enforce business rules:

- **Operational constraints**: "At least one router per site must be active"
- **Compliance requirements**: "All devices must have security classifications"
- **Naming conventions**: "Hostnames must follow the pattern: `{site}-{role}{number}`"
- **Capacity limits**: "No rack can exceed 80% power utilization"

#### Artifact checks

Validate that generated configurations remain valid:

- **Syntax validation**: Configurations parse correctly
- **Semantic checks**: Settings make logical sense
- **Diff analysis**: Changes are expected and safe
- **Rollback planning**: Changes can be reversed if needed

### Conflict detection and resolution

Conflicts arise when the same data changes in both the source and destination branches. Infrahub's conflict detection goes beyond simple text comparison to understand the semantic nature of changes.

#### Types of conflicts

**Attribute conflicts**: The same field modified differently in each branch

- Example: Device status changed to "maintenance" in one branch, "decommissioned" in another

**Relationship conflicts**: Competing changes to object associations

- Example: Interface moved to different VLANs in each branch

**Schema conflicts**: Incompatible model modifications

- Example: Field made required in one branch, deleted in another

**Constraint violations**: Changes that would break system rules

- Example: Both branches assign the same IP address to different devices

#### Resolution strategies

Infrahub provides multiple approaches to resolve conflicts:

1. **Automatic resolution**: Non-conflicting changes merge automatically
2. **Branch selection**: Choose to keep changes from source or destination
3. **Manual intervention**: Custom resolution for complex scenarios
4. **Rebase and retry**: Update source branch and revalidate

### The review workflow

While automation handles validation, human review ensures changes align with operational goals and standards.

#### Review components

**Change summary**: High-level overview of modifications

- Objects added, updated, or removed
- Relationships changed
- Schema modifications
- Affected systems and services

**Detailed diffs**: Granular examination of changes

- Side-by-side comparisons
- Historical context
- Change attribution

**Impact assessment**: Understanding consequences

- Which devices need reconfiguration
- What automation will trigger
- Who needs to be notified
- When changes should be deployed

**Discussion threads**: Collaborative evaluation

- Inline comments on specific changes
- General discussions about approach
- Change requests and suggestions
- Approval tracking

## Design philosophy

### Safety through validation

Infrastructure changes carry significant risk. A misconfiguration can cause outages, security vulnerabilities, or data loss. Proposed Changes embody a "trust but verify" philosophy:

- **Comprehensive checks**: Multiple validation layers catch different error types
- **Fail-safe defaults**: Changes blocked until all checks pass
- **Explicit approval**: Human review required for merge
- **Audit trail**: Complete record of who changed what and why

### Automation with oversight

While Proposed Changes automate much of the validation process, they maintain human control at critical decision points:

- **Automated validation**: Machines check for technical correctness
- **Human judgment**: People evaluate business impact and risk
- **Assisted resolution**: Tools help resolve conflicts, humans make decisions
- **Gated deployment**: Automation executes, humans authorize

### Transparency and traceability

Every aspect of a Proposed Change is visible and auditable:

- **Change visibility**: See exactly what will change before merge
- **Check results**: Understand why validations pass or fail
- **Decision history**: Track who approved or rejected changes
- **Rollback capability**: Revert changes if issues arise

## Performance considerations

### Scalability factors

Proposed Change performance depends on several variables:

**Branch divergence**: More changes mean longer validation

- Optimization: Keep branches short-lived
- Optimization: Merge frequently to minimize divergence

**Check complexity**: Custom checks can be resource-intensive

- Optimization: Write efficient check queries
- Optimization: Cache intermediate results

**Data volume**: Large datasets increase processing time

- Optimization: Use targeted queries in checks
- Optimization: Parallelize independent validations

**Repository size**: Git operations scale with repository size

- Optimization: Keep repositories focused
- Optimization: Use shallow clones where possible

### Optimization strategies

To ensure Proposed Changes remain performant:

1. **Incremental validation**: Re-run only affected checks on updates
2. **Parallel execution**: Run independent checks simultaneously
3. **Result caching**: Reuse validation results when possible
4. **Smart scheduling**: Prioritize critical checks
5. **Resource limits**: Prevent runaway validations

## Advanced concepts

### Check dependencies

Checks can depend on each other, creating validation workflows:

```python
# Example: Check dependency chain
class NetworkValidation:
    dependencies = ["schema_check", "ip_allocation_check"]
    
    async def validate(self):
        # Only runs after dependencies pass
        return await check_network_connectivity()
```

### Custom validators

Extend Proposed Changes with domain-specific validation:

```python
# Example: Custom business logic validator
class SiteRedundancyValidator:
    """Ensure each site has redundant uplinks"""
    
    async def validate(self, diff_data):
        for site in diff_data.affected_sites:
            uplinks = await get_site_uplinks(site)
            if len(uplinks) < 2:
                raise ValidationError(f"Site {'{site}'} needs redundant uplinks")
```

### Merge strategies

Different approaches for integrating changes:

- **Fast-forward**: Direct application when no conflicts exist
- **Squash**: Compress all changes into a single commit
- **Preserve history**: Maintain full change timeline
- **Cherry-pick**: Selective change application
