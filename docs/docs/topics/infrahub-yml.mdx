# Understanding the `.infrahub.yml` configuration file

The `.infrahub.yml` file serves as the central manifest that defines how Infrahub integrates with external Git repositories. This topic explains the role of this configuration file, the design philosophy behind its structure, and how it enables the seamless integration of infrastructure code with infrastructure data.

## Why `.infrahub.yml` exists

Infrastructure automation requires both structured data (device inventories, network topologies) and executable code (templates, validation scripts, generators). The `.infrahub.yml` file solves the fundamental challenge of bridging these two worlds by:

- **Declaring intent**: Explicitly stating what resources from a Git repository should be imported into Infrahub
- **Enabling selective integration**: Allowing fine-grained control over which files and resources are processed
- **Providing metadata**: Supplying the necessary context for Infrahub to properly interpret and use repository contents
- **Supporting evolution**: Allowing different branches to have different integration requirements

## Design philosophy and structure

The `.infrahub.yml` file follows a declarative approach where you specify *what* should happen rather than *how* it should happen. This design choice reflects several key principles:

### Explicit over implicit

Rather than scanning the entire repository and making assumptions about file purposes, the configuration file requires explicit declaration of all resources. This approach:

- Prevents unexpected imports of unintended files
- Makes the integration surface clear and auditable  
- Allows for different file organizations across repositories
- Enables precise control over resource loading order

### Resource categorization

The configuration organizes resources into distinct categories based on their purpose and processing requirements:

- **Executable code**: Python transformations, generators, and checks
- **Templates**: Jinja2 templates for configuration generation
- **Data definitions**: Schemas and object files
- **Query definitions**: GraphQL queries for data retrieval
- **UI components**: Menu definitions for custom interfaces

Each category has its own processing pipeline and validation requirements, reflecting the different ways Infrahub handles these resource types.

### Metadata richness

Beyond basic file paths, the configuration captures essential metadata about how resources should be used:

- **Dependencies**: Linking transformations to their required GraphQL queries
- **Targeting**: Specifying which infrastructure groups a resource applies to
- **Parameters**: Defining the inputs required for executable resources
- **Naming**: Providing human-readable identifiers for UI and API access

## Resource types and their integration patterns

### Schemas: infrastructure data modeling

Schemas define the structure of your infrastructure data model. When listed in `.infrahub.yml`, they:

- Extend Infrahub's built-in data types with domain-specific models
- Enable validation and relationships specific to your infrastructure
- Support schema evolution through versioning and migration

The schema loading order matters because schemas can depend on previously loaded types.

### GraphQL queries: Data access patterns

GraphQL queries encapsulate specific data access patterns that your automation code needs. By declaring them in `.infrahub.yml`:

- Queries become reusable across multiple transformations and generators
- Query performance can be optimized by Infrahub's query planner
- Changes to queries are version-controlled alongside the code that uses them

### Transformations: data processing pipelines

Transformations convert data between different formats or structures. The configuration distinguishes between two transformation types:

**Jinja2 transformations** provide template-based processing:

- Link to specific GraphQL queries that provide template data
- Generate text-based outputs like configuration files
- Support complex template inheritance and inclusion patterns

**Python transformations** enable programmatic data processing:

- Implement complex business logic that templates cannot express
- Process structured data with full programmatic control
- Integrate with external systems and APIs

### Generators: infrastructure provisioning

Generators create new infrastructure objects based on templates or algorithms:

- Target specific infrastructure groups for object creation
- Use GraphQL queries to understand the current state
- Apply business rules to determine what should be provisioned

### Artifact definitions: output specification

Artifact definitions specify how to package and deliver generated content:

- Define the content type and format of outputs
- Link transformations to specific target groups
- Specify parameters for customizing artifact generation

### Object files: Bulk data loading {#objects}

Object files contain infrastructure data to be loaded into Infrahub:

- Support JSON and YAML formats for structured data
- Enable bulk loading of initial infrastructure inventories
- Maintain referential integrity through controlled loading order

### Menus: interface customization {#menus}

Menu definitions customize the Infrahub user interface:

- Add navigation elements specific to your infrastructure
- Organize views and actions by operational workflows
- Provide context-aware access to relevant functionality

## Loading behavior and dependency management

The `.infrahub.yml` file controls not just *what* gets loaded, but *how* and *when*:

### Processing order

Infrahub processes configuration sections in a specific order to handle dependencies:

1. **Schemas**: Loaded first to establish the data model
2. **GraphQL queries**: Loaded before resources that depend on them
3. **Objects**: Loaded to populate initial data
4. **Python files**: Check definitions, Python transformations, and generators are loaded together
5. **Jinja2 transformations**: Loaded after their required queries are available
6. **Artifact definitions**: Loaded last to reference existing transformations

### File vs. directory handling

When you specify a directory in any resource list:

- Infrahub processes all relevant files within that directory
- Files are processed in alphabetical order
- Subdirectories are processed recursively

This behavior enables organizing complex repositories while maintaining predictable loading order.

### Dependency resolution

The configuration enables Infrahub to resolve dependencies between resources:

- Transformations reference their required GraphQL queries by name
- Artifact definitions reference transformations and target groups
- Generators specify their data dependencies through query requirements

## Version control and branch behavior

The `.infrahub.yml` file itself is version-controlled, enabling sophisticated integration patterns:

### Branch-specific configuration

Different Git branches can have different `.infrahub.yml` files:

- Development branches can include experimental resources
- Production branches can exclude debug or testing resources
- Feature branches can temporarily modify resource definitions

### Evolution and migration

As your infrastructure automation evolves, the configuration file supports:

- Adding new resource types without affecting existing ones
- Deprecating old resources by removing them from the configuration
- Refactoring resource organization while maintaining functionality

## Integration with the broader Infrahub workflow

The `.infrahub.yml` file connects Git repository contents to Infrahub's core workflows:

### Proposed changes

When you modify resources in Git and create a Proposed Change:

- Infrahub compares the new `.infrahub.yml` with the existing version
- Added, modified, or removed resources are processed accordingly
- Dependencies are validated before allowing the change to proceed

### Automation pipelines

The resources defined in `.infrahub.yml` integrate with Infrahub's automation:

- Checks run automatically when data changes
- Generators respond to infrastructure modifications
- Artifacts are regenerated when their dependencies change

### Error handling and validation

The configuration enables robust error handling:

- Missing files or invalid configurations are caught during import
- Dependency issues are identified before deployment
- Resource conflicts are detected and reported clearly

## Best practices and design patterns

Effective `.infrahub.yml` design follows several patterns:

### Logical organization

Group related resources together and use consistent naming:

- Organize files in directories that reflect their purpose
- Use descriptive names that indicate resource function
- Maintain parallel structure across similar repositories

### Dependency management

Minimize and clearly express dependencies:

- Keep transformations focused on specific data processing tasks
- Design queries to serve multiple consumers when possible
- Avoid circular dependencies between resources

### Testing and validation

Structure resources to support testing:

- Use parameterized resources to enable unit testing
- Separate business logic from data access patterns
- Design generators and transformations for deterministic behavior

## Future evolution and extensibility

The `.infrahub.yml` format is designed to evolve with Infrahub's capabilities:

- New resource types can be added without breaking existing configurations
- Additional metadata fields can be introduced with backward compatibility
- Processing behavior can be enhanced while maintaining existing semantics
