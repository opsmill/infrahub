Allocate addresses and prefixes from a Resource Manager pool when a Generator, a provisioning pipeline or a CI/CD job creates the devices and interfaces that need them, such as those of a new data center or a customer service. Add IPAM prefixes to the pool as its resources. For each request, Infrahub creates the next available address or prefix in those prefixes, and returns the existing one when a request repeats an identifier. To record and query IP data that already exists, a pool is not needed.

## How a pool uses your prefixes

A `CoreIPAddressPool` or a `CoreIPPrefixPool` takes IPAM prefixes as its `resources`, and allocates in one namespace. The `resources` relationship is the connection point between IPAM and the Resource Manager:

- When a pool allocates an address or a prefix on a branch, it reserves the value on every branch at that moment. A request to the same pool from another branch receives a different value, so two branches that allocate from one pool do not hold the same value when they are merged. See [Branch-agnostic allocation](../resource-manager/overview.mdx#branch-agnostic-allocation).
- When you pass the same `identifier` on repeated allocation requests, Infrahub returns the existing allocation instead of creating a new one, on any branch that can read that allocation. A provisioning script can then run more than once without allocating a second address or subnet for the same object.
- Infrahub handles one allocation request at a time for each pool, across every Infrahub worker, so two concurrent requests to the same pool never receive the same resource.
- When a pool has several prefixes as resources, it allocates from the prefix with the highest `allocation_weight` first. The attribute comes from the `CoreWeightedPoolResource` generic. The Marketplace `IpamPrefix` does not inherit from it, so add it to your prefix node to use weights. See [Weighted allocation](../resource-manager/weighted-allocation.mdx).

In the following example, a loopback pool allocates from `10.0.0.0/24`. A request with a new identifier receives the next available address, and a request that repeats an identifier receives the address already allocated to it:

## Create a pool

Give the namespace by its HFID, which holds its name: `{hfid: ["default"]}` in GraphQL, `["default"]` in the Python SDK. Give each prefix in `resources` by its ID: the relationship accepts a prefix of any kind that inherits from `BuiltinIPPrefix`, and that generic has no HFID.

  <TabItem value="graphql" label="GraphQL" default>

```graphql
mutation {
  CoreIPAddressPoolCreate(data: {
    name: {value: "Management IP Pool"},
    default_address_type: {value: "IpamIPAddress"},
    default_prefix_length: {value: 24},
    resources: [{id: "<prefix-id>"}],
    ip_namespace: {hfid: ["default"]}
  }) {
    ok
    object {
      id
    }
  }
}
```

  <TabItem value="sdk" label="Python SDK">

```python
resource = await client.get(
    kind="IpamPrefix",
    prefix__value="10.0.0.0/24",
    ip_namespace__name__value="default",
)

pool = await client.create(
    kind="CoreIPAddressPool",
    name="Management IP Pool",
    default_address_type="IpamIPAddress",
    default_prefix_length=24,
    resources=[resource],
    ip_namespace=["default"],
)
await pool.save()
```

## Allocate from Generators

A Generator has the same Python SDK client available as any other script, so allocating from a pool inside a Generator is an ordinary SDK call:

```python
loopback_pool = await client.get(kind="CoreIPAddressPool", name__value="Loopback pool")
interconnection_pool = await client.get(kind="CoreIPPrefixPool", name__value="Interconnection pool")

device_loopback = await client.allocate_next_ip_address(
    resource_pool=loopback_pool,
    identifier=device_name,
    data={"interface": interface.id},
    branch=branch,
)

interconnect_subnet = await client.allocate_next_ip_prefix(
    resource_pool=interconnection_pool,
    identifier=network.identifier,
    branch=branch,
)
```

`allocate_next_ip_address` and `allocate_next_ip_prefix` take the same `resource_pool` and `identifier` arguments as the underlying `InfrahubIPAddressPoolGetResource` and `InfrahubIPPrefixPoolGetResource` mutations. Pass a stable `identifier`, such as the device name, so that a Generator receives the same address each time it runs again. The [infrastructure-edge topology model](https://github.com/opsmill/infrahub/blob/stable/models/infrastructure_edge.py) is a worked example that allocates loopback and management addresses, and interconnection subnets, this way.

## Return an address to the pool

An address you allocated from a pool stays in use as long as it exists on any branch. To return it to the pool, delete it. If a branch was created before you deleted the address, that branch still has it, so the address stays in use until you rebase or delete the branch.

Deleting the device or interface that uses an address does not delete the address, unless the relationship between them has `on_delete: cascade` or is of kind `Component`. Delete the address itself.

After the address is deleted, Infrahub allocates the next available address to a request with the same identifier, as it does for a new identifier. See [Releasing an allocated resource](../resource-manager/overview.mdx#releasing-an-allocated-resource) for the full rules.

## Advanced: next-available GraphQL queries

`InfrahubIPAddressGetNextAvailable` and `InfrahubIPPrefixGetNextAvailable` are read-only GraphQL queries that return the next available address or subnet in a given prefix. They take the ID of the prefix in `prefix_id`, and an optional `prefix_length`:

```graphql
query {
  InfrahubIPPrefixGetNextAvailable(prefix_id: "<prefix-id>", prefix_length: 24) {
    prefix
  }
}
```

Unlike a pool allocation, they create no record, and they do not provide the pool's guarantee across branches: two callers on different branches can receive the same next available value and both try to create it.

Use a pool for production workflows. Use these queries only to look up a value without storing it. To list all the available blocks of a prefix instead of the next one, see [Query IPAM data](./query-ipam-data.mdx#list-the-available-space-in-a-prefix).
