# Hierarchy

Infrahub supports organizing nodes of similar types into a tree structure. Hierarchy mode enables ancestor and descendant queries, and allows filtering related data across multiple levels of the tree without direct relationships between every node.

## Enabling hierarchy

A hierarchy must be defined around a specific `Generic` to ensure that all nodes that are part of a given hierarchy share some attributes.
In the schema the attribute `hierarchical: true` on a `Generic` activates the hierarchical mode.

> All nodes inheriting from this main `Generic` will automatically have the hierarchical mode enabled as well.
> Each node can only inherit from one `Generic` with hierarchical mode at the same time.

:::success Examples

- [Groups](../groups/overview) can be organized in a hierarchy by default which makes it possible to query the members of all sub-groups at once.
- Assuming we have defined a `Person` object connected to a `City` object, which itself is part of a hierarchy of `Location` (`Region` > `Country` > `City`), it will be possible to query all `Person` per `Country` or per `Region` natively without having a direct relationship between `Person` and `Country`.

:::

All nodes with hierarchical support will automatically have 2 new relationships:

- `parent` of cardinality one
- `children` of cardinality many

## Specify the structure of the hierarchy

By default, any node inheriting from the main `Generic` can be a parent or a children, which might not be always desirable. It's possible to limit which type of models are valid `parent` or `children` in the schema with the attributes `parent` & `children` at the node level.

In the example below, we are defining a hierarchy of `Location` with `Region`, `Country` and `City`.
Only `Country` can be defined as children of a `Region` and only `City` can be defined as children of a `Country`

```yaml showLineNumbers
version: '1.0'
generics:
  - name: Generic
    namespace: Location
    hierarchical: true
    attributes:
      - name: name
        kind: Text
nodes:
  - name: Region
    namespace: Location
    inherit_from: ["LocationGeneric"]
    parent: ""
    children: "LocationCountry"
  - name: Country
    namespace: Location
    inherit_from: ["LocationGeneric"]
    parent: "LocationRegion"
    children: "LocationCity"
  - name: City
    namespace: Location
    inherit_from: ["LocationGeneric"]
    parent: "LocationCountry"
    children: ""
```

When `parent` or `children` is not set, any node inheriting from the main `Generic` is allowed on that side. An empty string allows no node: in the example, a `Region` has no parent and a `City` has no children.

## Change the hierarchy of an existing schema

You can add a hierarchy to node kinds that already have objects, for example by setting `hierarchical: true` on a `Generic` they already inherit from. Infrahub checks the change against the stored objects and refuses it when:

- A node kind defines its own `parent` or `children` relationship, because the hierarchy defines these two relationships itself.
- A node kind, or the `Generic` that becomes hierarchical, defines its own attribute or relationship named `ancestors` or `descendants`, because the hierarchy reserves these names.

When you change `parent` or `children` on a node of a hierarchy, Infrahub refuses the change if a stored object has a parent or a child of a kind that the new value does not allow.

A node kind cannot leave a hierarchy. For this reason, Infrahub refuses `hierarchical: false` on a `Generic` while node kinds still use its hierarchy, and the error lists these node kinds. To stop using the hierarchy, remove these node kinds in the same schema load or in an earlier one.

Infrahub checks these rules when it loads a schema. A branch merge does not check them again: when the default branch sets `hierarchical: false` on a `Generic` that no node kind uses, and a branch adds a node kind to that hierarchy, the merge succeeds and the node kind keeps a hierarchy that its `Generic` no longer has.

## Query data around a hierarchy in GraphQL

In GraphQL queries, all nodes with hierarchical support will have 2 additional fields:

- `ancestors` to access all ancestors of a given nodes (parent of parents)
- `descendants` to access all descendants of a given nodes (children of children)

:::info

`ancestors` and `descendants` are separated from `parent` and `children` to clearly indicate that we need to query the hierarchy and not the directly connected nodes.

:::

For all relationships of cardinality many, it's possible to query all the objects associated with `descendants` nodes as well by providing the `include_descendants` flag.

As an example, the GraphQL query below will query the members of all [groups](../groups/overview) that are defined as children of `Group1`.
Assuming that `Group1` has 2 sub-groups defined `Group A` and `Group B` (AKA children), the query will return the members of `Group1`, `Group A` and `Group B` together.

```graphql showLineNumbers
query {
    CoreStandardGroup(name__value: "Group1") {
        edges {
            node {
                id
                display_label
                members(include_descendants: true) {
                    count
                    edges {
                        node {
                            id
                            display_label
                        }
                    }
                }
            }
        }
    }
}
```
