# Remove schema elements

To remove a node, a generic, an attribute or a relationship, keep it in your schema file and add `state: absent` to it. Infrahub then removes the element and deletes its data on the branch where you load the change.

:::danger

When you remove an element, Infrahub deletes the data it contains:

- When you remove a node, Infrahub deletes all the objects of the node.
- When you remove an attribute or a relationship, Infrahub deletes its values on every object of the node.

To view the deleted data after you merge the branch, see [View the data of a removed element](#view-the-data-of-a-removed-element).

:::

:::warning

Nodes, attributes and relationships can be referenced in GraphQL queries, Transformations, Generators and checks, so these fail after a remove. Change them at the same time as you remove the element. To detect this kind of failure before a schema change reaches production, set up integration tests that run your automation against the new schema. See [Make schema changes in a controlled way](./operations#make-schema-changes-in-a-controlled-way).

:::

## Remove an element

1. **Mark the element `state: absent`.** Add the property to the element in your schema file:

   ```yaml {3}
     - name: Rack
       namespace: Infra
       state: absent
       attributes:
         - name: name
           kind: Text
   ```

2. **Check the change.** Run `infrahubctl schema check <file> --branch <branch>`. The element is listed under `removed`. If it is not, `state: absent` is missing or the element is not loaded on this branch.
3. **Load the change on a branch**, and merge it through a Proposed Change. The **Schema** tab of the Proposed Change lists the removal.
4. **Delete the element from the file once the removal is merged.** This step is optional. Infrahub ignores an element marked `state: absent` that is not loaded on the branch.

## Why deleting an element from the file does not remove it

Loading a schema file adds the elements in the file to the loaded schema and updates the ones that already exist. It does not replace the loaded schema, so an element that is loaded but is not in the file is left unchanged. If an element missing from the file meant "remove", loading one file would remove every element defined in the others, together with their objects. See [How a load works](./operations#how-a-load-works).

So you state each removal on the element itself, with `state: absent`. `infrahubctl schema check` lists every element you remove under `removed`, so you can confirm the removal before Infrahub deletes anything.

## Remove an attribute or a relationship

Properties of the same node and of other nodes can name an attribute or a relationship. When you remove the element, Infrahub removes it from some of these properties, and refuses the load when another property still names it.

### Check what refers to the element

- **`human_friendly_id`, `uniqueness_constraints` and `order_by` of the same node.**
  - If your file does not set the property, Infrahub removes the element from the loaded value of the property. When nothing is left, the property is empty: a node whose `human_friendly_id` was only the removed attribute has no `human_friendly_id`.
  - If your file sets the property and still names the element, Infrahub refuses the load. The message names the property:

    ```text
    Unable to load the schema:
      InfraRack.human_friendly_id: name__value is invalid on schema InfraRack
    ```

    Remove the element from the property in your file. If the removed attribute was the whole `human_friendly_id`, give the node a new `human_friendly_id`, or clear it with an empty list (`[]`). See [Clear a property](./change-nodes-and-attributes#clear-a-property).
- **`display_label` of the same node.** Infrahub does not remove the element from `display_label`, even when your file does not set it, so it refuses the load while `display_label` names the element:

  ```text
  Unable to load the schema:
    InfraRack.display_label: name__value is invalid on schema InfraRack
  ```

  Set `display_label` in your file, without the removed element, such as `"{{ code__value }}"`.
- **Properties of other nodes, through a relationship.** In the `human_friendly_id`, `order_by` and `display_label` of a node, a path such as `rack__name__value` names an attribute of the node's peer. In this example, `InfraDevice` has the path `rack__name__value`, which names the attribute `name` of its peer `InfraRack`. If you remove `name` from `InfraRack`, Infrahub refuses the load, even when your file does not contain `InfraDevice`:

  ```text
  Unable to load the schema:
    InfraDevice.human_friendly_id: name is not a valid attribute of InfraRack
  ```

  Change the property of `InfraDevice` in the same load as the removal.

The same properties can name a relationship, either alone, such as `rack` in `uniqueness_constraints`, or followed by an attribute of its peer, such as `rack__name__value`. When you remove a relationship, Infrahub removes its name from `human_friendly_id`, `uniqueness_constraints` and `order_by` when your file does not set them. It refuses the load when one of these properties in your file, or a `display_label`, still names it.

### Number pools and branch-agnostic fields

- **For a `NumberPool` attribute**, Infrahub also removes the number pool that it created for the attribute. See [Number pools](./number-pool).
- **For a branch-agnostic attribute or relationship**, the value is stored once and shared by every branch. Infrahub keeps the value while any branch still declares the field in its schema, and removes it when no branch does. Infrahub does not delete the objects of the node. See [Branch-agnostic data](../branches/branch-agnostic-data.mdx).

## Remove an attribute or a relationship from a generic

When you remove an attribute or a relationship from a generic, Infrahub removes it from every node that inherits it, together with its values. A node that overrides it keeps its own attribute or relationship and its values. See [Change generics](./change-generics).

Check each node that inherits the element for properties that name it, as in [Check what refers to the element](#check-what-refers-to-the-element).

## Remove a node that other elements refer to

Infrahub cannot resolve a relationship whose `peer` is a kind that no longer exists. So it refuses to remove a node while a relationship on another node or generic has the node as its `peer`:

```text
Unable to load the schema:
  InfraDevice: Relationship 'rack' is referring an invalid peer 'InfraRack'
```

Remove the node and the references to it in your schema file:

- Mark each relationship that has the node as its `peer` with `state: absent`, or change its `peer`. If a property of the other node names the relationship, see [Check what refers to the element](#check-what-refers-to-the-element).
- Mark the node with `state: absent`.

Then load the file or files.

## Remove a generic

Infrahub refuses to remove a generic in two cases:

- **A relationship has the generic as its `peer`.** The error is the same as for a node. See [Remove a node that other elements refer to](#remove-a-node-that-other-elements-refer-to).
- **A node inherits from the generic.** The generic is in the `inherit_from` of the node. You cannot take a generic out of the `inherit_from` of a node that is loaded, so you cannot remove the generic while that node exists. To remove the generic, remove every node that inherits from it. See [Remove a node that other elements refer to](#remove-a-node-that-other-elements-refer-to) and [Remove a generic from a node](./change-nodes-and-attributes#remove-a-generic-from-a-node).

## Remove a dropdown choice

:::warning

You cannot remove a dropdown choice through a schema file. Infrahub keeps a choice that is missing from the file, and ignores `state: absent` on a choice with this warning:

:::

When you load a file, Infrahub merges its list of choices by name, as it merges the list of attributes of a node, so a choice that is missing from the file is kept. A choice has no `state` property.

Remove the choice from the running schema first, on the branch where you make the change:

- **Attribute defined on a node**: in the web interface, open the form of an object of that node, open the list of the dropdown field, select the delete button next to the choice, and confirm. You can also call the `SchemaDropdownRemove` GraphQL mutation with the node's kind.
- **Attribute defined on a generic**: the web interface refuses the removal. Call the `SchemaDropdownRemove` GraphQL mutation with the generic's kind:

  ```graphql
  mutation {
    SchemaDropdownRemove(data: { kind: "InfraGenericDevice", attribute: "status", dropdown: "provisioning" }) {
      ok
    }
  }
  ```

  The choice is removed from every node that inherits the attribute.

Then delete the choice from your schema file. Otherwise the next load adds it back.

Infrahub refuses the removal in two cases:

- **One or more objects still use the choice.** Those objects would have a value that is no longer a choice. Change them first.
- **It is the last choice of the attribute.** A `Dropdown` attribute needs at least one choice.

Removing a choice through a schema file is requested in [issue #10938](https://github.com/opsmill/infrahub/issues/10938).

## View the data of a removed element

Infrahub keeps the history of the schema and of the data. It records a removal at the time of the load, and keeps the earlier versions of the schema and data. To view a removed attribute and the values it contained, query the data at a time before the removal, in the web interface or in a GraphQL query. See [Query data at a specific time](../immutable-history/query-historical-data#query-data-at-a-specific-time).
