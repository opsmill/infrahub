Schemas are defined in YAML format and follow a strict structure. Splitting a schema into multiple smaller files is recommended to keep it maintainable as it grows.

:::note

Enable [schema validation](../reference/schema-validation) in your editor to catch errors while writing schema files.

:::

Once a schema file is ready, check it against a running Infrahub instance to see which changes Infrahub would apply and whether any existing object fails a new rule, then load it to apply the changes. Load schema changes on a branch, so you can review them before you merge them into the default branch. When the instance already holds objects, read [Schema operations](./operations) first: it explains how a load treats elements that are missing from your files, and which changes Infrahub refuses.

## Schema file

Most schema files use some combination of these top-level keys:

```yaml
---
version: '1.0'
generics:
    - <new generics are defined here>
nodes:
    - <new nodes are defined here>
extensions:
  nodes:
    - <node extensions are defined here>
```

For a full reference of all available properties, see [Nodes & attributes](./nodes-and-attributes), [Relationships](./relationships), and [Generics & inheritance](./generics-and-inheritance).

By convention, store schema files in a `schemas` folder at the root of your repository.

## Format schema files

`infrahubctl schema format` rewrites schema files with a consistent key order, so hand-edited files read the same way and produce small diffs in version control. It operates on the files on disk and does not contact a running instance.

```shell
infrahubctl schema format <path to schema file or a directory>
```

By default the command only reorders the keys within each node, generic, attribute, relationship, and dropdown choice. Comments, quoting, and inline sequences are preserved, and nodes in Infrahub-reserved namespaces are left unchanged.

Preview the result before writing it, or verify that files are already formatted:

```shell
infrahubctl schema format schemas/ --diff   # preview the changes, write nothing
infrahubctl schema format schemas/ --check  # exit non-zero if any file would change
```

`--check` lets you run the formatter in a pre-commit hook or CI step.

Three opt-in flags apply further changes and can be combined:

- `--strip-defaults` removes keys whose value matches the schema default.
- `--sort-by-order-weight` orders attributes and relationships by their [`order_weight`](./order-weight).
- `--backfill-order-weight` sets `order_weight` on entries that do not define one.

For the full list of options, see the [`infrahubctl schema` reference]($(base_url)infrahubctl/infrahubctl-schema).

## Check a schema

During development, you can validate a schema file and preview the changes it would apply:

```shell
infrahubctl schema check <path to schema file or a directory> [--branch <branch_name>]
```

The command first validates the files on your machine, then sends them to Infrahub, which compares them with the schema running on the branch. Infrahub writes nothing to the database. The output lists the changes the load would apply, grouped under `added`, `changed` and `removed`, and every existing object that fails a new rule, such as an object with no value for an attribute you made mandatory.

The check needs a running instance, and its result applies to the data on that instance and branch. It does not show what the migrations do to stored values, and it does not warn you about a change that is valid but not what you meant. A rename without the element's `id`, for example, shows as an element under `added`, and the load creates a second element. See [Rename schema elements](./renaming-schema-element).

## Load a schema file

Schema files can be loaded into Infrahub with the `infrahubctl` command or directly via the Git integration.

:::info

Use `infrahubctl` for development and testing. The git integration option is better suited for production.

:::

The `infrahubctl` command can be used to load individual schema files or multiple files as part of a directory.

```shell
infrahubctl schema load <path to schema file or a directory> <path to schema file or a directory> [--branch <branch_name>]
```

:::info

The `infrahubctl schema load` command can be used to both upload a new schema and update an existing one.

### How long a load takes

On an instance that holds many objects, a load can run for several minutes, because Infrahub checks and migrates every object the change affects. `infrahubctl` shows no progress while it runs.

Infrahub runs one schema load at a time, across all branches. While a load runs, other schema loads, branch merges and branch rebases wait until it finishes. `infrahubctl` waits at least 120 seconds for a response, or longer if `INFRAHUB_TIMEOUT` is set higher, and a proxy in front of Infrahub can return HTTP 504 sooner. In both cases the load can still be running on the server. Running the command again does not restart the load: the new load waits behind the first one, and merges and rebases wait behind both. See [A load that seems to hang](./troubleshooting#a-load-that-seems-to-hang).

## Inspect the loaded schema

Once a schema is loaded, list the kinds available in your instance and inspect any one of them from the command line:

```shell
infrahubctl schema list [--filter <name>] [--branch <branch_name>]
infrahubctl schema show <kind> [--branch <branch_name>]
```

`schema show` prints the attributes and relationships of a kind, which is useful when querying or creating objects with [`infrahubctl`](../objects/manage-from-cli).

### Compare the loaded schema with your files

A load reports success when Infrahub accepts the change, which does not tell you that the loaded schema now matches your files. An element you deleted from a file, for example, is still loaded. To compare them, export the loaded schema as files:

```shell
infrahubctl schema export --directory <directory> [--branch <branch_name>] [--namespaces <namespace>]
```

Infrahub writes one YAML file per namespace, with the nodes and generics you defined. Namespaces that Infrahub uses for its own nodes, such as `Core` and `Builtin`, are left out. Compare the export with your schema files using a diff tool: an element that is in the export but not in your files is still loaded, and a property with a different value was not changed as you expected.

The export leaves out the `id` and `state` of each element, so you cannot load an exported file to rename an element. See [Rename schema elements](./renaming-schema-element).
