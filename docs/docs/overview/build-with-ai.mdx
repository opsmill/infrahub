Skills give an AI coding assistant Infrahub-specific knowledge — schema conventions, `.infrahub.yml` registration, GraphQL patterns — so it produces working Infrahub resources from a plain-language description instead of a generic guess. Skills operate on your local files. The [Infrahub MCP server](https://docs.infrahub.app/mcp) is the live connection: it lets an assistant query and change data on a running Infrahub instance directly, through the same session-branch and Proposed Change workflow a person uses.

AI assists the person building with Infrahub — it writes schema, objects, checks, generators, transforms, and menus, and answers questions about your live data. There's no in-product chatbot; the assistant is the coding tool you already use (Claude Code, Cursor, GitHub Copilot, and others), extended with Infrahub-specific knowledge.

This is also not about modeling AI infrastructure — GPU clusters, training pipelines, inference services — as data *in* Infrahub. That's a separate, valid use of the platform. This page is about using AI *to build with* Infrahub.

## Why it's safe

Every write an AI agent makes through the MCP server lands on an automatically created session branch (`mcp/session-YYYYMMDD-<hex>`), never on the default branch directly. `mutate_graphql` rejects branch- and schema-management mutations outright, regardless of how the mutation is written, and `query_graphql` rejects any mutation at all — it's read-only. A change reaches `main` only through a Proposed Change, opened by the `propose_changes` tool and reviewed and merged by a person, the same path as a change made through the web interface or the SDK. No MCP tool merges a branch.

This is enforced in the server's code, not left to convention — see the [MCP methods reference](https://docs.infrahub.app/mcp/references/methods) if you want to verify it yourself, or read [Branches](../branches/overview) and [Proposed Changes](../proposed-changes/overview) for how the workflow looks on the receiving end.

## Install

Install the skills into your project:

```bash
npx skills add opsmill/infrahub-skills
```

This detects the AI tools already configured in your environment (Claude Code, GitHub Copilot, Cursor, and others) and installs the skills in the right format for each. Skills operate on local files, so this step alone covers schema, objects, checks, generators, transforms, and menus.

Some pages — [Analyze your data](../schema/analyze-your-data), and validating a generated schema or Generator against real data — need the MCP server connected to a running instance:

```bash
pip install infrahub-mcp
```

```bash
export INFRAHUB_ADDRESS=http://localhost:8000
export INFRAHUB_API_TOKEN=<your-token>
infrahub-mcp
```

See the [MCP server docs](https://docs.infrahub.app/mcp) for Docker deployment, remote transports, and client-specific setup (Claude Desktop, VS Code, Cursor).

## Two ways of working

Depending on how well-scoped the change is, work with the skills in one of two modes.

### Direct — describe, then go

For targeted changes, describe what you want and the assistant handles it with the right skill:

- *"Add a `contract_start_date` attribute to `InfraCircuit`"* — the assistant uses `infrahub-managing-schemas`, applies naming conventions, and updates the schema file.
- *"Create a check that validates every device has a primary IP"* — the assistant uses `infrahub-managing-checks`, writes the Python class and GraphQL query, and registers it in `.infrahub.yml`.
- *"Import this `inventory.csv` into Infrahub"* — the assistant uses `infrahub-importing-data`, checks the columns against your live schema, and loads the result on a fresh branch.

This is the fastest path for well-scoped work — adding an attribute, writing a check, populating objects. Most people start here and move to spec-driven mode once a change grows beyond one prompt.

### Spec-driven — plan, then build

For a bigger job — designing a new schema domain with relationships, building a chain of generators, standing up a new domain end to end — plan first with a spec-driven development (SDD) framework, then let the assistant execute against the plan: specify the feature, generate a plan validated against Infrahub conventions, break it into tasks, then implement each task with the right skill. The [infrahub-template](https://github.com/opsmill/infrahub-template) repository includes a ready-to-use SDD setup.

| Scenario | Approach |
|---|---|
| Add an attribute to an existing node | Direct |
| Write a validation check | Direct |
| Import a batch of objects from a CSV export | Direct |
| Create a new menu section | Direct |
| Design a new schema node with relationships | Spec-driven |
| Build a cascading Generator chain | Spec-driven |
| Stand up a complete new domain (schema + objects + checks + generators) | Spec-driven |
| Refactor relationships across multiple schema files | Spec-driven |

## What you can build

- `infrahub-managing-schemas` — turn a description into schema YAML: nodes, generics, attributes, relationships, hierarchies, validated against your live schema before it's handed back. See [Build your schema](../schema/build-your-schema).
- `infrahub-importing-data` — turn a CSV or TSV export into Infrahub object YAML and load it onto a fresh branch. See [Import data from CSV](../objects/import-from-csv).
- `infrahub-analyzing-data` — ask questions about live infrastructure data in plain language, through the MCP server. See [Analyze your data](../schema/analyze-your-data).
- `infrahub-managing-objects` — describe the objects you want and get YAML with references and load order handled. See [Load data in bulk using YAML file](../objects/load-from-yaml).
- `infrahub-managing-generators` — describe a target topology and get the GraphQL query, the `InfrahubGenerator` class, and the `.infrahub.yml` registration together. See [Build a generator](../generators/build).
- `infrahub-managing-transforms` — describe the output you need and get the query plus a Jinja2 template or Python transform, registered in `.infrahub.yml`. See [Write a Jinja2 Transformation](../transformations/jinja2) or [Write a Python transformation](../transformations/python).
- `infrahub-managing-checks` — describe a rule to enforce and get the query, the `InfrahubCheck` class, and tests, verified locally before a Proposed Change. See [Build a check](../academy/tutorials/build-a-check).
- `infrahub-managing-menus` — describe how you want the left-hand menu organized and get menu YAML. See [Menu customization](../menu/overview).
- `infrahub-auditing-repo` — audit a repository's `.infrahub.yml` and file structure against convention and get a report of what to fix. See [infrahub.yml configuration](../git-integration/infrahub-yml).
- `infrahub-reporting-issues` — figure out which `opsmill/infrahub-*` repository a bug or feature request belongs to, check for duplicates, and draft the issue for your review. See the FAQ's ["How do I get help with Infrahub?"](../faq/faq.mdx#how-do-i-get-help-with-infrahub) entry.

## What to watch for

An assistant can invent an attribute, relationship, or schema element that doesn't exist yet, especially from an ambiguous prompt. Check generated YAML against your actual schema before loading it — most of the skills already run their own validation (`infrahubctl schema check`, local test runs) before handing a file back, but that confirms syntax, not intent.

The [session-branch and Proposed Change guarantee](#why-its-safe) above means a mistake stays contained: nothing an assistant does through the MCP server reaches the default branch without a person reviewing it first.
