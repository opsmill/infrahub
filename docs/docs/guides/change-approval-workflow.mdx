This page covers how to enforce a change approval policy on a running Infrahub instance: configuring roles and permissions for reviewers and requesters, enforcing minimum-approval and auto-revocation rules at the platform level, and protecting the underlying Git repository from direct pushes.

The result is a governance system where direct modifications to the default branch are prevented, requesters and reviewers are separated by role, every change requires explicit approval before merge, and approvals are automatically revoked when the change is modified.

:::info Enterprise Edition
Some elements of this policy require the Enterprise Edition of Infrahub. In the Community Edition, the platform-enforcement mechanisms (minimum approvals, auto-revocation) are not available — you can still implement a process-based approach using roles and permissions.
:::

:::success Change Management Workflow Blog Post
For broader context on how change management works in Infrahub, see [Infrahub's Change Management Workflow Is Built for Infrastructure Data](https://opsmill.com/blog/infrastructure-change-management-workflow/).
:::

## Prerequisites

- An Infrahub instance with administrator access
- Familiarity with [roles and permissions](../topics/permissions-roles.mdx), [branching](../branches/index.mdx), and [proposed changes](../proposed-changes/index.mdx)
- Administrative access to the Git repository used by Infrahub
- User management permissions in your Infrahub instance

## Set up users and groups

This step can be skipped if appropriate users and groups are already configured (via SSO, for instance) — adjust the rest of the page to match your existing structure.

The pattern below uses two groups representing a typical separation:

- A **`<requester-group>`** (for example, a `Support team`) — proposes changes but cannot approve or merge them
- A **`<reviewer-group>`** (for example, a `Network team`) — reviews, approves, and merges proposed changes

Steps:

1. Navigate to **Admin → Users & Permissions**
2. Open the **Groups** tab and create:
   - `<requester-group>` (for example, `Support team`)
   - `<reviewer-group>` (for example, `Network team`)
3. Open the **Accounts** tab and create the user accounts your organization needs, assigning each to the appropriate group

## Configure roles and permissions

Configure platform-level permissions so the requester group can propose changes but cannot edit `main` directly, and the reviewer group can approve and merge.

:::tip
Adjust these roles and permissions to match your organization. For the full permission catalog, see the [Permissions reference](../reference/permissions.mdx).
:::

1. Navigate to **Admin → Users & Permissions**
2. Open the **Object Permissions** tab and create:
    - Namespace `Core`, Name `Proposed Change`, Action `Update`, Decision `Allow in all branches`
    - Namespace `Core`, Name `Proposed Change`, Action `Create`, Decision `Allow in all branches`
    - Namespace `Core`, Name `Change Comment`, Action `*`, Decision `Allow in all branches`
    - Namespace `Core`, Name `Change Thread`, Action `*`, Decision `Allow in all branches`
    - Namespace `Core`, Name `Thread Comment`, Action `*`, Decision `Allow in all branches`
3. Open the **Roles** tab and create:
    - **`Restricted Access`** (only allows edits on non-default branches)
        - Add groups: `<requester-group>` and `<reviewer-group>`
        - Add permissions:
            - `global:edit_default_branch:allow_all`
            - `object:*:*:view:allow_all`
            - `object:*:*:any:allow_other`
            - `object:Core:ChangeComment:any:allow_all`
            - `object:Core:ChangeThread:any:allow_all`
            - `object:Core:ThreadComment:any:allow_all`
            - `object:Core:ProposedChange:create:allow_all`
    - **`Change Reviewer`** (full review, approve, and merge)
        - Add group: `<reviewer-group>`
        - Add permissions:
            - `global:review_proposed_change:allow_all`
            - `object:Core:ProposedChange:update:allow_all`
            - `global:merge_proposed_change:allow_all`

With these permissions in place: nobody can edit the default branch directly, all changes flow through proposed changes, and only the reviewer group can approve and merge.

## Enforce change policy <EnterpriseBadge />

Configure platform policy to require minimum approvals and auto-revoke approvals when changes are modified after approval.

:::important
This change requires a restart of the Infrahub server and depends on your deployment method. See [How to configure Infrahub](./configuration-changes.mdx) for the procedure that matches your deployment.

The settings:

```shell
INFRAHUB_POLICY_REQUIRED_PROPOSED_CHANGE_APPROVALS=<minimum-approvals>
INFRAHUB_POLICY_REVOKE_PROPOSED_CHANGE_APPROVALS=<true|false>
```

For a one-approval policy with auto-revocation:

```shell
INFRAHUB_POLICY_REQUIRED_PROPOSED_CHANGE_APPROVALS=1
INFRAHUB_POLICY_REVOKE_PROPOSED_CHANGE_APPROVALS=true
```

:::

<ReferenceLink title="How to configure Infrahub" url="./configuration-changes" openInNewTab />

After applying these variables, proposed changes follow the configured approval logic.

## Secure the Git repository

Ensure that only the Infrahub service account can push to the default branch of the connected Git repository. Without this, users could bypass the approval process by committing directly.

:::info

- This applies only when using Infrahub's Git integration with a read/write repository.
- Refer to your Git provider's documentation for the exact steps; configurations vary.
- Adjust to match your organization's requirements.

:::

<details>
   <summary><b>Using GitHub</b></summary>

1. Open your repository's **Settings** tab
2. Select **Branches** in the left sidebar
3. Click **Add classic protection rule**, or edit the existing rule for the default branch
4. Configure:
   - Branch name pattern: the default branch name (for example, `main`)
   - Enable **Require pull request reviews before merging**
       - Enable **Require approvals**, set count to `<minimum-approvals>`
       - Enable **Dismiss stale pull request approvals when new commits are pushed**
       - In **Allow specified actors to bypass required pull requests**, add the Infrahub service account
5. Click **Create** / **Save changes**

</details>

After saving the protection rule, direct pushes to the default branch by regular users are rejected by the Git server.

## Verify the workflow

Verify each layer of the policy by running through a representative scenario.

As a member of `<requester-group>`:

1. Try to edit an object on the default branch — direct edits are blocked.
2. Create a new branch and an object on that branch.
3. Open a proposed change for the branch — the proposed change cannot be merged (approval required) and cannot be self-approved.

As a different member of `<requester-group>` (no reviewer permission):

1. Open the proposed change — the **Approve** action is unavailable (no permission).

As a member of `<reviewer-group>`:

1. Open the proposed change, review the diff, and click **Approve**.

Back as the original requester:

1. Modify the proposed change — the prior approval is automatically revoked.

Back as the reviewer:

1. Re-review and re-approve.
2. Click **Merge** — the change merges to the default branch.

After the run-through, the proposed change is marked merged, the new object exists on the default branch, and the change history shows the full approval flow.

## Advanced use cases

### Emergency bypass ("break glass") procedure

In genuine emergencies, you may need to temporarily bypass the change approval workflow to address a critical issue.

:::danger Emergency use only
This procedure bypasses governance controls and can lead to unintended consequences. All emergency changes should be documented and reviewed after the fact.
:::

To bypass:

1. Use the local `admin` account or a designated emergency account with `Super Administrator` privileges
2. Log in with that account
3. Make the necessary changes directly, or through an expedited proposed change

Users with `Super Administrator` permission can:

- Approve their own proposed changes
- Bypass minimum-approval requirements
- Make direct edits to the default branch
