# Import data from CSV

Prompt an AI coding assistant to translate a CSV or TSV export into Infrahub object YAML — the assistant writes the file, creates a branch, validates and loads it; you review the result.

:::info Prerequisite

Requires an AI coding assistant with the [Infrahub Skills](../overview/build-with-ai/setup.mdx) installed. The skill works from local schema files if the MCP server or `infrahubctl` isn't configured, though it's less accurate about your live schema without one of them.

:::

## What it does

`infrahub-importing-data` takes a CSV or TSV export — one file, a folder, or one large denormalized sheet — and checks its columns against your schema before writing anything. It tries these sources in order and uses the first one available:

| Source | Requires | What it sees |
|---|---|---|
| MCP server | The [MCP server](../overview/build-with-ai/setup.mdx) connected to your instance | Live, branch-specific state — including dropdown choices and HFIDs added on a feature branch |
| `infrahubctl schema export` | `infrahubctl` configured against your instance | The live schema, not branch-specific unless you pass `--branch` |
| `/api/schema` REST endpoint | Network access to the instance's API | The same live schema as the CLI export |
| Local `schemas/*.yml` files | Nothing — works with no connection to any instance | Whatever is on disk, which can lag what's actually deployed |

Without MCP or `infrahubctl` configured, the skill still runs the same workflow end to end — it just maps columns from further down this list. The trade-off is the last row: local files can go stale, so a mapping built from them alone is less trustworthy. That gap is exactly what `infrahubctl object validate` (below) exists to close — it checks against your live instance regardless of which source built the mapping, so a stale local schema doesn't silently produce a bad load.

It splits and translates the rows into the same object YAML format documented on [Load data in bulk using YAML file](./load-from-yaml).

From there, the skill runs the rest of the workflow itself. It self-checks the emission against the object-file rules and confirms every relationship reference resolves — before touching a server. Only once that passes does it create a fresh branch, run `infrahubctl object validate` against it to catch schema-resolution errors, and then `infrahubctl object load` — the same command documented on that page — to put the objects on the branch. It hands the branch back to you for review; it never merges it.

If a column doesn't map to anything in your schema, the skill stops and asks rather than guessing.

## Worked example

### 1. Provide the file

```text title="Example prompt"
Import this inventory.csv into Infrahub.
```

### 2. Review the generated object YAML

The assistant maps each column to a schema attribute or relationship and writes one numbered object file per kind, each carrying a provenance comment:

```yaml title="objects/001-devices.yml"
# Generated from inventory.csv
# sha256: 3f2a9c1e...  generated: 2026-08-13T10:04:00Z
---
apiVersion: infrahub.app/v1
kind: Object
spec:
  kind: NetworkDevice
  data:
    - name: sw01-svc01
      site: Stonehenge Visitor Centre
```

### 3. The assistant creates the branch, validates, and loads

```bash
infrahubctl branch create csv-import-20260813-1004
infrahubctl object validate objects/ --branch csv-import-20260813-1004
infrahubctl object load objects/ --branch csv-import-20260813-1004
```

You don't run these yourself — the assistant does, in this order, and only after its own local self-check passes. `infrahubctl object validate` catches schema-resolution errors (a kind that doesn't exist, a reference that doesn't resolve) before anything loads. By default, the branch is named `csv-import-YYYYMMDD-HHMM`.

### 4. Review the diff and open a proposed change

Review the loaded objects in the web interface, then open a Proposed Change to merge the branch into `main`. See [Proposed Changes](../proposed-changes/overview) for the review workflow.

## What to watch for

An unmapped column stops the import instead of guessing at a match. Resolve the mismatch — rename the column, or add the attribute to your schema — and re-run, rather than working around it. Check the branch name before merging; `csv-import-YYYYMMDD-HHMM` is only the assistant's default, not a required format.

Loading isn't transactional across files — if one file in a large batch fails partway through, the branch already has the earlier files applied. Discard the branch and re-run with a fresh name rather than hand-fixing the partial state.
