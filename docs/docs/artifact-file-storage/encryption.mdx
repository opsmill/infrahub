# Encrypt stored files

Infrahub can encrypt the artifacts and file objects it stores, on the local filesystem or in an S3-compatible bucket, and refuse to serve an encrypted file that was modified. Files are encrypted with AES-256-GCM using a key derived from `INFRAHUB_STORAGE_ENCRYPTION_KEY`, or from `INFRAHUB_SECURITY_SECRET_KEY` when no dedicated key is set.

Encryption protects stored files from someone who has access to the storage, or to a copy of it, but not to the API servers' key. It does not protect them from Infrahub users who can read the files through Infrahub, and it does not replace TLS for data in transit.

## Prerequisites

A key of at least 32 random characters, set to the same value on every API server. Generate it with a random generator, for example `openssl rand -hex 32`. Set it in one of two ways:

- `INFRAHUB_STORAGE_ENCRYPTION_KEY`: a key used only for storage encryption. When it is set, `INFRAHUB_SECURITY_SECRET_KEY` plays no part in encryption, so changing the secret does not affect stored files. Infrahub refuses to start when this key is shorter than 32 characters, and it does not fall back to `INFRAHUB_SECURITY_SECRET_KEY`.
- `INFRAHUB_SECURITY_SECRET_KEY`: used when `INFRAHUB_STORAGE_ENCRYPTION_KEY` is not set or is empty. Infrahub refuses to start with a generated secret, with the value from the example deployment files, or with a secret shorter than 32 characters. Changing the secret ends every user session: users have to log in again, while API tokens keep working.

:::warning
The encryption key is never stored: Infrahub derives it from `INFRAHUB_STORAGE_ENCRYPTION_KEY`, or from `INFRAHUB_SECURITY_SECRET_KEY` when no dedicated key is set, when it starts. Keep that value in your secrets manager. Without it, encrypted files cannot be recovered, even from a backup.
:::

:::warning
Infrahub checks the length of the key, not whether it is random. Anyone who can read an encrypted file can test guesses of the key against it offline. A key that a person chose, such as a phrase with a year, can be found this way. When no dedicated key is set, the key is derived from the secret that signs the access tokens of users, so a guessed secret also lets an attacker create valid tokens.
:::

## Enable encryption

Set `INFRAHUB_STORAGE_ENCRYPTION_ENABLED=true` on every API server, optionally with `INFRAHUB_STORAGE_ENCRYPTION_KEY`, then restart them. Task workers need neither the setting nor the key: they store and read files through the API.

From then on:

- Every artifact generated and every file uploaded is stored encrypted, and Infrahub checks that it is unchanged each time it serves it.
- A file stored before encryption was enabled stays as it is: enabling encryption does not encrypt existing files, and regenerating an artifact whose content did not change keeps its stored file. When the content of an artifact changes, Infrahub stores the new content encrypted. It does not delete the previous file, which stays in the storage in plaintext. Infrahub serves it only while it matches the checksum recorded when it was stored, even when `INFRAHUB_STORAGE_VERIFY_ARTIFACT_CHECKSUM` is `false`. A file for which no artifact or file object records a checksum is served as it is. This includes an encrypted upload that no artifact or file object refers to: someone who can write to the storage can replace it with plain content, and Infrahub serves that content.

## Turn encryption off

Set `INFRAHUB_STORAGE_ENCRYPTION_ENABLED=false` (or remove it) on every API server, then restart them. Nothing else changes for users:

- Files that were encrypted stay encrypted in the storage, and Infrahub keeps decrypting them when it serves them, as long as the key that applies (`INFRAHUB_STORAGE_ENCRYPTION_KEY`, or `INFRAHUB_SECURITY_SECRET_KEY` when no dedicated key is set) has the value that was in use when they were encrypted. Infrahub still refuses an encrypted file whose content was modified. A file that was truncated or replaced is no longer a complete encrypted file, and Infrahub checks it as described below. If that key is not set, is the value from the example deployment files, or is shorter than 32 characters, Infrahub cannot decrypt them and returns a `500` error that names the setting.
- Every artifact generated and every file uploaded from then on is stored in plaintext.
- Infrahub checks stored files as it did before encryption was enabled: artifacts against their recorded checksum, and file objects not at all. Someone who can write to the storage can replace an encrypted file object, or an encrypted artifact while `INFRAHUB_STORAGE_VERIFY_ARTIFACT_CHECKSUM` is `false`, with plain content, and Infrahub serves it.

You can turn encryption on again at any time. A file encrypted while it was on stays encrypted, so the files are a mix of encrypted and plain files.

## Files that fail their integrity check

Infrahub does not serve an encrypted file that was modified or that was encrypted with another key. It does not serve a file stored before encryption was enabled when it no longer matches its recorded checksum. The request fails with a `409` error, and the API server logs a warning with the storage identifier of the file, the reason (`unknown_key`, `tampered`, `unsupported_format` or `checksum_mismatch`) and the fingerprint of the current key. A file that is missing from the storage returns a `404` error, as it does without encryption.

To repair a file object, upload the file again. To repair an artifact, delete it and regenerate its artifact definition.

## Check the encryption of an artifact

Each artifact has a read-only `encryption` attribute with one of three values:

- `plaintext`: Infrahub stored the file without encryption.
- `encrypted`: Infrahub stored the file encrypted, and the current key can read it.
- `unreadable`: the file is encrypted, but the current key cannot read it. For example, the key changed after Infrahub stored the file.

Infrahub sets the value when it generates the artifact. The artifact page shows a notice for each value:

- A warning when encryption is enabled and the artifact is `plaintext`.
- A green notice when a check of the file has just confirmed that the artifact is `encrypted`.
- An error when the artifact is `unreadable`. When the check ran, the error also gives the reason.

Each time a signed-in user opens the artifact page, the UI sends a check request. The check reads only the first bytes of the stored file. These bytes name the key that encrypted the file, so the check finds a file that another key encrypted and a file that is incomplete. It does not decrypt the file, so it does not find a file whose content was modified: Infrahub refuses that file when it serves it. When the result differs from the stored value, Infrahub updates the stored value if the user may update artifacts. A user who is not signed in sees the stored value and no green notice.

The check describes the file and the key as they are now. When a user views the artifact at a past date, the artifact page sends no check: it shows the notice for the value stored at that date, with no green notice and no reason.

To check an artifact through the API, send `POST /api/artifact/{artifact_id}/encryption`. The response has these fields:

- `encryption`: the value found by the check.
- `reason`: why the file is `unreadable`: `no_key`, `unknown_key`, `unsupported_format` or `truncated`. When the file is missing from the storage, the reason is `missing` and the stored value stays as it is.
- `updated`: whether the check changed the stored value.

## Limitations

- Changing the key that applies makes the files encrypted with the previous value unreadable: they are refused until the previous value is restored. This includes setting `INFRAHUB_STORAGE_ENCRYPTION_KEY` after files were encrypted with a key derived from `INFRAHUB_SECURITY_SECRET_KEY`, and removing it again.
- An older encrypted copy of a file, put back under the same storage identifier, is served: only the storage identifier is authenticated, not the version of the file.
- Infrahub refuses a file stored before encryption when it looks like an encrypted file but does not decrypt. While encryption is on, that is any file that starts with the four bytes `IHSE`. While it is off, it is a file that starts with `IHSE`, has the format version byte `1` and is at least 41 bytes long.
- The API server holds a whole file in memory while it encrypts or decrypts it: about twice the size of the file at the peak, for example about 100 MB for a 50 MB file. Without encryption, an upload is written in chunks and a download holds the file once.
- The stored `encryption` value of an artifact can be out of date until the next check. For example, after the key changes, an artifact stays `encrypted` until a check finds that the file is unreadable.
- Files stored before encryption was enabled stay in plaintext in the storage, and so do their copies outside Infrahub, such as older backups, S3 object versions and filesystem snapshots.

## Back up and restore

Back up the graph database and the object storage at the same time, and restore them together. The backups contain neither the key nor the secret: restore them with the value of `INFRAHUB_STORAGE_ENCRYPTION_KEY`, or of `INFRAHUB_SECURITY_SECRET_KEY` when no dedicated key was set, that was in use when they were taken.
