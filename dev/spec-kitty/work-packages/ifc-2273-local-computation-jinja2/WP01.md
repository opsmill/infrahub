# Work Package WP01: Registry & Extra Filters Foundation

## Goal

Extend the computed attribute registry and Node peer-loading infrastructure to support inline recomputation.

## What Was Implemented

The registry was refactored beyond the original plan: `ComputedAttributes` is now a **thin facade** delegating to two extracted sub-registries.

### Refactoring: Sub-Registry Extraction

- `PythonTransformRegistry` extracted to `backend/infrahub/core/schema/schema_branch_computed_python.py` — owns `_map` of Python transform attributes
- `Jinja2ComputedRegistry` extracted to `backend/infrahub/core/schema/schema_branch_computed_jinja2.py` — owns `_map` of Jinja2 dependency graphs, `_defined_from_generic` validation state
- `ComputedAttributes` in `schema_branch_computed.py` delegates all operations to `self._python` and `self._jinja2`

### T001: relationship_fields via `relationship_peer_attributes`

Instead of parsing Jinja2 templates at read time (original plan), `relationship_peer_attributes` is populated at registration time in `Jinja2ComputedRegistry.register()`. `RegisteredNodeComputedAttribute.relationship_fields` is a read-only property returning a copy.

### T002: `get_local_jinja2_targets()` → `Jinja2ComputedRegistry.get_local_targets()`

Filters `get_impacted_targets()` to `target.kind == kind`. Exposed via `ComputedAttributes.get_local_jinja2_targets()`.

### T003: `_collect_extra_filters()` with `HasRelationshipFields` Protocol

- `_merge_relationship_fields()` now accepts `Sequence[HasRelationshipFields]` instead of concrete `HFIDDefinition | TemplateLabel`
- `_collect_extra_filters()` adds computed attribute entries via `schema_branch.computed_attributes.get_registered_jinja2_node()`, gated on `self._existing`
- New `HasRelationshipFields` Protocol in `core/node/__init__.py`

### T004: Unit tests

`backend/tests/unit/core/test_schema_branch_computed.py` — tests for `relationship_fields`, `get_local_jinja2_targets()`, `get_registered_jinja2_node()`
