## Executive Summary

This is an unusually well-grounded spec/plan pair. The problem is evidenced (a JPD item, a named
regression trigger in #8896, five concrete customer use cases, three named per-consumer workarounds),
the chosen solution shape was reached by *reversing* a near-merge alternative on the strength of
code-confirmed findings, and Phase 0 research verified every load-bearing claim against the working
tree rather than trusting the brief. The Complexity Tracking entry for the Principle III deviation is
exactly what the constitution's Governance section asks for. Architecture, security, and performance
review turn up nothing: the change adds no queries, no dependencies, no graph mutations, and it
*tightens* an input boundary.

Three items must be addressed before task generation. The most substantive is a genuine gap rather
than a documentation nit: **the interaction between `allow_prefix` and an attribute's `default_value`
is unhandled**. `SchemaBranch.validate_default_values()` routes defaults through the same
`validate_format` this feature is modifying, so a non-host-prefix default will start being rejected at
schema-load time — good, but unspecified and untested — while a `/32` default will be *accepted and
stored in the schema unnormalised*, leaving the schema advertising `10.0.0.1/32` as the default for an
attribute whose every node stores `10.0.0.1`. Second, the spec claims computed attributes and
templates receive the bare value as an edge case, but the plan carries no task or test for it, and the
constitution mandates Integration Docker coverage for computed-attribute features. Third, two headline
success criteria (SC-001, SC-004) cite baseline workaround counts that contradict the spec's own
Problem Statement, making them unverifiable as written.

None of the three threatens the design. All are resolvable inside the existing plan shape, which is
why the verdict is PROCEED WITH UPDATES rather than RETHINK.

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | **The `allow_prefix` × `default_value` interaction is unhandled.** `SchemaBranch.validate_default_values()` (`schema_branch.py:1048-1066`) calls `validate_format(value=node_attr.default_value, name=node_attr.name, schema=node_attr)` at schema-load time, and `basenode_schema.py:152-174` guarantees `node_attr` is the per-kind schema class, so `parameters.allow_prefix` is reachable there. Two consequences, neither specified nor tested: (a) `default_value: "10.0.0.1/24"` on a flagged attribute will start failing at **schema load** with a `default value ...` error — desirable, but undocumented behaviour of a modified validator; (b) `default_value: "10.0.0.1/32"` **passes** and is stored in the schema verbatim, because `_normalize_value` is an attribute-instance method that never runs against `schema.default_value`. The schema then advertises a default of `10.0.0.1/32` for an attribute where every created node stores `10.0.0.1`. | Normalise the default inside the new `IPHostAttributeSchema`: a model validator that strips a redundant host mask from `default_value` when `allow_prefix` is `False`. This mirrors FR-004 exactly (accept the redundant mask, store bare), keeps the schema self-consistent, needs no change to the shared schema-processing passes, and lands entirely in the class the feature is already adding. Non-host prefixes keep being rejected for free by `validate_default_values`. Add the accepted/rejected default rows to the schema contract and tests at both levels. |
| E5 | 💡 | The plan attributes flag reachability primarily to the defensive `getattr(schema.parameters, "allow_prefix", True)` read.
