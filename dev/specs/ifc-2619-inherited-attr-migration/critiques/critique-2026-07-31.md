# Critique Report: Inherited-Attribute Migration Fix and Healing Migration

**Date**: 2026-07-31 | **Spec**: [../spec.md](../spec.md) | **Plan**: [../plan.md](../plan.md)
**Reviewed artifacts**: spec.md, plan.md, research.md, data-model.md, quickstart.md, constitution v1.0.0

## Executive Summary

The spec and plan are unusually strong: the root cause is traced (not hypothesized) with verified file:line evidence, the design reuses existing machinery instead of inventing parallel mechanisms, the PRD's open questions arrive already resolved into documented assumptions, and the test strategy asserts user-observable behavior. The two deliverables are correctly sequenced (healing depends on the forward fix's machinery) and packaged (same release).

Two engineering-lens gaps warrant plan edits before task generation — both are sub-designs of the healing migration that would otherwise surface mid-implementation: (1) how m075 acquires per-branch schemas, and (2) how retroactive-timestamp derivation copes with duplicated same-UUID schema vertices. Both are resolvable with small plan/research additions; nothing suggests rethinking the approach.

**Verdict: ⚠️ PROCEED WITH UPDATES** (fixes applied in this pass — see Remediation).

## Product Lens Findings

### 3a. Problem Validation — strong

Real, reported, reproducible user pain (#9284, Jira IFC-2619) with a traced root cause. Silent data damage in an infrastructure source-of-truth product is close to the worst failure class the product can have; the "any install that performed such a change is damaged today" framing justifies the healing deliverable, not just the forward fix. Scope is well-bounded with explicit out-of-scope items and follow-up issues.

### 3b. User Value Assessment — strong

P1 (forward fix) alone is a viable MVP that stops the bleeding; P2/P3 (healing) deliver the remediation no operator can practically do by hand. Acceptance criteria are user-observable (reads, updates, filters) rather than implementation-flavored. No gold-plating found: continuous repair was explicitly rejected as out of scope.

### 3c. Alternative Approaches — adequately considered

research.md R1 records three rejected alternatives for the forward fix with reasons grounded in prior regressions (#7407). For healing, the rebase-based alternative (`MigrationRequiringRebase`) is explicitly rejected because forcing organization-wide rebases is the cost the feature exists to avoid. Cost of inaction: permanent silent damage — correctly treated as unacceptable.

### 3d. Edge Cases & User Experience — strong, one addition

Tombstones, deleted nodes, mandatory-no-default, generic-changed-later, simultaneous-change, partial failure, and pool concurrency are all enumerated with decided behavior.

- **P1 (💡)**: The healing migration reports errors loudly on failure, but on *success* an administrator has no record of what was repaired. Upgrade-time repair of user data should leave an audit trail. **Suggestion**: require the migration to log per-kind repaired-row counts (default branch and per branch) as part of its completion output. Cheap, and quickstart.md already assumes it exists ("migration logs per-kind repair counts") — spec/plan should actually require it.

### 3e. Success Measurement — strong, one nuance

SC-001–SC-004 are measurable and self-enforcing (SC-001 is the migration's own validation).

- **P2 (💡)**: SC-004 ("pre-existing branch reads healed attributes without rebase") holds only for branches whose `branched_from` postdates the retroactive timestamp; a branch created *before* the kind gained inheritance has no such attribute in its schema either, so absence there is correct behavior, not failure. **Suggestion**: add this negative case to the test matrix so the boundary is pinned rather than discovered.

## Engineering Lens Findings

### 4a. Architecture Soundness — sound, two sub-designs missing

The forward fix hooks the migration that already owns the triggering event; the transaction-nesting hazard is known and designed around; the phase split is derived from `MIGRATION_MAP` rather than hard-coded; the healing migration uses the established `ArbitraryMigration` escape hatch with precedent.

- **E1 (🎯)**: **Per-branch schema acquisition for m075 is unspecified.** The healing migration reuses `NodeAttributeAddMigration`, which requires concrete node-schema objects, and its branch pass needs each branch's *own* schema (branch schemas can differ from the default branch — that is precisely the branch-originated-damage case, FR-009). The plan never states where these schema objects come from at upgrade time. Known project gotcha: loading a schema from the DB for a branch with no schema changes returns an empty schema branch that must fall back to the default branch's schema. **Suggestion**: add to plan Design §5: m075 loads the schema from the database per branch (default branch first; per-branch load with fallback-to-default semantics when the branch has no schema of its own), and the detection query receives schema objects, never registry state.
- **E2 (🎯)**: **Retroactive-timestamp derivation must handle duplicated schema vertices.** Schema name/namespace/inheritance updates create *same-UUID copies* of schema nodes (kind-update duplication applies to schema vertices too). "When did the kind begin inheriting the generic" is therefore not readable off a single vertex's edge history — the query must resolve the edge timeline across all same-UUID copies (join on UUID for identity, use internal vertex id only within one copy's edge set). Unaddressed, the derived timestamps can be wrong in exactly the installs the healing migration targets (they performed kind updates by definition). **Suggestion**: add to plan Design §4 and research R8: derivation walks the full same-UUID vertex set of the schema node/attribute vertices and takes the earliest active `inherit_from`/attribute edge; component tests must cover a kind that was renamed (duplicated schema vertices) after gaining inheritance.

### 4b. Failure Mode Analysis — good

Partial-failure recovery is idempotency + retry + self-validation gate; phase-1 errors abort phase 2; a failure in m075 fails the upgrade (correct: better a loud failed upgrade than silent partial repair). Blast radius of the two-phase change is all schema loads — covered by the unchanged rollback suite and the case-coverage table.

- **E3 (💡)**: `NodeKindUpdateMigration.execute()` stops at the first failing sub-migration, and `schema_path_migrate` retries the *whole* migration (duplication no-ops via `already_migrated`, completed adds no-op via the attribute-add guard). This convergence argument is stated for healing but not for the forward path. **Suggestion**: state it explicitly in plan Design §2 and pin it with a component test (rerun of a partially-completed kind-update converges).

### 4c. Security & Privacy — no findings

No user input, no new endpoints, parameterized Cypher throughout, migration runs under the existing upgrade privilege model.

### 4d. Performance & Scalability — acceptable with the documented fallback

Per-kind batching bounds the detection scan; self-validation reuses the detection query (one extra pass); the sample/scope fallback is documented in spec Assumptions. NumberPool per-node allocation is the sanctioned exception and proportional to damaged pool-backed rows only.

- **E4 (🤔→resolved by best judgment)**: Is one extra full detection pass acceptable as self-validation on very large installs? **Resolution adopted**: yes — upgrade-time is the one window where a full pass is tolerable, and the fallback is already specified. No change.

### 4e. Testing Strategy — strong

Right pyramid shape (one pure unit target, DB behavior at component level, public-API integration repro), damaged states seeded the way real installs got damaged, healthy no-op asserted as first-class. Additions from this critique: the E2 renamed-kind timestamp case, the E3 partial-failure rerun case, the P2 branch-predates-damage case.

- **E5 (💡)**: "Zero writes" (SC-003) needs an objective measurement mechanism in component tests (e.g., write-counter deltas from the driver's result summary), not an implementation-detail assertion. Task generation should make this explicit.

### 4f. Operational Readiness — adequate, one addition

One-shot gating via `GRAPH_VERSION` 74→75 is the established mechanism; failure surfaces through the upgrade command. Graph migrations are not reversible, but healed rows are benign (schema-default values the schema says must exist) and the migration is rerun-safe — acceptable without a down-migration, consistent with every existing m0XX.

- Covered by **P1**: repaired-count logging is the missing observability piece.

### 4g. Dependencies & Integration Risks — low

No new dependencies. Sole orchestration caller (`SchemaUpdateCoordinator`) verified. The `infrahub upgrade` command picks up m075 through the existing registry. Same-release packaging is a process risk, not a technical one (see X1).

## Cross-Lens Insights

- **X1 (💡)**: The same-release constraint (spec assumption: no install experiences "new damage stopped, old damage present") is enforced by nobody in the artifacts. **Suggestion**: note in plan that PR 2's merge checklist includes verifying PR 1 is in the same release milestone; both PRs reference IFC-2619 so the release manager can see the coupling.
- **X2 (converged strength, no action)**: Both lenses independently conclude the healing migration must fail loudly rather than partially succeed silently — the spec already encodes this (FR-010), and it is the single most important property to protect during implementation.
