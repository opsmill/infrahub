## Executive Summary

The spec follows the Jira task and section B of the design document, and states what it decided
without a source. The plan puts the equivalence test suite first, which is the control the design
document asks for on the largest risk: every schema load goes through the new applier.

Two findings must be fixed before tasks are written. The time used to find main's version at a
branch's `branched_from` is the wrong one, which gives a wrong base version and a wrong parent for
a branch created while a load on main is running. And the history query shows stored error text
to anonymous readers when anonymous access is on, which the constitution does not allow for
internal error detail. Both have a small fix.

The other findings tighten points the plan left open: the order of operations inside a schema
change, how a migration result is matched to its record, a warning when the applier's schema
differs from the schema of the laid-over file, and the wording of one success criterion.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | `research.md` R10 finds main's version at a branch's `branched_from` from `applied_at`, and `data-model.md` sets `applied_at` when the status becomes `applied`, which is the time the load ended. A load writes the schema at one timestamp, `at`, taken when it starts. A branch created after `at` and before the load ends reads main's schema as of its `branched_from`, so it already has that schema change. With the end time, the branch gets a base version that is one too low and the wrong parent, and the later replay task would apply main's schema change to the branch a second time. | Define `applied_at` as the timestamp of the graph writes of the application (`at`), not the time the status changed. Find the base version with `applied_at <= branched_from`. Add a component test: main loads, a branch is created with `branched_from` after `at`, and the branch's first schema change has main's version plus 1. |
| E2 | 💡 | The plan does not fix the order of the operations inside one schema change. The applier resolves names against the schema as it changes, the summary comes from the first operation, and the later replay task rewrites operations that follow a rename. All three need one order. | Define the order in `research.md` R5: kinds in a fixed order, and inside a kind the property operations before the rename of the same element, so every operation before a rename names the element by its name before the load. |
| E3 | 💡 | `MigrationRecorder.migration_ended` receives only the result. A result holds the migration name and the schema path, and the list of migrations is not deduplicated, so two migrations of one application can have the same name and path. | Identify a migration record by its position in the application's list, and make the flow pass the position with each result. |
| E4 | 💡 | A dropdown or enum mutation saves the schema without a timestamp today, so the save uses the current time. The records need the timestamp of those writes (E1). | The mutation takes one timestamp and passes it to the save and to the recorder. |
