# Critique Report: Number Pools — Several Weighted Ranges per Pool (P1)

**Date**: 2026-09-08
**Artifacts reviewed**: `spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/graphql-schema-changes.md`, `quickstart.md`, `.specify/memory/constitution.md`

## Executive Summary

The spec and plan are strong and implementation-ready after two must-address items are folded into the plan. The problem is well-validated (derived from a grilled PRD; real pain — numbering plans are rarely one contiguous span), the P1 scope is coherent and — thanks to the decoupling decision (update, not delete, the taken-value scan) — independently valuable and releasable. The engineering approach is a net simplification (one effective-space calculator replacing three drifting computations) and reuses an existing generic.

The two must-address items are both about **sequencing and enforcement completeness**, not about direction: (1) the branch-inheritance combination the whole new kind rests on is unproven and must be de-risked first; (2) range validity (start≤end, intra-pool non-overlap) must be enforced on the schema-created write path, not only the GraphQL mutation. Both are remediated by small plan/data-model additions below.

**Verdict**: ⚠️ PROCEED WITH UPDATES.

## Product Lens Findings

### 3a. Problem Validation
Strong. The revision PRD reconciles three grilled briefs and cites concrete failures (allocation stalling on hand-set values, divide-by-zero, disagreeing utilization figures). No solution-looking-for-a-problem risk.

### 3b. User Value Assessment
Each user story delivers standalone value. US1 (fall-through across gaps) is the core; US2 (edit ranges without refusal) and US3 (consistent size/utilization) are independently testable. The decoupling decision is the right MVP call — P1 ships a coherent capability without waiting on P2.

**P1 (💡)** — SC-007 makes `start_range`/`end_range` read as null on multi-range pools, but the **existing frontend and API clients read those fields today**. The spec defers "the frontend" with P2, yet this read-contract change lands in P1. If an existing UI panel or client binds `start_range` non-null, it breaks the moment a second range is added. Suggestion: add an explicit assumption/verification that current consumers tolerate a null `start_range`/`end_range`, and confirm the changelog upgrade note calls this out for API consumers, not only pool authors.

### 3c. Alternative Approaches
Considered and recorded (JSON-list-of-ranges rejected in research D1; fix-in-place rejected in D5). The chosen approach reuses `CoreWeightedPoolResource` rather than inventing a parallel weighting mechanism. Cost of inaction is concrete (the three existing defects persist). Good.

### 3d. Edge Cases & UX
Thorough: zero ranges, clamp-to-empty, retained-out-of-range numbers, both-spellings conflict, overlapping ranges, weight change mid-drain, upgrade. Migration is zero-touch for operators (SC-005).

### 3e. Success Measurement
SC-001…SC-007 are measurable and mostly binary/observable. **P2 (🤔)** — no explicit at-scale performance acceptance for the generalised gap walk (a fully allocated 4094-entry VLAN pool). Not a P1 blocker (the PRD bounds the cost concern to P3's scoped reads), but worth one benchmark assertion. Resolved by judgment as a recommendation (E4), not a gating SC.

## Engineering Lens Findings

### 4a. Architecture Soundness
Sound and testable per layer. The effective-space calculator centralises arithmetic that is duplicated today — a genuine decoupling, not a new abstraction for its own sake (Principle VII satisfied; two-plus callers).

**E1 (🎯) — Branch-inheritance is unproven and load-bearing.** `CoreNumberPoolRange` must be `branch=AGNOSTIC` while its parent generic `CoreWeightedPoolResource` is `branch=AWARE`; it is the first core kind to inherit that generic (research D2). If schema validation forbids the mix, the entire kind design shifts. Suggestion: sequence this as the **first implementation task** (schema-load/component spike) with the recorded fallback (make the generic branch-neutral for inheritance) — fail fast before building queries and migration on top. Fold a one-line sequencing note into `plan.md`.

### 4b. Failure Mode Analysis
Zero-ranges and empty-effective-space are handled (D11 — PoolExhaustedError, no division). Held-number retention (FR-002a) is the correct conservative behaviour (never manufacture a collision). Blast radius is contained to the pool subsystem.

**E2 (🎯) — Range-validity enforcement must cover the schema-created path.** The plan places the `start≤end` + intra-pool non-overlap guard in `InfrahubNumberPoolMutation` (GraphQL). Schema-created pools author ranges through `NumberPoolParameters`, a separate write path. Without the same guard there, a schema-declared pool could define an inverted or overlapping range that the GraphQL guard would have refused. Suggestion: state in `data-model.md`/contract that `NumberPoolParameters` validation enforces the same range-validity rules (FR-004), and cover it with a validator test.

### 4c. Security & Privacy
No new trust boundary of concern. Range inputs are validated at the boundary; parameterised Cypher only (Principle V/VI). No sensitive data. PASS.

### 4d. Performance & Scalability
Gap detection stays in the database (Principle V respected). **E3 (💡)** — the generalised `NumberPoolGetFree` gap walk (UNWIND over the ordered union of ranges) should be `EXPLAIN`-ed and have one benchmark over a fully-allocated pool to confirm no regression versus today's single-span walk. Already noted in plan/quickstart; elevate to an explicit task.

### 4e. Testing Strategy
Comprehensive across unit/component/functional, fixtures reused. **E4 (💡)** — add the at-scale allocation benchmark (from P2/E3) so the range-set walk has a guardrail. E2E is not applicable to this backend/schema slice (frontend deferred); noting so the constitution's E2E clause is consciously scoped out, not silently skipped.

### 4f. Operational Readiness
**E5 (💡) — Migration idempotency / direction.** Infrahub graph migrations are forward-only (`ArbitraryMigration`, per `m066`). The plan should state the migration is idempotent/re-run-safe (must not create a second covering range for a pool that already has one) and forward-only by design, consistent with the migration framework. Suggestion: add re-run-safety to the migration task's acceptance and its test.

### 4g. Dependencies & Integration Risks
No new third-party dependency. Integration points: the migration touches every pool (bounded, one-time); `IS_RESERVED`/`HAS_SOURCE` untouched (correct — those are P2's territory). The `NumberPoolParameters` contract change is coordinated with P3 under one ADR-0010 review (recorded).

## Cross-Lens Insights

- **X1 (🎯 — folds E1)**: De-risking branch inheritance first protects both the schedule (product) and the architecture (engineering). Highest priority.
- **X2 (💡 — folds P1 + contract)**: The nullable-read change is simultaneously a UX surprise for existing clients (product) and a published-contract break (engineering). One action — an explicit consumer-tolerance check + upgrade note — resolves both.
