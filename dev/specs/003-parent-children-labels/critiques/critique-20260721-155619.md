# Critique Report: Peer-derived labels for hierarchical parent/children relationships

**Timestamp**: 20260721-155619
**Spec**: [../spec.md](../spec.md) · **Plan**: [../plan.md](../plan.md)
**Verdict**: ⚠️ **PROCEED WITH UPDATES** — one Must-Address gap (self-referential hierarchies), resolvable by an explicit spec decision; no architecture or constitution violation.

## Executive Summary

The feature is small, well-scoped, and technically sound: a single pure rule consumed at all relationship-label render sites, frontend-only, no governance gates. The spec/plan are internally consistent and the constitution check is clean. The one genuine gap is a **product/UX edge case the spec does not yet address**: self-referential hierarchies (parent and children share the same peer kind), which is exactly the IPAM prefix hierarchy — a flagship Infrahub use case. There the change makes both the parent and children label render identically (e.g. "Prefix"/"Prefix"), erasing the parent↔child direction that "Parent"/"Children" made explicit. It must be an explicit, accepted decision, not a silent omission.

## Product Lens Findings

### 3a. Problem Validation
- **Clear and evidenced.** Sourced from a concrete GitHub feature request; the pain ("Parent doesn't tell you what kind") is real and specific. Scope is appropriately narrow. No concern.

### 3b. User Value
- **Solid** for hierarchies where parent/children peers are *distinct* kinds (e.g. Location `Region`→`Site`). MVP is the whole feature — no over-build.

### 3c. Alternative Approaches
- The rejected alternative (author-set custom label via backend `label`) is correctly deferred. No simpler client-only approach exists. No concern.

### 3d. Edge Cases & UX — **P1 (🎯 Must-Address)**
- **Self-referential hierarchy direction loss.** When the hierarchy peer is the object's own kind (IPAM `IpamIPPrefix` parent = prefix, children = prefixes), C1 fires for both and the parent field and children tab both render "Prefix". In the **detail view** direction is still implied by placement (parent = field, children = tab), but in the **sort picker** and **filter list** two entries would both read "Prefix" with nothing to disambiguate them. The spec's Edge Cases don't mention this. → *Suggestion*: add an explicit edge case + accepted decision to `spec.md`; recommend a directional disambiguator in the flat sort/filter surfaces (see X1).

### 3e. Success Measurement
- SC-001/002/003 are measurable and tech-agnostic. No concern.

## Engineering Lens Findings

### 4a. Architecture — **clean**
- Pure rule in `domain/rules/`, peer passed in (no store coupling), consumed at the edges. Matches `is-hierarchical-schema.ts` precedent. Testable without mocks. No concern.

### 4e. Testing — **E2 (💡 Recommendation)**
- Plan mandates unit + E2E (constitution IV). **Pick the E2E fixture deliberately**: use a hierarchy with *distinct* parent/children peers (Location `Region`→`Site`) so the assertion proves the peer label actually replaced "Parent"/"Children". An IPAM self-referential fixture would assert "Prefix" == "Prefix" and prove little.

### 4g. Dependencies / Data — **E3 (💡 Recommendation / 🤔)**

The plan flags this for verification. → *Suggestion*: first task in implementation is a quick assertion (inspect a live/loaded schema, or the generated type + a fixture) that `hierarchical` is truthy on both before wiring 9 sites to it. If only one carries it, fall back to also matching `kind`/name for the other.
