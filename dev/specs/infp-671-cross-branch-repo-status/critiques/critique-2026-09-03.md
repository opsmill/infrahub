## Executive Summary

The problem is real and well evidenced (one page per branch today, one query per branch in the sync),
the scope is tight (no schema, no write, no worker), and the plan's contract-first split is the right
response to the request to unblock the frontend team early. The architecture follows the repository's
own conventions (Query class with frozen results, thin reader component, in-resolver permission where
the pipeline cannot help) and the query-count invariant is testable with existing helpers.

Two items must be settled before increment A ships, because increment A *is* the contract:

1. The `hfid` anchor cannot work. No repository kind declares a `human_friendly_id`, so the argument
   the SDL exposes would never resolve. Anchor on id or name through the existing default-filter lookup
   instead.
2. `own_values_only` is defined relative to "the selected attributes", so the same filter returns a
   different row set depending on which fields the client asks for, and it collides with FR-008 (read
   only what was selected). Pin the filter to a fixed attribute before the frontend builds against it.

Both are wording-level fixes across spec, SDL, contract and data model. Everything else is a
recommendation or a question for the sibling PRD.

**Verdict**: ⚠️ PROCEED WITH UPDATES.

## Product Lens Findings

### 3a. Problem Validation

Clear, evidenced, bounded. The problem statement quantifies the pain (up to 200 page opens; one query
per branch per sync cycle) and the PRD verified the codebase before fixing the contract. Nothing to add.

### 3b. User Value Assessment

- **P1 (🤔)**: User Story 1 is about the Branches card, but this slice delivers the query and the
  frontend team delivers the card in parallel (plan, Implementation Strategy). The spec does not say
  who owns the card or where its acceptance is tracked, and the constitution's E2E requirement is
  deferred to it. State in the spec that the card and its pytest-playwright test are delivered by the
  frontend team under INFP-671 against `contracts/graphql-repository-branch-status.md`, so the P1
  acceptance has an owner.
- **P2 (🎯, shared with E10 as X1)**: FR-014 defines `own_values_only` as "own value for at least one
  selected attribute". A client requesting only `sync_status` and one requesting only `commit` get
  different row sets from the same filter, and the fields a table shows are a rendering choice, not a
  filter choice. An import on a branch writes `commit` and `sync_status` together, so anchoring the
  filter on `commit` alone gives the same practical answer ("has this branch imported on its own?")
  and makes the result independent of selection. Proposed FR-014 wording below.

### 3c. Alternative Approaches

The PRD already rejected the node manager and a per-branch loop for sound reasons. Not building it
leaves the 200-page hunt and the once-a-minute per-branch loop in place. No cheaper alternative
delivers the count and filters server-side.

### 3d. Edge Cases & User Experience

- **P3 (💡)**: While increment A's stub is on `develop`, every demo stack and QA environment built from
  `develop` shows fabricated commits and a deterministic spread of `error_import` rows on real
  repositories. Expect confused bug reports from anyone not on the frontend team. Mitigate by
  announcing the stub window, adding "(preview, values fabricated until INFP-671 increment B)" to the
  root field description in the SDL for the duration, and tracking the removal as its own Jira
  subtask so it cannot silently outlive the frontend work.
- Edge cases in the spec are thorough; the `updated_at` trap is called out twice, which is right.

### 3e. Success Measurement

SC-002, SC-004 and SC-007 are asserted by tests; SC-001 and SC-003 are verified by the card. For an
internal read path that is adequate. The new Query class's `name` is picked up by the existing
per-query metrics automatically, which gives a post-launch signal for free.

- **P4 (🤔)**: The spec's open question (does the card fetch the git-derived drift column in a second
  request, or does a resolver fan out to a worker?) is deferred to "settle jointly with the sibling
  PRD", but the frontend team starts on the card the moment increment A lands. Settle it before
  increment A merges, or explicitly instruct the frontend team to build the card without that column
  first.

## Engineering Lens Findings

### 4a. Architecture Soundness

Follows `dev/knowledge/backend/query-pattern.md` and `.agents/rules/backend-component-design.md`:
primitives into the Query class, frozen result dataclass, reader component with `db` injected,
resolver as composition root. One resolver path. The stub is isolated in one module and its deletion is
the increment B acceptance.

- **E1 (🎯, part of X2)**: The SDL declares `hfid: [String!]`, but no repository kind declares
  `human_friendly_id` (verified against `backend/infrahub/core/schema/definitions/core/repository.py`).
  `NodeManager.get_one_by_hfid` has nothing to match. The kinds do declare `default_filter="name__value"`,
  and `NodeManager.get_one_by_id_or_default_filter` already accepts a uuid or a name. Replace `id: ID`
  plus `hfid: [String!]` with a single required `id: String!` resolved through that method. This is
  also what "the same not-found behaviour as other repository lookups" means in practice.
- **E9 (💡)**: The plan accepts that a caller without permission learns whether the id resolves,
  because the lookup precedes the check. This is avoidable at no cost: before the lookup, deny unless
  the caller holds the required `view` decision on at least one of `Core/Repository` and
  `Core/ReadOnlyRepository`; after the lookup, check the concrete kind. Two `has_permission` calls,
  no leak.

### 4b. Failure Mode Analysis

Read-only, no external dependency, no worker; the failure modes are a slow statement and a wrong row.

- **E2 (💡)**: The visibility predicate in data-model.md and contracts/core-primitive.md uses
  `r.from <= t` and `r.to > t`; `Branch.get_query_filter_path` emits `r.from < $time1 AND (r.to IS NULL
  OR r.to > $time1)` for the default-branch-at-fork-point arm and a separate `r.from <= $time AND r.to
  IS NULL` arm. A value written at exactly `branched_from` would be visible in one and not the other.
  Copy the operators from `get_query_filter_path` verbatim, and add a differential component test: for
  every branch in a fixture, the primitive's `(value, updated_at)` equals what
  `NodeManager.get_one(branch=...)` returns for the same attribute. That test catches any future drift
  between the two filters, not just this one.
- **E3 (💡)**: `is_isolated` is deprecated and forced to true on creation, but the `Branch` model still
  carries it and `get_query_filter_path` still honours a `false` value by reading the default branch at
  query time. A database upgraded from an older release may hold such branches. Either read
  `br.is_isolated` in the statement (`CASE WHEN br.is_isolated THEN br.branched_from ELSE $at END`) or
  record in data-model.md that legacy non-isolated branches resolve differently here than in a standard
  read. The E2 differential test with one non-isolated branch in the fixture decides which.

### 4c. Security & Privacy Review

Parameterised Cypher throughout; denial before any row leaves the resolver; no new permission.

- **E4 (💡)**: `GraphqlContext.active_permissions` raises `InitializationError` when the context has
  no `PermissionManager`. `prepare_graphql_params` loads one whenever an `account_session` is present,
  which includes anonymous sessions, but internal callers construct contexts without one. Make the
  resolver treat a missing manager as denial rather than a 500, and add two tests: anonymous read with
  a role grant (rows) and without (denied).

### 4d. Performance & Scalability

Three statements per page at any branch count up to `database.query_size_limit` (5000). `UNWIND` plus
the `Branch` join keeps one plan for any list. `EXPLAIN` is scheduled in increment B.

- **E6 (💡)**: `Branch.get_list(limit=None)` takes the base `Query` chunked path above 5000 rows, and
  that path is only correct over a total order (`dev/knowledge/backend/query-pattern.md`, Pagination).
  With the default `StandardNodeOrdering` (by id) that holds; with `order` by `created_at` or
  `updated_at`, confirm `StandardNodeGetListQuery` adds an id tiebreaker or add one. Cheap to check in
  increment A; add it to tasks.
- The `WITH DISTINCT (n, a, branch_name, branched_from)` before the `CALL` subqueries is essential: a
  repository attribute touched on k branches has k `HAS_ATTRIBUTE` edges and would otherwise run the
  election k times per row (query-pattern.md, Branch-Aware Edge Resolution). The plan implies it;
  make it an explicit task.

### 4e. Testing Strategy

Comprehensive at the component level; the pure helpers get unit tests; the sync bound is asserted.

- **E7 (💡)**: The 5-versus-200 branch fixture is created twice (primitive tests, resolver tests) and
  again for the sync bound. Creating 200 branches through the `create_branch` flow is seconds per run.
  Share one module-scoped fixture built with `Branch(...).save()` and reuse it in all three files.
- The FR-008 assertion ("attribute names reaching the reader equal the selection") depends on X1's
  resolution: with a filter anchored on `commit`, the read set is `selected ∪ {commit}` when
  `own_values_only` is true. Write the test against that rule.

### 4f. Operational Readiness

Rollback is one line (remove the attribute from `InfrahubBaseQuery`); no migration; per-query metrics
come from the Query `name`.

- **E5 (💡)**: The stub logs a warning on every call. A Branches card that refetches on focus or polls
  turns that into a warning per second per open tab. Log once at import time from the stub module (a
  module-level `log.warning` when the module is loaded into the schema) and at `debug` per call.

### 4g. Dependencies & Integration Risks

Additive GraphQL change; `sync_with_git` on `InfrahubBranch` is additive too. No new dependency.

- **E8 (💡)**: Increment C changes three behaviours of `get_repositories_commit_per_branch` at once:
  the `-global-` key disappears, `RepositoryData.repository` becomes the default-branch node instead of
  whichever branch the old loop visited last, and the per-branch `ref` of read-only repositories is no
  longer read (it never was reliably, for the same reason). Callers in `infrahub.git.tasks` and
  `infrahub.computed_attribute.gather` are unaffected on inspection, but assert it: extend the sync test
  to check `repository.default_branch` and `location` come from the default branch, and add a
  computed-attribute gather test that resolves `branches[branch.name]` for every non-global branch.

## Cross-Lens Insights

- **X1 (🎯)**: `own_values_only` semantics (P2 + FR-008 interplay). Product: a filter should not change
  meaning with the columns shown. Engineering: a selection-dependent filter forces the reader to widen
  the attribute set unpredictably and makes FR-008 untestable as written. Pinning the filter to
  `commit` resolves both and is a one-line change in spec, SDL and contract.
- **X2 (🎯)**: The `hfid` anchor (E1). Product: the frontend would wire an argument that always fails.
  Engineering: dead argument in a contract shipped as final. Replace with id-or-name lookup.
- **X3 (💡)**: The stub window (P3 + E5). The value is real (frontend unblocked weeks early); the risks
  are confusion and log noise, both cheap to contain: preview note in the SDL description, log once,
  Jira subtask for removal, release rule already in the plan.
