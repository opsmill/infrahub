# Critique Report: Numbers you give the pool

**Date**: 2026-09-16
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ **PROCEED WITH UPDATES** *(5 of 6 must-address items applied; X1/P2 overruled by the user — see Resolution)*

---

## Executive Summary

The spec and plan are unusually well-grounded: every architectural claim was verified against
`develop`, the research phase found and corrected eight factual errors in the source PRD, and the two
confirmed data-integrity defects are reproduced rather than asserted. The dependency ordering is
forced by the problem rather than chosen, and the one invariant the design withdraws is identified
and reconstructed deliberately. Constitution alignment is strong; the three gated principles are
gated on conditions that are already carried as work.

Five findings block task generation. Four are engineering defects the design would have shipped:
an **ordering bug in the migration** that leaves a losing pool's `HAS_SOURCE` edge winning the read
slot forever, a **missing interface** that makes the ledger's match-close-create unimplementable as
specified, a **missing index** on the edge that is about to move onto a hot generic read path, and
an **unstated irreversibility**. The fifth is a product gap: the release deliberately regresses
behaviour for anyone who does not attach, tells them to "attach your hand-set numbers", and
simultaneously deletes the only code that could tell them which numbers those are.

None is fundamental. All five are resolvable inside the current design, and the remedies are small.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | ✅ | Boundaries are clean: the resolver decides, the ledger writes, the reporter computes, the executor does I/O. Each new module is pure and unit-testable, which is the point — the decision table *is* the contract. No circular dependencies; the P1 dependency is inverted behind a seam. | No action. |
| E2 | 🎯 | **`get_resource` cannot implement match-close-create as specified.** `CoreNumberPool.get_resource(db, branch, attribute: AttributeSchema, identifier: str)` receives the attribute *schema* and a node uuid — it never sees the `Attribute` **vertex**. Both the new close-before-create and the re-anchored idempotency lookup need that vertex. `NumberPoolGetReserved`'s identifier-keyed lookup is also what makes re-creating the same node reuse its number, and the contract says release does no identifier matching, so the two halves disagree. | Thread the attribute vertex id through `get_resource` / `reserve` / the ledger, and restate the idempotency lookup as "is there a live record from this pool on **this attribute**". Name the signature change in the plan so it is not discovered during implementation. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | **Migration behaviour ordering bug.** Behaviour 4 deletes a legacy pool `HAS_SOURCE` only *"where a live record from that same pool exists for that same attribute"*. Behaviour 3 collapses multi-pool records, killing the losers. If 3 runs first, the losing pool A no longer has a live record, so **A's `HAS_SOURCE` survives the predicate** — and then wins the read slot forever, making the attribute report pool A while pool B actually tracks it. Exactly the failure FR-030b exists to prevent, reintroduced by ordering. | Evaluate behaviour 4's predicate against records **live at the start of the migration**, or run 4 before 3. Add a component test: two pools on one attribute, both with legacy `HAS_SOURCE` edges; after migration the attribute reports the surviving pool and **no** stored source edge. |
| E4 | 💡 | The `m066` partial-commit hazard is correctly flagged as "do not repeat", but the plan does not say what to do instead for a four-phase `ArbitraryMigration`. | Specify: one transaction per behaviour, with the phase's count read back before committing, and no `return` from inside a transaction context. |
| E5 | ✅ | `NumberPoolGetAllocated` applying no status/branch predicate to the reservation edge is caught as R8 rather than buried in "rewrite the query". That is the kind of latent-becomes-live defect this review exists to find, and it was already found. | No action. |

### Performance & Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E7 | 🎯 | **`IS_RESERVED` has no index, and is about to land on a hot generic read path.** `core/graph/index.py::rel_indexes` gives every property edge type a `branch` range index — `HAS_ATTRIBUTE`, `HAS_VALUE`, `IS_RELATED`, `IS_PROTECTED`, `HAS_SOURCE`, `HAS_OWNER`, `IS_PART_OF` — and **nothing for `IS_RESERVED`**. That was defensible while the edge was only touched by pool queries. FR-030b puts an `OPTIONAL MATCH` for it inside `NodeListGetAttributeQuery`, which runs for **every attribute of every kind** read with metadata, the overwhelming majority of which have no reservation at all. | Add `IndexItem(name="reserved_branch", label="IS_RESERVED", properties=["branch"], type=IndexType.RANGE)`. Then measure the source-derivation cost on a metadata read over a kind with **no** pool, not only on pooled reads — that is the blast radius, and the plan currently only reasons about pooled attributes. |
| E8 | 💡 | FR-036a's benchmark is well-scoped, but the plan measures only *allocation*. The same per-branch resolution lands in `NumberPoolGetUsed`, which backs the utilization read — a user-facing query with no lock but a wider fan-out. | Benchmark the utilization read alongside allocation, or state explicitly why it is not a risk. |

## Verdict

⚠️ **PROCEED WITH UPDATES**

Six must-address items, all resolvable within the current design. Three (E2, E3, E7) are concrete
defects the design would otherwise have shipped; one (P7) is a documentation gap on an irreversible
operation; two (P2, X1) are one product gap with one cheap remedy.

No finding calls the architecture into question. The re-anchoring decision, the dependency ordering,
the seam to P1 and the two pure modules all survive both lenses.
