# Critique Report: Git history-rewrite reconciliation

**Date**: 2026-09-29
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The spec and the plan are sound. The problem is real and evidenced by a reported bug (IFC-1450) and
a GitHub issue (#6299). The solution reuses two primitives that already exist rather than building
new ones. The branch-local decision is correct and is tested rather than assumed. The research
checked every claim against the base branch and corrected two of the facts it was handed.

Six items must be addressed before task generation. Four of them are contract gaps that would
produce a working feature with a broken edge: an unpopulated required field on a message that
older workers still read, an unstated ordering between a cache write and a workflow submission, an
unpinned lock scope around a read-then-increment, and a success criterion this epic cannot meet as
worded because the surface it names is out of scope. The other two add a requirement each: the loud
failure the PRD names in its edge cases but no requirement covers, and the log line that is the
only thing making the reconciliation explicable while INFP-671 is unbuilt.

None of them is an architecture problem. All six are additions to text, not changes of direction.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | ✅ | The package shape mirrors `git/refs_check/` from PR #10669, so a reviewer who has read one can read the other. The detector, recorder and models import no git library, which is what makes them unit-testable without a database. The classification is a four-member enum, so `REWRITE` and `RETARGET` cannot collapse at a call site. | None. |
| E2 | 🎯 | The plan says the recorder "runs under the repository lock, taken by its caller" but never pins **which** locked phase. In the sync path, `collect_pending_imports` runs under the lock and the per-branch import re-acquires it. A recorder call placed between them would do its read-then-increment of `rewrite_count` unlocked, and two workers could write the same count. | State the lock scope explicitly in `contracts/internal-interfaces.md` section 2: the recorder runs inside the same lock acquisition that applies the branch import, never between acquisitions. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | `RefreshGitFetch.infrahub_branch_name` and `.infrahub_branch_id` are required fields. A coalesced message must still populate them, or a worker running the previous code fails to construct the message at all. The plan says the fields "stay" but does not say they stay **populated**. | State that a coalesced message populates the single-branch fields from its first pair. A worker on the old code then converges one branch instead of none, which is a degradation and not a failure. |
| E4 | 🎯 | The suppression marker is written by the mutation "after the update succeeds". The same mutation submits the read-only pull and import workflows. If the marker write lands after the submission, the import can reach the recorder first and record a spurious rewrite on a deliberate re-target. | State the ordering: the marker is written after the update and **before** any workflow is submitted. |
| E5 | 💡 | One pair failing inside the coalesced handler is stated to not stop the rest, but the outcome for the failed pair is not stated. A silently skipped branch on one worker is exactly the divergence this feature removes. | State that a failed pair is logged with its branch, and that the branch converges on first contact through the pull-path rule of FR-005. That is the self-healing property doing its job. |
| E6 | ✅ | The prerequisite on PR #10465 is correctly scoped to the one slice that needs it, rather than blocking the whole epic. | None. |

### What three passes say about the process

Pass one read the documents and found six contract gaps. Pass two read the code and found seven
correctness errors the first pass could not see. Pass three found that pass two's own fixes were
applied in one file out of three, plus one new error introduced by a pass-one fix whose reasoning
was never checked against the code.

Two rules follow, and they cost less than a review round each:

1. **A design review that never opens the implementation will keep producing confident, wrong
   symbol names and file paths.** Four of the thirteen items in pass two were exactly that.
2. **A spec directory restates each decision across six or seven files, so changing one is a
   directory-wide edit.** `AGENTS.md` already says this. Grep the whole directory for the old
   statement before committing a change to any decision. Pass three existed almost entirely
   because pass two did not.
