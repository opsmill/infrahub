# Contract: Machine-Readable Catalogue Schema

**Feature**: INFP-468 | **Created**: 2026-05-19 | **Status**: v1

This file pins the format of `schema/error-catalogue.json` — the build artefact that the frontend binding generator (in-repo) and the SDK binding generator (cross-repo) both consume.

---

## File location

Committed to `schema/error-catalogue.json`. Regenerated by `uv run invoke backend.export-error-catalogue` from the in-process catalogue. Drift between this file and the Python catalogue is caught by CI (per FR-009 and research R-009).

---

## Top-level structure

```jsonc
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "infrahub_catalogue_version": "1",   // bumped on incompatible wrapper changes; codes have their own per-entry stability
  "codes": {
    "NODE_NOT_FOUND": { /* CatalogueEntry, see below */ },
    "AUTHENTICATION_REQUIRED": { /* ... */ },
    // ... 9 entries plus UNDEFINED_ERROR ...
    "UNDEFINED_ERROR": { /* ... */ }
  }
}
```

---

## Per-code entry shape

```jsonc
{
  "description": "<human-readable, max ~200 chars>",
  "stability": "stable" | "evolving",
  "http_status": <int>,
  "data_schema": {
    // A complete JSON Schema (draft 2020-12) describing the `extensions.data` payload
    // for this code. Generated by Pydantic's BaseModel.model_json_schema().
    "type": "object",
    "properties": { /* ... */ },
    "required": [ /* ... */ ],
    "additionalProperties": false,
    "title": "<PayloadModel class name>"
  }
}
```

### Field rules

| Field | Type | Required | Notes |
|---|---|---|---|
| `description` | string | Yes | One-sentence human description. Rendered into the docs page. |
| `stability` | enum | Yes | `"stable"` or `"evolving"`. Determines what consumers can rely on. |
| `http_status` | integer | Yes | Logical HTTP status; same value the formatter emits on the wire. |
| `data_schema` | object | Yes | A complete JSON Schema document describing the `data` payload. `additionalProperties: false` is mandatory. |

## Evolution rules

The wrapper version (`infrahub_catalogue_version`) follows these rules:

- **Same version**: codes may be added (FR-014 allows) and existing codes may receive additive optional fields (FR-019 allows).
- **Bump version**: only if the wrapper shape itself changes (e.g. adding a `deprecated_at` field at the entry level, or moving `http_status` into `data_schema`). Bumping a wrapper version requires the same deprecation policy as removing a code.

The per-code `stability` field is the consumer's relevant signal day-to-day; the wrapper version is rarely touched.

---

## Consumer expectations

- The schema is committed and pinned in `schema/error-catalogue.json`. Consumers may rely on its path and shape.
- The schema is also expected to ship with each release artefact (release pipeline change tracked in plan.md Phase 3 — R-012).
- Consumers MUST treat unknown codes as `UNDEFINED_ERROR` semantics (typed-fallback branch). This includes the case where a future Infrahub adds a code the consumer's bindings haven't been regenerated for.
