# Research: Licensing Resource-Allocation Telemetry

Phase 0 decisions. Each resolves an unknown surfaced while planning against the existing telemetry code, the heartbeat service, and the deployment topology. No `NEEDS CLARIFICATION` markers remain.

## D1 — psutil promoted from dev-only to a runtime dependency; no new package added

- **Decision**: Read host CPU/RAM via `psutil` and the enforced limit via stdlib `/sys/fs/cgroup` file reads.
- **Correction (found during CI, not planning)**: `psutil==6.1.0` was already pinned in `pyproject.toml`, but only under `[dependency-groups] dev` — the production images are built with `uv sync --frozen --no-dev`, so the shipped `task-worker`/`api_server` containers never had it installed. This surfaced as every Docker-stack-based CI job (`backend-docker-integration`, all `E2E-*`) failing with the Prefect worker unable to load its collection (`ModuleNotFoundError: No module named 'psutil'`) — not a CI quirk, a real gap that would have shipped a broken feature. Fixed by moving the `psutil==6.1.0` entry from `dev` to `[project] dependencies` and regenerating `uv.lock` (package version unchanged; no new third-party package pulled in).
- **Rationale**: cgroup quota/usage is not exposed by psutil and must be read from the pseudo-filesystem regardless — that read is stdlib. No new package is added to the dependency set, but promoting an existing dev-only pin to a runtime dependency is itself an Ask-First "new dependency" change (confirmed with the user before editing `pyproject.toml`), since it is new to what ships in production.
- **Alternatives**: adding a cgroup helper library — rejected (a few lines of file parsing do not justify a dependency + review gate).

## D2 — Logical cores, never physical

- **Decision**: All core counts are logical CPUs (vCPUs). Server/workers use `psutil.cpu_count(logical=True)` (a dev-only pin promoted to a runtime dependency, D1; a cleaner interface than, and equivalent to, `os.cpu_count()`); the database uses the JMX `AvailableProcessors` already collected.
- **Rationale**: (a) the enforced limit lives in cgroup, which is denominated in logical CPU-time only; a physical `available` would be un-comparable to a logical `assigned`; (b) the database figure already shipped is logical (`Runtime.availableProcessors()`); (c) tiers, cloud vCPUs, and container limits are all logical. `psutil.cpu_count(logical=False)` also returns `None` under most containers.
- **Alternatives**: physical cores — rejected on all three counts above.
- **Correction (comparability finding, post-implementation)**: `psutil.cpu_count(logical=True)` is not container-aware, while the `Runtime.availableProcessors()` behind the database figure has been since JDK 10 — under a cgroup CPU quota the JVM reports the quota (rounded up) and psutil the host. Measured on an 18-core host with `--cpus=2`: JMX 2, psutil 18. The same field therefore meant *usable cores* for the database and *host cores* for server/workers, which defeats FR-002. Fixed by capping the server/worker `processor_available` at the enforced quota (`min(host logical count, quota)`, the JVM's rule), so `processor_available` is the CPUs a component can actually use for every component. A later correction split the rounding rather than reusing the JVM's: the quota keeps its fraction, `processor_assigned` rounds it **up** (an audit must never understate the enforced cap) and `processor_available` rounds it **down**, floor 1 (a fraction of a core cannot keep a whole one busy). Under a fractional quota the server/worker figure therefore sits one below the database's, which rounds up for both — the one place the figures are not identical. `processor_assigned` is unchanged — the quota rounded up, `null` when unenforced — and may exceed `processor_available` under a fractional quota, under an affinity mask narrower than the quota, or when a quota is set above the host's count. The uncapped host count is no longer in the payload. A `cpuset` restriction (e.g. `docker run --cpuset-cpus` with no `--cpus`) pins the process to specific CPU IDs without setting a quota, so the quota cap alone misses it and the JVM's own container support does react to it; `processor_available` is also capped by the process's CPU-affinity mask (`psutil.Process().cpu_affinity()`, `None` — no additional restriction — where unsupported, e.g. macOS).

## D3 — `processor_assigned` = the configured limit, `null` when not enforced (live read, no fallback)

`assigned` means *configured* (confirmed by the backend owner). Infrahub does not enforce any core limit itself, so each `assigned` field is `null` wherever its limit is unset and becomes a real number once one is configured: the database figure where the `infrahub-enterprise` chart presets set `worker_limit` (4, 8 or 16), and the server and worker figures wherever a container CPU limit is set. Two rules:

1. `assigned` is **never** back-filled from `available` (FR-003). An unenforced component genuinely has no assignment; fabricating one erases the over-provisioning signal the audit needs. Where no limit is set, `assigned == available` *in meaning* (both reflect the same unbounded infra) — so we report the measured `available` and a `null` `assigned`, not the same number duplicated into a field that implies a limit that isn't there.
2. Each `assigned` field is a **live read that returns `null` wherever its limit is unset** and lights up automatically once the corresponding limit is configured — carrying a comment documenting the intended source. Not a dead stub, not a fabricated value.

- **Database** — source is the Neo4j setting `server.cypher.parallel.worker_limit`, read over Bolt with `SHOW SETTINGS YIELD name, value WHERE name = $setting_name RETURN value AS value`, the setting name passed as a query parameter. It defaults to `0` (auto = use all cores), which maps to `null` (not enforced). This is the confirmed intended knob — "we do not enforce this value today (and we should)". When a tier sets it to a positive value, the read returns that number with no code change — and the `infrahub-enterprise` chart presets now do, setting it to the preset's Neo4j CPU request (4, 8 or 16) so the parallel runtime stops sizing itself from the whole node (infrahub-helm#93). The setting bounds the parallel runtime's worker threads only; Neo4j still runs without a CPU limit and can burst above it for other work. (Supersedes the earlier `server.threads.worker_count` candidate, which is HTTP-only and does not influence Bolt/query execution.)
- **Server / workers (container CPU cap)** — source is the container cgroup CPU quota (v2 `cpu.max`, v1 `cpu.cfs_quota_us`/`cpu.cfs_period_us`), read locally by each process. `max` / `-1` (unlimited) → `null`. The sized docker/helm configs set the replica count, not `limits.cpus`, so this is `null` until a CPU limit is configured. Fractional quotas (e.g. `--cpus=1.5`) round **up** to the next whole core (integer field; conservative for an audit).
- **No separate "not limited" marker** — `processor_assigned` is `null` both where no limit is enforced and where the limit cannot be read; there is no special value for either. For one server or worker reading the pair of CPU figures tells them apart: `processor_available` set and `processor_assigned` `null` means no CPU limit is enforced, and both `null` means the CPU limit could not be read, since an unusable limit file nulls both. One exception: where psutil cannot count the host's CPUs and the affinity mask is unreadable, `processor_available` is `null` even with no limit enforced. For the database, `null` covers an unset setting and a failed read alike; the failed read is logged.
- **Number of workers** — Pete's "number of workers configured" is the existing `workers.total`/`active` count, which telemetry already reports; it is distinct from the container CPU cap above and is a real value today (see D14). The new `server` and `task_workers` blocks break it down by component (D17).

## D4 — Memory: reuse the DB representation (`memory_total` + `memory_available`)

- **Decision**: memory is reported as `memory_total` (capacity — cgroup `memory.max` when limited, else `psutil.virtual_memory().total`) and `memory_available` (free — the smallest `max(0, memory.max − memory.current)` over every level that enforces a limit when limited, else `psutil.virtual_memory().available`), in bytes — the exact fields and semantics the database `system_info` already uses. Usage is derived by the consumer as `memory_total − memory_available`; there is no `*_used` field.
- **Rationale**: adopting the existing `memory_*` names/semantics for the new components makes DB, server, and workers byte-for-byte comparable (the naming decision, D14), and matches how the DB JMX (`TotalMemorySize` / `FreeMemorySize`) already reports. Pete's "RAM used" is preserved as a derived value, consistent with the DB.
- **No `memory_assigned`**: memory has no enforced-limit field — the container memory limit surfaces as `memory_total` capacity. Only `processor_assigned` carries the FR-003 no-fallback-null rule.

## D5 — cgroup v2 primary, v1 fallback, whole-host figures otherwise; resolve the process's own cgroup path

- **Decision**: Read cgroup v2 first (`cpu.max`, `memory.max`, `memory.current`); fall back to v1 (`cpu.cfs_quota_us` + `cpu.cfs_period_us`, `memory.limit_in_bytes` + `memory.usage_in_bytes`), read under each controller's own mount, which the reader discovers under `/sys/fs/cgroup`, including a comma-joined co-mount such as `cpu,cpuacct`. Where neither is present (non-Linux dev, unusual mounts), memory falls back to psutil's whole-host figures and `processor_available` to the host's count capped by CPU affinity; only `processor_assigned` is `null`.
- **Correction (review finding, post-implementation)**: the v2 files were initially read only at `/sys/fs/cgroup` itself. That is correct under a *private cgroup namespace* (the default on Docker 20.10+/modern K8s, where the apparent root *is* the container's cgroup) but wrong without one (older runtimes on v2, explicit `cgroupns: host`, bare-metal systemd services with unit limits): the v2 root cgroup carries no `cpu.max`/`memory.max` at all, so a limited component reported `processor_assigned = null` and — worse for an audit — the whole **host's** memory as `memory_total`. Fixed by resolving the process's own cgroup from the `0::<path>` line of `/proc/self/cgroup` and consulting **every level up to the root**, taking the most restrictive limit (a limit may be enforced on an ancestor slice); free memory is the smallest headroom (limit minus usage) across every level that enforces a limit, since an ancestor's limit is charged against its whole subtree (D4). Any resolution failure falls back to the previous root-only read.
- **Correction 2 (review finding, post-implementation)**: a limit file that exists but fails to read (permission denied, I/O error) was treated the same as one that is absent, so the ancestor walk silently kept going and could return a looser ancestor's value in place of the leaf's real, unreadable one — understating the enforced restriction for an audit that must never overstate what's available. Fixed by distinguishing "file does not exist at this level" (`FileNotFoundError`, the expected case for most levels) from any other read failure: the latter now stops the walk and reports the metric as unknown (`null`), with a warning logged, instead of falling through.
- **Known limitation**: limits set *above* a private namespace root (e.g. a K8s pod-level limit when the container itself has none) are invisible from inside the namespace and cannot be self-reported — a fundamental property of self-observation, not an implementation gap.
- **Rationale**: production runs containers (v2 on current hosts, v1 still common); developer machines are macOS (neither) and correctly report `null` for `assigned`. v1 `memory.limit_in_bytes` reports a sentinel near `INT64_MAX` when unlimited — treat values at/above a high threshold as no limit at that level, so with no other limit the machine's memory is reported. Under v1 each controller mounts separately and names the process's own path on its own `/proc/self/cgroup` line, so the directories are resolved per controller — including comma-joined co-mounts such as `cpu,cpuacct` — and every level up to that controller's mount is consulted, most restrictive wins, the same ancestor walk as v2. A container whose own controller directories are bind-mounted reports the root path, which collapses that walk to the mount itself: the layout the earlier root-only read assumed, and the fallback when resolution fails.

## D6 — Self-report through the existing heartbeat channel (storage superseded by D18)

- **Decision**: Each process writes its own reading to a new cache key `workers:resources:{component}:worker:{WORKER_IDENTITY}` alongside the existing `workers:active:` key, at heartbeat time, with the same short TTL. The value is the JSON of a per-process reading including a **host identifier**. The gatherer reads these keys with a separate `workers:resources:*` key scan and a multi-get of their values.
- **Rationale**: reuses the mechanism telemetry already uses to know which workers are alive; no new transport. The read later moved to a schedule of its own (see the correction below). Reading own resources is local and cheap. A component that fails to read retries a small bounded number of times (FR-005) and, failing that, writes a reading with every figure `null`.
- **Alternatives**: a dedicated resources query flow — rejected (duplicates the heartbeat's liveness scan; more moving parts).
- **Correction (liveness moved to its own thread)**: the liveness heartbeat now runs on a dedicated thread that only touches the cache, so a flow blocking the main loop cannot make a worker look dead. The resource write stays with it — alongside the active key, same expiry — but the *read* moved: a schedule on the main loop (every 5 minutes, D12) starts the reading on a separate thread and publishes it, and each beat writes the latest published one. The cgroup and psutil reads therefore stay out of the liveness path, where a blocking read could not be cancelled by the beat's deadline, and a worker stalled in a long merge keeps reporting its last reading for as long as it is alive. The alternative of reading and writing on a main-loop schedule was rejected because a stalled worker's resource key would expire while its liveness key did not, dropping its reading while still counting it active.
- **Correction (review finding, post-implementation)**: the schedule and the startup heartbeat first ran the read on the main loop itself, which held up requests and flows for as long as each read took. The read now runs on a separate thread that the main loop starts and waits for. Two reads never run at once, because the startup read finishes before the schedule starts and the schedule waits for each read before it starts the next.
- **Superseded by D18**: the heartbeat no longer carries the reading. The read that takes it stores it, with a 2-hour expiry, and the report keeps only the readings of active workers.
- **Superseded in part by D19**: the reading carries no host identifier, and a read that fails on every try stores nothing instead of a reading with every figure `null`.

## D7 — Host identifier for grouping readings by container (superseded by D19)

- **Decision**: Host identifier = the hostname (`socket.gethostname()`) followed by the process's PID namespace, read from the `/proc/self/ns/pid` link, for example `api-1/pid:[4026532001]`. Docker and Kubernetes give each container its own PID namespace by default, and every process inside it, gunicorn's forked workers included, shares it. Where the link cannot be read (outside Linux), the identifier is the hostname alone.
- **Rationale**: identifies which readings share one container's allocation, so its figures can be divided between them (D16). Stdlib, no privilege needed.
- **Assumption**: readings are grouped by component before host, so a pod whose containers run different components is still divided correctly. Two containers of the same component are still treated as one when they share both the hostname and the PID namespace (for example both run with Docker's `--network=host --pid=host`, or Kubernetes `hostNetwork` and `hostPID`), or when they run on different machines under one fixed hostname and get the same namespace number, since each machine numbers its namespaces separately.
- **Correction (review finding, post-implementation)**: the identifier was first the hostname alone. Separate containers of one component can share a hostname: Docker host networking gives every container the machine's hostname, so does Kubernetes `hostNetwork`, and a fixed `hostname:` on a scaled Compose service gives every replica the same one. Their readings were grouped as one container, so each share was divided by the processes of all of them and `per_worker × active` understated the total. The shipped Compose files and Helm chart do not do this. The control-group path was rejected as the identifier, because under a private cgroup namespace every container sees `/`.
- **Superseded by D19**: readings are no longer grouped by container, so the host identifier is gone. Each reading carries how many processes share its container, and the report sends one container's figures undivided with that count.

## D8 — Aggregate over distinct hosts, not processes (superseded by D16)

- **Decision**: For the `server` (api_server) and `workers` (git_agent) rows, group active processes' readings by host identifier, take one reading per host (readings within a host are identical), and **sum across distinct hosts**.
- **Rationale**: `api_server` runs several gunicorn processes in one container sharing one cgroup; `git_agent` runs one process per container (`replicas: N`). Dedup-by-host counts each container's cores exactly once for both. See Complexity Tracking in the plan.
- **Worker count**: `workers.total`/`active` count every worker process; the `server` and `task_workers` blocks count each component's own processes (D17).

## D9 — Aggregation null and undercount rules (superseded by D16)

- **Decision**:
  - No host reported a given field → that aggregate field is `null` (unknown). The aggregate has no worker count of its own to tell a genuinely empty fleet from one where nothing reported, so both collapse to `null`; in practice at least one worker always runs (telemetry itself runs in one).
  - A host whose self-read failed writes a reading with every figure `null`; such a reading is **dropped** before summing, so it undercounts like a non-reporting host rather than nulling the whole field.
  - Some hosts reported, some did not → **sum the reporters** (undercount tolerated per FR-005); the separately-tracked task-worker count still includes the silent host's process, but the aggregate does not record how many hosts contributed, so the gap is not directly computable; an exact reporter count remains a candidate for the next gated `payload_format` bump (D13).
  - For a field where any *contributing* host is `null` because it is genuinely unbounded (e.g. one worker host has no cgroup CPU quota) → the aggregate for that field is `null`: a fleet containing an unbounded node has no finite total.
- **Rationale**: keeps `null` meaning "unknown / unbounded" throughout (no separate measured-empty `0` the consumer would have to distinguish), and keeps a partly-silent fleet reporting a finite, if low, figure rather than nulling the whole thing.

## D10 — Payload version bump + receiving-service coordination (superseded by D13)

- **Decision**: Increment `TELEMETRY_VERSION` (`payload_format`, currently `"20260628"`) to the change date. All new fields are additive; no existing field is renamed or removed.
- **Rationale**: FR-008. The receiving cloud processor + data mart must tolerate the new block and the new version — a cross-team dependency tracked outside this branch. Additive-only + version bump lets older ingestion ignore what it does not recognise rather than break.

## D11 — Reuse `safe_metric` for independent degradation

- **Decision**: Wrap the feature's gather-side reads in the existing `safe_metric` helper so one failing source yields `null` for its own figures only and never blocks the snapshot (FR-006): the database `processor_assigned` read, and the scan of worker resource readings, whose failure nulls `processes_per_container` and every `per_container` figure in the `server` and `task_workers` blocks (D19; first every `per_worker` figure). Choosing the reading to report is a pure computation over the scanned readings and is not wrapped. Per-field failures inside a process's own read are caught by the reader, not by `safe_metric` (FR-005).
- **Rationale**: single degradation boundary already established in the parent telemetry work; no new error-handling pattern.
- **Not covered**: the JMX query behind the existing `system_info` figures, the database gather around it, and the worker-count read are not wrapped — a gap that predates this feature — so a failure in any of them aborts the snapshot.
- **Component self-read logging**: the per-process self-read (started by the main loop at startup and every 5 minutes, run on a separate thread) is a path *separate* from `safe_metric` — it is not wrapped by it. When its bounded retries are exhausted, it MUST log a warning carrying the component type, the worker identity, and the error text, and store nothing, so the last stored reading is kept (FR-005, D19; first it stored a reading with every figure `null`). Without this, a worker that silently stops reporting resources shows only as an old or missing reading, with no way to trace which worker or why; the log closes that gap. Warning level (a tolerated degradation, consistent with the existing `safe_metric` warning), structured context, no sensitive data (cores/RAM/worker-id only).

## D12 — Cache the resolved cgroup path and host CPU count; re-read the limit values every 5 minutes

- **Decision**: The resolved cgroup directory list and the host's logical CPU count (`psutil.cpu_count(logical=True)`) are constant for a process's lifetime — neither can change without a container restart — so they are read once (at process start / first heartbeat) and cached. The `host` container name was read once with them until D19 removed it. `processor_available`, `processor_assigned`, `memory_total`, and `memory_available` are re-read every 5 minutes, on a separate thread the main loop starts, and stored by that read (D18; first carried by the liveness heartbeat, D6).
- **Correction (review finding, post-implementation)**: the original decision cached all four figures for the process's lifetime, on the reasoning that they never change. That is false for a *live* limit reconfiguration — `docker update --cpus=...`, a Kubernetes in-place pod resize, a systemd unit reload — which changes the content of `cpu.max`/`memory.max` at an already-resolved cgroup path without restarting the process. A cached reading made such a change invisible until the process restarted, which defeats the feature's purpose: an audit against a currently-contracted tier should reflect a limit raised or lowered after the worker started, not require a restart to notice. Fixed by splitting what is genuinely static — the cgroup *path* (resolving it means walking `/proc/self/cgroup` and its ancestors, which cannot move without a restart) and the host's logical CPU count — from what can be reconfigured live — the *values* inside `cpu.max`/`memory.max` at that path. The path stays cached; the values are re-read each call.
- **Rationale (what stays cached)**: re-walking `/proc/self/cgroup` and the ancestor directories on every read would be wasted work for a path that cannot change short of a restart, so that resolution — and the host CPU count — is still read once.
- **Rationale (what is now re-read)**: re-reading a handful of small cgroup files (`cpu.max`, `memory.max`, `memory.current`, typically 1-3 directories deep) is a few file reads, and it reflects a live limit change in the next snapshot instead of requiring a process restart.
- **Correction (review finding, interval)**: the values were first re-read every 10 seconds. The snapshot is taken once a day, so that was far more often than it needs, and every read of a limit file that exists but cannot be used logs a warning, which at 10 seconds is 8,640 identical warnings a day per process. Every 5 minutes still reflects a live limit change in the next snapshot. The interval only sets how old a reading can be: the heartbeat wrote the latest reading again on every beat, and since D18 each read stores its reading for 2 hours, far longer than the 5 minutes between reads. The cost is that `memory_available`, the one figure that moves on its own, can be up to about 5 minutes old, and a process whose read at startup fails has no reading until a later read succeeds, since a failed read stores nothing (D19).

## D13 — Additive-only is the invariant; the version bump is gated

- **Decision**: The payload change is additive-only (no existing field renamed/removed/retyped). The `payload_format` identifier is **not** incremented until the receiving service confirms it tolerates the new fields; until then the fields ship under the existing version.
- **Rationale**: a version-strict receiver could break on an unexpected version string — the exact regression to avoid. Additive-under-existing-version guarantees current ingestion is untouched, and the bump becomes a coordinated follow-up rather than a unilateral producer change.

## D14 — No parallel `resources` block; extend `system_info`, add one block per component (amended by D17 and D19)

- **Decision**: Do not add a parallel `resources` block. Extend the database's existing `system_info` with `processor_assigned`. Add a `server` block for the api_server, which has no existing representation, and a `task_workers` block for the task workers (D17). Each carries its own `total`/`active`, a `processes_per_container` count and a `per_container` object with the four figures (D19). All new fields **reuse the existing `system_info` names** (`processor_*`/`memory_*`), so every component is represented identically. The overall worker count stays the existing `workers.total`/`active`, unchanged.
- **Rationale**: a parallel block duplicated DB cores/RAM (already in `system_info`) and the worker count — a confusing second API surface. Keeping each component's resources next to its own count, with the existing field names, adds nothing redundant and keeps DB/server/task workers directly comparable. Pete's ask is DB + workers; `server` is an explicitly-chosen future-proofing addition.
- **Amended by D17**: the task-worker figures first extended the existing `workers` block, under `per_worker`. They moved to the new `task_workers` block so that `workers` keeps exactly its existing fields and meaning.
- **Amended by D19**: the four figures were first one worker's share of its container, in a `per_worker` object (D16).
- **Accepted trade-off (superseded by D15, then by D17)**: `workers.total`/`active` counted all worker processes (api_server + git_agent) while the new `workers` resource fields covered the git_agent fleet only. Since D17, `workers` carries no resource fields, so the mismatch is gone. (Naming is *not* a trade-off — the new fields reuse the legacy `processor_*`/`memory_*` names, so the payload is uniform.)

## D15 — Each block counts its own component's processes (reversed by D17)

- **Decision**: `workers.total`/`active` count task-worker (git_agent) processes only, and `server` gains its own `total`/`active` for the API server's processes. A consumer wanting every worker sums the two.
- **Rationale**: with `workers.total` spanning both components while the block's resource fields covered task-workers alone, the block described two populations at once. Every downstream reading had to be hedged — no per-worker average, no undercount check, a warning in the contract against the obvious division — and review kept finding documents that drew the wrong conclusion from it. Scoping each block to one component makes both self-describing, and the old figure stays one addition away.
- **Why this is allowed under D13**: the key and type of `workers.total`/`active` are unchanged; only the population narrows. A snapshot carrying `server` is unambiguously on the new scoping, since no earlier release emits that block, so a consumer can continue an all-workers series without a `payload_format` bump to tell the two apart.
- **Attribution**: a process's component is read from the component name its own cache keys carry (`workers:active:`, `workers:resources:`, `workers:schema_hash:`), parsed as the segment before `:worker:` and accepted only for a known component. The generic `workers:worker:` presence key names none and lasts two hours after a process's last beat. The `workers:schema_hash:` keys do name the component and also last two hours, but are rewritten by the branch-refresh schedule, which waits 900 seconds after each run (other events, such as a schema change, can rewrite them sooner), so they expire before the presence key by the time between the process's last schema-hash write and its exit. That is normally up to about 15 minutes, and longer when a refresh failed (a failed refresh skips the schema-hash write) or a long flow blocked the main loop, where the schedule runs, while the heartbeat thread kept the presence key alive. Since D18 the `workers:resources:` key also lasts two hours and is rewritten by every 5-minute read, which shortens that stretch to normally at most about 5 minutes; a long flow blocking the main loop still lengthens it, and so do failed reads, since a failed read stores nothing (D19). An exited process counts in neither block only for that last stretch of its tail. This holds with the background runner enabled, the default; with it disabled there is no recurring heartbeat either, so the worker counts are not meaningful at all. `active` is always attributable, since the heartbeat key itself names the component.
- **Alternatives**: keeping `workers.total` as-is and adding separate per-component count fields — rejected: it preserves the two-population block this decision exists to remove, and adds a field that duplicates what the sum already gives.

## D16 — Per-worker share instead of fleet totals (superseded by D19)

- **Decision**: The `server` and `task_workers` blocks each carry a `per_worker` object with the four figures: one worker's share of its container. The gatherer takes the most complete healthy reading of the component (the one with the most non-null figures) and divides each of its figures by the number of readings from the same host, failed ones included, rounding the processor figures to two decimals and dividing memory with floor division to whole bytes. A failed reading (every figure null) is never chosen, but it still counts as a sharer: it keeps the process's container name, and the process still uses part of that container, so leaving it out would overstate the share. With no usable reading, every figure is null. `per_worker × active` is the component's total: a task worker runs one process per container, so its share is the whole container, while the API server runs several gunicorn processes in one container (4 by default), so each gets a fraction. Replicas of a component are assumed to share one configuration, so one container's reading stands for all of them. The scan returns every reading per component rather than one per host, and `host` stays on the reading, never in the payload, as the grouping key for the share. Supersedes D8 and D9.
- **Rationale**: summing over the fleet needed per-host deduplication, two different null rules (sum the reporters for three figures, all-or-null for `processor_assigned`), and an undercount whenever a host stayed silent, which a consumer could not detect from one snapshot. One worker's share and the existing `active` count give the same total with none of that. Choosing the most complete reading means one process's failed read of a single field does not blank a figure the other processes of its container reported.
- **Known limitation**: a process that has not yet written a reading is not counted as a sharer, so its container's share reads high until it writes one; each process publishes a reading at startup, so the window is short. A process whose read failed is still a sharer, unless even its container name could not be read: its reading then names the container `"unknown"` and is not counted. An active worker that never reports is still counted in `total`/`active`.
- **Correction (consumer check, post-implementation)**: the telemetry endpoint (`opsmill/telemetry-endpoints`) verifies the checksum by serialising the parsed `data` again in JavaScript, where `2.0` and `2` are the same number. A whole-number processor share sent as `2.0` therefore failed the check, and the endpoint dropped the whole report. Both processor figures are now written to JSON as integers when whole (`2`, not `2.0`); fractional shares keep their two decimals.
- **Alternatives**:
  - Fleet sums (D8/D9) — rejected: the deduplication, the two null rules, and the undercount above.
  - Each worker's raw container figures — rejected: `per_worker × active` would overstate the API server by its number of processes per container (a 4-CPU container shared by 4 gunicorn processes would read as 16 CPUs).
  - A container-count field beside the raw figures — rejected: an extra payload field, and it would still count only the containers that reported.
- **Superseded by D19**: each block reports one container's figures undivided, in `per_container`, with the number of processes that share that container, in `processes_per_container`, so the total is `per_container × active ÷ processes_per_container`. The share, the count of sharers, the whole-number serializer and the container name are gone. The rejection of each worker's raw container figures above no longer holds, because the count is now sent and the formula divides by it.

## D17 — Keep `workers` unchanged; break it down in new blocks (amended by D19)

- **Decision**: An existing field keeps its meaning, and new information goes into new blocks that follow the same convention. `workers` keeps exactly its existing fields, `total` and `active`, which count every worker process: API server processes, task workers, and any process known only by its generic presence key. Two new blocks, `server` and `task_workers`, count one component's processes each, the same way, and add the CPU and memory of one of the component's containers, in `per_container`, with the number of processes that share that container, in `processes_per_container` (D19). Reverses D15.
- **Rationale**: `workers.total` is used downstream, so narrowing it to task workers would change an existing series, even with its key and type unchanged. With new blocks instead, the payload change is purely additive (D13): no existing field is renamed, removed, retyped or changes meaning.
- **How the counts add up**: each process is matched to its component as D15's attribution bullet describes, which still applies. `server.active + task_workers.active` always equals `workers.active`, because the heartbeat key names the component. `server.total + task_workers.total` equals `workers.total`, except for a process known only by its generic presence key, which names no component: `workers` counts it and the new blocks do not. For a server or task-worker process that has stopped, this normally lasts at most about 5 minutes since D18, longer if its reads failed (a failed read stores nothing, D19) or a long task blocked its main loop. `infrahub recover merge` registers as an API server process and stores a reading when it starts, so its 2-hour resource key names its component for as long as its presence key keeps it in `workers`. If that read fails, it stores nothing, and once its 15-second active key expires the process is counted only in `workers`, for up to two hours.
- **Amended by D19**: the blocks first carried a `per_worker` object with one worker's share of its container (D16).
- **Alternatives**:
  - Narrowing `workers.total` to task workers (D15) — rejected: it changes the meaning of a field that is already used downstream.
  - Putting the task-worker figures in `workers`, next to a count that includes API server processes — rejected: the component's total, worked out from `active`, would be wrong, because `active` would also count the API server processes.

## D18 — Store each reading from the read that takes it; keep only live workers' readings

- **Decision**: `refresh_resources()` stores the reading itself, under `workers:resources:{component}:worker:{WORKER_IDENTITY}` with a 2-hour expiry (`KVTTL.TWO_HOURS`), from the main-loop cache connection. The heartbeat writes only the liveness keys. The gatherer passes the IDs of the active workers, taken from the worker list it already fetched to count workers, to `read_worker_resources()`, which returns only those workers' readings. At startup the liveness keys are written before the reading is stored. Supersedes the D6 correction that had the heartbeat carry the reading.
- **Rationale** (review finding, post-implementation): the heartbeat-carried reading was rejected earlier only in a version with a 15-second expiry and no filter, where a main loop held up by a long task let the reading expire while the heartbeat kept the worker alive. A 2-hour expiry keeps the reading through such a task, and the filter drops a stopped worker's reading once its active key expires, within 15 seconds, so the counts and the figures still describe the same processes. The change removes the process-wide `LatestResourceReading` slot, which plan.md recorded as a deviation from the component-design rule, and a cache write from every 5-second beat. That write repeated the same reading about 60 times between two 5-minute reads, and it ran inside the beat's time limit before the primary API server election and the presence key, so a failed or slow write skipped those two in that beat. The filter uses the same worker list as the counts, so the two are taken at the same moment.
- **Accepted costs**: a worker whose main loop is held up for more than 2 hours loses its reading. After the cache is emptied, for example by a restart, the readings come back at each process's next read, within 5 minutes, instead of at the next beat.
- **Alternatives**: keeping the heartbeat-carried reading — rejected for the reasons above. A second `list_active_worker_ids()` lookup for the filter — rejected: it would take the active set at a different moment from the counts.

## D19 — Report each container whole, with how many processes share it

- **Decision**: After `total` and `active`, the `server` and `task_workers` blocks carry `processes_per_container` and a `per_container` object (`TelemetryContainerData`) with the four figures. `per_container` is one container of the component, undivided, from the most complete of the active workers' readings, and `processes_per_container` is the count carried by that same reading. A component's total is `per_container × active ÷ processes_per_container`. With no reading, the count and every figure are `null`; a reading with no figures still gives the count. Every figure is a whole number. Each reading carries the count (`WorkerResourceReading.processes_per_container`, required, at least 1), and the reading's `host` is gone. A read that fails on every try logs its warning and stores nothing, so the last stored reading stays. Supersedes D7 and D16; amends D14 and D17.
- **Where the count comes from**: an API server process started by gunicorn gets gunicorn's worker count, set by its `-w` option (4 by default in the Docker Compose file, 2 in the community Helm chart). The gunicorn worker class `InfrahubUvicorn` writes `self.cfg.workers` to the environment variable `INFRAHUB_INTERNAL_PROCESSES_PER_CONTAINER` in `init_process()`, before the app loads, and `processes_per_container()` in `backend/infrahub/serve/processes.py` reads it back, giving 1 when the value is missing or is not a positive whole number. A task worker, `infrahub server start` (a single uvicorn process) and any other process that gunicorn did not start therefore count 1. `build_component()` builds `ProcessResources(machine=PsutilMachine(), processes_per_container=processes_per_container())` and passes it to `InfrahubComponent.new()`, which now requires it. The `InfrahubComponent` attribute keeps a default reader with a count of 1 for direct constructions, all of them in tests.
- **Rationale** (review finding on PR #10894, post-implementation): the share hid how big a container was and how many processes shared it: a 2-CPU container running 2 processes and an 8-CPU container running 8 sent the same CPU figures. Working the share out also needed the container name built from the hostname and the PID namespace (D7), the rule that a failed read still counted as a process sharing its container, and a serializer that sent whole-number CPU shares as JSON integers for the telemetry endpoint's checksum. The share also read high until every process of a container had stored its first reading. Sending the container whole with its process count gives the same total without any of these. The count comes from gunicorn's own setting, not from the readings, so it does not depend on how many processes have stored a reading. D16 rejected sending each container's raw figures because `per_worker × active` would overstate the API server by its number of processes per container; sending that number and dividing by it removes the objection. Checked with a real gunicorn started with 3 workers: each process reported 3.
- **Accepted costs**: the count comes from how gunicorn was started, not from the processes that run. An API server started another way with several processes in one container, for example by `uvicorn --workers N` or by gunicorn with a different worker class, counts 1 per container, so its total is overstated by its number of processes per container. Every way OpsMill ships Infrahub (Docker Compose, both Helm charts, the testcontainers stack) starts it through gunicorn with this worker class. A process whose first read fails has no reading until a later read succeeds, and while a process's reads keep failing, its last reading, up to 2 hours old, can still be the one reported. A failed read no longer refreshes the resource key, so a stopped process whose reads were failing is counted only in `workers` for longer (D15, D17). While a container runs fewer processes than its count, for example for the moment gunicorn takes to restart one, `active` is lower and the total reads low; the share counted the processes that had stored a reading, so it did not.
- **Alternatives**: dividing each container's figures among the processes that stored a reading from it (D16, with the container name of D7) — rejected for the reasons above. Reporting each container whole without the count — rejected: `per_container × active` would overstate the API server by its number of processes per container (a 4-CPU container shared by 4 gunicorn processes would read as 16 CPUs).
