# Critique Report: Stop emitting value-intrinsic constraint validators on data-only diffs

**Date**: 2026-08-31
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES → ✅ **PROCEED** (all must-address items resolved; see [Resolution Log](#resolution-log))

---

## Executive Summary

The core argument is sound and unusually well-evidenced for a spec at this stage: the premise (the declaration mechanism exists and is honoured at both determiner decision points) was verified against the code rather than assumed, the classification table was enumerated from the live registry rather than transcribed, and the one question that could have sunk the feature — whether the rebase schema-hash gate becomes a correctness gap — was settled with an argument that turns on the candidate schema rather than on the gate, which is the right place for it to turn. The risk register names the specific traps (two checkers in one file, multi-identifier fan-out) rather than generic ones.

Two defects block task generation, and both are in the same area: **the feature's two CI-gated success criteria are not implementable as written.** SC-002 states a reduction formula that is arithmetically wrong — it conflates attribute pairs with relationship pairs, and the "triple" it names can never apply to a single pair. Separately, FR-002 — the safety property the entire feature rests on — is homed in a test file that structurally cannot verify it: `test_determiner.py` exercises only the data-diff producer, so it cannot assert that the *schema-diff* producer contributes at unrestricted scope. There is currently no test anywhere covering `MergeSchemaAnalyzer.calculate_validations`.

Neither defect challenges the design. Both are specification/verification-placement errors, fixable by editing `spec.md` and `plan.md` before tasks are generated. Everything else is a recommendation.

### Success Measurement

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| **P5** | **🎯** | **SC-002's reduction formula is wrong, and it is marked "Gated in CI".** It states: *"total scheduled constraints fall by approximately 3K — the attribute-kind, attribute-optionality and relationship-peer triple currently scheduled unconditionally for every pair."* The named triple can never apply to a single (kind, field) pair: a pair is either an attribute or a relationship, never both. Verified against the determiner's behaviour and the existing fixtures — an attribute pair schedules `kind`, `optional`, `unique` (3, of which **2** are value-intrinsic); a relationship pair schedules `peer`, `cardinality`, `optional`, `min_count`, `max_count` (5, of which **1** is value-intrinsic). The real reduction is **2 per attribute pair + 1 per relationship pair**, plus one for each optional attribute parameter that happens to be set (regex, enum, choices, length bounds, numeric bounds). A CI gate written against "3K" either fails on correct behaviour or gets quietly loosened until it asserts nothing. | Restate SC-002 as `2A + R + P`, where A = attribute pairs, R = relationship pairs, P = set optional attribute parameters among the fourteen value-intrinsic identifiers. Name the test that implements the gate. |
| P6 | 💡 | **No rollback trigger is defined.** This change *removes* validation work; the failure mode is silent under-validation, which by definition produces no error at the time it happens. Yet nothing states what observation would justify reverting. For a change whose risk is invisibility, "we would revert if we noticed" is not a plan. | Add a rollback trigger to the spec: *a constraint violation reaching the default branch that merge-time validation should have caught, for any constraint in the value-intrinsic table*. Note that revert is a single-commit operation (declarations only, no migration, no persisted state), so no feature flag is warranted. |
