# Critique: Coalesce Python transform computed attributes on merge and rebase

**Feature**: [../spec.md](../spec.md) | **Plan**: [../plan.md](../plan.md) | **Date**: 2026-08-11

**Method**: three independent reviewers with fresh context. One product lens, one engineering lens with code verification, one tasked only with refuting the two load-bearing design decisions. The author of the spec and plan did not self-review; every finding below came from a reviewer who did not write the documents. The three highest-impact findings were then re-verified directly.

---

## Executive Summary

**Verdict: 🛑 RETHINK.**

The plan is technically sound and its research holds up under independent checking. That is not the problem. The problem is that **the feature is already substantially built on three local branches that no document mentions**, and that two of the plan's own decisions contradict requirements in its own spec.

Three findings decide this:

1. **The work largely exists.** `coalesce-python-chain` is 26 commits ahead of develop with 834 lines of production code across 12 files, last touched 2026-08-05. It includes the coalescing engine, the chain leg, a reader-group reconcile, and a read-set index. Two sibling branches carry 15 and 23 commits. One is pushed to origin. Two spec directories exist under `dev/specs/infp-667-*`.
2. **The owner-axis shortcut violates FR-004 and can make merges slower.** Today's trigger filters on the transform's read fields. The plan drops that filter. On a merge that touches only fields the transform does not read, this goes from zero transform executions to N.
3. **SC-001 cannot be met as written.** Submissions are chunked, so the run count is a step function of the changed-node count, not flat.

The good news is that finding 1 makes findings 2 and 3 cheap to resolve: the existing branch already ships `read_set_index.py`, which is precisely the mechanism that fixes finding 2.

**Recommended action**: stop planning, evaluate the three branches, and decide whether to land them or to rebase this design onto what they proved. Do not run `/speckit-tasks` yet.

### X2 — The owner-axis shortcut violates the spec's own FR-004 (🎯)

Verified at `backend/infrahub/computed_attribute/models.py:237-245`:

```python
update_fields = computed_attribute.query_analyzer.query_report.fields_by_kind(
    kind=computed_attribute.computed_attribute.kind
)
event_trigger.match_related = {
    "prefect.resource.role": ["infrahub.node.attribute_update", "infrahub.node.relationship_update"],
}
if update_fields:
    event_trigger.match_related["infrahub.field.name"] = update_fields
```

Today's owner-axis automation fires **only** when a changed field is one the transform reads. The plan's schema-only derivation cannot reproduce that, because the read fields come from the parsed GraphQL query, which lives in the database.

Concrete case. A transform on `InfraDevice` reads only `name`. A merge changes `description` on 2000 devices.

| | Transform executions |
|---|---|
| Today | **0** |
| Plan | **2000** |

FR-004 says the coalesced refresh "MUST NOT refresh more nodes than the per-node refresh would have, except where a widening is recorded under FR-008", and FR-008 covers only the reader-lookup failure case. The plan's Complexity Tracking defends the shortcut as "strictly smaller than the whole-kind fallback the spec already accepts", which is a bound, not a permission.

Worse, no success criterion would catch it. Every criterion counts flow runs or wall-clock; none counts executed transform runs. FR-005 and SC-003 still pass, because the skip-unchanged gate means no extra *writes*, only extra *work*.

**The fix already exists on the prior-art branch.** `read_set_index.py` (+68 lines) is exactly this. The plan's stated reason for refusing it — "resolving them properly would put the expensive gather on every merge" — does not hold: the coalesced pass is not on the merge critical path in the sense claimed, and the plan already adds a collaborator that does I/O on that same path. There is no principled reason to pay for I/O on the reader axis and refuse it on the owner axis.

**Suggestion**: resolve the read fields in the same collaborator as the reader lookup and filter the owner-axis node ids by `changed_fields ∩ read_fields ≠ ∅`, reproducing the trigger's behaviour including the empty-`update_fields` case. If the team prefers the shortcut, FR-004 must be rewritten, the "Out of Scope: narrowing below today's precision" line deleted, and a criterion added that bounds executed transform runs.

## Product Lens Findings

**Problem validation (P2, 🎯)**. The trailing-window numbers come from the archived profile of the Jinja2, display-label and HFID families — the three IFC-2705 already coalesced. The 73,000-run figure comes from the pre-1.11 all-of-kind fan-out after a single rename, not from a merge. Nobody has measured a Python-family merge. The spec concedes this. The result is circular: cheaper alternatives are dismissed as worse while admitting there is nothing to compare against.

**Success measurement (P1, P3, 🎯)**. SC-001 is arithmetically unreachable, because `get_submission_chunk_size()` returns half the Prefect related-resource maximum and the planner chunks every target by it. The count is a step function, not flat. SC-002 is a ratio against a baseline this feature will produce with a harness this feature will restore. No criterion has a threshold that would stop the work.

**Scope and MVP (P4, P5, 💡)**. P1 bundles the owner axis, the reader axis, rebase parity, chaining in both directions, a cycle bound, a pre-existing delete bug and a widening fallback, across ten acceptance scenarios. The deleted-peer bug in particular is user-visible, reproducible without any merge, and predates this work; bundling means it cannot ship without the performance work and the performance work carries its risk.

**Alternatives (P6, 💡)**. Two options were never priced. Batching the existing reader flow by passing it the union of changed ids keeps resolution asynchronous and off the merge path and removes the resolver entirely — and is what the prior-art branch did. Origin-filter-plus-all-of-kind would satisfy SC-001 literally better, because its run count depends on kind population rather than changed-node count.

**Operator experience (P7, 💡)**. The logging is the feature's only user-visible surface, and the claim that FR-008 "falls out naturally" from `fallback_used` is wrong: `fallback_used` appears only in tests, never in production code. The three existing families widen silently today.

## Engineering Lens Findings

**Data model (E1, 🎯)**. `ReaderLookup` cannot express "every node of this kind", and `plan()` chunks an empty id set into zero submissions. A widened target therefore disappears rather than widening. This directly contradicts the data model's own invariant 1 and the contract's guarantee 2.

**Failure modes (E2, 🎯)**. The coalesced pass runs inside `log_exception_guard`, which absorbs every exception. Today that is harmless because the per-node triggers still run. After suppression, one resolver error means every Python computed attribute on that merge is silently stale, with one log line.

**Performance (E3, E9, E12, 🎯 / 💡)**. The pass runs under the global merge lock, so a lookup whose payload scales with the changed-node count serialises every other merge. Separately, coalescing may *reduce* concurrency: a batch runs at SDK batch concurrency while per-node runs are bounded only by the worker pool. And the batched subscriber query returns all subscribers of every matching group with no pagination, so the payload can be O(members × subscribers per group).

**Correctness (E4, E5, E6, E8, 🎯 / 💡)**. Four independent defects: `process_transform` has no `recompute_depth` parameter and ignores its target-kind arguments, so a coalesced submission silently no-ops; the unconditional point-in-time rule hides memberships the merge itself created; the builder's `include_self=False` on update is correct for the three inline-recomputing families and wrong for Python; and the Jinja2 coalesced-flag heuristic cannot be copied because three different callers pass `object_ids`.

**Testing (E7, E13, 🎯 / 🤔)**. The integration test the plan proposes to extend has no run-count assertion; the real suppression check is a component test using an in-process recorder, which cannot observe Prefect trigger matching at all. Phase 5 is the riskiest phase and currently has no test that could fail if the origin filter is wrong.

**Operational readiness (E10, 💡)**. No kill switch, where the adjacent selective-regeneration work has `INFRAHUB_SELECTIVE_EXECUTION_AFTER_MERGE`. The plan's claimed rollback ("revert the two trigger changes") leaves both paths active, which is a double-refresh state, not a restore.

## What survived the critique

Worth recording, because it is the part not to throw away:

- **The R3 reversal is correct.** The reviewer tasked with refuting it confirmed the direction: subtract from the coalesced pass, never from the schema-driven one. Two supporting statements need rewording ("certainly covers" overstates it, and the description of which nodes the coalesced pass writes is wrong for cross-relationship targets), and FR-015 is insufficient because it guards only the send and not the flow that follows it.
- **Every code claim in research.md that was independently checked held up**: the missing delete legs, the absent origin filter on both Python triggers, the schema-only owner resolution being pure, the swallowed schema-event send, and the two-pass overlap.
- **The `RecomputeChainSubmitter` refactor is safe.** All call sites are enumerable, and no import cycle results. Whether it is worth its churn is a fair question, but it does not break anything.

🛑 **RETHINK** — on X1 alone. The remaining findings are all resolvable, and several are already solved on the existing branches.
