## Executive Summary

The rewrite closed 43 of the 50 rated first-pass items fully and 7 partly. The documents agree with
each other far better than before, and no active text keeps the old design. The new code claims hold
where I could check them: GitPython 3.1.61 accepts `kill_after_timeout` on fetch and push,
`ValidationError` is the usual base for a refusal, and the schema-scoped recompute of a merge runs
on the default branch.

The new defects sit where the rewrite moved work out of the repository lock:

- **The delivered entries stay queued after the lock is released** (E37). An abandonment that
  waited for the attempt then abandons merges that are already on the remote and records them as
  dropped. The branch-deletion guard, which also waited for the lock, flags the entry after the
  delivery deleted the flagged branches, so the branch is never deleted. The first-pass E15 defect
  comes back by this route.
- **A held-only run can release a second time while the first release still runs** (E38). The
  recovery check has no age gate for held work behind an empty queue. FR-015 then fails on the
  normal path, not only after a crash.
- **The narrowed cache keeps only the latest hold of an item** (E39). The members of an earlier hold
  are never regenerated, which is under-execution.
- **The most common transient faults are not classified as transient** (E40). No stage covers the
  fetch, and a GitPython timeout produces text that no classifier rule matches.
- **The recovery flow refuses the held-only work it exists for** (E41). Its workflow re-check needs a
  non-empty queue.

All five are local fixes. Four of them share one shape: the end of an attempt should look like the
abandonment. Remove the entries under the lock, mark the release with a lease, release, then clear
by sequence (X5).

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E37 | 🎯 | **The delivered entries stay queued after the lock is released.** [D] R4 removes the entries only at step 15, after it left the repository lock (step 13) and after the release (step 14). Two waiters get the lock in that window. (1) An abandonment that waited for the attempt: R8 step 1 compares the version, which moves only at step 15, so it passes. It then removes merges that are already on the remote and writes them into the abandonment record as dropped. SC-006 and the operator's view are then false. The spec edge case "If the attempt delivered entries, the version moved and the abandonment is refused as stale" is false. (2) The branch-deletion guard: [V] `git/tasks.py::git_branch_delete` takes the repository lock before it checks, so it runs just after step 13. It finds the entry, sets `delete_source_git_branch`, and skips the deletion. Step 13 has already run, and step 15 removes the entry. The branch is never deleted, and E15 is back. R12's "The attempt then deletes the branch a few seconds later" holds only when the guard ran before the attempt took the lock. | Under the repository lock, after step 13, do one state transition: remove the delivered entries into `removed_entry_ids`, bump the version, write the last delivered commit, set the status from what remains, and keep the held set. Then leave the lock, release, and clear the held set by sequence. This is the order R8 already uses. Make the deletion at step 13 accept a branch that is already gone. |
| E38 | 🎯 | **A held-only run can release a second time while the first release runs.** [D] R20 and contracts §7 submit the recovery "when the state is stale, or when held work or an owed import waits behind an empty queue". Only the first condition has an age gate. The abandonment moves no `last_progress_at` (data-model transitions, contracts §2 `abandon`). So during R8 step 2, which awaits generator runs and can take minutes, the next synchronisation cycle (each minute) submits a retry. That flow finds "only held work" (R4 step 1) and releases again. A retry chain that wakes during step 2 does the same. US3 #7 says "the release still runs, exactly once", and FR-015 allows a repeat only after a failure. With E37's fix, the same window opens at the end of every delivery. | Store a release lease in the held set: `release_lease_until` and the snapshot's highest sequence, set in the transition that empties the queue. A held-only run, the recovery check included, does nothing while a lease is live. An expired lease means the release is owed. Apply the `STALE_AFTER` gate to all three recovery conditions. |
| E40 | 🎯 | **The most common transient faults are classified as permanent.** (1) [D] `DeliveryStage` has no `fetch`, and every transport row of R5 says `push`. R4 step 2 fetches first, so a remote that is down fails at the fetch. A literal reading of the table gives "anything else → `unclassified`, not retried". US4 #1 then fails. (2) [V] On a timeout, GitPython kills the process and writes "error: process killed because it timed out. kill_after_timeout=N seconds" (GitPython `cmd.py::handle_process_output`). [V] `git/base.py::_raise_enriched_error_static` matches no rule for that text and raises a plain `RepositoryError`. Contracts §4 promise "A timeout raises `RepositoryConnectionError`", but no document says what maps it. | Add `fetch` to `DeliveryStage`, with the same transport rows as `push`. Add the GitPython kill text to the connection rules of `_raise_enriched_error_static`, and add a classifier test row for a fetch outage and for a timeout of each command. |
| E41 | 🎯 | **The recovery flow refuses the held-only work it exists for.** [D] The recovery check submits `GIT_REPOSITORY_DELIVERY_RETRY`. The GraphQL contract says the availability rules are "checked in the mutation and again in the workflow under the locks", and one rule is "the queue is not empty". R7 lists "nothing is pending (both)". Held work or an owed import behind an empty queue (invariant 2) therefore never reaches R4 step 1, and a crash between R8 step 1 and step 3 leaves a release that is never dispatched. SC-005 fails. | State that the retry workflow delegates to `deliver`, whose step 1 is the only re-check, and that "something to do" means a non-empty queue, a held set or an owed import. Keep the "nothing pending" refusal in the mutation only. |
| E42 | 💡 | **M is undefined when nothing is replayed.** [D] R4 step 8 says "Let M be the final head". When every entry is observed (the FR-012 path, push accepted and record failed), no entry is replayed. If step 6's reset to H does not run, the worktree is still at the pre-attempt commit from the earlier reset, so M is R. The attempt then records R, clears the entries and releases against R, while the remote holds H. | State that step 6 resets the worktree to H even when no entry remains, so that M is H on the observation path. Add that case to the service's unit tests. |
| E44 | 💡 | **Staleness ignores the import and the queue wait.** [D] `last_progress_at` moves only at an enqueue, an attempt start and a recorded failure. R20 rejects a heartbeat because "The Git timeouts already bound an attempt". The import of step 11 is not a Git command and has no bound, and a large import takes many minutes. A first attempt can also wait more than 15 minutes in the Prefect queue or behind a synchronisation import that holds the repository lock. In all three cases a live delivery reads as stale. The recovery then submits a duplicate attempt, and the UI enables a retry while the attempt runs. "Attempt running" in the action table cannot be detected at all, because nothing marks the end of an attempt. | Move `last_progress_at` at each step boundary (after the fetch, the push and the record, and before and after the import), and every few minutes during the import. Or require, for staleness, that the repository lock is free: [V] `lock.py::InfrahubLock.locked` exists. |
| E46 | 💡 | **The kept branch behaves differently per worker.** (1) R12 says that after an abandonment "the next synchronisation imports it as a new Infrahub branch". [V] The guard sends no local-delete message, so workers keep the local branch, and `git/base.py::compare_local_remote` does not list a branch as new when a local branch of that name exists. Only a worker with a fresh clone imports it. (2) While the delivery is pending, a developer can push to the kept branch, whose Infrahub branch is deleted. On a worker that kept the local branch, the branch is then "updated", not new, so R11's skip does not cover it. [V] `collect_pending_imports` then calls `pull`, which records the commit on a deleted Infrahub branch. Graph errors "are left to propagate" there, and `git/tasks.py::sync_repository_from_origin` catches only `RepositoryError` and `CommitNotFoundError`. [R] The error then stops the synchronisation cycle for every repository after this one. | Apply R11's skip to the updated branches as well as the new ones. After an abandonment, pick one behaviour (P19): send the local-delete message so that every worker imports the branch, or keep the branch out by checking the entries of `delivery_last_abandonment`. |
| E47 | 💡 | **The recovery check can be skipped.** Contracts §10 call `git/tasks.py::sync_repository_from_origin` "the per-repository sync flow". [V] It is a plain function, called from the cron flow only when `bootstrap_local_repository` returned a repository. Its `try` catches the `RepositoryBranchesFailedError` that any single failing branch raises. A check placed "after the sync" inside that `try` is skipped whenever one branch of the repository fails to synchronise, which is common. | Run the check from the loop of `git/tasks.py::sync_remote_repositories`, for every repository, before the bootstrap and whatever the sync outcome, under its own guard. Correct the name in contracts §10. |
| E51 | 💡 | **The queue version and the tombstones are too coarse.** [D] The version "increases by one at every change of `entries`", and the deletion guard changes `entries` when it sets a flag. A user's abandonment is then refused as stale because a branch deletion was requested. [D] `removed_entry_ids` keeps 256 ids, and one abandonment can remove more.
