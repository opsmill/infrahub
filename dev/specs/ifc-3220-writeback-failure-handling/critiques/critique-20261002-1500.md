## Executive Summary

The spec solves the right problem, and the core shape is sound. A persisted queue on
`CoreRepository`, one store that is the only writer, one service for the first attempt and the
retry, and a barrier for held regeneration are the correct parts. I confirmed most facts of
`research.md` R0 and R1 in the code. The `LOCAL` plus `read_only` choice, the absence of node events
on a core `Node.save`, and the task-only `retry_condition_fn` are all correct.

The defects concentrate in five areas: the two desired-state imports, the release step, the
held-set clear, the remote branch guard and the enqueue rule.

- The abandonment re-import (FR-024) is not in the PRD, and the import cannot do what FR-024
  promises. It never deletes artifact definitions, and it can raise on a delete. The only exit can
  therefore fail.
- Both imports race with merges that land during the import. The delivery import also runs before
  the record, so regeneration that the import itself starts reads the old commit.
- The release runs under the repository lock and before the broadcast. A released generator can
  wait for that same lock, which is a deadlock.
- The held set is cleared by value, so a hold that arrives after the snapshot can be dropped. That
  breaks FR-016 and SC-005.
- The kept remote branch comes back as a new Infrahub branch at the next sync, because
  `import_sync_branch_names` is empty by default and empty means "import every branch".
- The enqueue skip rule is false for any branch forked before the trunk moved. The hold, and its
  whole-kind recompute, then becomes the normal path for most git-synced merges.

Product concerns are smaller but real. The MVP ships a queue with no exit and no sync deferral.
SC-001 cannot be met by design. A non-destructive exit exists, and the spec says it does not.

None of the findings changes the architecture. About half are text and contract fixes. The other
half change R4, R8, R10 and R12. Run a second critique pass on those four sections before task
generation.
