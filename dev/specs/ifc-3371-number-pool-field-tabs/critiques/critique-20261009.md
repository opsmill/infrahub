# Critique Report: Number attribute — set a number or take it from a number pool

**Date**: 2026-10-09
**Artifacts reviewed**: spec.md, plan.md, research.md, data-model.md, contracts/form-submission.md
**Verdict**: ⚠️ PROCEED WITH UPDATES — two must-address items, both applied in the same commit as
this report.

## Executive Summary

The feature is small and well bounded: the tabs already exist for Number attributes, and the
backend contract is settled. The two must-address items are a state-shape flaw (a number typed in
the pool tab before a pool is picked has nowhere to live) and an unverified promise that backend
errors appear on the field. Both are fixed by narrowing the spec to what the existing form
supports.

## Engineering Lens Findings

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | FR-014, D7 and contract row C4 require handling "number typed, no pool picked". The staged number lives at `value.from_pool.number`, which exists only once a pool is picked; writing it earlier would produce a malformed value. | Render the number input only once a pool is picked, as the IP overrides do (`getPendingFromPool`). Remove FR-014, D7 and C4. **Applied.** |
| E2 | 💡 | `getDefaultValueFromPool` currently casts the raw number into the `from_pool` shape. Changing it changes what `isDeepEqual` compares and what `getFieldDefaultValue.test.ts` asserts. | Add a task to update those tests and to check every consumer of `source.type === "pool"` in `shared/components/form/` for number-pool assumptions. |
