# Critique: Git Repository Commit Visibility

**Feature**: IFC-3101 | **Branch**: `pog-repo-commit-visibility-ifc-3101` | **Date**: 2026-09-03
**Inputs**: spec.md, plan.md, research.md, data-model.md, contracts/, quickstart.md,
checklists/requirements.md, `dev/constitution.md` v1.0.0. No tasks.md yet. No prior critique.
**Mode**: read-only. Nothing in spec.md or plan.md was modified. Every finding carries a proposed edit.

Claims below that name code were checked against the tree on 2026-09-03, not taken from the design
documents. Where a claim was not checked it says so.

## Executive Summary

**Verdict: PROCEED WITH UPDATES.**

The spec solves a real, quantified problem (two hours of Solution Architecture time per "my commit has
not appeared" incident) with a well-bounded slice, and the central decision (commits are values read
from a worker's clone, never nodes) is right: it removes every merge, diff and storage concern in one
move. The plan is unusually well researched: every design decision cites the existing code it reuses,
the shared-path change is isolated in its own pull request, and the clone shape, the fetch broadcast
pinning and the cache set-if-absent primitive all check out in the current tree.

One item blocks: the per-branch drift resolver calls a fleet-wide helper that runs one graph query per
Infrahub branch and returns every repository each time, on a page load. The constitution forbids N+1
patterns and the plan marks this PASS while its Complexity Tracking section says there is nothing to
justify. It is cheap to bring within bounds (filter to the one repository) and the rest can be recorded
as a justified, temporary deviation that IFC-3104 retires.

The remaining findings are recommendations that tighten the operational story (an off switch for the new
background job, network I/O outside the repository lock, non-accumulating on-demand runs), narrow the
contract to what has a caller (`count`, `author_email`, `answered_by`), and close two user-experience
gaps the plan leaves open (no UI for the on-demand check; a freshness timestamp that will look stale for
idle read-only repositories even though the check just ran).

Counts: 1 must-address, 22 recommendations, 2 questions. The stakeholder question list at the end has
four entries, because two of them attach to recommendations rather than standing on their own.

## Product Lens Findings

### 3a. Problem Validation

**P1 (no finding, noted as strength).** The problem statement is concrete, sourced from support load,
and bounded to the question users actually ask. The MVP analysis in User Story 1 ("delivers the whole
business case for read-write repositories on its own") is credible and correctly ordered.

**P2. 💡 The default 15-minute read-only interval is the whole user experience unless the on-demand
check has a UI.** For read-write repositories the answer is at most one minute stale. For read-only
repositories the spec proposes 15 minutes and leans on "the operator can also trigger the check on
demand" (User Story 2). Phase D of the plan lists no button, banner or action for that mutation; it is
GraphQL-only. The realistic read-only experience is therefore "push a tag, wait up to a quarter of an
hour". An idle repository costs one `ls-remote` per interval, so a shorter default is cheap.
*Suggestion*: either lower the default (5 minutes is still 300 times cheaper than the every-minute
read-write sync in transferred bytes, since nothing is fetched when idle) or make the on-demand
trigger part of Phase D. See P5 and Q1.

### 3b. User Value Assessment

**P3. 💡 SC-002 is the business case but is not measurable as written.** "Moves from roughly two hours
with Solution Architecture involvement to self-service" has no metric, owner or window. Nothing in the
spec says how anyone will know, three months after release, whether the feature worked.
*Suggestion*: add a proxy that can be counted: number of support conversations tagged "commit not
imported" per month before and after, and a target (for example, halve within two release cycles). Add
a rollback trigger to the same criterion (see P9).

**P4. 💡 `author_email` is in the contract but no view in this slice reads it.** The example query in
`contracts/repository_git_state.graphql` selects `author_name` only. Emails are personal data that
every repository viewer would receive on every page. The spec's own YAGNI stance (FR-024 dropped the
count badge for exactly this reason) applies.
*Suggestion*: remove `author_email` from `RepositoryCommit` until a view needs it. Adding a nullable
field later is non-breaking.

**P5. 💡 No user-facing entry point for the on-demand refs check.** FR-015 says the check "MUST also
be exposed on demand" and acceptance scenario 2.2 has "the operator triggers the check". The plan
satisfies this with a mutation only. Operators do not open GraphiQL to check a tag.
*Suggestion*: add a "Check remote now" action to the Commits tab for read-only repositories in Phase D,
disabled while a check task is running, and confirm the design canvas has a home for it.

### 3c. Alternative Approaches

**P6 (no finding, noted as strength).** Provider webhooks and provider APIs were the obvious
alternatives and the spec's reason for rejecting them (arbitrary remotes, no new credentials) is
sound for Infrahub's customer base. Reading from the worker's clone is the simplest thing that works
for every remote.

**P7. 🤔 Does the frontend team need a running backend with fabricated commits, or is the SDL enough?**
Phase A ships a `SampleRepositoryGitStateReader`, a new experimental setting, a generated
configuration-reference entry in the public docs, a compose environment mapping, and a unit test for
the sample reader's determinism, all to be deleted in Phase B2. The frontend types against the
checked-in `schema/schema.graphql`, not a live server, so the SDL alone unblocks type generation and
component work; the sample reader only helps someone clicking through a running stack. If the frontend
team can build against fixtures in Vitest and the `UNAVAILABLE / NOT_IMPLEMENTED` state on the stack,
the throwaway code and the public documentation of a flag that will vanish can be skipped. If they need
the live states, keep it but do not document the setting in the user-facing reference. This is a
stakeholder question, not a decision the plan can make alone. See E12.

### 3d. Edge Cases & User Experience

**P8. 🤔 The repository page's existing "in sync" status will contradict the Commits tab.** The
problem statement calls out that the status badge reflects the default branch only. This slice does not
change it (that belongs to IFC-3104). Until then a user on a feature branch can see "in sync" at the top
of the page and `BEHIND` or `REWRITTEN` in the Commits tab below it.
*Suggestion*: decide with the sibling PRD owner whether the tab should carry a one-line note that the
badge describes the default branch, or whether IFC-3104 must land first. Record the decision in the
spec's Dependencies section.

**P9. 💡 Accessibility is not mentioned anywhere.** The imported marker, the head marker and the pending
range are the whole feature. If they are conveyed by colour alone they are invisible to a meaningful
share of users, and the design canvas is not referenced on this point.
*Suggestion*: add to FR-005's presentation counterpart (or a new FR) that each commit state is
conveyed by a text label or icon with an accessible name, not colour alone, and that the copy-hash
button announces success to screen readers. Add the check to the Vitest tests for the tab.

**P10. 💡 The freshness statement will look stale for idle read-only repositories.** Research defines
`fetched_at` as the modification time of `FETCH_HEAD`. `git ls-remote` does not touch that file, so a
read-only repository whose remote has been quiet for three weeks will report "fetched 3 weeks ago" even
though the check ran two minutes ago and confirmed nothing moved. FR-007 is technically satisfied and the
user is technically misinformed. The cache key `git:refs_check:<id>` already stores an ISO timestamp at
check time for the life of the interval, so the data exists.
*Suggestion*: add `checked_at: DateTime` to `RepositoryCommits` and `RepositoryBranchDrifts`, sourced
from that cache value for read-only repositories (null for read-write, where `fetched_at` already means
what the user thinks it means). Show "checked N minutes ago" when present. Amend FR-007 accordingly.

**P11. 💡 A loaded list must not blank out when a cold worker answers a later poll.** Any warm worker
answers the RPC, so a cold worker can answer `UNAVAILABLE / NOT_CLONED` in between two good answers
during the warm-up window. With TanStack Query's default behaviour the tab would flip from a populated
list to the empty state and back.
*Suggestion*: in Phase D, keep the previous page while a refetch returns `UNAVAILABLE`
(`placeholderData: keepPreviousData` or equivalent) and show the not-yet-available state only when
there is no previous data. Add a Vitest case.

### 3e. Success Measurement

**P12. 💡 No rollback trigger and no post-launch metric.** SC-001 to SC-012 are all verifiable before
release; none is observable after it. Combined with P3.
*Suggestion*: add one line to Success Criteria: "Rollback trigger: the read-only refs check is disabled
(see E6) if it is shown to delay imports or exhaust worker capacity in production; the Commits tab is
hidden behind the existing tab gate if timeout errors exceed N per day."

## Engineering Lens Findings

### 4a. Architecture Soundness

**E1. 🎯 The drift resolver is an N+1 query on a page load, and the plan marks it PASS.**
`infrahub.git.utils::get_repositories_commit_per_branch` (checked in the tree) loops over every
registry branch and runs `NodeManager.query` for the whole repository kind on each, with no filter; the
function's own docstring says it should be refactored to a single query. Reusing it from
`InfrahubRepositoryBranchDrift` means a repository with B branches in an installation with R
repositories costs B graph queries returning R nodes each, per request, on a user's page load. The
constitution (Principle V) says N+1 patterns MUST be avoided and Governance says any deviation from a
principle MUST be documented in the plan. The plan's Constitution Check says "PASS with note" and its
Complexity Tracking says "No constitution violations to justify". SC-005 also says "the cost of that
request does not grow with branch count", which is true of the worker request and false of the API
request.
*Suggestion* (two parts, both cheap): (1) do not call the fleet-wide helper from the resolver; either
pass `filters={"ids": [repository_id]}` through a new parameter, or write a small
`RepositoryBranchValuesQuery` that reads `commit`, `ref` and `default_branch` for one repository on
each branch. That brings the result volume from R times B to B. (2) Move the remaining B-query cost
into Complexity Tracking as an explicit, bounded deviation with its retirement plan (IFC-3104's
cross-branch query), and reword SC-005 to "the worker cost of that request does not grow with branch
count". Neither part changes the contract.

**E2. 💡 Reading `RepositoryCommitState` precedence from `data-model.md` is hard.** The `HEAD` row
reads "takes precedence when it also equals the imported commit only if they differ", which is
self-contradictory; the paragraph below it is correct.
*Suggestion*: replace the `HEAD` row's meaning with "the remote head, when it differs from the imported
commit" and leave the precedence paragraph as the single rule.

**E3. 💡 `answered_by` exposes worker identity to every repository viewer.** Principle VI says
responses must not expose internal implementation details. The plan takes care that the timeout error
names only the operation, then puts the worker identity in every successful payload.
*Suggestion*: drop `answered_by` from the GraphQL types and log it on the API server with the request
id instead; support can correlate from logs. If the frontend truly needs it, gate it on the account
being an administrator.

**E4 (no finding, noted as strength).** Top-level queries rather than fields injected onto the generated
repository type is the right call given the analyzer limitation the research documents, and the
imperative permission check reproduces the same decision the analyzer would make. The reader protocol
has a real second implementation (worker) plus test adapters, which is exactly when the constitution
permits an interface.

### 4b. Failure Mode Analysis

**E5. 💡 `ls-remote` runs under the repository lock.** The per-repository check body takes
`lock.registry.get(name=..., namespace="repository")` and then performs the network call. `ls-remote`
only reads the remote; it does not touch the local copy. A slow or hung remote (git has no default
network timeout) would hold the lock that imports and the fetch broadcast handler also need, for as
long as git waits. The existing fetch path has the same exposure, but this feature runs it every
interval for every read-only repository.
*Suggestion*: perform `ls-remote` and the local `origin/<ref>` comparison outside the lock; take the
lock only around the fetch when movement was detected. Amend FR-019 to make the serialisation
requirement about operations that modify the local copy. Consider passing a git-level timeout for the
new call (`GIT_HTTP_LOW_SPEED_LIMIT` / `GIT_HTTP_LOW_SPEED_TIME` via the environment) and record it as
a follow-up if the existing fetch is left alone.

**E6. 💡 There is no off switch for the new background job.** `read_only_refs_check_interval_mins` is
constrained `ge=1`. An operator who finds the check misbehaving in production can only set the
interval to an absurd value; the cron itself is registered at startup and cannot be removed.
*Suggestion*: define `0` as "disabled" (constraint `ge=0`, the cron flow returns immediately) and
document it in the configuration reference. Make this the rollback mechanism in P12.

**E7. 💡 Behaviour when `ls-remote` fails is unspecified.** Authentication failure, DNS failure and a
deleted remote are all routine. The plan says nothing about whether the flow logs and continues, raises
and marks the flow run failed, or how the user learns of it. Because the `git:refs_check` key is set
before the check runs, a failed check is silently not retried until the interval expires.
*Suggestion*: specify: log at warning with repository name and reason, do not raise for a single
repository, continue the loop, and delete the due-check key on failure so the next tick retries. Decide
whether a persistently failing check should surface in the UI; if not, say so in the spec's Edge Cases.

**E8. 💡 On-demand runs can accumulate, against FR-019.** The mutation submits a new
`GIT_READ_ONLY_REPOSITORY_CHECK_REFS` flow run per call. Ten clicks produce ten flow runs that queue
behind the repository lock. FR-019 says overlapping runs MUST NOT accumulate; `CANCEL_NEW` protects the
cron flow only.
*Suggestion*: give the on-demand path an in-flight guard using the same set-if-absent primitive
(`git:refs_check:inflight:<id>`, TTL a few minutes), and have the mutation return the existing task id
when one is already running. Also specify how the cron flow runs the per-repository body: inline and
serial (one slow remote delays every other repository, and a tick longer than a minute is cancelled by
`CANCEL_NEW`, so intervals drift) or as submitted sub-runs (a burst of flow runs after a cache flush
makes every repository due at once). The plan describes neither.

**E9. 💡 Git subprocess work blocks the worker's event loop.** GitPython runs subprocesses
synchronously. One commit page is one `rev-list` for the page, up to `limit` `merge-base
--is-ancestor` calls, and up to two more `rev-list --count` calls, all on the message handler's
event loop. The existing `git.file.get` handler has the same shape, so this is a scaling note rather
than a defect, but polling tabs multiply it.
*Suggestion*: run the git portion of the two new handlers in `asyncio.to_thread` so the worker keeps
consuming other messages; cap `limit` at 50 rather than 100 unless a view needs more. Add a component
test that asserts the number of subprocess invocations per page is bounded by `limit + 3`.

**E10. 💡 Convergence is broken on the NATS driver and this feature makes it user-visible.** Research
records that `refresh.git.*` has single-consumer semantics on NATS. `BrokerDriver.NATS` is a supported
option in `config.py` and appears in the public configuration reference (checked). On NATS, FR-017
cannot be met and a cold worker can keep answering `NOT_CLONED` after the warm-up "completed"
elsewhere, so FR-014's "resolves on its own" is also at risk.
*Suggestion*: state the NATS limitation explicitly in the spec's Assumptions and in the user
documentation for this feature; file the separate issue before Phase C starts so it has a number to
point at; consider making the warm-up flow itself target the answering worker (the `NOT_CLONED` reply
already carries the worker identity in the cache key) as a driver-independent fallback.

### 4c. Security & Privacy Review

**E11. 💡 Harden the new git invocations against option injection.** The `ref` attribute is set by
users with update permission on the repository and reaches `git ls-remote origin <ref>` and
`rev-parse`. Git's `ls-remote` stops option parsing at the first non-option (`origin`), so a ref
beginning with `-` is treated as a pattern, and the existing fetch path already passes the same value.
The exposure is therefore small and pre-existing, but the new code is the right place to stop relying
on argument order.
*Suggestion*: validate `ref` with `git check-ref-format --allow-onelevel` (or an equivalent regex) at
the edge of the check flow and refuse to proceed on failure, and pass `--` before ref arguments where
the git subcommand accepts it. One unit test with a `-` prefixed ref.

(See also E3 on `answered_by` and P4 on `author_email`.)

### 4d. Performance & Scalability

See E1 (graph side) and E9 (worker side). The worker-side page cost is constant in history length as
claimed; `iter_commits` with `skip` is `rev-list --skip`, which walks `offset` commits, so deep pages
grow linearly with offset. That is acceptable for a newest-first UI and worth one sentence in the plan.

**E12. 💡 `count` has no caller and costs a full history walk.** The spec allows an optional total
(FR-024, "MAY keep") and the plan keeps it. Principle VII says not to implement for hypothetical
requirements. Keeping it means a worker code path, a laziness test, and a contract field that no view
uses.
*Suggestion*: drop `count` and `include_count` from the contract, message and handler. Reintroduce when
a caller exists; a nullable field is additive.

### 4e. Testing Strategy

**E13. 💡 Multi-worker convergence has no named test.** FR-017, SC-009 and User Story 2's
independent test all require more than one worker. The plan's integration tests run against Gogs in
`backend/tests/integration/git/`, which is a single-process suite. Nothing states which suite starts two
task workers.
*Suggestion*: either add an e2e scenario on the testcontainers stack with two task workers and assert
both clones reach the new head while `commit` is unchanged, or state explicitly that the single-process
suites assert the broadcast was sent with the pinned commit (via `BusRecorder`) and that fan-out
delivery is covered by existing message-bus tests. Pick one and write it into the plan's Phase C.

**E14. 💡 The e2e "pending appears after the sync tick" test waits for a fixed one-minute cron.**
That is 60 seconds of wall time per run with no way to shorten it, and a classic flake source.
*Suggestion*: keep one e2e scenario on a pre-seeded state (behind before the test starts, by adding the
repository from a fixture whose remote is advanced after the first import completes but before the tab
is opened, with the sync tick awaited once in a fixture rather than in the test body), and move the
"push, then observe" transition to the component level on `FileRepo`.

**E15 (no finding, noted as strength).** Test adapters rather than mocks, a pure classification module
with unit tests, permission-denial tests, and the timeout test with a bus double that never replies all
match the constitution's Test Discipline. The plan names each test file up front.

### 4f. Operational Readiness

**E16. 💡 No observability is planned for the refs check.** Operators will want to know: how many
repositories were checked per tick, how many moved, how many failed, and how long the tick took.
Prefect flow logs exist but nothing structured is specified.
*Suggestion*: emit one structured log line per tick (checked, moved, failed, duration) and one per
movement (repository, ref, old head, new head). If the codebase has metrics counters on the worker, add
`git_refs_check_total{outcome}`; if not, do not introduce a metrics stack for this.

(See also E6 on the rollback mechanism.)

### 4g. Dependencies & Integration Risks

**E17. 💡 The bounded RPC changes behaviour for `get_file`, which today swallows error replies.** The
research notes that `infrahub.api.file::get_file` never calls `raise_for_status`, so an
`RPCErrorResponse` becomes an HTTP 200 with an empty body. After Phase B1 the same endpoint will start
returning 504 on timeout while still returning 200 on a worker-side error. The quickstart even lists
"confirm `GET /api/file/...` now fails with 504" as a check.
*Suggestion*: include the one-line `raise_for_status()` fix in the Phase B1 pull request, since that
PR is already the reviewed shared-path change and the fix makes its behaviour coherent; or state in the
plan why it is left out.

**E18 (no finding, noted as strength).** No new dependency, additive GraphQL, a defaulted `timeout`
parameter, and the shared-path change isolated in its own pull request with its own test.

## Cross-Lens Insights

**X1. 🎯 (from E1) Narrow the drift resolver's graph read to one repository.** Product wants the
branch list to load in one shot on a 200-branch repository (SC-005). Engineering has the constitution's
N+1 rule. Filtering the existing helper to one repository satisfies both for this slice and hands the
single-query version to IFC-3104, which needs it anyway.

**X2. 💡 (from P4, E3, E12) Ship only fields that have a reader.** `count`, `author_email` and
`answered_by` each add a code path, a test and a privacy or disclosure question, and no view in this
slice selects any of them. Removing all three shrinks Phase A and Phase B2, removes a worker-side
history walk, and leaves a contract that grows additively when a caller appears.

**X3. 💡 (from P2, P5, P10) The read-only experience is under-served by the plan relative to the
spec.** Three small additions close it: an on-demand action in the UI, a `checked_at` timestamp next to
`fetched_at`, and a shorter default interval or a clear statement of why 15 minutes is right.

**X4. 💡 (from E5, E6, E7, E8) The refs check needs an operations paragraph.** Lock scope, off switch,
failure behaviour, and non-accumulation of runs are each a sentence in the plan and a few lines of code.
Together they are the difference between a background job operators trust and one they disable.

**X5. 🤔 (from P7) Sample data in production code is a cost paid for a benefit that should be
confirmed.** One question to the frontend lead settles whether Phase A's experimental flag, its public
documentation and its removal in Phase B2 are needed at all.

## Addendum: resolving E1 inside this feature

Added 2026-09-03 after the author asked that the N+1 be corrected here rather than deferred.

**Code findings (checked in the tree).** No query class returns a branch-resolved attribute value for
one node across many branches. `Branch.get_query_filter_path` targets exactly one branch.
`core/diff/query/artifact.py::ArtifactDiffQuery` reads attribute values on two branches in one
statement and `core/query/diff.py::DiffCountChanges` returns one row per branch; together they are
the template. Repository kinds are node-level AGNOSTIC; `CoreRepository.commit` is LOCAL, so its
creation edge sits on the global branch and later writes sit on the real branch, which is why a
never-imported branch resolves to the default branch's value today. Branches are isolated by default,
so a user branch reads its origin at `branched_from`.

**Boundary with IFC-3104.** That PRD claims the primitive (FR-009), the paginated status query and
the sync-job refactor (FR-010). Building the primitive here makes IFC-3104 its second caller; its
filters, pagination, count and sync refactor stay there.

**Resolution.**

1. New `core/query/repository.py` query: one repository node, explicit branch list, explicit
   attribute-name set. Unwind a per-branch scope (branch, origin, fork-point time, query time),
   apply the standard edge-activity predicate per scope in a subquery with
   `ORDER BY branch_level DESC, from DESC, status ASC LIMIT 1`, active-status check, one row per
   branch and attribute. Frozen dataclass rows via `get_data()`. Global branch excluded.
2. The drift resolver calls it once, then sends the single worker message. Graph side is one query
   for any branch count; the fleet-wide helper is no longer called from the resolver.
3. Row set follows IFC-3104 FR-002: `sync_with_git` branches for read-write, all branches for
   read-only, excluding MERGED, DELETING and global. Spec User Story 3 scenario 4 changes from "shown,
   not drifted" to "absent for read-write repositories"; `NOT_TRACKED` remains for read-only branches
   with nothing imported.
4. Spec: FR-004 adds "and a number of database queries independent of branch count"; SC-005 becomes
   "database query count and worker request count for 200 branches equal those for 5".
5. Plan: Principle V is a clean PASS; Complexity Tracking stays empty; structure gains the query
   module and a component test; the query lands in Phase A with the resolver; the per-branch-cost risk
   row becomes a coordination row pointing IFC-3104 FR-009 and FR-010 at this query.
6. Research and data model: rewrite the drift decision; add the result row dataclass.
7. Tests: own commit returned; never-imported branch returns the fork-point value, still after the
   default branch imports again, and follows a rebase; non-synced branches absent for read-write;
   read-only `ref` per branch; same query count at 5 and 200 branches by instrumentation.
8. Comment on IFC-3104 that the single-repository primitive lands in IFC-3101.

## Open questions on the two remaining recommendations

### Question 1: WITHDRAWN, 2026-09-04 — the premise was wrong

Author: the two-hour figure is irrelevant. The goal is that the information is visible in Infrahub so
nobody has to hunt it down on the git remote, and the commit list is useful outside troubleshooting
simply as a repository's history.

P3 is therefore **withdrawn, not deferred**. It existed only because I read the two-hour estimate in
the Problem section as the feature's business case and then observed that nothing would measure it.
The estimate was context, not a target, so there is nothing to measure and no support-tagging
convention to negotiate.

What changed instead, because the spec carried the same mis-framing: the Problem section no longer
presents a per-incident time cost as the motivation and now states that the information exists but
not in Infrahub, with an explicit paragraph that this is not only a troubleshooting gap. SC-002 was
rewritten from a time saving to the capability itself, holding whether or not anything is wrong. The
Solution Summary and User Story 1's rationale now say the commit list has standalone value rather
than framing it purely as the answer to a support question.

Lesson for future critiques in this repo: a number in a Problem section is not necessarily a target,
and "this is unmeasurable" is not a finding when nobody proposed to measure it.

### Superseded: how will we know the feature worked?

**The situation.** SC-002 says that diagnosing "my commit has not appeared" moves from about two hours
of Solution Architecture time to the user answering it themselves. That is the business case for the
whole feature.

**The problem.** Nothing counts either number. Today's "two hours" is an estimate from experience, not
a measurement, and after release nothing will tell us whether it fell. Every other success criterion
in the spec can be checked by a test before release. This one cannot be checked at all.

**What I cannot decide alone.** Whether anyone counts support requests by topic, and whether someone
outside this repository is willing to start. That is a process commitment, not a code change.

**The options, as I see them:**

1. Count it. Someone tags incoming "commit not imported" requests in whatever tool support uses, we
   read the count for the month before release and the months after, and SC-002 names a target.
   Needs an owner in support and a tag that survives.
2. Use a proxy already in the product. For example, count how often the commit view is opened, on the
   theory that usage displaces support requests. Cheap and automatic, but it measures use rather than
   the outcome we care about, and a busy view could equally mean people are confused.
3. Drop the measurement. Reword SC-002 so it states the intent without claiming it will be verified,
   and accept that we will judge success from anecdote.

**My recommendation.** Option 1 if a support tagging convention already exists or is easy to add,
because the two-hour figure is the feature's justification and going unmeasured makes it unfalsifiable.
Option 3 if not, stated honestly, rather than inventing a proxy that would be quoted later as if it
measured the real thing.

### Question 2: WITHDRAWN, 2026-09-04 — E6 reverted, and P12 with it

Author: "Why would we want to switch this off?" Correct challenge, and I could not justify it.

**Evidence against my own recommendation.** Of the five cron workflows in `workflows.catalogue`, only
`ANONYMOUS_TELEMETRY_SEND` can be turned off, via `main.telemetry_optout`, and that is a privacy
opt-out rather than an operational kill switch. `GIT_REPOSITORIES_SYNC`, `CLEAN_UP_DEADLOCKS`,
`WEBHOOK_CONFIGURE` and `MERGE_WATCHER` have no equivalent. The nearest analogue for the setting
itself, `CacheSettings.clean_up_deadlocks_interval_mins`, is `ge=1`, which is exactly the constraint
E6 proposed to relax. On cost: an idle repository is one refs listing per interval with no content
transfer, strictly less than the every-minute sync already spends per read-write repository, and that
job has no off switch. So the load an off switch would have relieved is smaller than load the product
already carries without one.

My justification was "an operator who finds it misbehaving can only set the interval absurdly high",
which is reasoning from a hypothetical fault, and Principle VII forbids configurability for
hypothetical requirements. Lengthening the interval genuinely covers the realistic complaint, that
the check is too frequent.

**Reverted**: FR-015's disabling clause and its verify step, the edge case describing the switched-off
state, the plan's off-switch bullet, the `ge=0` constraint in data-model.md and research.md, and the
quickstart step. SC-014 was rewritten from "can switch it off" to "can lengthen the interval without a
restart", which is a real capability the design already has. The research decision now records the
rejection and the evidence, so the question does not get reopened from scratch.

**P12 falls with it.** P12 asked for rollback trigger conditions. Its metric half died with Question 1,
and its lever half assumed the off switch existed. With no off switch and no time-saving metric, there
is nothing left of it. Withdrawn.

Net: 17 of the 22 recommendations applied, 5 withdrawn (P2 declined into P5, E10 out of scope, P3
premise wrong, E6 unjustified, P12 dependent on both), 0 open.

### Superseded: when should someone switch this off?

**The situation.** Two levers now exist. Setting the read-only check's interval to zero stops the
background job. The existing tab gate hides the Commits tab.

**The problem.** Nothing says under what conditions to pull either one. A lever nobody knows when to
use is not a rollback plan, and the read-only check is the part of this feature most likely to
misbehave in a way the team notices before a user does, because it adds standing background load
proportional to the number of read-only repositories.

**What I cannot decide alone.** The thresholds. They depend on what your production installations
tolerate and on what your monitoring can actually see, and I have no data for either.

**The two decisions needed:**

1. **Switch off the background check when what happens?** Candidate triggers: it measurably delays
   imports; its per-cycle failure count stays high; worker capacity is visibly consumed by it. How
   bad, and for how long, before someone acts?
2. **Hide the Commits tab when what happens?** The obvious trigger is the rate of `WORKER_TIMEOUT`
   errors on the commit queries. Above what rate is a tab that often fails worse than no tab?

**Also acceptable.** Say "operator judgement, levers documented, no thresholds until we have
production data". That is a legitimate answer for a first release, and better than numbers invented
now that later get treated as if they meant something. If you want a starting pair to react to rather
than a blank page: switch off the check if a quarter of checks fail for a day, and hide the tab if
more than a few per cent of commit queries time out over a day. Both are guesses.

**My recommendation.** Take the "operator judgement, no thresholds yet" answer, and add one line to
the spec naming the two levers and what to watch. It commits to nothing false and still tells whoever
is on call where the switches are.
