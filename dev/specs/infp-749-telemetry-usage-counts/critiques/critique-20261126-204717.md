# Critique Report: Usage counts in the daily telemetry report

**Date**: 2026-11-26

**Feature**: [spec.md](../spec.md)

**Plan**: [plan.md](../plan.md)

**Verdict**: PROCEED WITH UPDATES

---

## Executive Summary

The specification describes the end state of a run as the result of the work. The code shows that this holds for 5 of the 8 workflows. The three workflows that run inside a proposed change end in `COMPLETED` when the generator, the artifact generation or the check failed. The report therefore cannot count those failures, and the figure for unchanged artifact generations that the analyst computes includes them. The specification, the contract and the research must state this before the task list is written (P2). The owner of the telemetry code must decide whether the release needs those failure counts (P3). The plan must also record why a change with a changelog fragment of type `added` targets `stable` (E1).

The other findings change wording or add a check before the pull request is merged:

- Confirm that the telemetry endpoint accepts a report with the new values. The research lists this as an item that blocks nothing (E8).
- Measure the two new reads of the graph database on a large dataset. They run with no time limit (E6).
- State the real wait when the task manager does not answer: about 7 minutes for one read, not 60 seconds (E4).
- State that `with_generator_instance` does not count the nodes of a generator definition that runs only inside proposed changes (P4).

Not decided yet:

- Whether the release needs the failure counts inside a proposed change (P3).
- Whether the sentence of the public FAQ about the use of the information still holds (E5).
- Whether Infrahub Enterprise depends on the function whose parameters change (E9).

No statement about the code in plan.md, research.md or data-model.md was found to differ from the working tree, apart from the difference that plan.md already lists (the rule of FR-014 for a failed read of the validator kinds). Two statements in those documents are inaccurate for other reasons: the statement about constitution violations (E1) and the wait of a failed read (E4).

### P2. The end state of a run is not the result of the work for three workflows

- Evidence in the code:
  - `backend/infrahub/artifacts/tasks.py::create` (`git-repository-check-artifact-create`) catches every exception of `render_artifact`, sets the conclusion to `ValidatorConclusion.FAILURE`, saves a check and returns the conclusion. The comment in the code says: "any render failure must be recorded as a failed artifact check, not crash the flow".
  - `backend/infrahub/proposed_change/tasks.py::run_generator_as_check` (`run-generator-as-check`) catches `ModuleImportError` and `Exception`, sets the conclusion to `FAILURE` and returns it.
  - `backend/infrahub/git/tasks.py::run_user_check` (`git-repository-run-user-check`) catches `CheckError` and returns `FAILURE`. `backend/infrahub/git/integrator.py::InfrahubRepositoryIntegrator.execute_python_check` turns every exception of the check into `CheckError`.
  - `backend/infrahub/git/tasks.py::generate_artifact` (`artifact-generate`) and `backend/infrahub/generators/tasks.py::run_generator` (`generator-run`) raise the exception again, so these runs end in `FAILED`. The two transformation workflows in `backend/infrahub/transformations/tasks.py` do not catch exceptions.
  - `backend/infrahub/git/integrator.py::InfrahubRepositoryIntegrator.render_artifact` sends the created or updated event only after it stored new content. A failed artifact generation sends no event.
- Statements that the code contradicts:
  - spec.md, User Story 1, acceptance scenario 2: "Given an artifact generation that failed on the previous UTC day, When the report is produced, Then the run is counted in the `FAILED`, `CRASHED` or `CANCELLED` row of its workflow, according to the state it ended in."
  - spec.md, User Story 1: "The number of artifact generations that left the content unchanged: the completed runs of the two artifact generation workflows, minus `artifacts_created`, minus `artifacts_updated`." A failed artifact generation inside a proposed change is a completed run with no event, so the result counts it as unchanged.
  - spec.md, SC-001: "an analyst computes each of these five figures per end state".
  - contracts/telemetry-payload.md, "Figures that the reader computes", repeats the formula.
  - research.md R5, "What one run means", does not say which state a failed run ends in.
- Checked by: reading the six functions. A short script on Prefect 3.8.6 confirmed that a flow that returns `ValidatorConclusion.FAILURE` ends in `COMPLETED` and that a flow that raises ends in `FAILED`. No real workflow was run in a deployment.
- Suggested edit 1, spec.md, User Story 1: add this paragraph after the list of workflows.

  > The end state is the state of the workflow run. It is the result of the work only for `generator-run`, `artifact-generate`, `transform_render_python` and `transform_render_jinja2_template`: when the work fails, the run ends in `FAILED`. The three workflows that run inside a proposed change (`run-generator-as-check`, `git-repository-check-artifact-create` and `git-repository-run-user-check`) record a failed generator, a failed artifact generation or a failed check as a check with the conclusion `failure`, and the run ends in `COMPLETED`. For these three workflows, the `FAILED` and `CRASHED` rows count only the runs in which the workflow itself stopped, and the report does not count the failed generators, artifact generations or checks.

- Suggested edit 2, spec.md, User Story 1, acceptance scenario 2: replace it with two scenarios.

  > 2. **Given** a run of `artifact-generate` whose artifact generation failed on the previous UTC day, **When** the report is produced, **Then** the run is counted in the `FAILED` row of `artifact-generate`.
  > 3. **Given** a run of `git-repository-check-artifact-create` whose artifact generation failed on the previous UTC day, **When** the report is produced, **Then** the run is counted in the `COMPLETED` row of `git-repository-check-artifact-create`, and no row separates it from an artifact generation that succeeded.

- Suggested edit 3, spec.md, User Story 1, second computed figure: replace it.

  > The largest possible number of artifact generations that left the content unchanged: the completed runs of the two artifact generation workflows, minus `artifacts_created`, minus `artifacts_updated`. The result also contains the artifact generations that failed inside a proposed change, because those runs end in `COMPLETED` and send no event.

- Suggested edit 4, spec.md, SC-001: replace "computes each of these five figures per end state with no further data" with "computes the number of runs of each of these five figures per end state of the workflow run with no further data", and add: "The report separates failed work from successful work for generator runs and artifact generations outside a proposed change and for transformations. It does not separate them inside a proposed change."
- Suggested edit 5, contracts/telemetry-payload.md: add the paragraph of edit 1 under `activity_24h.workflow_runs`, and replace the line about unchanged artifact generations with the wording of edit 3.
- Suggested edit 6, research.md R5, "What one run means": add for each workflow the state that a failed run ends in, with the function named above, marked as read in the code.
- Suggested edit 7, `dev/knowledge/backend/telemetry.md`, row `workflow_runs` of the table "Activity (24h) field semantics": add "For the three workflows that run inside a proposed change, a failed generator, artifact generation or check ends the run in `COMPLETED`."

### P4. `with_generator_instance` leaves out generator definitions that run only inside proposed changes

- Evidence:
  - `backend/infrahub/core/schema/definitions/core/generator.py::core_generator_instance` has `branch=BranchSupportType.LOCAL`. `docs/docs/schema/branch-awareness.mdx` says about a branch-local node: "merging the branch never copies it to the default branch".
  - `backend/infrahub/proposed_change/tasks.py::_define_instance` creates the generator instance on the source branch of the proposed change.
  - `backend/infrahub/generators/tasks.py::run_generator_definition` skips a generator definition after a merge when `execute_after_merge` is false. `docs/docs/generators/overview.mdx` documents this value: "When `false`, the Generator will not run after the branch has been merged."
  - spec.md, Edge Cases, says only: "A generator ran only on another branch: generator instances and artifacts are stored per branch, so the node is not counted on the default branch." User Story 3 says the analyst uses the totals "to find deployments that run generators and use no artifacts".
- Checked by: reading the schema definition, the two functions and the two public pages. The value of the total in this case is an inference. It was not run.
- Suggested edit, spec.md, Edge Cases: replace the bullet "A generator ran only on another branch".

  > - **A generator ran only on another branch**: generator instances and artifacts are branch-local. They stay on the branch where the run created them, and a merge does not copy them to the default branch. A node is counted in `with_generator_instance` only after a generator has run for it on the default branch. A generator definition with `execute_after_merge: false` runs only inside proposed changes, so its nodes are never counted, although the merge brings the nodes that the generator created to the default branch. For such a deployment, the analyst reads the runs of `run-generator-as-check`.

- Add the same two sentences about `execute_after_merge: false` to `database.node_count` in contracts/telemetry-payload.md and to the section "Two ways of counting in `features` and `database.node_count`" of `dev/knowledge/backend/telemetry.md`.

### E4. The wait of a failed read is understated, and the full outage case is stated wrongly

- Evidence:
  - spec.md, Edge Cases: "The task manager does not answer: each failed read can wait 60 seconds, and retries add to that. The report is late by the wait of each read and is still stored and sent." research.md R6 repeats it: "When the task manager does not answer, the report is late by the wait of 8 calls."
  - In Prefect 3.8.6, `prefect/settings/models/api.py::APISettings.request_timeout` is 60 seconds and `prefect/settings/models/client.py::ClientSettings.max_retries` is 5. `prefect/client/base.py::PrefectHttpxAsyncClient.send` retries a read timeout, and `_send_with_retry` waits 2, 4, 8, 16 and 32 seconds between the attempts, before the random variation that it adds. One read that never gets an answer therefore takes 6 attempts of 60 seconds and 62 seconds of waits: about 7 minutes. The root compose file, the development compose files and `development/Dockerfile` do not set `PREFECT_API_REQUEST_TIMEOUT` or `PREFECT_CLIENT_MAX_RETRIES`. Only the test compose files of `python_testcontainers` set the first one, to 120 seconds.
  - The change adds 14 reads: 8 run history reads and 6 validator counts. `backend/infrahub/telemetry/task_manager.py::gather_activity_24h` already makes 12 calls. When no read gets an answer, the activity part takes about 3 hours with the change, against about 1 hour 25 minutes before it.
  - `backend/infrahub/telemetry/tasks.py::AnonymousTelemetryGatherer.gather` calls `gather_prefect_information()` without `safe_metric`. `dev/knowledge/backend/telemetry.md` says about such parts: "a failure in any of them stops the whole report". When the task manager answers no call, the report is therefore not stored.
- Checked by: reading the Prefect client code, the two settings and the Infrahub code. The times are computed from the settings. They were not measured.
- Suggested edit, spec.md, Edge Cases: replace the bullet "The task manager does not answer".

  > - **The run history or the event count of the task manager does not answer**: with the default settings of the task manager client, one read waits up to 60 seconds and is tried 6 times, so one read takes about 7 minutes before it is reported as failed. The change adds 14 reads, so the report can be later by about 100 minutes. The report is still stored and sent when the other calls to the task manager succeed. When the task manager answers no call at all, the report fails as it did before the change, because the work pools, the event tally and the automations are read with no protection.

- Suggested edit, research.md R6, Consequence: replace it with "A read that gets no answer takes about 7 minutes: 6 attempts of 60 seconds and 62 seconds of waits between them. These are Prefect's defaults; Infrahub sets no shorter limit. The 8 run history reads and the 6 validator counts can delay the report by about 100 minutes."
- For the owner to decide: whether this delay is accepted, or whether the two new reads pass a shorter `timeout` to `client._client.post`. A shorter timeout is not a limit on the number of failed reads.
