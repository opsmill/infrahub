# Feature Specification: Prefect Client Port & Adapter (with Test Adapters)

**Feature Branch**: `ifc-2499-prefect-test-adapter`  
**Created**: 2026-04-23  
**Status**: Draft  
**Input**: User description: "I would like to create a test adapter for prefect client for several use cases. First it would allow us to await some event to be really processed to avoid flakiness this is P2. And first it would allow us to assert against this service without having to do some ugly AsyncMock or createAutoSpec which are not the real service"

## Clarifications

### Session 2026-04-23

- Q: Does production code migrate off `prefect.client` to depend on the adapter interface, or is this a test-only adapter? → A: Production code migrates to depend on the adapter interface, incrementally (subsystem-by-subsystem). `import prefect` / `from prefect...` is allowed only inside the adapter module and integration tests.
- Q: How rich is the in-memory test adapter in v1 — a recorder, a full stateful simulator, or somewhere in between? → A: Recorder in v1 (records calls, returns seeded responses, exposes event-wait primitive); a stateful-test-adapter follow-up (flow-run state transitions, callbacks, controllable time, injectable errors) is committed as an explicit FR (FR-018) and tracked as a separate ticket out of scope for this feature's delivery.
- Q: What Prefect surface is covered by the v1 interface? → A: Full v1 — every Prefect surface currently imported from `prefect` in production code: automations, deployments, events, flow runs, and work pools. (Work queues were listed aspirationally; the import audit in research R-2 shows no production caller uses them, so they are added on-demand if a future caller needs them — same rule as any other speculative surface.) v1 is complete when no production module outside the adapter imports from `prefect` (FR-015).
- Q: Are adapter methods named in domain vocabulary (`schedule_report_generation`) or mirrored from Prefect (`create_flow_run_from_deployment`)? → A: Prefect-mirror names at the adapter layer. Subsystems MAY wrap the adapter in thin domain-named helpers inside their own module when it clarifies local call sites. Domain vocabulary emerges bottom-up from real usage rather than being designed top-down.
- Q: How is "contract parity" between the real and in-memory test adapters enforced? → A: Each contract assertion is authored once in a shared helpers module (`backend/tests/helpers/prefect_client_contracts.py`) and invoked from two thin test packages — `backend/tests/unit/prefect_client/` (backed by `InMemoryPrefectClientTestAdapter`, gates merges in the unit/component CI job) and `backend/tests/integration/prefect_client/` (backed by `RealPrefectClientTestAdapter`, runs in the integration CI job against an ephemeral Prefect server via the existing `prefect_test_fixture`). Split is directory-based (no pytest marker); both jobs gate merges, and failures on the integration job are analyzed before relaunch — never auto-skipped and not treated as a nightly-only / non-blocking lane.
- Q: How is the production port kept separate from the test-only capabilities? → A: Two ABCs. `PrefectClientAdapter` is the production port — 18 concrete Prefect client operations; `emit_event` mirrors Prefect's native signature exactly (caller-providable `id: UUID | None`, returns `Event | None`) so no test concept leaks into production. `PrefectClientTestAdapter(PrefectClientAdapter)` is the test port, extending the production port with three test-oriented primitives (v1: `wait_for_event` keyed on Prefect's native `Event.id`, sync `checkpoint() -> Checkpoint` watermark, and async `captured_emits() -> AbstractAsyncContextManager[EmitCapture]`; FR-018 follow-ups: controllable clock, injectable errors, callbacks). Production code type-hints against the production port and receives `RealPrefectClientAdapter`; tests type-hint against the test port and receive either `RealPrefectClientTestAdapter` (real Prefect + polling wait, server-side filtering by event id) or `InMemoryPrefectClientTestAdapter` (in-memory + condition-variable wait, plus recorder helpers). The boundary is enforced by the type system, not by convention or lint.
- Q: SC-010's "effectively zero" flake rate — what is the numeric acceptance threshold? → A: Zero. Zero Prefect-attributable flakes on the unit and component suites over a rolling 30-day window. Any non-zero count is treated as a regression and filed as a bug, not a tolerance.
- Q: What is the Prefect version support policy for the real adapters? → A: Pin one Prefect version at a time. SDK upgrades are deliberate discrete work: bump the pin, update `RealPrefectClientAdapter` and `RealPrefectClientTestAdapter` to match, re-run the full contract test suite (both the in-memory-backed and real-backed lanes), merge. The production and test port ABCs are stable across upgrades; the real adapter classes absorb the signature delta in one place.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Assert against a real-shaped Prefect surface without hand-rolled mocks (Priority: P1)

A backend engineer writes a test for code that talks to Prefect (automations, deployments, events, flow runs). Today they reach for `create_autospec(PrefectClient)` or stand up `AsyncMock` ladders to stub each call site, then assert `mock.create_automation.assert_called_once_with(...)`. These mocks drift from the real client's behavior: they accept any argument shape, return shapes the engineer invents, and silently hide real contract breaks until integration tests fail. The engineer wants a shared test adapter that stands in for `PrefectClient`, behaves like the real service for the calls tests need, records the interactions, and lets the test make precise assertions against those recordings without rebuilding a bespoke stub in every file.

**Why this priority**: This is the bulk of the pain. Every new Prefect-touching feature today adds another bespoke mock setup; each one is a chance to drift from reality and a chance to bit-rot when Prefect bumps. A shared adapter removes that cost on first use and makes every subsequent test cheaper. It is also what unblocks Story 2 — a recording adapter is a precondition for a deterministic "wait for ingest" primitive.

**Independent Test**: Port one existing unit test that currently uses `create_autospec(PrefectClient)` (e.g., `backend/tests/unit/webhook/test_webhook_automation.py`) to the adapter. The test must pass with equivalent or stronger assertions (argument shapes validated against real Prefect types) and no `AsyncMock`/`create_autospec` imports remaining in that file.

**Acceptance Scenarios**:

1. **Given** a test that exercises code calling `PrefectClient.create_automation`, `read_automations_by_name`, and `read_deployment_by_name`, **When** the test substitutes the adapter for the real client and runs the code under test, **Then** the adapter accepts those calls with real Prefect argument and return types, records each call, and the test asserts on the recorded interactions without writing per-test `AsyncMock` glue.
2. **Given** the code under test passes a malformed payload (wrong field name, wrong type) to a Prefect method, **When** the adapter receives it, **Then** the test fails with a clear signal at the call site — not a silent pass that only surfaces in integration.
3. **Given** a test needs a specific return value from a Prefect method (e.g., an existing automation with a given id), **When** the test pre-seeds the adapter with that return value, **Then** the code under test receives it and the adapter still records the call for later assertion.
4. **Given** Prefect introduces a new method on `PrefectClient` that no test has adapted yet, **When** code under test calls it through the adapter, **Then** the test fails with a message naming the un-adapted method rather than silently returning `None`.

---

### User Story 2 - Deterministically wait for an emitted event to be observable (Priority: P2)

A backend engineer writes a test that triggers Infrahub code which emits Prefect events, then asserts those events were recorded. Today the test polls the Prefect events filter for a fixed window (recently raised from 10s to 30s) because Prefect's ingest pipeline is asynchronous and the window is a guess. The engineer wants the adapter to expose a primitive that blocks until a specific emitted event is actually observable by a query, so tests are deterministic: they wait exactly as long as needed and no longer, and they fail fast and clearly when the event never arrives.

**Why this priority**: This solves a narrower, currently-tolerable problem (flakiness patched by a 30s timeout) and builds on top of Story 1. Delivering it without the adapter first would mean another one-off helper; delivering it after means it's just a method on the adapter.

**Independent Test**: Rewrite `backend/tests/functional/proposed_change/test_thread_events.py::test_thread_events` to use the adapter's wait primitive instead of `assert_event`'s 30-iteration poll. The test must pass on the same CI runners that exhibit the lag, complete faster than the existing 30s ceiling in the median case, and fail with a message that identifies the missing event and the time waited when the event truly does not arrive.

**Acceptance Scenarios**:

1. **Given** code under test emits a Prefect event, **When** the test calls the adapter's wait primitive for that event by name or id, **Then** the call returns as soon as the event is observable to a query — not after a padded fixed delay.
2. **Given** code under test never emits the expected event, **When** the test waits for it, **Then** the wait fails within a bounded timeout with a message naming the expected event and the elapsed time, and does not hang the test suite.
3. **Given** multiple tests in the same class each emit events of the same name, **When** one test waits for "its" event, **Then** it waits for an event emitted during that test only, not one left over from a prior test in the class.

---

### Edge Cases

- A test seeds a return value for a Prefect method, and the code under test never calls that method — the adapter should make it trivial to assert "unused seed" so dead stubs don't accumulate.
- The code under test calls a Prefect method many times in one test; the adapter must preserve call order so the test can assert on the sequence, not just the set.
- Prefect upgrades change an argument or return type; adapter tests must fail at the adapter layer with a clear signal, not at a downstream assertion that happens to notice.
- An event is emitted but Prefect's ingest lags longer than the wait's bounded timeout; the failure message must distinguish "not emitted" from "emitted but not yet observable" whenever the adapter can tell the difference.
- Two tests in the same class or module share the adapter instance via a class-scoped fixture; state (recorded calls, seeded returns, emitted events) must not leak across tests.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Both real and in-memory test adapter implementations MUST be usable anywhere code currently depends on `PrefectClient` — production code and tests alike — through the shared port, without the caller knowing which implementation is injected. Production code depends on `PrefectClientAdapter`; test code depends on `PrefectClientTestAdapter`.
- **FR-002**: The adapter MUST validate that calls made to it use the argument shapes and types defined by the real Prefect client, and MUST fail the test when a call does not match.
- **FR-003**: The adapter MUST record every call made to it — the method name, arguments, and invocation order — in a form tests can query after the fact.
- **FR-004**: The adapter MUST allow a test to pre-seed return values for specific Prefect methods, keyed by method and optionally by argument match, so code under test receives realistic responses.
- **FR-005**: The adapter MUST return values of the real Prefect response types (not arbitrary mocks), so contract drift in Prefect shows up as test failures.
- **FR-006**: The adapter MUST fail a test with a clear message when code under test calls a Prefect method for which no adapter behavior has been defined, rather than silently returning `None` or a generic mock.
- **FR-007**: The adapter MUST expose assertion helpers tests can use without reaching into the underlying mock library (no `assert_called_once_with` on an internal `AsyncMock`).
- **FR-008**: The adapter MUST provide a primitive that blocks until a specified emitted event is observable by a Prefect query, returning as soon as it is observable and failing with a bounded timeout and a descriptive message when it is not.
- **FR-009**: The event-wait primitive MUST scope its search to events emitted during the current test, so prior tests in the same class or module cannot cause false positives.
- **FR-010**: The adapter MUST be resettable between tests (per-test fixture scope) such that recorded calls, seeded returns, and observed events from one test do not leak into the next.
- **FR-011**: The adapter MUST be usable in the existing pytest fixture patterns (the same place tests currently receive a `PrefectClient`) so migrating a test from mocks to the adapter changes the fixture and the assertions, not the code under test.
- **FR-012**: The adapter MUST make it straightforward to identify unused seeded return values at the end of a test, so dead stubs are visible.
- **FR-013**: At least one real test file currently using `create_autospec(PrefectClient)` or `AsyncMock` for Prefect MUST be migrated to the adapter as part of this feature, demonstrating parity.
- **FR-014**: Business/production code MUST depend on the production adapter port (`PrefectClientAdapter`) rather than on `prefect.client` directly. The port lives in a domain-owned module; the production real implementation (`RealPrefectClientAdapter`) wraps the Prefect client and is the only production module permitted to import from `prefect`. Test-only capabilities MUST live on a separate `PrefectClientTestAdapter` subclass of the production port so production callers cannot reach them through the type system.
- **FR-015**: `import prefect` and `from prefect...` statements MUST NOT appear outside the adapter module and the test trees that stand up an ephemeral Prefect server (currently `backend/tests/integration/conftest.py` and `backend/tests/functional/conftest.py`, which import `prefect.testing.prefect_test_harness`). A check (lint rule, import-linter contract, or equivalent) MUST enforce this boundary in CI; runtime-decorator imports covered by R-1's whitelist are a separate carve-out and do not count as violations.
- **FR-016**: Production-code migration MAY proceed incrementally subsystem-by-subsystem; the boundary check in FR-015 MUST be enforced per-subsystem as it migrates, not deferred until all subsystems are done.
- **FR-017**: The v1 in-memory test adapter (`InMemoryPrefectClientTestAdapter`) MUST be a recorder: it records calls with ordering and arguments, returns seeded responses, and exposes the event-wait primitive (FR-008) via condition-variable observation of its in-memory log. It is NOT required to simulate Prefect flow-run state transitions, fire callbacks, offer a controllable clock, or inject transport-level errors in v1.
- **FR-018**: A stateful-test-adapter follow-up — flow-run state transitions (Pending → Scheduled → Running → Completed), registered callbacks, a controllable clock, and injectable error conditions (e.g., API errors, timeouts, rate limiting, disconnects) — MUST be tracked as an explicit follow-up ticket linked from this feature. It is out of scope for this feature's delivery. The new capabilities land on the `PrefectClientTestAdapter` ABC so both `RealPrefectClientTestAdapter` and `InMemoryPrefectClientTestAdapter` can offer them where meaningful. The follow-up MUST be designed as a **programmable** test adapter, not a **simulating** one: state is held in explicit data structures, and transitions/errors/callbacks are driven by test-called hooks (e.g., `test_adapter.flow_runs.get(id).transition_to("Running")`, `test_adapter.inject_error(APIError)`). The in-memory implementation MUST NOT autonomously replicate Prefect's state-transition logic, retry semantics, or rate-limiting behavior. This constraint exists to prevent the in-memory adapter from drifting as Prefect evolves and to keep contract-test coverage (FR-021) meaningful.
- **FR-019**: The v1 production port (`PrefectClientAdapter`) MUST cover every Prefect surface currently imported from `prefect` in production code: automations (create/update/delete/read), deployments (read/run), events (emit/filter/count), flow runs (read/update state/logs), and work pools (read/create). The event-wait primitives (`wait_for_event`, `checkpoint`, `captured_emits`) are **test-only** capabilities and live on the `PrefectClientTestAdapter` subclass, not on the production port. Work queues are not wrapped in v1 — no production caller uses them today; they are added on-demand when a caller needs them (same rule as any speculative surface per FR-019's "currently imported" scope). v1 is considered complete when no production module outside the adapter imports from `prefect` (per FR-015). The concrete surface set is enumerated during planning by auditing every `import prefect` / `from prefect...` in production code.
- **FR-020**: Adapter port method names MUST mirror the Prefect client operations they wrap (e.g., `create_automation`, `run_deployment`, `emit_event`), so the mapping from adapter call to Prefect operation is obvious at review time. Subsystems MAY define thin domain-named wrappers around adapter calls inside their own module when this clarifies local call sites; such wrappers are subsystem-owned and not part of the adapter port.
- **FR-021**: A contract test suite MUST exist whose assertions are authored exactly once, in a shared helpers module, and invoked from two thin test packages: an `InMemoryPrefectClientTestAdapter`-backed package in the unit/component test tree and a `RealPrefectClientTestAdapter`-backed package in the integration test tree (the latter running against an ephemeral Prefect instance). The in-memory-backed package runs in the unit/component CI job; the real-backed package runs in the integration CI job. Both jobs gate merges. The integration job's failures MUST be analyzed and relaunched only when a transient cause is confirmed — they are never auto-skipped and the lane is never configured as non-merge-blocking. Contract tests type-hint against `PrefectClientTestAdapter` (the test port) so the `wait_for_event` / `checkpoint` / `captured_emits` primitives are reachable; production-exercising tests and production code itself type-hint against `PrefectClientAdapter` (the production port) and cannot reach test-only primitives.
- **FR-022**: Integration tests that exercise the real adapter against an ephemeral Prefect instance MUST live under `backend/tests/integration/` as a dedicated sub-package (which runs in the integration CI job — the same job that runs the rest of `backend/tests/integration/` — distinct from the unit/component CI job). The sub-package reuses the `prefect_test_fixture` already exposed by `backend/tests/integration/conftest.py`, and its own `conftest.py` MUST depend on that fixture explicitly so missing/broken setup fails loudly rather than silently skipping. Unit and component suites MUST NOT require a running Prefect server, Docker, or a network connection.
- **FR-023**: The `InMemoryPrefectClientTestAdapter` MUST support use without Docker, a Prefect server, or network access, so unit tests that substitute it do not depend on any of those resources. (An asyncio event loop is required because all adapter methods are `async`, but the adapter itself performs no blocking I/O.)
- **FR-024**: The real adapters (`RealPrefectClientAdapter` and `RealPrefectClientTestAdapter`) MUST target a single pinned Prefect version at any given time. Prefect SDK upgrades are delivered as deliberate, discrete work: the version pin is bumped, the real adapters are updated to match, and the full contract test suite (both the in-memory-backed and real-backed lanes) is re-run before merge. The production port and test port ABCs MUST remain stable across such upgrades; all signature deltas are absorbed inside the real adapter classes.

### Key Entities

- **Production Port (`PrefectClientAdapter`)**: A domain-owned ABC describing every production-used Prefect operation (18 methods in v1: automations, deployments, events emit/filter/count, flow runs, work pools). The only type production code depends on. Method names mirror the Prefect client operations they wrap (FR-020). Does **not** include `wait_for_event`.
- **Test Port (`PrefectClientTestAdapter`)**: An ABC that extends the production port with test-oriented primitives. v1 adds three: `wait_for_event` (matches by Prefect's native `Event.id`, by `name`, or by both — combined with a `since=Checkpoint` watermark when needed), `checkpoint() -> Checkpoint` (sync watermark for the simple "wait for the next event of this name after my action" case), and `captured_emits() -> AbstractAsyncContextManager[EmitCapture]` (async context manager that records every emission inside its scope for strict per-emission matching by id). FR-018 follow-ups add controllable clock, injectable errors, and callbacks. Only test code type-hints against this port; the type system itself keeps production code out.
- **Real Production Adapter (`RealPrefectClientAdapter`)**: The production implementation of the production port. Wraps the real `PrefectClient`. The only production module permitted to import from `prefect` (FR-014, FR-015). Has no test capabilities.
- **Real Test Adapter (`RealPrefectClientTestAdapter`)**: Inherits from `RealPrefectClientAdapter` and implements `PrefectClientTestAdapter`. Adds `wait_for_event` as a bounded polling loop over `filter_events` with **server-side filtering only** via Prefect's `EventFilter` (`id=EventIDFilter(...)`, `event=EventNameFilter(...)`, `occurred=EventOccurredFilter(...)`). Implements `checkpoint()` by recording a wall-clock instant and `captured_emits()` by intercepting its own `emit_event` to mirror the returned `Event` into every active capture. Used by the integration-lane contract tests and by functional tests that need a live Prefect server.
- **In-Memory Test Adapter (`InMemoryPrefectClientTestAdapter`)**: Implements the test port entirely in memory — every production-port method operates on in-memory state (event log, seed registry, call log), and `wait_for_event` resolves via an `asyncio.Event`/condition variable signalled by every `emit_event` (no polling). Additionally exposes in-memory-specific concrete helpers (`seed_return`, `recorded`, `call_count`, `recorded_calls`, `unused_seeds`, `reset`) that are **not** on any ABC — no real backend can deliver them. A recorder in v1 (FR-017): accepts calls with real Prefect argument/return types, validates shapes, records them, and returns seeded values. Usable without Docker, a Prefect server, or network (FR-023). Reset per test (FR-010).
- **Recorded Call**: A single invocation the in-memory test adapter observed — method, arguments, order, resulting return or error. The substrate of all adapter-level assertions.
- **Seeded Return**: A test-provided response to a specific port method call (optionally narrowed by argument match) that the in-memory test adapter will hand back when the code under test makes that call.
- **Observed Event**: A Prefect event emitted during the current test and visible to `wait_for_event`, scoped so prior-test emissions are excluded.
- **Contract Test**: A pair of tests — one `InMemoryPrefectClientTestAdapter`-backed (unit/component lane), one `RealPrefectClientTestAdapter`-backed (integration lane) — that invoke the same assertion helper from `backend/tests/helpers/prefect_client_contracts.py` to check observable behavior is equivalent across implementations (FR-021). The mechanism that prevents in-memory/real drift.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Authoring a new Prefect-touching test using the adapter requires no `AsyncMock` or `create_autospec` imports and no per-test stub helpers; the test sets up return values and assertions entirely through the adapter's API.
- **SC-002**: At least one existing test file that currently relies on `create_autospec(PrefectClient)` is migrated to the adapter with equal or stronger coverage and no loss of assertions.
- **SC-003**: A test that calls a Prefect method with a wrong argument shape fails at the adapter layer with a message that names the method and the mismatch, rather than silently passing.
- **SC-004**: The existing `test_thread_events` flake (and any other event-wait test migrated to the adapter) passes on the same CI runners that exhibited the 10s-timeout flake, using the adapter's wait primitive in place of the 30s polling loop.
- **SC-005**: In the median case, a migrated event-wait test completes in less time than the current fixed 30s ceiling, because the wait returns as soon as the event is observable.
- **SC-006**: When an expected event is never emitted, the migrated test fails within a bounded timeout with a message that identifies the missing event and the elapsed wait — with no suite-level hang.
- **SC-007**: When Prefect is upgraded and a method signature changes in a breaking way, at least one adapter-using test fails at the adapter layer, surfacing the break before it reaches integration tests.
- **SC-008**: After the v1 cut-over, no production module outside the adapter module contains an `import prefect` or `from prefect...` statement, enforced by a CI check that fails the build when violated.
- **SC-009**: Unit tests that substitute the `InMemoryPrefectClientTestAdapter` execute in under 10ms each (median, measured on CI) with no network, no Docker, and no Prefect server. Tests that exercise `wait_for_event` against the in-memory adapter complete as soon as the event is observable (condition-variable fast path; no polling latency).
- **SC-010**: Zero Prefect-attributable flakes on the unit and component CI suites over a rolling 30-day window once all call sites on an affected subsystem have migrated to the adapter port. Any non-zero count is treated as a regression and fixed as a bug, not absorbed as a tolerance.
- **SC-011**: The contract test suite passes identically against the `InMemoryPrefectClientTestAdapter` and the `RealPrefectClientTestAdapter` for every covered Prefect surface listed in FR-019; a surface added to the port without a corresponding contract test fails a CI check.
- **SC-012**: Integration tests using `RealPrefectClientTestAdapter` live as the sub-package `backend/tests/integration/prefect_client/` and run in the existing integration CI job (alongside the other `backend/tests/integration/` sub-packages); unit/component jobs pass with no Prefect server available, and the sub-package's `conftest.py` fails loudly rather than skipping when its required live-Prefect fixture is unavailable.

## Non-Goals

- Reimplementing any Prefect feature or orchestration behavior. The adapter wraps; it does not replace Prefect as the runtime.
- Wrapping the entire Prefect client surface speculatively. Only operations actually used by production code are in scope (see FR-019).
- Replacing integration tests. Integration tests against a real Prefect instance remain necessary and continue to exist; this feature does not remove them, only scopes them narrowly and isolates their cost from the fast suites.
- Eliminating flakiness in integration tests themselves. The adapter's `wait_for_event` primitive does reduce event-related flakiness at the integration layer (cross-test false positives, bounded timeouts) — but Prefect-server-inherent flakiness (startup variance, ingest lag, socket contention) is not eliminated by this feature. That residual is owned by the integration/functional CI-lane policy: separate CI job from unit/component, and failures analyzed before relaunch (never auto-skipped).
- Designing for a hypothetical migration off Prefect in v1. The interface preserves that optionality by construction (benefit 7), but no second backend (e.g., Dagster, Airflow, Temporal) is designed or stubbed for in this feature.

## Assumptions

- The adapter defines two domain-owned ports: `PrefectClientAdapter` (production) and `PrefectClientTestAdapter(PrefectClientAdapter)` (test). Production code depends on the production port; test code depends on the test port. Production code is migrated to the production port incrementally, subsystem-by-subsystem, and the "no `import prefect` outside the adapter/test conftest whitelist" boundary is enforced per-subsystem as each migrates.
- The v1 production port covers every Prefect surface currently imported from `prefect` in production code (automations, deployments, events emit/filter/count, flow runs, work pools). The test port adds `wait_for_event` only. The concrete production-port set is enumerated during planning by auditing imports; surface not used by production code — including work queues — is out of scope for v1 and added on-demand when a caller needs it. Speculative surface additions (for future features) are not in scope.
- Prefect remains the event and orchestration backend for Infrahub for the foreseeable future; building against its client is worth the investment. The port/adapter shape preserves optionality for a future backend change without designing for one now.
- Tests that need true end-to-end behavior against a live Prefect server (e.g., full integration tests with `prefect_test_fixture`) continue to use the real adapter (which wraps the real Prefect client). These tests live either as a sub-package of the existing integration test tree (`backend/tests/integration/prefect_client/` for the real-backed contract suite) or in the existing functional tree (`backend/tests/functional/proposed_change/test_thread_events.py` for the end-to-end thread-events scenario). Isolation from the fast lane is at the CI-job level — integration and functional each run as their own job, separate from unit/component — not at the directory level (the Prefect tests share their directory with every other test in that lane). Failures on those jobs must be analyzed and relaunched only when a transient cause is confirmed — they are not auto-skipped and not treated as free-to-ignore.
- The event-wait primitives live only on `PrefectClientTestAdapter` (`wait_for_event`, `checkpoint`, `captured_emits`). `RealPrefectClientTestAdapter` implements `wait_for_event` as a bounded polling loop over `filter_events` with **server-side filtering only** via Prefect's `EventFilter` (id, event-name, and occurred-since fields all filter at the API). `InMemoryPrefectClientTestAdapter` implements `wait_for_event` via an `asyncio.Event`/condition variable signalled by every `emit_event` — no polling, no latency. Matching is keyed on Prefect's native `Event.id` whenever possible (no custom token stamped into `payload`); `checkpoint()` produces an opaque watermark and `captured_emits()` records emissions in its async-with scope. Determinism of the wait is the problem being solved, not availability of the query.
- The flakiness categories the adapter is expected to eliminate at the unit/component level are: asyncio event-loop mismatches, state-transition race conditions, shared ephemeral-server state under pytest-xdist, network latency variance, and system resource contention from spinning up Prefect/SQLite/ports in-test. Tests hitting the real Prefect (the `integration/prefect_client/` contract suite and the migrated `functional/proposed_change/test_thread_events.py`) benefit partially — the adapter's `wait_for_event` primitive (Prefect-native `Event.id` matching plus `Checkpoint`-watermark `since=` scoping, bounded timeout per R-6) replaces the current polling-with-retry anti-pattern and eliminates the cross-test false-positive class — but the residual flakiness categories inherent to a live Prefect server (server startup time variance, ingest lag, socket contention) remain. Those are owned by the integration/functional CI-lane policy (FR-022, SC-012): the Prefect-using tests run in CI jobs separate from the unit/component lane, and failures on those jobs are analyzed before relaunch, never auto-skipped.
