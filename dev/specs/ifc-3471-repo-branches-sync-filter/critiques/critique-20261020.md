# Critique: Filter a repository's branches by sync status

**Date**: 2026-10-20 | **Artifacts**: spec.md, plan.md, research.md, contracts/, quickstart.md | **Verdict**: PROCEED WITH UPDATES

## Executive summary

The problem is real and evidenced (IFC-3156 test plan names it as a follow-up), the scope is one card, and the backend already does the filtering. One must-address item: the end-to-end test design in R7 relies on a branch that the read-write repository's Branches section does not list, and on a stored value that a synchronization cycle can overwrite. Everything else is a recommendation.

## Product lens

- **3a Problem validation**: Clear. IFC-3156 documents the GraphQL sandbox workaround. Scope is right: one filter, one value at a time.
- **3b User value**: User Story 1 alone delivers the need. Stories 2 and 3 follow the existing Status filter, so they add little risk.
- **3c Alternatives**: A preset "Failing branches" button would be one click, but it is a new pattern the section does not have and would need two values per request, which the query cannot do. Not pursued (P1).
- **3d UX**: Empty, combined and invalid-URL states are covered. The picker lists values in schema order with "Unknown" first; the failure values are second and third (P2, question).
- **3e Success**: SC-001 to SC-004 are verifiable by tests and the quickstart.

## Engineering lens

- **4a Architecture**: The optional formatter keeps the shared component's other two callers on unchanged code. The toolbar taking `schema` mirrors the columns.
- **4b Failure modes**: An invalid value is guarded. If the repository schema has no `sync_status` attribute, the definitions omit the field and the column is absent; no crash path.
- **4c Security**: No new trust boundary; the URL value is validated before reaching the request.
- **4d Performance**: No change; one request per filter change, as today.
- **4e Testing**: Unit and component coverage is thorough. The end-to-end design has a gap (E1). A test should also prove that the Dropdown value input accepts the "contains" condition, which no current card test exercises with a Dropdown field (E2).
- **4f Operations**: Frontend-only, reverted by a revert of the PR. `graphql-cache.d.ts` conflicts on rebase are resolved by regenerating (E3).
- **4g Integration**: The backend argument is untyped `String`; the guard is the only protection. A new backend value is offered by the picker but dropped by the guard until the list is updated (accepted in R3).

## Cross-lens insights

- X1: The docs question (no page documents the Branches section) is left to phase 4.6; the changelog fragment is the user-visible record either way.
