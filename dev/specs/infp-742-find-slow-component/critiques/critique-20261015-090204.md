## Executive Summary

The spec and the plan solve a real, recorded problem: operators cannot name the slow component, and
OpsMill support investigates without data (card [INFP-742](https://opsmill.atlassian.net/browse/INFP-742),
design document sections 1 and 5, the 2026-08-13 incident). The scope follows the card, each user
story ships on its own, and the plan reuses a tested draft instead of starting again. Two items must be
fixed before tasks are written:

- Masking covers span attributes but not span events. The exception messages that OpenTelemetry stores
  as span events can carry URLs with query strings and other secrets, so SC-005 cannot pass.
- The main user story (story 1) depends on an SDK change that is not started and has no ticket. Without
  it, the 1.13 goal "one trace from a task to its queries" is not met.

The other findings are improvements to verification, rollback and documentation, and three questions
for stakeholders.

What was checked: the spec, the plan, research, data model, contracts and quickstart of this feature;
the constitution; and the draft code on branch `dp-20261008-diagnose-slow-instance-infp-611-for-testing`
for the points named below. Not checked: the Helm chart repository, the service that builds the Compose
file on `infrahub.opsmill.io`, and the draft tests (not run).

### Security & Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | 🎯 | `infrahub.trace::mask_span` masks span attributes and copies span events unchanged. OpenTelemetry stores exceptions as span events (`exception.message`, `exception.stacktrace`). An HTTP client error raised during a single sign-on token exchange, for example, has the full URL with its query string in its message. Such values reach the trace store unmasked, so SC-005 fails. | Add to FR-012: span event attributes are masked with the same rules, and `exception.message` has URL query strings replaced. Add a unit test with an exception whose message contains a URL with `code` and `state`. Update `contracts/masking.md`. |
| E5 | 💡 | The design document asks to check whether the flow run logs that task workers send to the Prefect server pass through the masking (section 6, log audit). The draft adds the filter to that handler, but no test in the quickstart proves it. | Add a test: a log line with a token in a flow run reaches the Prefect API handler with `[MASKED]`. |
