# Critique Report: Scoped number pools — one pool serves every scope

**Date**: 2026-10-02
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ **PROCEED WITH UPDATES**

---

## Executive Summary

The spec and plan are well-grounded: research §0 corrected four PRD assumptions against HEAD, the
branch seam is designed rather than discovered, the user's delivery constraint (contract first, then
seams, then internals, concurrent after set A) is carried faithfully through User Story 1, FR-018,
FR-019 and the four change sets, and the central claim — that the fork-window visibility rule the
value read applies can be lifted onto the relationship hop — holds against the code:
`query/relationship.py::RelationshipDeleteQuery` writes a `deleted` edge on the *same* `Relationship`
vertex when the live edges belong to another branch and closes `to` when they belong to the writing
branch, and `relationship/model.py::RelationshipManager.update` replaces the vertex on a peer change,
so "a hiding edge on the same vertex" means the same thing for `IS_RELATED` as for `HAS_VALUE`.

Five findings block task generation. Four are engineering gaps a task writer would hit mid-implementation:
the **template-applier path allocates before the node has any relationship** (so "on create nothing
changes" is false for templates); the **records fragment projects no branch**, so the branch split
the per-division report needs is not available from the fragment the plan moves the allocated query
onto; the planned **`process_diff` change for removal constraints is redundant and the checker would
receive a schema the field is already gone from**; and the frozen contract makes `display_label`
non-nullable for a peer the reading branch may not be able to read. The fifth is a product trap the
two lenses converge on: validating every save against the mutation branch while storing the scope
once, branch-agnostically, means a scope saved on a branch **cannot be re-sent unchanged from the
default branch** — the pool form's round trip is refused.

None is fundamental. All five fit inside the design; the remedies are small and named below.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | **The template-applier path allocates before the node has a single relationship, and without a node.** Plan §3 says "On create nothing changes: relationships are already applied first" and set C says "the template path passes the division of the node they allocate for". But `node/__init__.py::Node._process_fields` calls `handle_object_template` — which drives `templates/node_applier.py::NodeTemplateApplier._handle_pool_relationship` → `pools/default_allocator.py::DefaultPoolAllocator.allocate_for_attribute(pool_relationship, target_schema, attribute_name, identifier)` — *before* `_process_fields_relationships`. That allocator receives no node; the only state is the raw `fields` dict holding `{"id": …}` / hfid payloads. `DivisionResolver.division_of(node, …)` has nothing to read. Only the component path (`node/create.py::allocate_from_resource_pools`, after `obj.new()`) has the node. A device created from a template that names a scoped pool would be allocated in the *empty* division. | `plan.md` §3 and §1 set C: for the applier path, defer the number-pool allocation instead of computing a division without a node — `_handle_pool_relationship` adds the attribute to `TemplatePoolFields.pending` (the mechanism exists; `_validate_mandatory_attributes` already tolerates pending pool fields) and records the pool id, and `_process_fields_attributes` runs `handle_pool` for it after relationships are applied, as it does for `from_pool`. Add a functional test: template-created device in site C with a scoped pool receives the number free in C. `research.md` D4: replace "On create nothing moves" with the two create paths. |
| E2 | 🎯 | **D8's `process_diff` change is redundant, and the checker will be handed a schema the field is gone from.** `core/models.py::SchemaUpdateValidationResult.add_validator_for_migration` already appends a constraint for every migration whose name is in `CONSTRAINT_VALIDATOR_MAP` — that is exactly how `node.attribute.add` reaches `NodeAttributeAddChecker`. Registering `node.attribute.remove` / `node.relationship.remove` in `core/validators/__init__.py` is sufficient; the planned "append the removal constraints beside the removal migrations" in `_process_attrs_rels` would produce two constraints per path and run the checker twice. Separately, `api/schema.py::_validate_migrations` builds `SchemaValidateMigrationData(schema_branch=candidate_schema)`, and `validators/tasks.py::schema_validate_migrations` resolves `node_schema` from that candidate — so for a removal the request's `node_schema` no longer has the field, and any `get_attribute`/`get_relationship` call in the checker raises (the task then degrades it into an opaque violation). | `research.md` D8 and `plan.md` §5: drop the `process_diff` change and `core/models.py` from the source tree; "register the two removal names in `CONSTRAINT_VALIDATOR_MAP`; `add_validator_for_migration` does the rest". State that `ScopedPoolDependencyChecker` reads only `request.schema_path.schema_kind` and `field_name` and never the field from `request.node_schema`. Add a unit test with a `node_schema` lacking the field. |
| E3 | 💡 | **`DivisionResolver.division_of` is not pure.** `relationship/model.py::RelationshipManager.get_peer_id` reads the database when the relationship was not in the payload (the update path's `obj` comes from `NodeManager.find_object` without prefetched peers) or when the peer is named by hfid. The plan calls the three `pools/` modules "pure" (Complexity Tracking, Testing Strategy) and tests `division_of` in `tests/unit/`. | `plan.md` Complexity Tracking row 3 and Testing Strategy *Unit*: `division_of` is async, takes `db`, and gets a component test; only `entries_in_force`, `ScopeValidator` and `DivisionReporter` are unit-tested. |
