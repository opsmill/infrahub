# Critique Report: Schema-defined field sections

**Date**: 2026-11-04
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: PROCEED WITH UPDATES

---

## Executive Summary

The spec states a real, customer-sourced problem (reading a node with sixteen rows) and keeps the
change inside the schema layer, with validation at load time and no graph or GraphQL change. The
plan reuses the existing validator plug-in interface, the hashable-model list merge and the
react-aria Disclosure already used in the repository card, and sequences the SDK submodule
correctly. Six points block the tasks: the `state: absent` removal (FR-007) cannot work with the
generator list as written, because a field the list omits becomes read-only in the write contract
and is dropped (this is why `state` on a dropdown choice is dropped today); the narrowed per-section
schema loses the resource-pool row, because the summary filter removes `_from_resource_pool`
relationships before the partition; the accessibility contract contradicts the header design (the
description inside the trigger button becomes part of the region's name); plan risk 7 is wrong
(`InfraLagInterfaceL3` can redeclare `mtu` with `container: layer3`, so the demo can show a Layer 3
card and SC-002 can be tested); constitution II asks for merge behaviour to be specified and tested
and the plan has no merge test; and `getFormFieldContainer` is a one-caller helper, which
constitution VII forbids. All six have small, local edits.
