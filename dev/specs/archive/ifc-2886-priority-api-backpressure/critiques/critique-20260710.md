# Critique Report: Priority-aware API backpressure (server-side)

**Feature**: IFC-2886 | **Date**: 2026-07-10 | **Artifacts reviewed**: spec.md, plan.md, research.md, data-model.md, contracts/

## Executive Summary

The spec and plan are **strong and implementation-ready**. The problem is well-evidenced (a real "app appears hung under background load" failure mode), the scope is tightly bounded (server-side only, per-worker, no persistence), the design is grounded in the actual codebase, and the constitution check passes. The dual-lens review surfaced **one Must-Address** issue — the shedding load signal (slot-sojourn) only fires when *slot* contention is the binding constraint, so the derived cap must be validated to actually produce that signal before Neo4j saturates silently — plus several recommendations around rollout sequencing, Prometheus multiprocess gauges, and the request↔connection ratio. None are architectural rethinks.

**Verdict**: ⚠️ **PROCEED WITH UPDATES** — the Must-Address item is resolved in-place by tightening the spec's assumption/success-criteria and the plan's capacity note (applied below); no redesign required.

## Product Lens Findings

### 3a. Problem Validation
- **Strong.** The problem statement names concrete contended resources (uvicorn worker pool, Neo4j connection pool) and a concrete symptom (frontend unresponsive/hangs). Evidence is the existing origin-blind DB throttle (`database/__init__.py:338`) that delays rather than sheds — the limitation this feature removes. This is a real pain, not a solution looking for a problem.

### 3b. User Value Assessment
- The P1 user story ("frontend stays responsive under background overload") is the whole value and is independently testable. **Caveat (P1 below):** that value is only realized once the *frontend* actually sends `X-Priority: high` — a separate ticket. Until then interactive traffic is `normal` and is shed on the same footing as background `normal` traffic.
- MVP is already the plan: server-side only, three classes, per-worker. Nothing obvious to cut.

### 3c. Alternative Approaches
- Simpler alternatives (fixed queue-length limit, token bucket) were considered in research.md and correctly rejected — they need per-deployment tuning, which contradicts the "no hand-tuned limits" goal. Reusing an off-the-shelf library was implicitly rejected; CoDel + a 3-queue slot pool are small enough that a dependency isn't warranted (Constitution VII). Reasonable.
- Cost of inaction is concrete: instances continue to appear hung under heavy background load.

### 3d. Edge Cases & UX
- Edge cases are unusually well-covered (disconnect-while-queued, sub-interval burst, malformed header, overload-end recovery, low-priority starvation). 
- **Gap (P2):** the *operator* experience on first enable is under-specified — see P1. No end-user UI surface (correctly out of scope).

### 3e. Success Measurement
- SC-002…SC-006 are measurable. **SC-001 is intentionally deferred** ("discovery-measured") — acceptable per the PRD, but it means there is no committed pass/fail latency bound until the discovery scenario is defined. Tracked as Q1 (a question, not a blocker, since the PRD explicitly defers it).
- Rollback trigger exists (the `backpressure_enabled` kill-switch) — good operational hygiene.

## Engineering Lens Findings

### 4a. Architecture Soundness
- **Sound.** Pure-ASGI outermost middleware, pre-auth, path-excluded for liveness/scrape — the right layer. Clear separation: parser / slot pool / CoDel / controller / metrics / middleware, each independently testable. No circular deps. The primitives are small and swappable.

### 4b. Failure Mode Analysis
- **E1 (Must-Address) — the load signal can be blind to the real bottleneck.** Sojourn measures *time waited for a slot*. It only rises when in-flight requests reach `max_concurrency`. If the derived cap (`= Neo4j pool size`, default 100) is **larger** than what Neo4j can actually serve at acceptable latency, requests are admitted freely, pile onto a saturating database, handler latency balloons — yet slot-sojourn stays near zero and **nothing is shed**. The feature would then fail to protect the frontend under exactly the overload it targets. The design implicitly assumes slot contention binds before DB saturation; that assumption is not stated or validated. *Suggestion:* make it explicit that the discovery scenario (SC-001) MUST confirm the derived cap produces a sojourn signal under the real DB bottleneck, and provide the `backpressure_max_concurrency_factor` (< 1.0) as the headroom knob to pull the cap below raw pool size when it doesn't. (Applied to spec Assumptions + SC-001 and plan capacity note.)
- Graceful degradation is otherwise good: shed = fast 429, kill-switch, self-terminating shedding.

### 4c. Security & Privacy
- **E2 (Recommendation).** `X-Priority` is untrusted; any caller can claim `high`. v1 accepts this (cooperative first-party). Beyond the missing-header counter (FR-OBS-7), there's no visibility into *who* is claiming `high` — a misbehaving first-party SDK defaulting to `high` would silently defeat the gradient and it wouldn't show up distinctly in metrics. *Suggestion:* note this as a known adoption risk and consider (fast-follow) a per-source breakdown; not a v1 blocker. No sensitive data is handled; no compliance surface.

### 4d. Performance & Scalability
- **E3 (Recommendation) — request↔connection ratio.** Deriving `max_concurrency = pool_size` assumes ~1 DB connection per in-flight request. A single request that holds two connections concurrently (e.g. nested transactions / parallel queries) could exhaust the pool before the slot cap binds, again muting the sojourn signal and handing work to the old busy-wait throttle. *Suggestion:* state the 1:1 assumption explicitly and default the headroom factor conservatively (or document why 1.0 is safe here). Ties into E1.
- Hot-path cost is minimal (header read + slot attempt + CoDel eval) — fine for 10× growth since it's per-worker and O(1).

### 4e. Testing Strategy
- **Comprehensive and correct for the risk.** Fake-clock CoDel, cancellation-safety, gradient, metric deltas, no-mocking. The plan even identifies this as the first direct middleware test coverage in the repo. Nothing to add.

### 4f. Operational Readiness
- **E4 (Recommendation) — Prometheus multiprocess gauges.** Under gunicorn (4 workers) the API serves metrics per-process; the plan notes gauges are per-worker (acceptable). But if the API server runs with `PROMETHEUS_MULTIPROC_DIR` set, plain `Gauge`s (`in_flight`, `waiters`, `max_concurrency`) aggregate incorrectly across workers unless a `multiprocess_mode` (`livesum`/`max`) is set. *Suggestion:* the implementation task should verify whether the API (not just the task-worker) runs in multiprocess mode and set `multiprocess_mode` on the gauges accordingly, or explicitly document that per-worker series is the intended read. Add a task note.
- Rollback (kill-switch), observability (8 families), and no migrations = good operational posture.

### 4g. Dependencies & Integration Risks
- **E5 (Recommendation) — `prometheus_client` is a transitive pin.** Research flagged it: imported directly in-tree but only resolved via prefect/starlette-exporter. Adding another direct importer is consistent with current practice, but declaring it explicitly in `pyproject.toml` removes a latent break if an upstream drops it. *Suggestion:* add `prometheus-client` as an explicit direct dependency in the same PR (low-risk, no version change). Governance: this keeps "no new dependency" honest (it's already resolved).
- Integration with the existing DB throttle is complementary, not conflicting — but see E1/E3 for the interaction that must be validated.

## Cross-Lens Insights

- **X1 (Must-Address, = E1 + P1): "enable safely" couples rollout to effectiveness.** Two things must both hold for the P1 promise to be real on day one: (a) the derived cap must actually produce a sojourn signal under real overload (E1), and (b) the frontend must send `X-Priority: high` (P1) — otherwise interactive traffic is `normal` and gets shed alongside background load, i.e. the deploy converts *hangs* into *429s* for interactive users without protecting them. *Resolution:* document the rollout sequencing (validate cap via discovery scenario → ship inert/kill-switch-off or after frontend sends `high`), and record that shipping with `backpressure_enabled=True` before the frontend sets `high` is a deliberate, kill-switch-guarded choice. Applied as a spec assumption + plan note.

## Remediation applied (autonomous, per prep workflow)

- **E1 / X1 (Must-Address):** added an explicit assumption to `spec.md` (slot contention must bind before DB saturation; headroom factor as the lever), sharpened SC-001 to require the discovery scenario to validate the sojourn signal, and added a capacity/rollout note to `plan.md`.
- **E3, E4, E5 (low-risk Recommendations):** folded into `plan.md` (capacity note, metrics multiprocess note, explicit-dependency note) so the tasks phase picks them up.
- **P1, E2, Q1:** left as documented notes/assumptions (P1 cross-referenced; Q1 already reflected as a deferred SC per the PRD). No blocking action.
