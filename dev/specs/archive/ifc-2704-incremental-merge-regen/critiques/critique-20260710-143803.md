# Critique: Incremental generator & artifact execution on merge

**Date**: 2026-07-10 · **Feature**: [../spec.md](../spec.md) · **Plan**: [../plan.md](../plan.md)

**Verdict**: ⚠️ **PROCEED WITH UPDATES** — the diff-capture/serialization/threading half (D1–D3,
D8, D9) is sound. The member-level selection half over-claimed reuse of the proposed-change
machinery and had two under-execution holes (the one forbidden failure mode). All Must-Address
findings are resolved inline in `research.md`, `plan.md`, `data-model.md`, and the contracts;
see the "Resolution" column. No RETHINK: the core architecture survives; only the member-level
mechanism was re-specified.

## Executive summary

Selectivity has two halves. **Capture** (get the changed-set out of the merge before the diff
freezes, in the pipeline's cache shape) is well-researched and safe. **Selection** (turn that
changed-set into a minimal dispatch) reused proposed-change helpers that were built for a
*live source branch*, *artifact-id-space* comparison, and *live-group iteration* for new
members — none of which transfer unchanged to a diff-only, member-id-filtered, post-merge
default-branch context. Left unfixed, the SPECIFIC and new-member cases (common, and exactly
what the feature optimizes) would leave artifacts stale. The plan is corrected to reproduce the
proven live-group reconciliation on the target branch and to map impacted subscribers to member
ids.

## Engineering Lens findings

### 4a / 4b — Architecture & failure modes (the under-execution holes)

- **E1 🎯 (Failure mode) — subscriber-id vs member-id mismatch.**
  `get_field_level_impacted_subscribers` returns subscriber (artifact/generator-instance) node
  ids (`proposed_change/tasks.py:836`), but `target_members`/`members` filter on member node
  ids (`generators/tasks.py:227`, `git/tasks.py:594-598`). Passing the impacted ids straight
  into the member filter makes `member.id not in members` true for every real member → zero
  regeneration for the definition. **Resolution**: member selection now maps impacted subscriber
  ids → member ids via the live group's `member.id → subscriber_id` map, and only member ids
  are ever placed in the dispatch filter (research D4, data-model §5, contract
  branch-merge-post-process).

- **E2 🎯 (Failure mode) — new-member / membership coverage not delivered (FR-007).**
  The PC path covers new members by fetching the *live group* and rendering any member whose
  existing subscriber is `None` (`validate_artifacts_generation:902`, `_should_render_artifact`
  short-circuit `:1044-1045`). The plan replaced that with a diff-derived member filter, which
  cannot enumerate a newly added member (its subscriber query returns `[]`) or an
  existing-object membership-only change (surfaces as a relationship element the query never
  reads). **Resolution**: the merge selection now fetches the live group on the target branch
  and applies the same `_should_render_*` reconciliation (new member → always render); a
  group-membership definition gate selects a definition when its target group appears in the
  diff. (research D4/D4a, data-model §5, contract branch-merge-post-process, quickstart #3/#15.)

- **E3 🎯 (Failure mode) — analysis bound to a live, possibly-deleted source branch.**
  The impact analysis runs live schema/graphql/subscriber lookups against `source_branch`
  (`tasks.py:810-835`), which may be deleted by the concurrently-submitted `BRANCH_DELETE`
  (`post_merge.py:93-104`, `delete_branch_after_merge`) or is a pre-merge view. **Resolution**:
  all live lookups run against the **default/target branch** (where merged data lives); the
  captured summary is tagged with the **default-branch name** so `get_modified_kinds` /
  `_relevant_node_changes` and the live queries use one consistent branch, and source-branch
  deletion is irrelevant (only its data, now on default, is needed). (research D2/D3/D4,
  contract merge-diff-summary.)

### 4b — D7 direct-merge cascade

- **E4 💡→🎯 (Failure mode) — cascade has no sequencing.** D7 submitted full artifact regen
  *concurrently* with the generator run, so artifacts could render against pre-generator state
  and stay stale. **Resolution**: the D7 validation spike is now a **blocking prerequisite**.
  If the event-driven machinery covers generator→artifact staleness, rely on it and drop the
  fallback; otherwise the fallback must *await* generator completion before artifact regen
  (research D7, plan phase 6, quickstart #11).

### 4d — Performance & the "no new hot-path Cypher" claim

- **E5 💡 — correct new-member coverage requires group/subscriber fetches.** These are the same
  fetches the PC CHECK flow already does; the earlier "no new Cypher on the hot path" phrasing
  was wrong for the member level. **Resolution**: plan Constitution V note corrected — the diff
  is already loaded, but member reconciliation performs bounded per-selected-definition group
  fetches, matching the existing PC cost profile.

### 4b — Null-fingerprint fallback signal

- **E6 💡 — repo-commit signal may be absent at capture.** D6's null-fingerprint fallback
  assumed a `CoreRepository.commit` change in `branch_diff.nodes`, but the repo re-import
  happens on the default branch during the follow-up (after capture). **Resolution**: a
  verification task confirms the signal; if unreliable, the null-fingerprint case escalates to
  full regeneration of the affected repository's definitions (coarsest safe fallback; the state
  is transient and self-heals on re-import). (research D6, quickstart #9.)

### 4a — Capture safety (MINOR, hardened)

- **E7 💡 — capture must not endanger the merge.** The capture point sits inside the merge's
  rollback try-block; a serialization bug there could roll back a correct merge. **Resolution**:
  capture + cache-write is wrapped in its own inner try/except that yields
  `merge_diff_cache_key = None` (→ full-regen fallback) and never propagates. The
  "cache-write-succeeds-but-key-lost" case is benign (cache-miss → fallback; TTL expiry).
  (research D1, contract merge-diff-summary.)

### 4f — Operational readiness

- **E8 💡 — observability for silent under-execution.** **Resolution**: each merge logs/metrics
  whether it took the selective or fallback path and the dispatched counts, so under-execution
  or unexpected full-regen is observable. (research D9, plan phase 1.)

### NOT A PROBLEM (recorded)

- Fingerprint-only change fires `_definition_changed` correctly (converter emits the
  `fingerprint` ATTRIBUTE element; matched on node id + triggering action).
- Config default-True is safe as a mechanism (every fallback and the `None` key route to
  byte-for-byte current behavior); with E1–E3 closed, default-True is acceptable.

## Product Lens findings

- **P1 💡 — problem & value are well-grounded.** Clear originating incident (IFC-2306,
  ~20-minute unusability), measurable success criteria, correct MVP framing (selectivity with a
  safe fallback). No action.
- **P2 🤔→resolved — rollout metric.** "How do we know it's working / when to roll back?" is
  answered by SC-004 (before/after dispatched-task count, flag-off baseline) plus the E8
  observability metric and the reversible flag. Resolved with best judgment; no spec change.
- **P3 💡 — migration for existing users.** Pre-IFC-2844 (null fingerprint) data is a transient
  state that self-heals on re-import and is covered by the over-execution fallback; no user
  migration action required. Documented in Assumptions.

## Cross-lens synthesis

- **X1 🎯 — the reconciliation is the load-bearing safety mechanism, not an optimization.**
  Both lenses converge: the product requirement "new targets regenerate" (FR-007) and the
  engineering invariant "no under-execution" are the *same* requirement, and both are satisfied
  only by iterating the live group and force-rendering members with no subscriber — the exact
  step the first draft dropped. This is now the spine of the member-level design (research D4).
