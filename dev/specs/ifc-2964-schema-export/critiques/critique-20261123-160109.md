# Critique Report: Export the running schema

**Date**: 2026-11-23

**Feature**: [spec.md](../spec.md)

**Plan**: [plan.md](../plan.md)

**Verdict**: PROCEED WITH UPDATES

Severity labels: Must-address (blocks `/speckit-tasks`), Recommendation, Question (needs stakeholder input).

---

## Executive Summary

The spec and plan solve a problem with clear sources: INFP-723 asks for an export that loads without editing, and IFC-2964 asks for Infrahub to own the rules because the SDK copy drifted. The plan's main idea, finding the values to leave out by running schema processing on a candidate and comparing, removes the hand-written rule list that caused the drift. Four items block task generation:

- the reduction loop can run forever on a stored schema that processing would not reproduce (E1);
- the SDK cannot tell an older server from a failed export, because both answer 422 (E2);
- the cached baseline shares its schema cache with every copy, so each export adds entries that are never removed (E3);
- the constitution requires a `dev/knowledge/backend/` update for a backend architecture change, and the plan defers it (E6).

All four have direct fixes in `plan.md` and `research.md`.

## Engineering Lens Findings

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
| --- | --- | --- | --- |
| E1 | Must-address | Research R3 stops the loop "until no field differs" and states that each pass puts back at least one field. That is false when a differing field is already in the candidate. It happens when the stored schema is not what processing produces from the `FULL` document, for example a schema stored by an earlier release whose processing differed. The R8 tests prove the `FULL` round trip only for the test schemas, not for every stored schema. The loop then repeats the same pass forever, inside an API request. | In R3, stop when a pass puts back no field, and cap the passes at the number of fields in the document. Define what the response does with the remaining differences (see X1). Add a unit test with a stored schema that processing changes, and assert that the export ends. |
| E6 | Must-address | The constitution, section Documentation Requirements, says "Backend architecture changes MUST update `dev/knowledge/backend/`". The exporter adds a component with a non-obvious mechanism (the reduction loop and the core-only baseline). The spec lists the knowledge file as a follow-up, and the plan does not include it. | Add `dev/knowledge/backend/schema-export.md` to the plan's source tree and delivery order: the field classes, the reduction loop, the baseline, and the pinned properties. |
| E8 | Recommendation | Research R9 pins `uniqueness_constraints` on a node when it equals the first generic's stored value. Processing merges a node's own unique attributes into its `uniqueness_constraints` (`SchemaBranch.sync_uniqueness_constraints_and_unique_attributes`), so a node with a copied value and one unique attribute of its own is not pinned. The loop then decides, which is probably correct because `human_friendly_id` stays pinned, but no variation schema covers it. | Add a variation schema in R8: a node that inherits `human_friendly_id` from a generic and has its own `unique: true` attribute. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
| --- | --- | --- | --- |
| E2 | Must-address | On an older server, `GET /api/schema/export` reaches `get_schema_by_kind`, which raises `SchemaNotFoundError` with HTTP 422 (`backend/infrahub/exceptions.py::SchemaNotFoundError`). The contract returns 422 for a failed `BRIEF` export too, because `SchemaNotValidError` also has `HTTP_CODE = 422` (`backend/infrahub/api/exceptions.py::SchemaNotValidError`). Research R7 treats any 404 or 422 from the URL as "endpoint missing", so a failed export on a new server tells the user to upgrade a server that is already up to date. | Return a failed export as a server error (500) with its own exception class, because it is a defect and not a client error. In R7, treat only a 422 whose body is the schema-not-found error for the kind `export` as "endpoint missing". Add an SDK test for each response. |

### Performance and Scalability

| ID | Severity | Finding | Suggestion |
| --- | --- | --- | --- |
| E3 | Must-address | `SchemaBranch.duplicate` keeps the same `_cache` dictionary as the original (`backend/infrahub/core/schema/schema_branch.py::SchemaBranch.duplicate`), and `SchemaBranch.set` adds every schema it stores to that cache. Research R4 caches the baseline for the life of the process and duplicates it on each pass. Each export therefore adds the candidate's nodes and generics to the baseline's cache, and nothing removes them. Memory grows with every schema change exported. | In R4, give each export a cache of its own, copied from the baseline's cache, and drop it at the end of the request. Add a unit test that checks the baseline's cache size is the same before and after an export. |
| E4 | Recommendation | The plan runs processing on the request's event loop, as `POST /api/schema/load` does. A load is rare and done by a schema owner. An export can be called often by automation, for example the comparison tool in INFP-751, and each call processes the schema several times, so it delays other requests on the same worker. | Once E3 is fixed and each export works on its own objects, run the export in a thread (`asyncio.to_thread`) from the start instead of as a follow-up. Keep the timing record in the functional test. |

### Testing Strategy

| ID | Severity | Finding | Suggestion |
| --- | --- | --- | --- |
| E5 | Recommendation | Research R8 resets the database inside a `TestInfrahubApp` class with `delete_all_nodes` and `first_time_initialization`. That removes the accounts and API tokens the class fixtures created (`admin_account`, `bot_account`, the unprivileged account) and the account groups, so the SDK client fails to authenticate after the reset. | Name a helper in R8 that, after the reset, creates the accounts again with the same tokens and runs `initialization`. ### Dependencies and Integration

| ID | Severity | Finding | Suggestion |
| --- | --- | --- | --- |
| E7 | Recommendation | Two ordering risks between the repositories. First, `SchemaLoadAPI` is a subclass of the SDK's `InfrahubSchemaWrite`, so the moment the submodule bump brings in `infrahub_version`, `SchemaRoot` (`extra="forbid"`) rejects payloads that carry it unless `build_internal_schema` excludes it in the same commit. ## Resolution (2026-11-23, added after the review)

- Loop could run forever (E1): fixed in research R3. The loop stops when a pass puts back nothing, and remaining differences are logged.
- Older server and failed export both return 422 (E2): resolved differently from the suggestion. The export never returns an error for a failed pass. It returns the `FULL` document and logs a warning (research R3), so the SDK reads only the older server's schema-not-found 422 as "endpoint missing" (research R7). A 500 stays reserved for uncaught exceptions.
- Shared schema cache grows with each export (E3): fixed in research R4. Nothing is cached between exports, and each pass uses a new schema cache.
- Knowledge doc deferred (E6): in scope as FR-019.
- `FULL` cannot clear values or remove elements (P2): added to spec Edge Cases and FR-018.
- CLI output changes (P4): listed in the plan's changelog fragments.
- Export blocks the event loop (E4): not changed. The export stays on the event loop until the timing numbers from the functional test show a problem.
- Database reset removes test accounts (E5): the reset helper deletes only the user schema and its objects (research R8).
- Order of the pull requests (E7): recorded in the plan's delivery order, including an SDK integration test added after the first release with the endpoint.
- `uniqueness_constraints` pinning untested (E8): variation schema added to research R8.
- No timing record (E10): debug log in research R4.
- Where the referenced kinds go (P3, X2): naming referenced kinds is left out of the first version. The document has no field for it.
- Public SDK symbols (P5): removed, with a `removed` changelog fragment.
- Telemetry (P6): none. Spec Out of Scope states it.
