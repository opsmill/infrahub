# Data Model: Export the running schema

No stored entity is added or changed. The export is built from the schema held in the schema registry and is not persisted. The models below are API and in-process models.

## SchemaExportMode

Enum in `backend/infrahub/schema/export/models.py`. The names are working names (spec Assumptions).

| Value | Meaning |
| --- | --- |
| `BRIEF` | Default. Values that processing produces again on load are left out (D3), except the pinned properties (research R9), the fields marked `keep_in_export`, and a derived value written next to the value it comes from (research R3). |
| `FULL` | Every write-visible value of the user-defined elements, except the exclusions in research R2 (D6). |

`IDS` is deferred (D6) and is not a value of the enum.

## SchemaExportDocument

Response model of `GET /api/schema/export`, in `backend/infrahub/schema/export/models.py`. It is a subclass of the SDK `InfrahubSchemaWrite`, so a document that validates as a response also validates as a load payload.

| Field | Type | Rule |
| --- | --- | --- |
| `version` | `str` | Always `"1.0"`, the version of the schema file format. Unchanged (FR-010). |
| `infrahub_version` | `str` | `infrahub.__version__` of the server that produced the export (D7). Accepted and ignored by the load. |
| `generics` | `list[GenericSchemaWrite]` | User-defined generics in the selected namespaces, sorted by kind. |
| `nodes` | `list[NodeSchemaWrite]` | User-defined nodes in the selected namespaces, sorted by kind. |
| `extensions` | not written | Extensions of user nodes are written as attributes and relationships of the node. Extensions of kinds in restricted namespaces and of other kinds Infrahub defines, such as `IpamNamespace`, are never exported (D2, research R2). |

Sorting by kind makes two exports of the same schema identical apart from `infrahub_version` (SC-003). Attributes and relationships are sorted by `order_weight`, then by name, because a schema read back from the database does not keep the order in which they were loaded (found by the `models/base/` functional test on 2026-11-26).

## Element fields

Each node, generic, attribute, relationship and attribute-parameter entry is the write model of that element (research R1). The tables below group the fields by how the export treats them. Each rule is kept in one place in the code: the field's `visibility` decides whether it can be written, the reduction loop and the field's `keep_in_export` mark decide whether `BRIEF` writes it, and the inheritance constant decides whether it stays on a node. The field coverage test records only which test schema uses each field (research R10).

### Removed in both modes

| Field | Element | Reason |
| --- | --- | --- |
| `id` | all | IDs match nothing on the target (D6). |
| Nodes and generics whose kind the core schema definitions define, such as `IpamNamespace` | node, generic | Defined by Infrahub, not by the schema owner, although the namespace is not restricted (research R2). |
| `inherited: true` attributes and relationships | node | Written only on the generic that defines them (FR-004). |
| `member_of_groups`, `subscriber_of_groups`, `parent`, `children`, `profiles`, `object_template`, matched by kind, name and identifier | node, generic | Generated by processing (FR-003). A user relationship of the same kinds is exported. |
| Top-level `regex`, `min_length`, `max_length` | Text, TextArea, List attribute | Written in `parameters` instead (D5, FR-008). |
| `parameters.start_range`, `parameters.end_range` | NumberPool attribute | Written as one entry of `parameters.ranges` (D5, FR-009). |

### Pinned on a node in `BRIEF` mode

On a node with `inherit_from`, each property in the inheritance constant of `backend/infrahub/core/schema/node_inheritance_handler.py` is written when its value equals the stored value of the first generic in `inherit_from` that sets it (research R9). The exporter reads the list from that constant. Today it holds:

- `human_friendly_id`
- `display_label`
- `display_labels`
- `default_filter`
- `menu_placement`
- `uniqueness_constraints`
- `icon`
- `order_by`

### Kept in `BRIEF` mode by the field definition

Fields whose definition has the `keep_in_export` mark (working name) in `ExtraField` are removed by the reduction loop only when they hold the write-model default, because a candidate without them fails validation. Processing never sets some of them, such as `inherit_from`, and derives others, such as a relationship `identifier`, but the candidate fails validation before processing can derive them. The exporter reads them from the constant that `uv run invoke backend.generate` writes into `infrahub_sdk/schema/generated/contract.py` (research R3).

### All other fields in `BRIEF` mode

Removed when the reduction loop (research R3) finds that processing produces the same value, written otherwise. Examples from the design document that the loop leaves out: `label` taken from the name, `order_weight`, `branch` equal to the value derived from the node or the peer.

A derived value and the value it comes from are both written when the first pass removed both, because both then differ after processing (research R3). Examples: a `human_friendly_id` and `uniqueness_constraints` derived from a `unique: true` attribute are written with that attribute; `optional` is written with `default_value`. The design document lists these derived values as left out; this difference needs the feature owner's agreement.

## Conversions

| Stored form | Exported form |
| --- | --- |
| `regex: "^a"` at the top level of a Text attribute, `parameters.regex` unset | `parameters: {regex: "^a"}` |
| `parameters: {start_range: 10, end_range: 20}` | `parameters: {ranges: [{start: 10, end: 20}]}` |
| `parameters: {start_range: 10}` | `parameters: {ranges: [{start: 10}]}`, the end stays unset |

Processing keeps the deprecated top-level fields and `parameters` equal (`SchemaBranch._reconcile_legacy_attribute_parameters`), so both stored forms hold the same value. NumberPool parameters are stored in the form that was loaded (`NumberPoolParameters.update`), which is why the export converts them. For the same reason, the reduction loop and the round-trip tests compare both sides after these conversions, or a NumberPool loaded with `start_range` and `end_range` would never equal the processed export (research R3, R8).

## Serialization

The `BRIEF` document holds only the keys the reduction loop kept. The candidate is a dict, and the document is validated from it at the end, so its set fields are those keys. The endpoint serializes it with `exclude_unset=True`; otherwise every write-model field would be written with its default value (research R3). `infrahubctl schema export` writes the JSON body it received, so the files hold exactly the keys of the response.

## SchemaExporter

Component in `backend/infrahub/schema/export/exporter.py`.

| Part | Description |
| --- | --- |
| Constructor | `baseline_factory`: a function that builds a new processed core-only `SchemaBranch`, with its own schema cache, on each call (research R4). |
| Entry method | `export(schema_branch, mode, namespaces) -> SchemaExportDocument` |
| State | None kept between calls. The baseline, the candidates and their schema caches belong to one call and are dropped when it returns. |

The API creates one `SchemaExporter` through a FastAPI dependency and passes the branch schema from `registry.schema.get_schema_branch`. The exporter only reads that branch schema.

## State transitions

None. The export reads the schema and changes nothing.
