## Executive Summary

The spec and plan are unusually well-grounded: every claim is anchored to a code site that was
verified, the root cause is stated once and every finding is derived from it, and the fix strategy
(replace each object-level proxy with the edge-level fact the same code path already computes) is
both minimal and uniform. Scope discipline is good — two adjacent value-correctness defects
discovered during investigation were explicitly pushed out rather than absorbed.

The concerns are concentrated in the two places where this work stops being a local gate fix and
starts touching shared machinery. First, **FR-007 silently breaks a documented invariant of
`GraphRollbacker`** — that vertex metadata is written only for default/global-branch operations —
by causing schema migrations on user branches to write `previous_updated_at/by` snapshots that no
rollback can ever consume. Second, **the repair migration is destructive in a way m050 was not**:
m050 only filled NULLs, and dropping its `IS NULL` guard turns it into an overwrite of existing
values with no dry-run, no reported counts, and no reverse. Third, the shared recompute oracle is
internally inconsistent — its Node scope in the contract's corollary does not match its recompute
table — which matters because the tests and the migration are supposed to agree by construction.

None of these are architectural rethinks. All three are resolvable by stating a decision the plan
currently leaves implicit.

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | The shared recompute oracle in `contracts/vertex-metadata-invariant.md` is **internally inconsistent**. Corollary 2 states a Node vertex is stamped only when it has an active `branch_level = 1` `IS_PART_OF`; the recompute table places no such restriction on `:Node`, deriving `created_at` as a uuid-wide `min()` and `updated_at` from linked field vertices. For a kind-migrated twin pair, the table therefore assigns metadata to the *deleted* twin as well. Since the same oracle is the test assertion **and** the migration implementation, an ambiguity here lets the two agree with each other while both being wrong. | Restrict the recompute's `:Node` rows to vertices holding an active level-1 `IS_PART_OF`, while keeping the uuid-wide `min()` for `created_at` (which is what makes twins report the true creation time). State explicitly that a migrated-out twin is not a recompute target. |
| E2 | 💡 | `RelationshipDeleteQuery` and `RelationshipDeleteAllQuery` stamp three vertices: the two peers **and** the Relationship vertex `rl`. FR-004 and D5 name only the peer Node vertices. The `rl` stamp is already correct — the relationship's own branch level is the right gate for its own vertex — but the plan does not say so, and an implementer applying "add the peer guard" uniformly could wrap `rl` in it too and reintroduce an under-set. | Add one sentence to D5 stating that the `rl` stamp keeps its existing gate and only the peer Node stamps change. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 🎯 | **FR-007 breaks a documented invariant of `core/rollback.py::GraphRollbacker`.** Its docstring states restoring `previous_updated_at/by` "is only allowed when the target branch is the default or global branch — vertex metadata properties are maintained solely for those branches, so there is nothing to restore anywhere else," and `rollback()` raises if asked otherwise. Today that holds because `set_metadata` is false on a user branch. After FR-007 a schema migration on branch `foo` writes both the bump **and** the `previous_*` snapshot for its `-global-` rows — but a rollback of `foo` runs with `restore_metadata=False`, so the snapshot is never consumed. It is left orphaned, and a later default/global rollback whose window catches it could restore a stale value as if it were current. | Decide explicitly: when the gate fires via the new edge-level path on a non-default branch, write `updated_at` / `updated_by` **only** and skip the `previous_updated_at/by` snapshot. The snapshot exists solely to serve a rollback that can restore it; where no rollback can, writing it is strictly worse than not writing it. Record this in FR-007 and in plan D3, or an implementer will simply OR the gate and create the orphans silently. |
| E4 | 💡 | D3's `node_remove` change reorders a `WITH` across a metadata write. The plan's risk table argues it is safe because only a pure scalar computation is hoisted. That reasoning is right but it is asserted, not pinned by a test. | Note in D8 that the existing `backend/tests/component/core/migrations/schema/` suite must pass unchanged as the regression pin for the reorder — no new assertions needed, but the reorder is not "done" until that suite is green. |
