# Critique — Git status indicator (IFC-3199)

**Date**: 2026-09-15 · **Artifacts**: spec.md, plan.md, research.md, data-model.md, quickstart.md

## Executive summary

The spec and plan are in good shape: the data source was correctly rejected on evidence, the
architecture reuses existing machinery rather than duplicating it, and the known gaps are
disclosed rather than buried. The requirements are testable and the constitution check is
honest.

Three findings must be addressed before tasks. One of them — the time-machine interaction —
is a genuine blind spot that neither the spec nor any of the three planning explorations
noticed, and it can make the indicator report "healthy" on a branch that is currently broken,
which is precisely the failure this epic exists to prevent.

**Verdict: ⚠️ PROCEED WITH UPDATES.**

---

## Engineering lens

### 🎯 E1 — The time machine silently rescopes the indicator (Architecture / Failure modes)

`useObjectsCount` supplies `atDate` from `datetimeAtom` internally. That is exactly why the
plan chose it — branch and date wiring come for free. But this feature does not want the date.

Infrahub has a time-machine control **in the same header**. When an operator moves it, every
`useObjectsCount` consumer silently re-scopes to that timestamp, including this indicator.
Consequences, in increasing order of seriousness:

1. Polling every 10 seconds for a historical timestamp is pure waste — the answer cannot change.
2. The indicator shows Git health *as of the selected time*, with nothing in its tooltip
   saying so. FR-010a's texts all speak in the present tense.
3. **An operator viewing a past date sees the neutral state while the branch is broken right
   now.** The whole premise of the epic is that a green-looking signal during a real failure
   is the thing to eliminate. This reintroduces it through a different door.

Neither the spec nor plan mentions the time machine anywhere. All three planning explorations
treated `atDate` as a free convenience.

**Suggestion**: the indicator should always ask about *now*. Add a functional requirement
stating the indicator is not affected by the time-machine selection, and have the plan pass an
explicit present-time/`null` date rather than inheriting the atom. If the hook cannot express
that, this is the one place a bespoke query is justified — and that changes the R3 trade-off,
so decide it consciously rather than inheriting it.

### 🎯 E2 — The state precedence produces a false alarm when the total count is zero

`data-model.md` orders `either errored → check-failed` **above** `total === 0 → inert`. That is
wrong in one reachable case: the total count succeeds with `0` and the failing count errors.

If a branch has zero repositories, the failing count is necessarily zero — it counts a subset
of an empty set. The application therefore *does* know the answer, and `check-failed` alarms
about a check whose result cannot matter.

The plan's own justification for the precedence ("a half-successful check is not a fact") is
sound in general and wrong in this specific case, because here the successful half fully
determines the result.

**Suggestion**: split the error rule around the empty check:

```
1. either pending        -> loading
2. total errored         -> check-failed   (nothing is known)
3. total === 0           -> inert          (failing is irrelevant; subset of empty)
4. failing errored       -> check-failed
5. failing > 0           -> error
6. otherwise             -> neutral
```

Cheap to change now, and it deserves its own unit test case — it is exactly the kind of
ordering bug that survives a green suite.

### 💡 E3 — There is a far cheaper E2E path, and it is new evidence

The decision to seed a genuine import failure was taken believing the alternative was either a
broken fixture repository or asserting nothing. There is a third option the planning agents
did not surface: **`sync_status` is an ordinary writable Dropdown attribute** on the generic
repository schema (`optional=False`, `branch=BranchSupportType.LOCAL`, no read-only flag), with
four choices including the import-error value.

An E2E test can therefore set the existing fixture repository's `sync_status` to the error
value through a normal update mutation, and assert the header reacts — no second import
fixture, no dependence on the importer's exception path, no extra clone in the slowest shard.

This is not a purity compromise for *this* feature specifically: the indicator reads
`sync_status` and nothing else. A test that sets `sync_status` exercises the entire contract
the indicator depends on. What it does not prove is that a real import failure *results in*
that status — but that is the importer's behaviour, which backend tests already own and which
this frontend ticket does not change.

**Suggestion**: reconsider on this new evidence. If the genuine-failure fixture is still
wanted, keep it — but knowing a five-minute alternative exists, and that the expensive path
adds the suite's only test that depends on an import failing by design.

### 💡 E4 — `isPending` versus `isFetching` is an easy and invisible mistake

The precedence says "either pending → loading". With `refetchInterval`, `isFetching` becomes
true on *every* poll while `isPending` stays false once data exists. Using the wrong one makes
the glyph flash a spinner every 10 seconds — irritating, and it would pass an obvious test
written against a first render.

**Suggestion**: state `isPending` explicitly in the plan and the rule's input type, and give
the component test a case that asserts the resolved state survives a background refetch.

### 💡 E5 — SC-004 (no layout shift) is asserted by nothing

Three of the five states substitute different content into the glyph's slot: a spinner, a
different icon, the base glyph. Nothing guarantees these share a bounding box, and SC-004 is
one of the ticket's explicit requirements ("held in place… so the red state never shifts the
header layout"). `quickstart.md` relegates it to a manual eyeball check.

**Suggestion**: constrain the slot to fixed dimensions in the component rather than relying on
three icons happening to agree, and assert those dimensions in the component test. That turns
a visual-inspection item into a cheap automated one.

## Product lens

### 🎯 P1 — Operators without repository permission get a permanent red alarm

This follows directly from the permission-denied amendment, and it was not thought through
when the amendment was made.

If an operator cannot read repositories, the count fails on every page, on every load, forever.
FR-011 renders check-failed **in the danger colour**. That class of user now sees a permanent
red error glyph in the header, about a subsystem they cannot act on and may not have access to
by design.

A permanent red state that the viewer can never clear is worse than the inert state the
amendment replaced, and it trains everyone who sees it to ignore the colour — degrading the
signal for the operators the feature is actually for.

**Suggestion**: keep permission-denied mapped to check-failed (the reasoning for that stands —
it is the honest state), but **do not render check-failed in the danger colour**. A muted or
warning treatment says "this check did not run" without competing with the real failure state.
That satisfies FR-011's substance, removes the permanent alarm, and preserves the error state's
meaning. This needs an FR-011 wording change.

### 💡 P2 — Three polls per ten seconds, for a mostly-unchanging answer

This feature adds two pollers to the one the task indicator already runs. Repository sync
status changes on the order of minutes at best. The cost is modest and SC-006 is satisfied,
but the cadence was inherited from the task indicator without asking whether *this* signal
needs it — a running task is genuinely short-lived; a broken import is not.

**Suggestion**: not a blocker, and consistency with the neighbouring control has real value.
Worth one sentence in the spec saying the cadence was chosen for consistency rather than
because the data demands it, so a future reader does not treat 10 seconds as load-bearing.

## Cross-lens

### X1 — E1 and P1 both point at the same missing idea: the indicator does not say what it does not know

The time-machine case shows a confident neutral state built on data that may not describe now.
The permission case shows a confident danger state built on an absence of data. Both are the
same failure: the indicator asserting more than it knows.

The five-state model is right to separate "could not check" from "checked and fine" — it just
needs that separation applied consistently: not affected by the time machine (E1), and not
shouting when the check merely could not run (P1).
