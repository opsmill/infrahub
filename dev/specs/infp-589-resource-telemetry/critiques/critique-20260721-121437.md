## Executive Summary

The spec and plan are strong: the problem is well-evidenced (Pete's metric list, Matt's licensing-gap finding, Fatih's setting confirmation), scope is appropriately narrow (report-only; enforcement deferred), and the design reuses existing infrastructure (gatherer, `safe_metric`, heartbeat, JMX) with zero new dependencies — aligning with Constitution III/IV/VII. No fundamental product or architecture concerns.

Two 🎯 Must-Address items are wording/contract corrections that align the artifacts with decisions already made this session (assigned = null until enforcement; no breaking changes). Both are low-risk and resolved inline. Verdict: **⚠️ PROCEED WITH UPDATES** (applied).

## Product Lens Findings

**3a Problem validation** — Strong. Grounded in real sources; not a solution seeking a problem. Scope correctly excludes enforcement.

**3b User value** — Every requirement serves the internal audit. One clarity gap (P1 below): the headline "audit against tier" rests today on `cores_available` (+ RAM + worker count), because every `cores_assigned` is `null` until enforcement. And DB cores-available + worker count *already* ship in the current payload — so the net-new value of this phase is specifically the **server + worker CPU/RAM figures** and the **forward-compatible `assigned` scaffolding**. Worth stating so a reviewer doesn't ask "aren't we already sending this?"

**3c Alternatives** — Telemetry self-report is the right call for air-gapped fleets; the infra-manifest route is correctly deferred to the license file. No simpler alternative delivers the offline audit.

**3d Edge cases** — Well covered (no-limit, no-workers, DB-unreachable, partial reporting, old consumer). Not user-facing, so accessibility N/A.

**3e Success measurement** — SC-1/SC-2 use the word "allocated cores," which reads as *assigned* — but assigned is `null` today, so the measurable audit basis is *available*. Reword for accuracy (P2).

## Engineering Lens Findings

**4a Architecture** — Sound; follows the DI/builder pattern and `backend-component-design`. Host-dedup is justified in Complexity Tracking. **Blast-radius note (E1):** `WorkerInfo`/`list_workers` is a *shared* component (also backs the workers listing beyond telemetry). The new `workers:resources:*` key sits in the scanned `workers:*` namespace — the design must confirm it does not alter the existing `workers.total`/`active` counts or the workers API. (Analysis says safe: same identity, same TTL, `add_key` only flips `active` for `:active:` keys — but this needs an explicit regression test.)

**4b Failure modes** — `safe_metric` gives per-field degradation; snapshot never blocked. **Efficiency (E2):** cores, cgroup limits, and total RAM are *static for a process's lifetime*; only `ram_used` is dynamic. Reading `/sys/fs/cgroup` + `os.cpu_count()` on every heartbeat (~15 s) is wasteful and adds retry latency to a hot-ish loop. Read the static values once per process and cache them; refresh only `ram_used`.

**4c Security/privacy** — Reads only local trusted `/sys` files; no user input, no injection. Cores/RAM not PII. **Confirm (E3):** the per-process `host` identifier (`socket.gethostname()`) is used for dedup only and is **not** emitted in the payload (FR-004 aggregate-only) — keep it internal; state it in the contract.

**4d Performance/scale** — Trivial (daily cold path, few workers). The extra `workers:resources:*` keys ~double the `workers:*` scan — negligible.

**4e Testing** — Unit (cgroup parsing, aggregation) + component (end-to-end) match Constitution IV. **Gap (E4):** add an explicit test that the new heartbeat key leaves `workers.total`/`active` unchanged (pairs with E1), and the SC-005 backward-compat assertion is in quickstart scenario 5 — good.

**4f Operational readiness** — Additive, reversible, no migration. The version bump is the sole coordination point (see X1).

**4g Dependencies/integration** — No new dependency. The one integration risk is the **receiving service** and the payload-version bump (X1).

## Cross-Lens Insights

**X1 (🎯 Must-Address) — Version bump is the only breaking-change vector.** FR-008 currently *mandates* incrementing `payload_format`. If the receiver is version-strict, that bump alone breaks ingestion — the exact regression the stakeholder flagged. Product (data must keep landing) and Engineering (don't break prod ingestion) converge: make **additive-only the hard invariant** and make the version bump **conditional on the receiving service confirming tolerance**. Ship new fields additively under the existing version until then.

**X2 — Net-new value vs scaffolding cost.** Because assigned is null and some available metrics already ship, a skeptic could question building host-dedup + heartbeat plumbing now. Resolution (keep in scope): server/worker `available` CPU/RAM is genuinely net-new and directly serves Matt's audit across all components, and the scaffolding is cheap and reused. State the net-new explicitly (P1) rather than cut scope.
