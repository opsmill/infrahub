## Executive Summary

The spec and plan are unusually strong. The problem is a confirmed customer incident with a
reproduction path, the invariant is stated precisely enough to be mechanically checkable, and the
design deliberately chooses the failure direction that degrades rather than destroys (time-close
over status tombstone). The research phase grounded every claim in the shipped tree rather than
in the PRD's assertions, and it found the direct precedent — `BranchDataDeleter._delete_agnostic_peers`
— which turns the constitution's soft-delete deviation from a new exception into a completion of
existing behaviour.

The concerns are not with the invariant but with **three unspecified operational details that
each admit a wrong answer causing exactly the failure the feature exists to prevent**:

1. **Where the branch list comes from.** The predicate must evaluate every open branch. The
   in-process `registry.branch` cache is populated lazily and only ever *purged*, never
   proactively filled — so a branch created by another worker is invisible to this one. Reading
   the predicate's branch set from that cache would miss a retaining branch and retire a live
   object's value. Neither spec nor plan names the source.
2. **What happens when retirement fails.** Retirement is a side effect of a delete that has
   already committed. If it raises, user deletes start failing; if it is swallowed without a
   fallback, leaks return silently. The project already has a rule for exactly this shape and
   the plan does not invoke it.
3. **Whether the performance gate is measured on a representative graph.** The predicate's cost
   grows with the number of *open branches*, not with graph size. A gate measured on a
   three-branch component fixture proves nothing about a deployment with two hundred.

None of these is an architecture flaw — the design absorbs all three without restructuring. They
are gaps in what the plan commits to, and all three are cheap to close now and expensive to
discover during implementation. One further gap (SC-007's pool re-allocation has no owning task)
is a traceability miss rather than a design one.

Verified against the tree at `2a706caa77`; the code claims below were checked, not inferred.

#### Correction to E1 (recorded 2026-08-12, after maintainer review)

The claim that `registry.branch` is a lazily-filled, never-updated cache does not survive contact
with the code. It is a *maintained* cache:

- `refresh_branches` (`backend/infrahub/tasks/registry.py:84`) pulls **every** branch from the
  database and calls `create_branch_registry` for any it does not already know — it adds, it does
  not only prune. The `purge_inactive_branches` call I cited is the last step of that same
  function, not the whole of it.
- `BranchCreatedEvent`, `BranchMergedEvent`, `BranchRebasedEvent` and `BranchDeletedEvent`
  (`backend/infrahub/events/branch_action.py`) each publish `RefreshRegistryBranches`, and the
  handler (`backend/infrahub/message_bus/operations/refresh/registry.py`) runs `refresh_branches`
  on every worker but the originator.
- The creating worker populates it synchronously (`backend/infrahub/core/branch/creator.py:73`).
- A scheduled `branch_refresh` runs every 900s behind all of that
  (`backend/infrahub/services/scheduler.py`).

A propagation window does exist — between a branch being created on one worker and the refresh
landing on another — but it is bounded by message delivery, not by 15 minutes, and it is the same
window every other consumer of `registry.branch` already tolerates. Under the time-close mechanism
of FR-013 a miss in that window is a degraded read on one branch, self-correcting on its next
rebase, which is precisely the failure mode that mechanism was chosen to bound.

**What this changes**: the in-query `(:Branch)` read is dropped, `AgnosticBranchWindowBuilder`
remains the single place the fork-window collapse lives (fed from the registry at runtime and from
an explicit database read in the migration), and one task disappears rather than being added. The
"unspecified source" half of the finding was real and is now closed; the alarming half was not.

> **Outcome (recorded 2026-09-04, after implementation)**: this correction was itself overtaken.
> The 2026-08-17 design revision removed `AgnosticBranchWindowBuilder` along with the rest of the
> component layer, and the shipped predicate reads the branch set in-query after all —
> `MATCH (branch:Branch)` in `core/query/agnostic_retention.py`, collapsing the fork window in
> Cypher and excluding `DELETING` branches there. So the original Must-Address #1 (read the branch
> set from the database, preferably in-query) is what landed; the registry is not the source at any
> call site, and no migration-side `Branch.get_list` call exists. Read Must-Address #1 as
> implemented, and this correction as the argument that the registry *would* also have been sound.

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E2 | 🎯 | **No decision on retirement failure at an enforcement point.** Retirement runs after a delete/merge/rebase has committed.
