# Critique Report: Record template fingerprints in the database instead of placeholder automations

**Date**: 2026-11-19
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The plan matches the code. The checks covered the following:

- `computed_attribute/tasks.py::computed_attribute_setup_jinja2` takes its candidates and the default-branch hash from the gathered trigger definitions, not from a stored hash.
- `display_labels/tasks.py::display_labels_setup_jinja2` submits only for modified triggers that have a `target_kind`, which are the placeholders and the self-peer triggers.
- `trigger/setup.py::setup_triggers` lists every deleted automation in `report.deleted`.
- `cli/upgrade.py` reaches the task manager only in step 5.

The spec and the plan disagree in two places:

- The spec still records fingerprints for Jinja2 computed attributes.
- SC-002 forbids any extra recompute, but the plan accepts extra recomputes in some cases.

One race can suppress a recompute: a late setup run writes records for a branch that was just deleted, and a new branch reuses the name. Nothing calls for rethinking the approach.

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | `delete_branch` runs without the lock, and the registry of a worker can still hold a deleted branch (Decision 10). A `SchemaUpdatedEvent` flow for branch B that runs after the deleter can write records for B again. A new branch B with the same template hash then skips its recompute, which breaks US4 scenario 2 until a setup run removes the out-of-scope records | In the `upsert` query, write the records only when a `Branch` vertex with that name exists (`MATCH (:Branch {name: $branch})` in the same query). Apply the same check to `insert_missing` |
| E6 | 💡 | Some display label or HFID templates read a peer of the same kind. Their peer trigger has the same name `X::by::X` as the placeholder. When that automation holds the peer trigger, it is not deleted, so it is not carried over | Document this in Decision 8: one extra recompute for that kind after the upgrade, never a missing one |
