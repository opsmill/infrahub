## Must-Address 🎯

### E23 — `merge_git_repository` is a fifth direct read-write factory caller with no branch assigned

**Lens**: Engineering. **Category**: Architecture soundness / contract completeness.

`git/tasks.py:734` constructs the object directly:

```python
repo = await InfrahubRepository.init(
    id=model.repository_id, name=model.repository_name, client=client, default_branch_name=model.default_branch
)
```

`research.md:29-33` correctly lists it among the carriers FR-003 removes, and
`contracts/repository-object.md`'s removed-carriers table drops
`git/models.py::GitRepositoryMerge.default_branch`. But no decision assigns this call site an
`infrahub_branch_name`:

- D1's alternatives name four direct `init` callers (`git_branch_create`, `git_branch_delete`,
  `_validate_repository_merge_conflicts`, `webhook/models.py`). `merge_git_repository` is a fifth.
- D4's table of callers needing a branch they do not carry lists four rows. This is not one of them.
- `plan.md`'s Source Code map never mentions `git/tasks.py::merge_git_repository`.

So the commit that removes `GitRepositoryMerge.default_branch` breaks this call site with no
specified replacement, and `tasks.md` generated from the current plan would not carry a task for it.
The plan's own risk note ("a missed caller fails at call time with a clear `TypeError`") is the
mitigation for a *forgotten* caller, not for one the artifacts identify and then leave unassigned.

This is the merge write-back path — spec US1 scenario 5 and SC-001's "merge write-back" — so it is
not a peripheral site. The branch choice is also not self-evident: `model` carries both
`source_branch` and `destination_branch`, and the flow's staging path (`git/tasks.py:738-752`) exists
precisely because the repository node's `internal_status` differs between them. The likely correct
answer is `model.destination_branch`, because the flow reads `model.internal_status` for its own
control flow and never asks the object for its status — but that reasoning belongs in D4, not in a
reviewer's head.

**Suggestion**:

1. Add a fifth row to D4's table: `git/tasks.py::merge_git_repository` → `model.destination_branch`,
   with the reason (the merge lands there; the flow takes its staging decision from
   `model.internal_status`, not from the object's field).
2. Add `git/tasks.py::merge_git_repository` to `plan.md`'s Source Code map alongside the other
   `git/tasks.py` entries.
3. Add a D7 row: the non-default-trunk write-back still resolves the trunk with
   `GitRepositoryMerge.default_branch` gone. The existing
   `backend/tests/component/git/test_git_repository.py::test_merge_writes_back_to_non_main_default_branch`
   is the natural home, and D7 already has a row adapting it for construction.

### E24 — The factories' required `infrahub_branch_name` shadows the existing optional field of the same name

**Lens**: Engineering. **Category**: Failure-mode analysis / contract completeness.

`data-model.md:32` keeps the base field `infrahub_branch_name: str | None` **unchanged**.
`contracts/repository-object.md:34-36` makes `infrahub_branch_name` a **required** parameter of
`init` and `new`. Nothing in the artifacts says whether the factory populates the field with it.

The field is live today. `_get_initialized_repo` (`git/repository.py:477`, `:480`) omits it, so every
one of the ~25 downstream callers currently holds an object whose `infrahub_branch_name` is `None`,
and two paths read it:

- `base.py:247`, `_update_operational_status`, sends
  `branch_name=self.infrahub_branch_name or registry.default_branch`.
- `repository.py:441-442` and `:460`, the read-only write-back, pass the field straight to
  `update_commit_value`.

Both answers are consequential and neither is stated:

- **If the factory sets the field**, every artifact, transform, generator, computed-attribute and
  proposed-change call site that today writes `operational_status` on the default branch starts
  writing it on the operation's branch. `operational_status` is branch-scoped, so this moves an
  operator-visible value on the exact surface SC-005 promises — an unspecified behaviour change
  riding along with a bug fix.
- **If it does not**, the object holds two different answers to question (b), "which Infrahub branch"
  — the field, and the value the factory read the node on. That is the ambiguity D3 exists to remove,
  reintroduced one layer up.

**Suggestion**: state the answer in `contracts/repository-object.md` under "Factories". The
recommended answer is that the factories **do** set `infrahub_branch_name` — one value, one meaning,
which is what D3 is for — with two consequences recorded alongside it:

1. `_update_operational_status` now targets the operation's branch. Say so explicitly, and add a D7
   row pinning which branch the status write lands on for a call site running on a non-default
   branch. If that change is unwanted, `_update_operational_status` should name
   `registry.default_branch` outright rather than inheriting whatever the field holds.
2. The read-only write-back's branch becomes the factory's value rather than `None`.

If the intended answer is "the factory does not set the field", the contract must say that and
explain why the object then carries two branches.

## Recommendations 💡

### E25 — `resolve_graph_settings` puts graph I/O on a pydantic model

**Lens**: Engineering. **Category**: Architecture soundness (SOLID).

`.agents/rules/backend-component-design.md`, "Persistence lives in Repository/Query classes, not on
models": *"For new code, database access and (de)serialization do not belong on the model. A model is
a plain data holder; give it no `save`/`get`/`get_list`/`from_db`/`to_db` methods … when you extend
an existing model that follows it, prefer adding a Repository/Query rather than another method on
the model."*

`InfrahubRepository` is a pydantic model. `resolve_graph_settings` is a new classmethod performing an
SDK `get`. FR-003 requires one resolution point; it does not require that point to be on the model.
The plan's Constitution Check marks Principle VII PASS and Complexity Tracking does not mention this,
so the deviation is currently invisible.

In fairness: the same rule closes with *"If existing nearby code violates this pattern, do not
refactor it as part of an unrelated change"*, and `init`/`new` already do IO on this class. Extracting
the resolver is not a drive-by refactor of existing code though — it is a placement choice for a new
symbol, which the rule addresses directly.

**Suggestion**: put the resolver in its own module — `git/graph_settings.py` holding
`RepositoryGraphSettings` and either a `RepositoryGraphSettingsResolver` taking `client` in
`__init__` with one entry method, or a module-level `async def resolve_graph_settings(...)`. The
factories call it. Cost is one small module; the payoff is that the single resolution point and its
`RepositoryError` wrapping are testable without constructing a repository object at all, which is
what D7's `resolve_graph_settings` and error-contract rows want anyway. If the classmethod is kept,
add a Complexity Tracking row so the deviation is a decision rather than an omission.

### E26 — Three abstract hooks are one collaborator

**Lens**: Engineering. **Category**: Architecture soundness (SOLID — SRP/ISP).

`_get_mapped_remote_branch`, `_get_mapped_target_branch` and `_resolve_worktree_identifier` all
answer one question: how this repository's remote branch names and Infrahub's branch names map onto
each other. The read-only kind implements all three as identity — a subclass satisfying an interface
it has no concept of, which is the ISP smell. And they land on `InfrahubRepositoryBase`, which is
already ~1,200 lines carrying clone, fetch, push, worktree, branch validation and error
classification, against the rule's *"Each component should have one reason to change … Prefer
composition of small components over large multi-purpose ones."*

The SOLID-cleanest shape is one `BranchNameMapper` protocol with two implementations —
`TrunkBranchMapper(trunk, platform_default)` and `IdentityBranchMapper` — held as a field and
selected per kind. A third repository kind then adds a mapper rather than three method overrides
(OCP), the mapping becomes a pure object testable without a repository, and the base class stops
growing.

In fairness, the counter-case is strong and the plan already makes half of it: the hooks exist as
concrete methods today, so declaring them abstract is much the smaller diff; constitution VII and the
rule's own *"a single implementation does not need an interface yet"* both cut against a new
protocol; and the rule's constructor-injection requirement would push a mapper through the same
factories this feature is already reshaping. For a bug fix, the smaller diff is the right call.

**Suggestion**: keep the hooks for this feature, and record the mapper as the rejected alternative in
`plan.md`'s Complexity Tracking (one line in the existing "Three abstract hooks" row), so the next
reader does not rediscover it as a fresh objection. The extraction itself belongs in
`dev/specs/infp-546-git-solid-refactor`, whose whole remit is behaviour-preserving structural work on
this module — add it there when that spec's Story 6 is updated, which is already a task in this
feature.

### E27 — `list_remote_refs` is a classmethod on the base purely as a namespace

**Lens**: Engineering. **Category**: Architecture soundness (SOLID — SRP).

`contracts/connect-time-trunk-validation.md:33` declares
`InfrahubRepositoryBase.list_remote_refs(cls, name, url) -> RemoteRefs` — a classmethod that touches
no instance state — while the pure check beside it, `ensure_branch_exists(refs, branch_name,
repository_name)`, is a free function. The connectivity flow calls the former as
`InfrahubRepository.list_remote_refs(...)` (contract line 77) from a path that has no repository
object and no reason to pick the read-write kind over the read-only one.

So a cohesive stateless pair is split across a class attribute and a module function, and the
connect path is coupled to a concrete repository class it does not use. `check_connectivity`'s
current placement is the shape being replaced, not one worth preserving.

**Suggestion**: put `RemoteRefs`, `list_remote_refs` and `ensure_branch_exists` together in
`git/remote_refs.py` as a dataclass and two module-level functions. The connectivity flow imports
three symbols and needs no repository class; the base class does not grow; and D7's three-shape
parser row tests a function rather than reaching through a class. This also keeps the connect path
free of the graph read the factories now perform, which it has no need of.

### P14 — SC-006 has no test row asserting the artifact's *content*

**Lens**: Product. **Category**: Success measurement.

SC-006 is the PRD's E2E scenario: connect a non-default-trunk repository, synchronise, regenerate an
artifact, "and confirm the artifact reflects the trunk's content". D7's final row pairs SC-001 and
SC-006 into one integration-docker entry: the existing `test_artifact_composition.py` (already on
`initial_branch="production"`) "plus a warm-clone regeneration step". That covers *regeneration
succeeds*. Nothing in it asserts the produced artifact reflects the trunk's tree rather than some
other branch's — which is the whole claim, and the one the PRD's own test-quality note singles out:
*"a test that a warm-clone worker produced the right artifact proves everything."*

**Suggestion**: split SC-006 into its own D7 row and make the assertion content-based — the artifact
rendered from the trunk's tree differs from what the Infrahub-default-named branch's tree would
produce, and the observed output is the former. A test that only checks the regeneration did not
raise would have passed before this feature too.

### P15 — The PRD's test-quality principle is nowhere in the artifacts, and eight D7 rows are property assertions

**Lens**: Product. **Category**: PRD fidelity — testing.

The PRD's Testing Decisions open with a design constraint, not a preamble: *"Test the branch an
operation actually targeted, not how it decided … A test that asserts a property returns a value
proves nothing; a test that a warm-clone worker produced the right artifact proves everything."*
Nothing in `spec.md`, `plan.md` or `research.md` restates it.

Meanwhile D7 now carries eight unit rows that are exactly property assertions: the mapping hooks for
both kinds, `resolve_graph_settings`'s return values, `validate_remote_branch`'s reasons, the two
`model_fields` absences, and the worktree identifier. Several were added in round 3 to satisfy the
PRD's *other* testing ask — "every module in the sketch gets its own suite". The two asks pull
against each other, and only one of them is written down, so the next reader sees a unit-heavy D7
with no record of the standard it is meant to be measured against.

**Suggestion**: add the principle to D7 as a one-sentence preamble, and mark which row is the
outcome-level evidence each headline requirement rests on — FR-001 on the warm-clone functional
test, FR-007 on the Gogs integration test, FR-008 on the component sync tests, SC-006 on P14's new
row. The unit rows stay; they are simply no longer mistakable for the proof.

### P16 — Principle IV's E2E requirement is waived through a mechanism the constitution does not offer

**Lens**: Product. **Category**: Governance.

Constitution Principle IV: *"E2E tests (`tests/e2e/` at the repo root): pytest-playwright tests MUST
be included for all user-facing features. Feature implementation is not complete until E2E tests
pass."* Governance sanctions Complexity Tracking for one principle only: *"Any deviation from
Principle VII (Simplicity) MUST be documented in the relevant plan or PR."*

`plan.md` marks Principle IV **"PASS with one deviation"** — a status the constitution does not
define — and records the Playwright waiver in Complexity Tracking, which is the Principle VII
mechanism. The reasoning behind the waiver is sound (no fixture remote lacks `main`, and the Gogs
integration test drives the same GraphQL mutation the UI calls, asserting the exact rejection
message). The problem is procedural: as written, a reviewer citing Principle IV has no documented
basis on which to accept it, and "PASS with one deviation" reads as self-granted.

**Suggestion**: cheapest correct path is to state in the plan that the waiver requires maintainer
sign-off and raise it in the PR description, so it is a decision someone makes. If a fixture remote
without `main` is cheap to add to the e2e suite, covering US3's rejection in the browser removes the
question entirely. If this class of waiver recurs — a feature whose only user-facing surface is a
GraphQL error message — that is a constitution amendment worth proposing separately.

### P17 — `location` keeps the optional-override shape the feature exists to delete

**Lens**: Product. **Category**: Requirement consistency.

`data-model.md:70`: the factories "construct with `default_branch`, `internal_status` and `location`
(a caller-supplied `location` wins over the node's)". So of the three values the resolver reads, two
become required with no fallback and the third keeps precisely the optional-value-with-a-silent-
precedence-rule shape that FR-001 through FR-005 exist to remove. Nothing says which callers rely on
the override or why the node's value is not authoritative, so a reviewer cannot tell whether this is
a considered exception or an oversight.

**Suggestion**: one line in `contracts/repository-object.md` naming the callers that pass `location`
and why (a `file://` path in tests, or a location not yet persisted during create), or drop the
parameter if nothing production-side needs it.
