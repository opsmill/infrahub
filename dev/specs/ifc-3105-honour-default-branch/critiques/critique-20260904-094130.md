## Must-Address 🎯

### X3 — The PRD's "current state" requirement is dropped, and the residual gap is not named

**Lens**: Both. **Category**: Requirement fidelity × operational visibility.

PRD FR-008 reads: the system "MUST expose that condition as **current repository state**, naming the
skipped branch, **for as long as it holds** … and the state MUST clear when the condition no longer
holds." PRD SC-004: "discoverable from the repository **at any time while it holds**." PRD user
story 10: "remain visible for as long as it holds **rather than scrolling past me in logs**."

The spec delivers a warning in a task log: one entry at connect, then one per synchronisation cycle
that imported at least one branch. This was a deliberate, owner-signed-off trade (critique round 2,
X1 — the alternative was roughly 1,440 linked tasks a day, and persistent state crosses the GraphQL
gate). **The decision is right and should stand.** Two things about how it is recorded are not.

**First, the residual gap is real and unnamed.** For a repository with a standing collision that is
not importing anything — a dormant repository, or one whose only active branch is the colliding one
— the sole record is the "Adding repository" task. Prefect flow runs are retained for a finite
window. Once that task ages out, the condition is invisible: no state on the node, no recent task,
nothing. That is precisely the failure PRD user story 10 names ("scrolling past me in logs") and it
falls inside spec SC-005's own promise that "an OpsMill support engineer can diagnose any of the
conditions above from the repository's reported state and task history alone." An actively-importing
repository re-surfaces the warning regularly, so the gap is confined to dormant repositories — but
the spec currently reads as though the task-log design is equivalent to the PRD's, and it is not.

**Second, the PRD is still the source of record and still describes the superseded design.** It
lists both open questions as open, describes P3 as a new repository surface, and declares the
GraphQL gate crossed. The plan flags this in Risks; nobody owns the edit.

**Suggestion**:

1. Add one bullet to the spec's Assumptions, immediately after the existing task-log paragraph:
   > The gap this accepts: for a repository with a standing collision that imports nothing for a
   > long stretch, the only record is the connect-time task, which ages out with Prefect's flow-run
   > retention. An actively-importing repository re-surfaces the warning on any cycle that imports.
   > Closing this properly needs persistent repository state, which crosses the GraphQL "Ask First"
   > gate and belongs to the sibling visibility effort (INFP-670).
2. Add the same row to `quickstart.md`'s SC-005 surface table, so the support-diagnosis check is
   honest about the one condition it does not fully cover.
3. Make "amend the PRD and IFC-3105 to the resolved decisions" an explicit task, not a risk note:
   both open questions closed, P3 re-described as a task-log warning, the GraphQL gate uncrossed,
   and the documentation pointer corrected from `git-integration.md` to `git-sync.md`.

### E18 — The skipped-branch predicate is specified in two places

**Lens**: Engineering. **Category**: Architecture soundness.

`contracts/sync-task-log.md` says `collect_pending_imports` "evaluates, for each new or updated
remote branch, `branch_name == registry.default_branch and branch_name != self.default_branch`".
That is character-for-character the condition already inside `validate_remote_branch`
(`git/base.py:890`), which `collect_pending_imports` calls at **two** sites
(`git/repository.py:178` for new branches, `:211` for updated ones).

So the contract mandates one predicate held in two files. If either copy drifts, the warning stops
matching the skip and the operator is told nothing while the branch is still dropped — a silent
divergence between a decision and its report. This is the same defect class the feature exists to
delete: a value derived independently in two places instead of resolved once.

**Suggestion**: have `validate_remote_branch` report *why* it rejected a branch rather than
returning a bare `bool` — a small enum or result type distinguishing the default-branch collision
from the `Branch(name=...)` validation failure. `collect_pending_imports` appends to
`skipped_branches` on the collision reason, at both call sites. The predicate then lives where the
decision is made, and the two call sites cannot disagree with it. Update
`contracts/sync-task-log.md` "Collection" and `data-model.md` accordingly, and add a unit row to
D7 for the reason returned by `validate_remote_branch` for each of its rejection paths.

### E19 — "Exactly one entry at connect" is not guaranteed

**Lens**: Engineering. **Category**: Failure-mode analysis.

`RepositorySyncer.sync` ends with `repo.raise_if_branches_failed(failed_imports)`
(`git/sync.py:129`), and `contracts/sync-task-log.md` states "the report is returned only on
success". `add_git_repository` calls `sync(repo)` uncaught (`git/tasks.py:103`).

Therefore: if the first synchronisation imports the trunk fine but any other branch fails, `sync`
raises, no `SyncReport` is produced, and **no skipped-branch warning is emitted at all**. FR-008's
"It MUST be recorded when the repository is connected" does not hold — and it fails specifically for
a repository that is already in trouble, which is the case an operator most needs the full picture
for. Carrier 1's whole claim is that it runs exactly once per repository and is therefore the
guaranteed entry; a partial import failure removes the guarantee silently.

Carrier 2 inherits the same hole in milder form: a cycle that imports A and fails B raises, so that
cycle records no warning. It recurs on the next successful cycle, so the consequence is a delay
rather than a loss.

**Suggestion**: emit the skipped-branch warnings **before** `raise_if_branches_failed`, so the
report is observable on the failure path too — either by moving the warning emission into the
carriers ahead of the raise, or by attaching the `SyncReport` to the raised error. Then state in
`contracts/sync-task-log.md` that a skipped branch is reported whether or not the run's imports all
succeeded. Add the case to D7's component rows: a first sync with one failing branch import still
records the skipped-branch warning at connect.
