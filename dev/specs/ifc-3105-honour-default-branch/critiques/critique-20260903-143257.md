### X1 resolution: where the skipped-branch warning is emitted

The per-minute volume comes from the colliding branch being permanently unimportable. `compare_local_remote`
diffs remote heads against local heads; the colliding branch is never created locally, so it is reported as a
*new* branch on every cycle, `validate_remote_branch` skips it again, and the early return for "nothing changed"
never fires. The run therefore has a non-empty `new_branches` and an **empty** `imports` list.

That empty `imports` list is the stateless discriminator. Revised design:

1. **One guaranteed entry at connect.** `git/tasks.py::add_git_repository` already tags itself with the
   repository node and already runs the first `RepositorySyncer.sync`. That first sync sees the colliding branch
   and skips it, so the warning is emitted there. Exactly one entry per repository, in the repository's Tasks tab,
   at the moment the operator connects it.
2. **Per-cycle only when the cycle did real work.** `sync_git_repo_with_origin_and_tag_on_failure` emits the
   warning and links the node only when the report lists a skipped branch **and** the run produced at least one
   import. A quiet repository with a standing collision produces nothing.

`SyncReport` therefore carries the imported branches alongside the skipped ones:

```python
@dataclass(frozen=True)
class SyncReport:
    skipped_branches: tuple[str, ...]
    imported_branches: tuple[str, ...]
```

Resulting volume for a repository with a standing collision: one entry at connect, then at most one per push that
changed an imported branch, and zero on idle cycles. A push that touches only the colliding branch produces no
entry, which is consistent: nothing changed for Infrahub.

FR-008 and US4 need rewording, because both currently mandate a warning for *every* synchronisation run that
skips the branch, which is the behaviour being rejected. US4 scenario 1 becomes "connecting the repository records
the warning once", and a new scenario covers "an idle cycle records nothing".

### E3 resolution: the factory's error contract

The SDK raises `NodeNotFoundError`, `BranchNotFoundError`, `GraphQLError` and `ServerNotReachableError`, none of
which derive from `infrahub.exceptions.RepositoryError`. Existing callers catch `RepositoryError` and
`CommitNotFoundError` only, so an unwrapped SDK failure would escape `bootstrap_local_repository` and the sync
flows and fail the whole periodic sync rather than skipping one repository.

`resolve_graph_settings` therefore catches the SDK's `Error` and re-raises `RepositoryError(identifier=name,
message=...)`, preserving the cause with `from exc`. A missing branch and a missing node are both configuration
failures for one repository, which is exactly what the existing handlers are shaped to isolate.

## Executive Summary

The spec and plan are unusually well grounded. Every claim about the current code that the plan rests on was
re-verified against the branch and holds: the `default_branch_name or registry.default_branch` fallback in
`git/base.py`, the graph read that happens only on the cold-clone path of the integrator's `init`, the branch-less
`get_initialized_repo` factory and its cache key, the tags-only `ls-remote`, the sync child flow that tags the
repository node only on failure, and the documented mid-run `add_tags` rebuild. The two product questions the PRD
left open were closed with defensible reasoning, the scope is tightly bounded, and the design (required constructor
fields, one resolution point, three explicit hooks, reuse of the connectivity RPC and the per-repository sync run)
is the simplest shape that satisfies the requirements without crossing any of the repository's "Ask First" gates.

Five items block implementation as written. Two are call sites whose "Infrahub branch" the plan labels as simply
"pass the branch" when the correct value is something else: the transform webhook currently uses the trunk fallback
as an *Infrahub* branch, so a literal port turns the trunk into a branch name that may not exist, and the fan-out
git branch delete runs after the Infrahub branch is gone, so reading the node on that branch fails. Both are
one-line plan corrections. The third is the task-log volume for US4, which the owner has rejected at one entry per
minute and which now needs a two-carrier design plus rewording of FR-008, US4 and SC-004. The fourth is the
factory's error contract: the SDK's exceptions do not derive from `RepositoryError`, so a construction-time graph
failure would abort the whole periodic sync rather than skipping one repository. The fifth is the spec
follow-through on the third. Beyond those, an unquantified test-migration cost across 22 files and a set of
wording and recording items remain as recommendations.
