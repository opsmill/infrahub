# Feature Specification: Honour the Configured Repository Default Branch

**Feature Branch**: `pog-honour-default-branch-ifc-3105`

**Created**: 2026-09-03

**Status**: Draft

**Input**: PRD "Honour the configured repository default branch across the pipeline" (Confluence, Product space, page 858357761) and Jira epic IFC-3105. The PRD is the source of record for requirements and design decisions; this spec restates them in spec-kit form. The PRD's two open questions were resolved on 2026-09-03 during specification: a trunk absent from the remote rejects the connect request (FR-007), and a skipped colliding branch is reported as a warning in the repository's task log rather than as new persistent repository state (FR-008). The second decision means no GraphQL schema gate is crossed. Part of INFP-670 (Git repository sync robustness and recovery). Supersedes IFC-2870. Related: IFC-2740 (resolved, regression coverage only), IFC-2998, PR #10449 (attribute description, in flight separately).

## Problem Statement

An operator can tell Infrahub which branch on a connected Git repository is that repository's trunk, but most of the pipeline ignores it. Artifact generation, transforms, generators, computed attributes and proposed-change checks silently substitute Infrahub's own default branch instead, with no error, no log line and no status change. The repository appears healthy while serving content from the wrong branch, or fails with a confusing "couldn't find remote ref" that names a branch the operator never configured.

The behaviour is intermittent. A repository resolves its trunk correctly the first time a worker touches it (the initial clone, fixed under IFC-2870) and incorrectly on every subsequent operation that worker runs against its warm local clone. Because Git storage is per worker, the same repository can work on one worker and fail on another.

The friction is not hypothetical. IFC-2998 opens by calling the Git integration "a large source of customer friction". This defect was reported separately as GitHub issues #9600 (periodic sync) and #8749 (artifact generation) before IFC-2870 traced both to the single fallback, and #9601 fixed only the periodic-sync call site, which is the evidence that per-call-site patching does not close the class. IFC-2870 also names the blocked use case: the multi-environment single-repository pattern, one non-`main` branch per environment, which cannot work today for any flow beyond plain import and sync. That pattern is what makes User Stories 3 and 4 worth sequencing rather than deferring: an operator adopting it hits the misconfigured-trunk and colliding-branch conditions as a matter of course, not as an edge case.

Infrahub stops guessing. The configured trunk is resolved once, in a single place, and carried by every operation that touches the repository, so a repository whose trunk is `develop` behaves exactly like one whose trunk is `main`, on any worker, at any point in its life. Where the operator has configured a trunk that cannot work, Infrahub says so at the moment the repository is connected, naming the branch the remote actually uses, instead of failing somewhere downstream hours later.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A non-default-trunk repository works on every worker (Priority: P1)

An operator connects a read-write repository whose trunk is not named like Infrahub's default branch. Every downstream operation (artifact generation, transform execution, generator runs, computed attribute updates, proposed-change checks including merge-conflict validation, merge write-back and periodic synchronisation) targets the configured trunk, regardless of which worker runs it or how many times that worker has handled the repository before. This holds equally when Infrahub itself has been initialised with a default branch other than `main`, and when the repository is in staging during a proposed change.

**Why this priority**: This is the defect. Without it, any operator whose repository trunk differs from Infrahub's default branch gets silently wrong content or intermittent failures across the whole Git integration. Everything else in this feature is visibility on top of a working baseline.

**Independent Test**: Connect a repository whose trunk is `develop` to an Infrahub whose default branch is `main`, let a worker clone it, then trigger a second operation on the same worker (artifact regeneration) and assert the transform read the remote `develop` tree with no re-clone and no fallback to `main`.

**Acceptance Scenarios**:

1. **Given** a read-write repository whose configured trunk is `develop` on an Infrahub whose default branch is `main`, and a worker that already holds a local clone of it from a prior task, **When** that worker regenerates an artifact on Infrahub's default branch, **Then** the transform runs against the remote `develop` tree and the artifact is produced, with no re-clone and no fallback to `main`.
2. **Given** the same repository, **When** a generator run, a computed attribute update, or a proposed-change check (including merge-conflict validation) is executed against Infrahub's default branch, **Then** each operation reads from or compares against the configured trunk.
3. **Given** a repository that is both in staging during a proposed change and configured with a non-default trunk, **When** validation runs against it, **Then** it behaves identically to a repository where neither condition differs, and the validation result agrees with what the live repository would produce.
4. **Given** an Infrahub instance initialised with a default branch other than `main` and a connected repository whose trunk is `main`, **When** any operation in the read-write matrix runs, **Then** it targets `main` on the remote and succeeds.
5. **Given** a proposed change merged into Infrahub's default branch that must be written back to a repository whose trunk is `develop`, **When** the write-back runs on a worker that has never checked out a local branch named `develop`, **Then** the remote `develop` ref advances to the new commit and the merge is not silently dropped.
6. **Given** a read-only repository whose remote fetch fails, **When** the failure is classified for reporting, **Then** the operator sees the same classified error (for example authentication or missing ref) as today, not an internal crash that loses the original Git error.

### User Story 2 - The broken state cannot be reintroduced (Priority: P1)

A developer working on the Git integration cannot construct the per-flow repository object for a read-write repository without its trunk, and cannot leave its staging status silently defaulted. A new call site that forgets either is rejected at construction rather than caught in review. Regression coverage exists for pushing to a non-default trunk from a worker that never checked out a local branch of that name, so the previously fixed silent failure (IFC-2740) cannot come back unnoticed.

**Why this priority**: The defect exists because an optional value with a silent fallback was easy to omit. Fixing the current call sites without enforcing the contract leaves the door open for the next one. This is P1 because it lands with User Story 1 and is what makes the fix structural rather than a patch.

**Independent Test**: A construction-level test asserts that omitting the trunk (and, separately, the staging status) when building a read-write repository object is rejected. A second test reverts the push refspec behaviour and asserts the non-default-trunk push regression test fails.

**Acceptance Scenarios**:

1. **Given** the per-flow repository object for a read-write repository, **When** code attempts to construct it without a trunk, **Then** construction is rejected.
2. **Given** the same object, **When** code attempts to construct it without a staging status, **Then** construction is rejected on the same basis.
3. **Given** the per-flow repository object for a read-only repository, **When** it is constructed, **Then** no trunk is required or exposed, and its clone-initialisation and error-reporting paths continue to function.
4. **Given** the regression test for pushing to a non-default trunk from a worker with no local branch of that name, **When** the push refspec behaviour is reverted to its pre-fix form, **Then** the test fails.
5. **Given** the codebase after this change, **When** flows, tasks and message models are inspected, **Then** none of them supplies or carries a trunk; it is resolved in exactly one place.

### User Story 3 - A misconfigured trunk is rejected when the repository is connected (Priority: P2)

An operator tries to connect a repository whose configured trunk does not exist on the remote. Instead of the repository being created, appearing healthy and then failing downstream with a generic missing-ref error, the connect request is rejected with a validation error that names the configured trunk as absent and names the remote's actual default branch, so the operator can correct the trunk and retry in one step.

**Why this priority**: Once User Story 1 lands, a trunk that does not exist on the remote becomes the main remaining way to end up with a broken repository, and today it surfaces hours later in a worker log naming the wrong branch. Connect-time rejection is the cheapest point at which to catch it, it leaves no half-working repository behind, and it needs no clone because the connectivity check already lists remote references.

**Independent Test**: Attempt to connect a remote whose default branch is `stable` and which has no `main`, leaving the trunk at its default of `main`, and assert the request is rejected with an error stating that `main` is absent and that the remote's default branch is `stable`, and that no repository was created.

**Acceptance Scenarios**:

1. **Given** a remote whose default branch is `stable` and no branch named `main`, **When** an operator connects it leaving the trunk at its default of `main`, **Then** the connect request is rejected with a validation error stating that `main` does not exist on the remote and that the remote's default branch is `stable`, and no repository is created.
2. **Given** the rejection in scenario 1, **When** the operator retries with the trunk set to `stable`, **Then** the repository is created and synchronises normally.
3. **Given** a remote whose default branch is `stable` and which also has a branch named `develop`, **When** an operator connects it with the trunk set to `develop`, **Then** no error, warning or tracked condition is raised, because deliberately tracking a non-default branch is a supported configuration.
4. **Given** a remote that cannot be reached at all, **When** an operator connects it, **Then** the existing connectivity error is reported unchanged, not a trunk-absent message.
5. **Given** an already connected repository, **When** the operator later edits its trunk to a branch that does not exist on the remote, **Then** the edit is not rejected by this feature; reconciling trunk edits after connection remains a documented limitation and is out of scope.

### User Story 4 - A skipped colliding branch is visible in the repository's task log (Priority: P3)

An operator whose repository has a remote branch named like Infrahub's default branch, while its configured trunk is something else, can see from the repository's task history that the colliding branch is not being imported. The warning is recorded once when the repository is connected, in the task that adds it, and after that by a synchronisation task whose run either imported a branch or saw a new commit arrive on the skipped branch itself. A cycle in which nothing moved on the remote records nothing, so a standing collision does not accumulate an entry every cycle. Once the colliding branch is removed or the trunk is changed so the collision no longer applies, no further warning is recorded.

**Why this priority**: The tiebreak that skips the colliding branch is correct; only its invisibility is a defect. Today it is a line in the worker's process log, which an operator never sees. It affects a narrower set of operators than P1 and P2 and adds no new repository surface, so it is sequenced last.

**Independent Test**: Connect a repository whose trunk is `develop` and whose remote also has `main` to an Infrahub whose default branch is `main`; assert the task that added the repository, viewed from the repository, contains a warning naming `main` as skipped. Let several synchronisation cycles pass with no change on any branch of the remote and assert no further warning and no new task is recorded against the repository. Then push a commit to `main` and assert the next cycle records the warning again.

**Acceptance Scenarios**:

1. **Given** a remote whose trunk is `develop` and which also has a branch named `main`, on an Infrahub whose default branch is `main`, **When** an operator connects it, **Then** the task that adds the repository records a warning in its task log naming `main` as skipped because it collides with Infrahub's default branch, and that task is linked to the repository.
2. **Given** the same repository, **When** the operator opens the repository's task history in the interfaces where tasks linked to a node are already shown, **Then** the warning is discoverable there, without reading worker process logs.
3. **Given** the same repository and no change on any branch of the remote, the colliding branch included, **When** any number of synchronisation cycles run, **Then** no skipped-branch warning is recorded and no synchronisation task is linked to the repository for those cycles.
4. **Given** the same repository, **When** a commit is pushed to a branch Infrahub does imports from and the next synchronisation cycle imports it, **Then** that cycle's synchronisation task records one skipped-branch warning naming `main` and is linked to the repository.
5. **Given** the same repository, **When** a commit is pushed to the colliding `main` and to no other branch, **Then** the next synchronisation cycle's task records one skipped-branch warning naming `main` and is linked to the repository, even though the cycle imported nothing. This is the moment the operator is most likely to be expecting an import and getting none.
6. **Given** the same repository, **When** the colliding branch is deleted from the remote, or the trunk is changed to `main` so the collision no longer applies, **Then** no subsequent task records a skipped-branch warning.
7. **Given** a repository with no colliding branch, **When** it is connected and synchronised, **Then** no skipped-branch warning is recorded and the task logs are otherwise unchanged.

### Edge Cases

- The configured trunk names a branch absent from the remote. The connect request is rejected under User Story 3; before that lands it surfaces as a downstream missing-ref failure.
- The configured trunk differs from the remote's own default branch. This is a legitimate, working configuration and MUST NOT be treated as an error, a warning, or something to track. An operator may deliberately track a non-default trunk.
- The remote has a branch named like Infrahub's default branch while the trunk is something else. That branch is unimportable and is correctly skipped; only its invisibility is a defect, addressed under User Story 4.
- The colliding branch is later deleted from the remote, or the trunk is changed so the collision no longer applies. No subsequent task records a skipped-branch warning; earlier task logs keep their historical warnings, which is correct because they describe what happened in that run.
- The collision holds but nothing changes on any branch of the remote for days. No warning is recorded for those cycles and no synchronisation task is linked to the repository because of the collision. The entry recorded when the repository was connected remains in its task history.
- The collision holds and the only activity is on the colliding branch itself. Each cycle that observes a new commit on it records one warning, so the operator learns that the branch they are pushing to is not the one Infrahub imports. A worker that has not synchronised the repository since before the push reports it as well, so a single push can produce one entry per worker.
- The repository is connected inside an Infrahub branch, so it is in staging and the add does not synchronise it. No warning is recorded at that point. It is recorded by the first synchronisation run that imports a branch once the proposed change has merged, which is the first moment the condition is observable.
- A remote is added or the trunk edited to a missing branch after connection. User Story 3 covers connect time only; a trunk edited to a missing branch after connection is not rejected and remains covered by the trunk-edit limitation below.
- The trunk is edited after the repository has been connected. Nothing re-clones, re-validates or reconciles branches already imported under the old mapping, and the trunk is served from cache for a short interval after the edit. Recorded as a known limitation in `docs/docs/git-integration/connect-repository.mdx`, not addressed here.
- A read-only repository's fetch fails. Its error-classification path currently reads the trunk fallback; removing that fallback naively crashes inside the error handler and loses the original Git error. This is the specific trap User Story 1 must avoid.
- Infrahub itself is initialised with a default branch other than `main`, so every connected repository is mismatched rather than just one. Same defect, total blast radius; covered by User Story 1 scenario 4.
- The remote is unreachable at connect time. The existing connectivity failure is reported; no trunk-absent rejection is produced because the remote's default branch cannot be determined.
- The remote is reachable but has no default branch (an empty repository, or a detached `HEAD`). The connect request is rejected because the configured trunk is absent, and the message states that the remote is empty or has no default branch rather than naming one.
- Two workers hold clones of the same repository. Each worker's local state is independent; the trunk they target must be identical because it is resolved from the graph, not from the local clone.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: A repository object used by any flow MUST carry that repository's configured trunk. No code path may substitute Infrahub's default branch for it. *Verify:* User Story 1 scenario 1 on a warm worker clone.
- **FR-002**: It MUST be impossible to construct a read-write repository object without a trunk. *Verify:* a construction-level test asserting the omission is rejected (User Story 2 scenario 1).
- **FR-003**: The trunk MUST be resolved in exactly one place. No flow, task or message model may supply or carry it. *Verify:* the redundant optional trunk fields are removed from the repository add and merge task models and no caller passes a trunk (User Story 2 scenario 5).
- **FR-004**: The read-only repository kind MUST NOT require or expose a trunk, and its error-reporting and clone-initialisation paths MUST continue to function once the inherited fallback is removed. *Verify:* a test that a read-only repository's fetch failure still produces its classified error (User Story 1 scenario 6), plus type checking passing with the trunk absent from the shared base.
- **FR-005**: A repository's staging status MUST be required rather than silently defaulted, on the same basis as the trunk. *Verify:* a construction-level test mirroring FR-002 (User Story 2 scenario 2).
- **FR-006**: A repository that is both in staging and configured with a non-default trunk MUST behave identically to one where neither differs. *Verify:* an acceptance case exercising both conditions together (User Story 1 scenario 3).
- **FR-007**: When an operator connects a repository whose configured trunk does not exist on the remote, the system MUST reject the connect request with a validation error that names the configured trunk as absent and names the remote's actual default branch. No repository MUST remain after a rejected request. The check MUST be performed from the reference listing the connectivity check already performs, without cloning the repository. When the remote is unreachable, the existing connectivity error MUST be reported instead. *Verify:* User Story 3 scenarios 1, 2 and 4.
- **FR-008**: When a remote branch is skipped because its name collides with Infrahub's default branch, a warning naming the skipped branch and the reason MUST be recorded in the task log of a task linked to the repository, so it is discoverable from the repository's task history. It MUST be recorded when the repository is connected, and thereafter by a synchronisation task whose run either imported at least one branch or observed the skipped branch's own remote head move. A synchronisation run that did neither MUST record no such warning and MUST NOT be linked to the repository for this reason, so a standing collision does not add an entry every cycle. Both triggers MUST be answerable from within the run: no new repository attribute, status value or relationship is introduced for this condition, and no state is persisted in the graph across synchronisation runs. *Verify:* User Story 4 scenarios 1 to 7.
- **FR-009**: The system MUST carry regression coverage for pushing to a non-default trunk from a worker that never checked out a local branch of that name. *Verify:* a component test that pushes to a non-default trunk from a worktree with no local branch of that name; a manual mutation check confirms the test detects the pre-fix refspec (User Story 2 scenario 4).
- **FR-010**: A configured trunk that differs from the remote's own default branch MUST NOT be treated as an error, a warning, or a tracked condition. *Verify:* User Story 3 scenario 3.
- **FR-011**: The Git integration knowledge documentation under `dev/knowledge/backend/` MUST document the repository object lifecycle as shipped when User Story 1 lands, and MUST NOT be left describing the superseded design. *Verify:* the documentation describes the single resolution point, records that the read-only kind carries no trunk, and describes the current skip-and-report path rather than the superseded one. Two pages are in scope and the split depends on merge order (see Assumptions): `git-integration.md` owns the repository object lifecycle and is the page the PRD and the epic cite, but it arrives separately in PR #10525; `git-sync.md` owns the branch-import section, which this feature makes wrong regardless of that PR, so its refresh is unconditional.

### Key Entities *(include if feature involves data)*

- **Read-write repository** (existing, `CoreRepository`): its configured trunk attribute (`default_branch`) keeps its current shape: mandatory, defaulting to `main`, freely editable. Its meaning is clarified rather than changed: it names the branch on the remote that Infrahub maps onto its own default branch, and makes no claim about the remote's own default branch. No change to this attribute, and no new attribute, status value or relationship is added by any user story.
- **Read-only repository** (existing, `CoreReadOnlyRepository`): unaffected from the operator's point of view. It tracks a single ref and gains no trunk concept; the internal fallback it currently inherits is removed.
- **Per-flow repository object** (existing, internal): the object representing a repository on a worker for the duration of one operation. Gains a required trunk on the read-write kind, a required staging status, and loses the silent fallback. The three questions it currently answers through one property are separated: which remote branch is the trunk, which Infrahub branch a commit is recorded against, and which branch name appears in an error message.

- **Repository task log** (existing): the per-run log of a task linked to a repository, already visible from the repository's task history. The task that adds a repository, and a synchronisation task that either imported a branch or saw the skipped branch's remote head move, gain a warning entry for each colliding branch skipped in that run. No change to its shape.

No new entities.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every operation in the read-write behaviour matrix (artifact generation, transform execution, generator runs, computed attribute updates, proposed-change checks, merge write-back and periodic synchronisation) succeeds on a repository whose trunk differs from Infrahub's default branch at the same rate as on one where they match. Target: full parity with zero branch-resolution failures on a non-default trunk in CI. The evidence is layered rather than one outcome test per flow, and the layering is deliberate: because the trunk is resolved in exactly one place (FR-003) and no call site can omit it (FR-002), a fourth test of the resolution mechanism adds nothing, while the residual risk moves to a call site passing the *wrong* Infrahub branch, which an outcome test on a warm clone does not catch either. So: outcome tests cover artifact generation and transform execution (warm-clone functional plus the integration-docker matrix), merge write-back (component push cases), periodic synchronisation (component sync cases), and proposed-change checks including merge-conflict validation, which earns its own case because its branch choice is the least obvious in the matrix. Generator runs and computed attribute updates are covered where the risk actually is, by asserting the branch each hands to the factory.
- **SC-002**: No code path can produce a read-write repository object without a resolved trunk or staging status. Target: zero, enforced at construction rather than by review, with a construction-level test for each.
- **SC-003**: An operator who configures a trunk that does not exist on the remote learns this when they connect the repository, from a rejection that names the branch the remote actually uses, and no repository is left behind in a broken state. Target: the first error the operator sees identifies the correct branch name, with no clone performed to produce it, and zero repositories created with an absent trunk.
- **SC-004**: A skipped colliding branch is discoverable from the repository's task history without the operator having to scroll past routine cycles, and is reported at the moment the operator is most likely to be looking for it: when they have just pushed to the branch that is not being imported. Target: exactly one warning when the repository is connected; at most one per synchronisation run that imported a branch or saw the skipped branch advance; zero for a run in which nothing moved on the remote; and zero once the collision lifts. Per-worker duplication is in scope for the target: a single push may be reported once by each worker that subsequently synchronises the repository, bounded by the worker count and not by the cycle rate.
- **SC-005**: An OpsMill support engineer can diagnose any of the conditions above from the repository's reported state and task history alone, without worker process logs. Target: every failure mode in this spec maps to a named operator-visible surface, enumerated in the support diagnosis check in `quickstart.md`.
- **SC-006**: The end-to-end scenario passes: connect a repository whose trunk is not named like Infrahub's default branch, let it synchronise, regenerate an artifact, and confirm the artifact reflects the trunk's content. Target: the assertion is on the artifact's **content**, which must match what the trunk's tree produces and differ from what a branch named like Infrahub's default would produce. A test that only confirms regeneration completed would have passed before this feature and is not evidence.

## Assumptions

- The remote's own default branch has no operational effect on Infrahub and is not worth tracking. Nothing in the pipeline consults it; every operation names an explicit ref. It is read only to produce the connect-time message under User Story 3.
- An operator deliberately tracking a branch other than the remote's default is a supported and reasonably common configuration, not a misconfiguration.
- Git storage is per worker, with no shared volume, so any statement about a repository's local state is a statement about one worker.
- Existing repositories keep whatever trunk they have. Nothing is rewritten during an upgrade, so a repository already misconfigured stays misconfigured until an operator edits it.
- Removing and re-adding a repository is not an acceptable remedy for any condition here, because deletion cascades away its transforms, queries, checks, generators and repository groups.
- The repository's task history is an acceptable carrier for the skipped-branch condition, provided the entry does not recur on idle cycles. The PRD preferred persistent repository state so the condition would be reported once rather than per cycle. A per-run warning on every cycle was rejected during critique: the collision is permanent by nature, so the synchronisation runs once a minute and would add roughly 1,440 linked tasks a day to the repository's task history, burying the failures that history exists to surface. The decision is to report it at connect time, in the task that adds the repository, and thereafter in a synchronisation run that either imported at least one branch or saw a new commit arrive on the skipped branch. This needs no new schema surface, because both triggers are answerable inside the run: a run that imports nothing is distinguishable from one that does, and the skipped branch's previous remote head is already held in the worker's clone as a remote-tracking ref.
- The gap that decision accepts, stated plainly: for a repository where nothing moves on any branch for a long stretch, the only record is the connect-time task, which ages out with Prefect's flow-run retention. After that the condition is invisible until the next cycle that imports a branch or sees the skipped branch advance. Any repository with activity on either side of the collision re-surfaces the warning, so the gap is confined to wholly dormant repositories. **The product owner settled this on 2026-09-04: a dedicated status surface for this one condition is overkill, so the task log is the intended design rather than a stand-in for something better.** The PRD's preference for persistent state is therefore superseded, not merely unimplemented, and nothing is owed against it. If the sibling visibility effort (INFP-670) later builds a general repository-health surface, this condition can ride on it; no work is deferred for it specifically. SC-005 is bounded accordingly.
- A commit pushed solely to the colliding branch is a reporting trigger, not a non-event. The earlier reading was that nothing changed for Infrahub because that branch is deliberately not imported, so no warning was warranted. That is true of Infrahub's state and false of the operator's expectation: pushing to the branch that is silently not imported is the single moment they are most likely to be waiting for an import that will never come, and the previous rule was silent exactly then while speaking up on cycles that imported some unrelated branch. The trigger is therefore inverted rather than dropped.
- Detecting that the skipped branch advanced needs no new persistent state. The fetch performed at the start of each synchronisation is unfiltered, so the colliding branch has a remote-tracking ref in the worker's clone that is already read for its commit when the remote heads are listed. Capturing that commit before the fetch and comparing it after is a local ref read with no extra network call and nothing written to the graph. The earlier rationale for excluding this, that it "would require remembering the last commit seen on a branch Infrahub deliberately does not import", was mistaken about the code: git already remembers it.
- The cost accepted in exchange is per-worker duplication. Git storage is per worker and the periodic synchronisation has no worker affinity, so "advanced since the last fetch" is answered independently by each worker, and one push to the colliding branch may be reported once by each worker that subsequently synchronises the repository. Deduplicating across workers is shared state, which is the gate this feature avoids, so the duplication is documented rather than fixed. It is bounded by the worker count, against the once-a-minute volume the per-cycle design was rejected for. A worker holding no prior clone has no previous head to compare and does not report on this trigger, because the connect-time carrier already announces the condition unconditionally.
- Rejecting the connect request when the trunk is absent is preferred over accepting and reporting. The operator's remedy is a one-field correction and a retry, which is cheaper than living with a repository that cannot synchronise. A trunk that will only appear on the remote later is not a supported connect-time state.
- No user story requires a schema change, a migration, a GraphQL schema change or an API change. None of the "Ask First" gates in `AGENTS.md` is crossed.
- One operator-visible side effect is accepted rather than avoided. Resolving the repository on the Infrahub branch the operation runs on means the object now knows which branch that is, and the repository's `operational_status` is written on that branch instead of always on Infrahub's default branch. Today every downstream flow reports the status on the default branch regardless of where it ran, which is why a failure on a branch was never visible on that branch. The new behaviour is the correct one and follows from resolving on one branch rather than two, but it changes where an existing status appears, so it is called out here rather than left to be discovered.
- User Story 1 stands alone and does not depend on the Git module refactor tracked in `dev/specs/infp-546-git-solid-refactor`.
- The PRD and the Jira epic both cite `dev/knowledge/backend/git-integration.md` as documenting the repository object lifecycle and containing a volatile section to update. **The PRD was right and the earlier planning note here was wrong.** That page is not committed on any branch, which is what the planning note observed, but it exists as unpushed work and arrives in **PR #10525** (`pog-em/git-integration-doc`, draft, targeting `develop`, single file). It documents the two branch namespaces, the per-worker storage model and the writeback gaps, and it carries exactly the volatile section the PRD promised: the IFC-2870 fallback and the unresolved factory, marked "update this section when that lands". No PRD or epic correction is needed on this point.
- FR-011's split therefore depends on merge order, and the order is not settled. If PR #10525 lands first, the lifecycle content updates `git-integration.md`'s volatile section and the sections this feature falsifies. If this feature lands first, the lifecycle content goes to `git-sync.md`, and PR #10525 must be revised before it merges, because its "Resolving the trunk on the repository object" section, its construction-paths table, its `internal_status` reference and its factory cache-key description would all describe deleted code on the day it arrived. Whichever lands second reconciles; the `git-sync.md` branch-import refresh happens either way.
- No reproduction test for the warm-clone defect exists today. IFC-2870 claims a deterministic one ("`test_initialized_repo_resolves_configured_default_branch` in `backend/tests/integration/git/test_multi_env_writeback.py` (PR #9798), `xfail(strict)`"), and that claim is stale: neither the file, the test name, nor any `xfail` marker exists anywhere in `backend/tests/integration/git/` or `backend/tests/functional/git/` on this branch. The first implementation task is writing the failing test, not enabling a skipped one, and correcting the ticket is part of the epic-amendment task.

## Out of Scope

- Tracking or reporting divergence between the configured trunk and the remote's own default branch.
- Any new attribute for the trunk itself, and making the existing attribute optional.
- Per-commit granularity in the skipped-branch warning. A new commit on the skipped branch triggers at most one warning for the run that observes it, and the warning names the branch and the reason, never the commits. The operator's remedy does not change with the number of commits, so nothing counts, lists or diffs them. (The trigger itself is in scope under FR-008; only reporting *per commit* is excluded.)
- Any new persistent repository attribute, status value or relationship for the skipped-branch condition.
- Rejecting or validating trunk edits made after the repository is connected. The "Check connectivity" action on an already connected repository stays what its name says, a reachability check, and performs no trunk validation. An on-demand configuration-validation action belongs with the manual repository controls (INFP-672).
- Connect-time validation of a read-only repository's tracked `ref`. The same class of misconfiguration exists there, but a `ref` may name a branch, a tag or a raw commit SHA, and a SHA cannot be confirmed from a reference listing, so a check modelled on FR-007 would falsely reject valid SHA-pinned repositories. Deferred to its own design.
- Reconciling a trunk edit after the repository has been connected: re-cloning, re-validating, or migrating branches imported under the old mapping. Revisit when manual repository controls exist (INFP-672).
- Blocking or gating merges on repository state. That belongs to the sibling visibility and manual-control efforts (INFP-670, INFP-671).
- The Git push ordering and merge-retry work: recording a commit before confirming the push, and making a failed push retryable from any worker. A separate effort.
- Correcting the trunk attribute's description, already in flight as PR #10449.
- SDK and CLI changes. None are needed.
