## Executive Summary

The spec follows the INFP-739 brief closely. The plan reuses existing query classes, the cache adapter and the workflow catalogue, and adds no middleware or dependency.

One finding must be fixed before tasks: the plan's rule for when the first step is counted (research D9) does not match the spec. The spec says the report without variables is "statistics only". The plan counts a query that declares no variables even when the report gets no `variables` argument.

The recommendations cover:

- how the refresh pages through large kinds without depending on the query planner's choice
- where database rows go when they belong to no field
- how duplicate selections are merged into one entry
- what a failed refresh leaves in the cache
- the order of delivery, so that the actual counts can ship and be checked before the statistics

Three questions from the brief stay open:

- how old the statistics may be
- whether `infrahub-private-tests` needs a CI change
- where the customer figures come from

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | Research D9 counts the first step when "every variable the query declares has a value", so a query that declares no variables is counted even when the report gets no `variables` argument. Spec FR-006 says the report without variables is labelled "statistics only", and its test calls the report without variables. The plan and the spec disagree. | Count the first step on the report only when the `variables` argument is given (an empty object counts as given). On `/graphql` and `/api/query` a request always runs with its variable values, so the first step is always counted there. Update research D9, data-model rules, the contract and the quickstart, and add this to FR-006 in the spec as a clarification. |
| E2 | 💡 | The estimation tree is built from the analyzer tree, and the actual counts from `info.path`. When a query selects the same response key twice (directly and through a fragment), graphql-core merges the selections. The analyzer can produce two tree nodes for that key. The estimate would then have two entries for one actual entry. | State in the data model that tree fields with the same path are merged. Also state that root fields not mapped to a schema kind (for example `InfrahubSearchAnywhere`) have no entry. |
| E3 | 💡 | Database rows that run while no field is set, other than the counted first step, have no place in the contract. | Add an `unattributed` counter (queries and rows) next to `estimate_queries` in the contract and the data model. |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | 💡 | A refresh that fails after writing some kind keys of version n+1 leaves them in the cache. The next run writes version n+1 again, but a kind removed from the schema in between keeps its old key forever. | Before writing a version, delete any existing keys of that version (`list_keys` on its prefix). |
| E5 | — | The pointer is written after every kind key, and a reader retries once when a key is missing. A failed refresh leaves the previous version in use. | No change. |

### Security & Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | — | The estimate's permission check reuses the full checker pipeline. The statistics reveal approximate totals that include other branches; the spec accepts this. The extra queries are bounded by SC-003. | No change. |

### Performance & Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E7 | 💡 | Research D7 pages each kind with `uuid > $after ORDER BY uuid LIMIT $page`. The `node_uuid` index is on the `Node` label, not on each kind. The planner can either scan the `Node(uuid)` index across every kind (slow for a small kind in a large graph), or scan the kind's label and sort it on each page. Which plan Neo4j picks is not known. | Use the pattern of `DiffCalculator`: read the kind's node IDs once, then run the degree query on chunks of IDs with `n.uuid IN $ids`. Check the plan with `EXPLAIN` during implementation (Principle V). |
| E8 | 💡 | Each API process holds the whole statistics snapshot in memory. With about 5,000 relationship sides at about 2 KB each, that is about 10 MB for each process. It is loaded only on the first request that asks for an estimate. | Record the expected size in the plan. Keep the lazy load. |

### Testing Strategy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E9 | 💡 | SC-002 says requests without the header run "the same number of database queries as today". A test cannot run the code from before the feature. | Test SC-002 by running the same request with and without the header with `CountingInfrahubDatabase`. Without the header, no first-step query runs and no recorder is created. With the header, the extra queries equal `estimate_queries.queries`, and that number is at most 1 + the number of direct relationship fields (SC-003). |
