# Critique Report: One branch deletion records the same number of task runs whatever the number of open branches

**Date**: 2026-11-04
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

The fix is sound. Removing the `@task` decorator from the per-branch gather makes the task-run count independent of the number of branches, and it is safe on `stable`. The `add_note` design for FR-005 keeps the exception type and puts the branch in the traceback that the task log shows.

The plan's test design had three gaps that would block implementation:

- It did not say how a test deletes a branch. `Branch.delete` raises `NotImplementedError`, and nothing in the flow purges the registry.
- The FR-004 fixture lacks the core models schema.
- The FR-002 check compared the automations with the gather's own output, which is equal by construction.

Several statements in the documents were also wrong. They cover:

- the automations that stay unchanged after a deletion;
- the task-run count of a schema update in production;
- the wording of the missing-transform warning for a transform wired by UUID;
- the deleted-branch edge case;
- the callers on `develop`.

All of these are fixed in the spec and plan in the same commit as this report.

The review was done by an agent with no access to this session's reasoning, then each finding was checked against the code before being applied. Paths are relative to the repository root, and Prefect paths to `.venv/lib/python3.14/site-packages`.

## Cross-Lens Insights

- E1 and P2 come from the same fact. A deleted branch stays in a worker's registry until the registry is purged. The test must purge it explicitly, and the spec must not claim to know what the gather does with such a branch.
- P3 and E6 come from reading the code paths that tests replace. UUID wiring and `run_deployment` behave differently in production from what the tests observe. The documents now name both.
