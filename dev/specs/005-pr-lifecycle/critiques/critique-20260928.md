# Critique report: PR lifecycle

**Date**: 2026-09-28

**Feature**: [spec.md](../spec.md)

**Plan**: [plan.md](../plan.md)

**Verdict**: PROCEED after updates recorded below

## Executive summary

Independent product and engineering review found no fundamental objection to the approved gated
closer architecture. Two must-address gaps required executable definitions: readiness information
and reminder delivery windows. Both are incorporated in the plan/contracts/spec. Five recommendations
were also incorporated. The plan can proceed to offline implementation; hosted validation and
production recovery remain separate evidence gates.

## Product lens findings

### Problem validation

The existing run logs establish the recovery need; the ticket and handoff establish the agreed
combined scope. No additional policy interview or staged feature rollout is needed.

### User value assessment

All four stories have observable outcomes. Independent tests do not authorize shipping cleanup
without reminders/dashboard. One early lifecycle vertical slice will validate composition.

### Alternative approaches

Stock timing conflicts with comment reminders. A forked closer or shared service adds scope;
companion timing with stock closure follows the user-approved refinement.

### Edge cases and experience

P1 (must-address): daily jitter can skip a strict last-24-hours notice window. The final plan uses
inclusive UTC calendar-date starts on warning date + 7/+13, ending at the stronger window/exact
expiry. Messages show absolute deadlines, and missed windows do not extend the cycle.

### Success measurement

Full inventory and independently verified outcomes are measurable. Upstream successful exits and
attempt counts are not coverage or recovery evidence. Production evidence remains outstanding.

## Engineering lens findings

### Architecture soundness

E1 (must-address): required-rule readiness was underspecified. The updated contract queries
headRefOid, mergeable, mergeStateStatus, and reviewDecision together; same-head CLEAN/MERGEABLE with
APPROVED or explicit null reviewDecision is authoritative, with current approval and no conflicting
review/blocker. Missing/error/unknown values block readiness. No branch-rule interpreter is added.

### Failure modes

E4 (recommendation): cache progress needed precise evidence. Record the exact `_state` key/ref and
cache identity/timestamps/size, distinguish replacement from natural deletion on completion, and
couple metadata with independently fetched candidate state. Last-access time alone proves nothing.

### Security and privacy

E2 (recommendation): authenticate dashboard provenance, not just its marker. The contract now
requires trusted creator or explicit adoption and independent warning-receipt validation before
closure. Do not trust arbitrary edited ledger fields as authorization.

### Performance and scalability

E3 (recommendation): define retention so historical PRs do not fill the issue ledger. Prune only
reconciled closed/merged entries after cleanup, retain unresolved operations, and keep compact
current-cycle/watermark records. Test many historical cycles and oversized current inventory.

### Testing strategy

E5 (recommendation): start with a full-lifecycle vertical-slice test before expanding the utility.
This is T004 and prevents independently plausible components from hiding integration defects.

### Operational readiness

E6 (recommendation): hosted validation requires a named authorized repository and suitable test
credentials. T030 records this input explicitly. It blocks hosted validation/activation, while
offline implementation can proceed. No production writes are substitutes for this evidence.

### Dependencies and integration

Source fixtures prove gate behavior, but not hosted cache transport or complete attribution.
Non-atomic approvals and transient human edits remain documented API snapshot limitations. No new
package, webhook application, database, or shared-bot deployment is planned.

## Cross-lens insights

Accurate deadlines and conservative failure handling both protect maintainers' trust. Own-write
receipts, bounded continuation, and independent postconditions add necessary complexity exposed by
the actual pinned action. Avoid expanding this into a general lifecycle engine.
