# Research: Task History and Activity Log Retention

The [Notion design doc](https://app.notion.com/p/opsmill/Task-history-and-Activity-log-retention-3dc228b830258012ba28dc3a23eece65) already decides the approach (D1-D10, with benchmarks). This file records what the codebase and the pinned Prefect release confirm about each decision, and the implementation choices the doc leaves open.

## R1. Prefect's cleanup of old runs (D1)

- **Decision**: Turn on Prefect's built-in flow-run vacuum by adding `flow_runs` to `PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED`, with `PREFECT_SERVER_SERVICES_DB_VACUUM_RETENTION_PERIOD` set from the task history retention.
- **Confirmed in Prefect 3.8.6** (`prefect/server/services/db_vacuum.py::vacuum_old_flow_runs`): it selects top-level runs (`parent_task_run_id IS NULL`) in a terminal state with a non-null `end_time` older than the cutoff, in batches of `batch_size`. It deletes each batch of runs in one transaction (task runs and states follow by cascade), and then deletes the logs and artifacts of those runs by `flow_run_id` in separately committed batches, the order R5 follows. Enabling `flow_runs` also schedules the daily orphaned logs and artifacts cleanup (`schedule_orphan_vacuum_tasks`). The default enabled set is `{"events"}`.
- **Rationale**: Prefect maintains it and it deletes in database batches. The existing API loop deletes one run per call at about 17 h per million runs.
- **Alternatives considered**: Scheduling `infrahub.task_manager.flow_run.retention::FlowRunRetention` as a workflow (rejected in D1).

## R2. How Infrahub sets Prefect settings in the task manager (D5)

- **Decision**: In `infrahub.prefect_server.app::create_infrahub_prefect`, read the `task_manager` section of the Infrahub configuration, validate the retention settings, and write the derived `PREFECT_*` variables into `os.environ` before `prefect.server.api.server.create_app` is called. A new `infrahub tasks background-services` command does the same translation and then runs Prefect's services (`prefect server services start` equivalent) in the same process.
- **Confirmed**: `prefect.settings.context::get_current_settings` returns the settings of `prefect.context.GLOBAL_SETTINGS_CONTEXT` whenever no settings context is active, and that context is built from the environment once, when `prefect.context` is imported. Values written to `os.environ` afterwards are picked up only after `prefect.context.refresh_global_settings_context()`; once refreshed, the vacuum services see them, since they read `get_current_settings()` on every run. The background-services command needs the same refresh.
- **Gap found**: `create_infrahub_prefect` loads the Infrahub configuration only in distributed mode (when block registration and migrations on start are off). The translation reads the `task_manager` section of the configuration in both modes; only distributed mode loads and validates the whole configuration, so a setting the task manager does not use cannot stop it.
- **Explicit Prefect settings win**: if an operator already sets one of the four Prefect settings, through a `PREFECT_*` variable that is not empty or through Prefect's `.env` file, `prefect.toml`, the `[tool.prefect]` table of `pyproject.toml` or active profile, Infrahub writes no variable for it, so existing deployments that tuned Prefect directly keep the values they set. Prefect gives an environment variable precedence over all of those files, so a variable written by Infrahub would replace a value from a file without a warning. Infrahub finds the settings already set through `model_fields_set` of Prefect's own settings models (`ServerServicesDBVacuumSettings`, `ServerEventsSettings`), which lists a field only when one of Prefect's sources supplies it; it reads them after removing a blank vacuum switch, which Prefect reads as `false`, and before writing any. Only the switch can be blank and read by Prefect at that point: Prefect refuses an empty retention period or per-type override when it is imported, so the task manager and every `infrahub` command stop before any Infrahub code runs, as they did before. For each of the three retention settings it logs one warning, naming the Prefect variable and the Infrahub setting it hides, and saying when a Prefect settings file or profile sets it. The vacuum switch (`PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED`) hides no setting: it only turns Prefect's cleanups on or off, and `task_history` still sets the task-run retention unless `PREFECT_SERVER_SERVICES_DB_VACUUM_RETENTION_PERIOD` is set, so a deployment that set only the switch, and kept runs for Prefect's default of 90 days, now keeps them for `task_history`. After the refresh, Infrahub reads the switch as Prefect parses it (`ServerServicesDBVacuumSettings.enabled_vacuum_types`, which Prefect checks only when it is read) and logs a warning for each of `flow_runs` and `events` that it leaves off, naming the retention that is then not applied. The startup log reads the four values from Prefect's parsed settings after the refresh, so it shows what Prefect applies whatever the source. The three Infrahub settings are the documented interface, and the configuration reference states the precedence.
- **Alternatives considered**: Prefect's `temporary_settings` context (scoped to a context manager, not the server lifetime); waiting for INFP-703 (rejected in D5).

## R3. Where the background services run (D5, Helm row)

- **Confirmed**: Compose and default Helm run Prefect's background services inside the task-manager process. The test compose file `python_testcontainers/infrahub_testcontainers/docker-compose.test.yml` and `docker-compose-cluster.test.yml` define `task-manager-background-svc` with `command: prefect server services start`, and the Helm chart offers the same split as an option.
- **Decision**: Replace that command with `infrahub tasks background-services` in both test compose files, and change the Helm chart in the infrahub-helm repository (separate PR).
- **Gap found**: a task manager started with `PREFECT__SERVER_WEBSERVER_ONLY` (set by `prefect server start --no-services` and by the scale-out setup of `python_testcontainers/infrahub_testcontainers/container.py`) runs none of Prefect's cleanup services, so the retention it applies to its own process deletes no task runs. With a shared Redis docket, its docket worker still runs some of the event-cleanup tasks that the services process schedules (`prefect/server/api/background_workers.py::task_functions`), and each task reads the settings of the process that runs it, so both processes need the same values. Until the background-services command exists, the task manager logs a warning at startup when the variable is set to any non-empty value, which is how Prefect reads it (`prefect/server/api/server.py::create_app`).

## R4. Event retention per type (D3)

- **Decision**: Set `PREFECT_SERVER_EVENTS_RETENTION_PERIOD` to the activity log retention and `PREFECT_SERVER_SERVICES_DB_VACUUM_EVENT_RETENTION_OVERRIDES` to `{event_type: prefect_own_events}` for every type in Infrahub's list of Prefect event types. When Infrahub sets the event retention and `prefect_own_events` equals `activity_log`, the overrides are set to `{}` instead: Prefect's general event cleanup (`vacuum_old_events`) deletes the same events, and each listed type costs at least two delete statements every hour (one for its related resources, one for the events). The variable is set to `{}` rather than left unset, because Prefect's default is `{"prefect.flow-run.heartbeat": 7 days}`, which would delete heartbeats earlier than both retentions when they are longer than 7 days. When the event retention is preset, Infrahub does not know whether the overrides shorten it, so it writes the full list.
- **Confirmed** (`db_vacuum.py::vacuum_events_with_retention_overrides`): overrides match `Event.event == event_type` exactly and the effective retention is `min(type_retention, global_retention)`, which is why an own-event retention longer than the activity log has no effect and is refused at startup. Because Prefect applies this cap with the event retention it actually uses, preset or derived, the overrides carry `prefect_own_events` as configured. Related resources are deleted before the events, so none are left behind.
- **List source**: a module-level constant in the backend, built from the pinned Prefect release (run and task-run state events, heartbeat, worker, automation, deployment, work pool, work queue, block and workspace transfer events). The benchmark found 26, 14 and 33 types across three datasets.
- **Guard**: an integration-docker test runs a workload of Infrahub tasks on the full stack (real workers, Postgres), including the failure paths it can reach (failed and cancelled flows, a worker restart), and fails when a stored event type that does not start with `infrahub.` is missing from the list. The functional tier is not enough: it runs Prefect's test harness on SQLite with non-essential services off and no real worker, so worker and work-pool events never appear. Unit tests also read the installed Prefect package's source and fail when it sends a `prefect.*` event name that is not listed, builds event names from a pattern other than the known ones, or has a deployment, work pool or work queue status, an automation trigger state or a lifecycle record kind whose events are not listed. They also check that `prefect.flow-run.<State>` and `prefect.task-run.<State>` are listed for every state name Prefect defines or sets in its source. A Prefect upgrade that adds one of these fails CI whatever the workload reaches. Names that exist only at runtime are not in the source, so these tests do not cover them:
  - custom state names;
  - load events of block types that Infrahub does not load;
  - `prefect.*` events that API clients post.

  The tests also do not read some values that Prefect's source puts into the known patterns, so a new value is caught only by the integration-docker guard, and only when the workload reaches it:
  - the actions of lifecycle events, which the tests take to be `created`, `updated` and `deleted`;
  - the phases in `prefect.concurrency-limit.<phase>` and `prefect.concurrency-limit.v1.<phase>`;
  - the statuses in `prefect.asset.materialization.<status>`;
  - an event name passed through a helper whose parameter is not named `event` or `event_type`.
- **Alternatives considered**: deleting every event whose type does not start with `infrahub.` once it is older than `prefect_own_events`, which needs no list. Prefect's settings cannot do this: the overrides match exact names and are capped by the event retention, and the general cleanup deletes every event older than the event retention. It would need a periodic delete that Infrahub runs in the process that runs Prefect's services, which goes against D1 and D3: both leave the deletes to Prefect's own cleanups.

## R5. The command for old runs and its endpoint (D9)

- **Confirmed**: `infrahub.cli.tasks::flow_runs` (`infrahub tasks flush flow-runs`) calls `FlowRunRetention.purge` through the Prefect API with its own `--days-to-keep` (default 30). `stale_runs` uses the same class with `delete=False`, so `FlowRunRetention` keeps a caller.
- **Decision**: `flow_runs` posts to a new task-manager route `POST /infrahub/task-history/cleanup` on `infrahub.prefect_server.app::router` and polls `GET /infrahub/task-history/cleanup/{job_id}` until it finishes. The route starts the cleanup as a background job inside the task manager, so a dropped session or an HTTP timeout does not stop it. The job deletes one day of end times at a time, at most 1,000 runs per transaction, and logs progress, so a re-run continues where it stopped. The command reads the task history retention setting; its `--days-to-keep` and `--batch-size` options are removed (design doc D9), which the changelog flags as breaking. The request's `rewrite` is a mode, `never` or `if_freed`; `--rewrite` sends `if_freed`, and the command sends `never` without it. (Until 11 Oct a third mode, `always`, served `--rewrite` and `if_freed` served the upgrade.)
- **One job across replicas**: the job holds a Postgres session-level advisory lock for its whole run (no table added). A replica that cannot take the lock answers `409` "a cleanup is running elsewhere". Every 30 s, the session that took the lock checks that it still holds the lock, which also keeps the session from sitting idle past an idle timeout (added on 28 Oct: a session ended by an administrator, an idle timeout or a failover dropped the lock while the job ran, and another replica could then start a second job). When the check fails, finds the lock gone or gets no answer within 30 s, the job cancels its current step and fails with "The cleanup stopped, because it could not confirm that it holds the cleanup lock; start it again": the deletes not committed yet roll back, and a rewrite in progress leaves its table as it was. A check that gets no answer closes its connection instead of cancelling its query, because the driver waits without a limit for the server's answer to a cancelled query (changed on 28 Oct: a lock session that stopped answering kept the job running, and another replica could start a second job once the server ended that session); releasing the lock waits for a check in progress, so at most 30 s, instead of cancelling it. A step whose own statement gets no answer cannot be cancelled before the server answers it either, so such a job fails only then. Behind a connection pooler in transaction mode, the check can run on a different database session from the one that took the lock, so the job stops. The job's status lives in the process that runs it, so the CLI treats `404` on the status route or `409` on start by waiting and posting again; because each transaction is committed, a new job continues from the oldest remaining run. A transport error, or a 502, 503 or 504 answer (a proxy in front of a restarting task manager, or the task manager's own 503 when its database is unavailable), while the CLI follows a job is handled the same way after Prefect's client retries, inside the same 3-hour limit; one on the first request means the task manager cannot be reached, and the command fails. A replica that already runs a job returns it, raising the job's mode to the request's when that is stronger (`never` < `if_freed`); the job decides about the rewrite with the mode it holds once its deletes end, and decides again before it completes when `if_freed` arrived after a decision with `never`, without rewriting twice. The escalation lives in the task manager because a request can only follow the job already running, and a second job started after it would rewrite the tables that the first one already rewrote. The mode change and the job's last check of its mode take the job registry's start lock, so a request either reaches the job before its last check or starts a new job. A request refused with `409` by another replica starts its own job, with its own mode, once that replica's job ends. On SQLite (test harness) the lock is a process-level lock.
- **Deletes**: written with SQLAlchemy Core against Prefect's ORM models (`PrefectDBInterface.FlowRun`, `Log`, `Artifact`), following the same selection as `vacuum_old_flow_runs`, so the logic runs on Postgres in production and on the SQLite database of the test harness. For each day: delete the day's eligible runs (task runs and states follow by cascade), then the logs and artifacts of the runs this job deleted, as in the design doc's D9. This is the order Prefect's own vacuum uses (`db_vacuum.py::vacuum_old_flow_runs` deletes a batch of runs in one transaction, then their children in separate batches; deleting the runs first prevents a concurrent state transition from preserving a run after some of its children were deleted). Each transaction deletes at most 1,000 runs of the day, the earliest ended first, then the logs and artifacts of those runs, and the job repeats it on the same day until a transaction deletes fewer runs, which leaves only runs that other sessions hold locked (changed on 28 Oct: one transaction deleted the whole day, so for as long as the day took it held its row locks, kept Postgres from vacuuming dead rows and showed no progress, and a failure rolled back the whole day). The bound is not Prefect's `batch_size` (200): Prefect deletes 200 runs per transaction, then their logs and artifacts in further transactions of 200 rows. The job keeps the logs and artifacts in the transaction of their runs, so a stopped job leaves no log or artifact without its run, and each log and artifact statement still removes many rows. It bounds the runs instead, so that one transaction holds its locks for, and rolls back, no more than 1,000 runs. Running next to Prefect's vacuum, which is now on, cannot deadlock: Prefect selects its runs with `FOR UPDATE SKIP LOCKED`, and each side deletes children only for runs it deleted itself. A second pass catches subflows left without a parent. Each delete transaction first sets a 60 s `lock_timeout` for itself only (`set_config` with `is_local`), because only the runs are selected with `SKIP LOCKED`: the cascaded task runs and states, the subflows whose parent is set to null, and the logs and artifacts would otherwise wait on a stuck session until the 24 h maintenance timeout, holding the cleanup lock all along; a job that reaches it fails naming the day (added on 28 Oct).
- **Rewrite** (changed on 8 Oct in the design doc): `VACUUM FULL`, only on Postgres and only with `if_freed`, on each of `flow_run`, `flow_run_state`, `task_run`, `task_run_state`, `log`, `artifact`, `events` and `event_resources` whose live rows hold less than half of its disk space, whoever deleted its rows and when. Prefect's own cleanup deletes old runs every hour and old events after their retention, so after the upgrade or after lowering a retention the command deletes little, and a rule on its own deletes would skip the rewrite exactly when the disk must come back. Each table is measured on its own: its size on disk (its main data and its TOAST table, without indexes, free-space map and visibility map) against the size of its live rows (`pg_column_size` of each column, which reads no value stored out of line, plus 28 bytes a row for the row header and line pointer). Up to 10,000 pages the whole table is read; above that the live size is estimated from `TABLESAMPLE SYSTEM` over about 10,000 random pages, which is built into Postgres. On Fatih's 1.10 large backup (12 GB `events`, 12 GB `event_resources`), the sample estimated the live size within 2 % of the full read, in 0.2 to 0.7 s against 4 to 6 s. A mostly live table, such as the event tables with a long activity log retention, is left as it is and named in the result. The measurement runs on the maintenance connection pool, like the deletes. Each rewrite runs outside a transaction (autocommit). Changed on 27 Oct to the limits of the manual cleanup of the event tables of OpsMill's production task manager on 26 Oct ([cleanup report](https://app.notion.com/p/405228b8302581d2b77cec9ee9b720f6)): a lock timeout of 3 s, because every query that reaches a table while a rewrite waits for its lock queues behind the rewrite; up to 4 retries 20 s apart, then the table is reported as not rewritten; a statement timeout of 60 s, which stops a rewrite and leaves the table as it was, reported as timed out; a plain `VACUUM (ANALYZE)` of each rewritten table, which blocks nothing; and a pause before the next table, so that Prefect catches up on the writes that waited. The manual cleanup paused 60 s after a 6.4 s lock; the job pauses ten times as long as the previous table was locked, up to 60 s, which is the full 60 s for every table locked 6 s or more and milliseconds for a table rewritten in milliseconds (decided on 27 Oct, so that the Docker test of the command does not wait 5 minutes for its six small tables). The job continues with the next table after one that stayed locked, was stopped at its time limit or failed with another database error, such as a lack of disk space for the copy (the last case added on 28 Oct), where the manual cleanup stopped at the first problem, because each table has its own limits and a table that was not rewritten stays as it was: Postgres rolls back a failed rewrite on its own, which removes its copy and leaves the session usable. A lost database connection, or an error that did not come from the database server, still fails the job. Before, the lock timeout was 60 s with up to 3 retries, which could make the queries on a table wait a minute behind a rewrite that had not started. Not adopted from the manual cleanup: its free-space check and its read of the table files into memory, because the task manager only sends queries to the database; and its rebuild of the indexes without blocking.
- **Vacuum switch** (added on 28 Oct): the route refuses to start a job with `403` and the reason, such as `Old task runs are not deleted, because PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED does not turn on flow_runs`, when the switch, as Prefect parses it, does not turn on `flow_runs`. Prefect's own cleanup then deletes no old task runs and the task history retention is not applied, so a job would delete runs that the automatic cleanup keeps. The command prints the reason and exits with code 1. The route answers `403` because the other codes already mean something to the command or to Prefect's client: `409` makes the command wait, `404` on a start makes it skip the cleanup, Prefect's client retries `429`, `502` and `503`, and FastAPI answers `422` for a request body that is not valid.
- **Old task manager**: when the route returns 404, the command prints that the task manager does not provide the cleanup yet and exits successfully.
- **Alternatives considered**: Prefect's own cleanup for the one-off cleanup (2 h 26 min against 8 min on 25 GB), a full read of every table to measure its live size (reads hundreds of GB of event tables that are then left as they are), and for the free-space rule a count of the runs when the job starts against the runs left after its deletes (a Compose run of the upgrade guide showed Prefect's cleanup at task-manager start deleting all 120,305 old runs before the job started; the job then deleted 0 runs and left the tables at 166.5 MB, not rewritten).

## R6. The upgrade's hint (D9, changed on 11 Oct in the design doc)

- **Confirmed**: `infrahub.cli.upgrade::_upgrade_execute` runs six numbered steps; step 5 configures the task manager through `get_client`.
- **Decision**: the upgrade runs no cleanup. In step 5 it reads `GET /infrahub/task-history/size` and prints `Task history takes <size>, with <count> runs older than the retention. To get the space back, run: infrahub tasks flush flow-runs --rewrite`. When Prefect's vacuum switch does not turn on `flow_runs`, the line ends with `Old task runs are not deleted, because <reason>.` instead, because the command would be refused (added on 28 Oct). The count, a suggestion in the design doc asked for on 11 Oct, tells an operator whether the hourly cleanup has already worked through the backlog; it stops at 100,000 so it stays fast. The size is `pg_total_relation_size` of the six task-history tables, which reads no table data. The read is bounded to 10 s, and a task manager that answers late, answers an error (`404` for one without the route, as during the Helm upgrade hook) or answers without a size gets a line naming the error type and the command, so the hint never fails or slows the upgrade. Operators of existing instances with a lot of task history run the command once after the upgrade, the same on Compose and Helm, with the instance running; the Helm chart's upgrade hook needs no extra option.
- **Alternatives considered**: the 4 Oct design, a "Task history cleanup" step in the upgrade with `--no-task-history-cleanup` for the Helm hook (about 8.5 minutes longer upgrades on 25 GB and 2 h 20 min on 100 GB, an irreversible delete inside the upgrade, and a separate Helm path); an exact count of the old runs (it reads every old run, millions on the instances that need the step).

## R7. Activities queries (D6)

- **Confirmed path**: `infrahub.graphql.queries.event::Events.resolve` → `infrahub.task_manager.event.models::InfrahubEventFilter.from_filters` → `infrahub.task_manager.event.query::PrefectEvent.query_events` posts to `/infrahub/events/filter` → `infrahub.prefect_server.events::read_events` → `infrahub.prefect_server.database::query_events`, which always calls `raw_count_events` and then `read_events` with `offset`.
- **Confirmed ID formats** (`infrahub.events.models::InfrahubEvent.get_related`): account `infrahub.account.<id>` (role `infrahub.account`), branch `infrahub.branch.<branch_id>` (role `infrahub.branch`), child events carry `prefect.resource.id = <parent event id>` with role `infrahub.ancestor_event`.
- **Filters today** match labels: `infrahub.resource.id` (account), `infrahub.resource.label` (branch), `infrahub.node.id` (primary node), `infrahub.event_parent.id` (parent), `infrahub.branch.name` (merged, rebased, migrated).
- **Decision**: rewrite the five filter methods to match `prefect.resource.id` (which Prefect maps to the indexed `resource_id` column), as in D6; resolve branch names to IDs in the GraphQL resolver through the branch registry, falling back to the newest `infrahub.branch.deleted` event with resource ID `infrahub.branch.<name>`.
- **Time windows**: implemented in `infrahub.prefect_server.database::query_events`, which receives the widest window (the activity log retention) and the anchor (`until` or now) from the request.
- **Count**: PR #10379 already adds `include_total: bool = True` to `InfrahubEventfilterInput`, set by the GraphQL resolver from the requested fields; this feature keeps that field and returns a null `total` when it is false.
- **Plan per query**: PR #10379 (open, not merged) sets `plan_cache_mode = force_custom_plan` for the Activities queries. It is a dependency of part 2, merged first or carried into it.
- **Frontend**: `frontend/app/src/entities/events/ui/queries/get-events.query.ts` pages by offset (`lastPageParam + DEFAULT_PAGE_SIZE`). It changes to `until` = `occurred_at` of the last event, with de-duplication by ID. The GraphQL document in `frontend/app/src/entities/events/api/get-events-from-api.ts` already passes `until` and **does not select `count`** (checked on `stable` and `develop`), so the design doc's premise that the page asks for the total count does not hold: the cost comes only from `infrahub.prefect_server.database::query_events` counting on every request. No frontend count change is needed; the design doc was corrected (D7 and Q2 removed).

## R8. Tests

- **Confirmed**: `backend/tests/component/conftest.py::prefect_test_fixture` starts `create_infrahub_prefect` through `prefect_test_harness` (SQLite). `backend/tests/helpers/constants.py` turns Prefect's vacuum off for tests (`PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED: "[]"`). Existing unit tests live under `backend/tests/unit/task_manager/event/` and `backend/tests/unit/task_manager/flow_run/` (including `test_retention.py`).
- **Decision**: the cleanup and filter guards are component tests on the existing harness: the cleanup equivalence test seeds runs, copies the database state, runs `vacuum_old_flow_runs` and the new cleanup, and compares remaining run, log and artifact IDs; the filter equivalence test seeds events and compares each new filter with the label filter. The event-type list guard is an integration-docker test plus unit tests over the pinned Prefect's source (see R4). A concurrency test runs Prefect's vacuum and the new cleanup at the same time on the same old runs and checks both finish with the same end state. The cleanup equivalence and the rewrite also run against Postgres in the integration-docker tier, which already boots the task manager on Postgres. Query speed stays with the private performance tests listed in the design doc.
