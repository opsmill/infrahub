## Executive Summary

The spec and plan follow a design doc that was benchmarked and grilled, so the problem, scope and main choices are solid: task history gets a hard bound, the Activities queries are fixed before the activity log can grow, and nothing is added to Prefect's database. Three items need fixing before tasks: the cleanup job's state lives in one task-manager process although the task manager can run more than one replica; the cleanup deletes runs before their logs while Prefect's own cleanup, now switched on and running during the upgrade, deletes logs first, which can deadlock on the same runs; and the new mutating route without authentication conflicts with constitution Principle VI and needs an explicit, approved deviation. The remaining findings are recommendations: keep the old command flags working, bound how long the table rewrite waits for locks, prove the cleanup on Postgres, and coordinate the Helm chart PR.

## Engineering Lens Findings 🔬

### Architecture Soundness
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | The cleanup job and its "one job at a time" rule live in one task-manager process. With more than one task-manager replica behind a service, the CLI can start a job on one replica and poll another (unknown job), and two replicas can run two cleanups and two rewrites at once. | Enforce one job with a Postgres advisory lock taken by the job (no table added). A replica that cannot take the lock answers that a cleanup runs elsewhere. The CLI treats an unknown job or "runs elsewhere" by waiting and posting again; since each day is committed, a new job continues where the previous one stopped. |

### Failure Mode Analysis
| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E2 | 🎯 | The plan's SQL deletes runs first and their logs and artifacts after, inside one transaction per day. Prefect's flow-run vacuum, now switched on and running in the task manager during the Compose upgrade and after any rollout, deletes logs and artifacts first and the runs after, also starting from the oldest runs. Two transactions taking the same rows in opposite orders deadlock, and Postgres aborts one of them. | Delete in Prefect's order: select the day's run IDs, delete their logs and artifacts, then the runs (task runs and states follow by cascade). Retry a day after a deadlock or serialization error, a bounded number of times, and report it. |
| E3 | 💡 | `VACUUM FULL` waits for every lock on the table, without limit, and cannot run inside a transaction. | Run each rewrite outside a transaction with a lock timeout; on timeout, report the table as not rewritten and continue with the next one, so the upgrade never hangs. |
