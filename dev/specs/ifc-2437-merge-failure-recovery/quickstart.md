# Quickstart: Merge Failure Recovery

This document is a verification walkthrough — what an operator or developer can do to confirm the feature works end-to-end. The implementation task breakdown will be generated by `/speckit-tasks` into `tasks.md`.

## Prerequisites

- Local Infrahub stack up (`uv run invoke dev.start` or equivalent).
- A non-default branch with at least one node-level change ready to merge.

## Scenario 1: Normal merge (regression check)

1. From the UI or CLI, merge the branch into the default branch.
2. Confirm merge completes successfully.
3. Query the source branch in Neo4j:

   ```cypher
   MATCH (b:Branch {name: "<source>"}) RETURN b.status, b.merge_started_at
   ```

   `status` MUST NOT be `"MERGING"` (the existing flow transitions it to `"MERGED"` after a successful full merge); `merge_started_at` MUST be `null`.

4. Logs MUST contain a `merge.graph.start` and a matching `merge.graph.complete` event with the same `(branch, started_at)` pair.

## Scenario 2: Catastrophic failure during merge

1. Configure the merge worker to receive a SIGKILL after the first bulk-merge query in `merge_graph` (test-only hook generated by `/speckit-tasks`).
2. Trigger a merge of the prepared branch.
3. Observe that the worker process dies before the merge completes.
4. Inspect the source branch in Neo4j — `status` MUST be `"MERGING_GRAPH"`, with `merge_started_at` populated.
5. Restart the API workers (`docker compose restart api` or equivalent).
6. Observe that the API does NOT begin serving requests until the recovery scan completes (FR-007). Health endpoint returns startup-not-complete during recovery.
7. Logs MUST contain `merge.recovery.detected`, `merge.recovery.rollback_started`, and `merge.recovery.rollback_complete` for the affected branch.
8. Once the API is ready, query the source and target branches and confirm both are in their pre-merge state (graph diff against pre-merge snapshot is empty).
9. Confirm the source branch's `status` is now `"OPEN"` and `merge_started_at` is `null`.
10. Re-attempt the merge; it MUST now succeed.

## Scenario 3: Concurrent recovery (multi-worker)

1. Force a partial merge as in Scenario 2.
2. Restart all API/task workers simultaneously (`inv dev.restart`).
3. Logs from one worker MUST contain `merge.recovery.rollback_started` for the affected branch; logs from the others MUST show that they observed the recovery lock held and skipped (or waited).
4. Exactly one `merge.recovery.rollback_complete` event MUST be emitted per affected branch (FR-008, SC-004).

## Scenario 4: Rollback failure (non-happy path)

1. With a partial merge marker set (`status=MERGING`), intentionally break the rollback path (e.g., by temporarily renaming `DiffMergeRollbackQuery` so the recovery raises).
2. Restart the API.
3. The startup MUST fail loudly: lifespan startup raises, the API does NOT begin serving requests, and a `merge.recovery.rollback_failed` event is emitted at error level (FR-012).
4. The branch's `status` MUST remain `"MERGING_GRAPH"` (with `merge_started_at` preserved) so that a subsequent corrected restart can complete the recovery.

## Scenario 5: Write-block enforcement (both windows)

1. Begin a long-running merge with a debug pause inside `merge_graph`. Source branch transitions to `status=MERGING_GRAPH`.
2. While paused inside `merge_graph`: attempt to write to the source branch via GraphQL — request MUST be rejected via `BranchStatusError` from `BranchStatusChecker.check_merging_status`.
3. Attempt to write to the default (target) branch — request MUST be rejected (target gate).
4. Attempt to write to an unrelated third branch — request MUST succeed (FR-004).
5. Release the debug pause. `merge_graph` completes; source branch transitions `MERGING_GRAPH → MERGING`. Insert a second debug pause inside the migration step (or repository-merge step).
6. While paused in the broad `MERGING` window: re-attempt the writes from steps 2–4. The source and target writes MUST still be rejected; the unrelated branch write MUST still succeed. This verifies the broad window covers post-graph-merge work.
7. Release the second pause and allow the merge to complete. Source branch transitions to `MERGED` via the existing post-merge code path. The target branch (default) becomes writable again.
