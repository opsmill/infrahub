# Critique Report: E2E proof runs for the bug pipeline

**Date**: 2026-08-25 19:35 | **Verdict**: ⚠️ PROCEED WITH UPDATES

## Executive Summary

The spec and plan are unusually well-grounded: every core mechanism (trigger, phase markers, verdict from junit, body embedding, runner sizing, image strategy) was demonstrated end-to-end by PoC PR #10411 on a real bug. The material risk is concentrated in the **one mechanism the PoC did not exercise**: release-asset storage. The PoC embedded images from an orphan branch; the plan swaps in release assets whose inline rendering through GitHub's camo proxy is assumed, not proven. That assumption must be validated first, with an explicit fallback, before the rest of the storage work is built on it. Remaining findings are hardening (reason-text sanitization, embed-script unit tests) and one workflow gap (what happens after an inconclusive verdict).

## Product Lens Findings

- **3a Problem validation**: strong — structural blocker identified (agents cannot boot the stack), backlog quantified (~4/14 open frontend bugs are E2E-class), PoC proves demand can be served. No findings.
- **3b User value / MVP**: P1 story is the feature; P3 stories are correctly ranked. The cleanup workflow (US4) could ship a week later without harming users — acceptable to keep in scope since it is tiny. No blocking findings.
- **3c Alternatives**: the orphan branch is the *proven* alternative and remains the fallback; the plan's preference for release assets is justified (zero git growth) but rests on an unvalidated rendering assumption → **P1 (🎯)**.
- **3d Edge cases / UX**: good coverage. Gap: after an `inconclusive` verdict (infra flake), the spec never says who acts — an agent loop could stall silently → **P2 (💡)**: define the re-run/escalation path (human or reviewer re-runs; test agent escalates after two consecutive inconclusive runs).
- **3e Success measurement**: measurable, PoC-anchored budgets. No findings.

## Engineering Lens Findings

- **4a Architecture**: scripts extracted with tests — better than the PoC's inline python. No findings.
- **4b Failure modes**: image-pull fallback, best-effort screenshots, junit-missing → inconclusive: covered. Bootstrap race on `gh release create` between concurrent PRs needs the idempotent guard the research already prescribes. No new findings.
- **4c Security**: trust boundaries stated. Gap: the embedded *reason* line originates from the junit failure message, i.e. from test code and app output; it is interpolated into PR-body markdown. Malicious or accidental markdown/HTML could distort the description → **E1 (💡)**: truncate (≤200 chars) and neutralize markdown in `reason` before embedding.
- **4d Performance**: bounded by PoC timings; concurrency-cancel prevents pile-ups. No findings.
- **4e Testing**: verdict script is unit-tested, but the embed script — the component with the strictest invariants (byte-identical outside markers, idempotency, marker preservation) — is only exercised by a quickstart dry-run → **E2 (💡)**: colocate unit tests for `e2e_proof_embed.py` (pure function over body strings) alongside the verdict tests.
- **4f Operational readiness**: rollback = remove two workflows; failures already surface via the pipeline's existing [aw]-failure issue automation. Acceptable.
- **4g Dependencies**: gh-aw compiler version churn on lock regeneration is called out; Docker Hub outage covered by build fallback. No findings.

## Cross-Lens Insights

- **X1 (🎯)**: Release-asset rendering is simultaneously the main product bet (screenshots readers can actually see) and the main engineering unknown (camo behavior over `releases/download` redirects). Resolution is cheap: make the first implementation task a 10-minute validation (upload one PNG to the prerelease, embed it in a scratch PR body, confirm it renders), and write the fallback into the spec: if rendering is unreliable, keep the FR-008 naming/cleanup contract but store on the PoC-proven orphan branch.
