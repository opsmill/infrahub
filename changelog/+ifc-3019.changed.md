A merge or a rebase no longer starts one recompute task per changed node for Python transform computed attributes. It now derives the affected attributes from the whole change set and submits one recompute per affected attribute per batch of changed nodes, the way Jinja2 computed attributes, display labels and human-friendly ids already worked. The stored values are the same, and every signal the derivation cannot narrow safely still recomputes the whole kind rather than risk a stale value. The saving grows with the number of changed nodes: a merge that builds a site with 68 nodes carrying Python computed attributes ran 68 recompute tasks and now runs a few, while a merge that changes a single node does not get faster.

An attribute whose transform query is not pinned to a single object is one of those signals: any number of objects can answer such a query, so a change that reaches the attribute recomputes its whole kind. Pin the query to get the narrowed recompute, the way a transform query normally is. See [Single-target queries](https://docs.infrahub.app/development-resources/graphql/single-target-queries).

Set `INFRAHUB_COALESCE_PYTHON_RECOMPUTE_AFTER_MERGE` to `false` to restore the previous per-node behaviour. The per-node automations carry the setting in their stored trigger definition, so run `infrahub upgrade` after the flip to rebuild them; until then a merge and a rebase recompute nothing for this family.
