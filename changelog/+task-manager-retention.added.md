Added three settings that control how long the task manager keeps its records: `task_manager.retention.task_history` (30 days by default), `task_manager.retention.activity_log` (7 days) and `task_manager.retention.prefect_own_events` (7 days). Set them in `infrahub.toml` or with the `INFRAHUB_TASK_MANAGER_RETENTION_TASK_HISTORY`, `INFRAHUB_TASK_MANAGER_RETENTION_ACTIVITY_LOG` and `INFRAHUB_TASK_MANAGER_RETENTION_PREFECT_OWN_EVENTS` environment variables, as a number of days (`30d`) or an ISO 8601 duration (`P30D`), from 1 to 36500 days. `prefect_own_events` must not be longer than `activity_log`, so set both when you lower `activity_log` below 7 days, or Infrahub refuses to start.

Until now, finished task runs were not deleted by age unless `PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED` turned on Prefect's deletion, which kept them for 90 days. Now they are kept for `task_history` (30 days by default), unless `PREFECT_SERVER_SERVICES_DB_VACUUM_RETENTION_PERIOD` is set. Every hour the task manager deletes the finished task runs older than that, together with their logs and artifacts. The deletion cannot be undone, so set a longer `task_history` before upgrading if you need older runs.

`infrahub upgrade` has a new step, "Task history cleanup", that deletes these runs before the instance starts and prints its progress. When the deleted runs were more than half of the task history, as on the first upgrade, the step also rewrites the task history tables to return their disk space, which needs free disk space for a copy of the runs that are kept. For an upgrade that runs while the instance still serves, such as the Helm chart upgrade hook, pass `--no-task-history-cleanup` and run `infrahub tasks flush flow-runs --rewrite` in a maintenance window after the rollout.

The activity log is still kept for 7 days by default. To keep it longer, raise `activity_log`, for example to `365d`, while the events the task manager records for its own use are still deleted after `prefect_own_events`.

When the task manager already has a value for `PREFECT_SERVER_SERVICES_DB_VACUUM_RETENTION_PERIOD`, `PREFECT_SERVER_EVENTS_RETENTION_PERIOD` or `PREFECT_SERVER_SERVICES_DB_VACUUM_EVENT_RETENTION_OVERRIDES`, whether from a `PREFECT_*` environment variable or from Prefect's `.env` file, `prefect.toml`, `pyproject.toml` or active profile, that value takes precedence over the matching setting, and the task manager logs a warning that names it. When `PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED` is already set in one of these places, it decides which of Prefect's cleanups run: if its value does not turn on `flow_runs` or `events`, the task manager logs a warning that names the retention it does not apply. An empty `PREFECT_SERVER_SERVICES_DB_VACUUM_ENABLED`, which a compose file passes when the host variable is not set, does not count as set: a value from Prefect's files, or from its active profile, applies when there is one, and otherwise the task manager deletes both old task runs and old events. An empty value of one of the other three variables still stops the task manager at startup with an error from Prefect, as it did before.

When the task manager runs only its web server (`PREFECT__SERVER_WEBSERVER_ONLY` is set) and its background services run in a process of their own, such as one started with `prefect server services start`, that process does not read these settings, so it deletes no task runs unless its own environment sets the matching `PREFECT_*` variables; the task manager logs a warning at startup.
