Where the schema migration views live

Six views from INFP-719 and the user journey, placed in pages that already exist in Infrahub. The branch, main and the proposed change share one Schema changes list and details panel. Nothing new in the menu, no side panel.

The six views, and the spec behind each

Journey 1.1 to 1.5

Staged schema change

What a staged file would do to the data on the branch, with Apply, Discard and Recalculate. While it is staged, Infrahub refuses to merge the branch or load a schema on it.

“View the staged schema and its impact from the API, the CLI and the UI.” INFP-719
→ Branch · Schema tab · Schema changes, first row
Journey 1.1

Schema difference

Each changed kind, its operations, and the nodes each one touches or deletes. The schema viewer also shows the staged schema in full detail.

“View the difference between the branch's current schema and the staged file.” INFP-719
→ The details of every schema change, linked to the schema viewer · Staged
Journey 1.4, 2.4, 2.5

Schema changes and revision

Every schema change of the branch, in order, with its runs. INFP-719 calls them stored migrations; the engineering investigation calls them schema changes.

“View the stored migrations and the revision with a new CLI command, infrahubctl schema view, and on a new page in the UI.” INFP-719
→ Branch and main · Schema tab · Schema changes
Journey 2.2

Progress of a run

How many migrations have ended, and how many nodes are done, during an apply, a direct load or a merge.

“View the progress per migration: which migration runs, with its name, as step N of M.” INFP-719
→ The details of the change that runs, the proposed change during a merge, and the task pages
Journey 4.1

What the merge applies on main

The branch's schema changes, each with the version it gets on main and whether it would fail against the current main.

“Before approving, view in the proposed change the migrations the merge will replay on main, in order.” INFP-719
→ Proposed change · Schema tab · Schema changes
Journey phase 5

Failed or stopped merge

Which step failed and why; the merge rolled back, so main did not change. A merge whose task stopped is rolled back with one button, without OpsMill.

A failed merge rolls back completely. Engineering investigation, followed by decision on 16 Nov 2026.
→ Proposed change · Schema tab · Schema changes

The two paths people take

Schema owner

  1. Runs infrahubctl schema load --stage
  2. →
  3. Branch · Schema · Schema changes, staged row
  4. →
  5. Schema viewer · Staged, to check a kind
  6. →
  7. Fixes the file and stages again, or presses Apply
  8. →
  9. Same list: the change becomes 00031

Reviewer

  1. Opens the proposed change
  2. →
  3. Schema · Schema changes
  4. →
  5. Checks which schema change would fail, and whether a staged change blocks the merge
  6. →
  7. Merges, or asks the owner to fix main or the branch

Decided from 16 to 19 November 2026

QuestionDecisionReason
Where the views live (revised 18 Nov)The branch Schema tab gets “Schema changes” and “Diff”. The proposed change Schema tab gets the same. Main gets a Schema tab.The diff and the steps that produced it sit together, and the branch and the proposed change share one structure.
Where the staged change goes (18 Nov)The first row of the Schema changes list, rather than its own “Staged” sub-tab.People see where the change sits in their workflow without opening another view.
Versions in the list (18 Nov)An applied change shows its version. A staged change shows the version it gets, in a dashed chip. A failed load shows a red cross: it never gets one.Every row starts with the same chip, so the order reads at a glance.
Details panel (18 and 19 Nov)A header with the actions, the facts and a link to each section. Sections open and close, and their titles stay on screen.The panel has long sections, and people must know each one exists.
Impact calculation (19 Nov)“Impact calculated … ago” and Recalculate in the header, next to Apply. Problems stay as messages in the panel.Apply relies on that calculation.
Role of the schema viewer (17 Nov)One “List | Graph | Staged” toggle. Staged uses the List layout for the schema after the staged change.The schema viewer has the detail of each kind, and the backend plans staged=true for it.
Name of the list“Schema changes”The backend's name. In the backend, a migration is one step inside a schema change, so “stored migrations” would name two levels.
ProgressIn the details of the change that runs, in the proposed change during a merge, and in the task pages. No new button in the header.Runs are tasks. One activity button for tasks, Git sync and schema is a separate design run.
Merge rules (19 Nov)A staged change blocks the merge. A stopped merge has Roll back the merge.The engineering investigation refuses a merge while a change is staged, and lets a user with the Merge branch permission roll back a stopped merge.

Not part of the design

No side panelRejected in rounds 1 and 2: unclear, and too narrow for the impact.
No new branch tab or menu entryThe views extend pages people already use.
No Staged sub-tabReplaced in round 15 by the first row of the list.
No separate list of merge stepsRejected in round 4: the same schema changes had two layouts.
No resume after a failed mergeThe merge rolls back completely, as the engineering investigation decides.
No view of what a rebase would doIt belongs to project E, which the engineering investigation marks optional.
