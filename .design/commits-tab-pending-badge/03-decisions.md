# Decisions

- **One kind of count per tab.** The badge shows either "pending import" (an import brings the commits) or "not on this branch" (only a rebase brings them), never both: the backend picks one case per repository and branch (`_resolve_remote_branch` in #11169).
- **"Not on this branch" includes commits the default branch has not imported yet** (declined round-1 note 1, decided by Paul Leménager on 2026-10-23). On a branch that does not sync with Git, a rebase brings only the default branch's commit, so commits not yet imported on the default branch need its next sync first. Accepted: the default branch syncs on its own within about a minute, and splitting the count needs a backend change and a more complex badge.
- **Wording: "behind main", not "not on this branch"** (requested by the user, 2026-10-23). The count meaning, the row badge ("Behind") and the header lines follow Git's own wording and name the tracked ref (`git_ref`, for example `main`), not "the default branch". The same strings go into [opsmill/infrahub#11189](https://github.com/opsmill/infrahub/pull/11189).
- **Scenario B5 shows "behind" and "pending import on main" together, as an option only** (requested by the user, 2026-10-23). The prototype shows the split in every direction except `today`. Showing it in the product needs a backend change: the API counts all 3 commits as `NOT_ON_BRANCH` today. It supersedes nothing yet: the decision above (accept the overlap and show 3 behind) stands until the user picks.

## Phase 3, round 1 (pill rev 2)

- **Direction: `pill`** (picked by the user, 2026-10-23). One count per tab, either pending import (download icon) or behind main (branch icon), never both.
- **B5 dropped, no backend change** (the user, 2026-10-23: "no B5"). The split of B5 into "behind" and "pending import on main" needs the API to tell those commits apart. The accepted overlap above stands: those commits count as behind main.
- **Tooltip says what brings the commits** (confirmed by the backend author of #11169, 2026-10-23):
  - Read-write branch that syncs with Git, and repository added on the branch: "3 commits pending import — the next sync imports them".
  - Read-only: "2 commits pending import — run Import latest commit to use them". Nothing imports a read-only repository on its own; the periodic check only notices that the ref moved. "Import latest commit" is the label of the read-only repository's action in the Actions menu (`repository-menu-section.tsx`).
  - Behind: "2 commits behind main — rebase the branch to use them".
  - The accessible name carries the count and kind only, for example "Commits, 2 commits behind main".
- **Which kind applies stays the frontend rule** (confirmed by the backend author of #11169, 2026-10-23): read-write repository, branch with `sync_with_git` false, repository not in `staging`. The response has no top-level flag, and `sync_with_git` alone is wrong on the branch the repository was added on.
- **Warning pill kept** for `REWRITTEN`, `ORPHANED` and, on read-only repositories, `REF_MISSING` (confirmed by the backend author of #11169, 2026-10-23): the same amber pill with a warning triangle and no number. It never appears next to a count pill, because a condition gives either a count or a warning, and the triangle differs from both count icons. Without it the tab bar says nothing while the tab shows a warning that may need a rebase (B4). B4's accessible name is "Commits, diverged from main", using the user's terms.
- **Count cap: 999, shown as "999+"**, with the exact number ("1,284 commits pending import") in the tooltip and the accessible name. Counts in the hundreds still compare usefully (a few commits against a few hundred); past that the action is the same, and the pill stays at most four characters wide, so the tab width does not jump between scenarios.
- **Overflow: the Commits tab stays outside the horizontal scroll area**, at the end of the tab bar, and a mask fades whichever edge of the scrolled tabs is cut. The signal on Commits is always visible, and the fade shows that more tabs exist. A mask, not a coloured overlay, because the card background is a gradient that no overlay colour matches in dark mode. The real fix belongs in the shared tab bar (`01-system.md`, Missing).
- **No motion on the pill.** The tab bar is seen tens of times a day, so the pill appears and disappears without animation, and it has no transition of its own. The tooltip uses the design system's default animation, opens after 200 ms on first hover, and opens at once on a hover within 600 ms of the last tooltip closing.
- **Contrast: the pill surface is `bg-warning-surface/60`.** With the full `bg-warning-surface`, `text-warning` on that surface measured 4.48:1 in light mode, under the 4.5:1 AA minimum for 12px text. At 60% it measures 4.69:1 in light mode and 10.35:1 in dark mode.
- **Settled values:** cap 999; tooltip delay 200 ms; tooltip warm window 600 ms; edge fade 48 px. The pill direction has no knobs.
